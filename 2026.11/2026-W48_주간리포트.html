정리되지 않은 연구 자료를 문헌 검토와 그림까지 갖춘 LaTeX 논문 원고로 바꾸는 멀티에이전트 프레임워크.

흩어진 연구 자료를 원고로 엮는 일은 AI 기반 과학 발견에서 중요하지만 덜 다뤄진 과제다. 저자들은 기존 자율 논문 작성 시스템이 특정 실험 파이프라인에 단단히 묶여 있고, 문헌 검토도 피상적이라고 지적한다.

PaperOrchestra는 아이디어 요약·실험 로그·학회 LaTeX 템플릿·가이드라인·선택적 그림을 받아, Outline·Plotting·Literature Review·Section Writing·Content Refinement 5개 에이전트가 단계별로 투고용 LaTeX 원고와 PDF를 만든다. 문헌 에이전트는 웹 검색으로 후보를 모은 뒤 Semantic Scholar로 존재를 검증한 논문만 인용하게 하고, 정제 에이전트는 시뮬레이션 리뷰의 전체 점수가 오르거나, 같으면서 하위 항목 순이득이 0 이상일 때만 수정을 채택한다. 평가를 위해 CVPR·ICLR 2025 논문 200편에서 아이디어 요약과 실험 로그를 Gemini-3.1-Pro로 역생성한 벤치마크 PaperWritingBench와 자동 평가기 묶음을 만들었다(W47 심층 분석 기준).

  • 특정 실험 파이프라인에 묶이지 않고, 형식 없는 사전 작성 자료를 문헌 종합과 그림이 들어간 LaTeX 원고로 바꾸는 멀티에이전트 프레임워크
  • 최상위 AI 학회 논문 200편의 원자료를 역재구성한 벤치마크 PaperWritingBench(저자들은 첫 표준 벤치마크라고 주장)와 자동 평가기 묶음
  • 사람이 결과물을 나란히 비교한 평가(평가자 11명, 40편)에서 자율 작성 베이스라인 대비 절대 승률 차가 문헌 검토 품질 50~68%p, 전체 원고 품질 14~38%p라고 보고. 같은 평가에서 인간 원본에는 전체 품질 승률 5% 대 81%로 뒤졌다
  • google-research GitHub 저장소(Apache-2.0, 약 6.2천 스타)에 파이프라인과 자동 평가기 일부 코드를 공개했다(ScholarPeer·AI Scientist-v2 Reviewer 평가 코드는 없다). README는 데이터셋을 '추후 공개'로 적지만 PaperWritingBench는 HuggingFace에 Apache-2.0으로 이미 공개돼 있다(W47 심층 분석 기준)

방법 상세

PaperOrchestra는 입력 5종(아이디어 요약 idea.md, 실험 로그 experimental_log.md, 학회 LaTeX 템플릿, 학회 가이드라인, 선택적 그림 폴더)을 받아 LaTeX 소스와 컴파일된 PDF를 내는 5단계 파이프라인이다(3.1절 Eq.1, 4장). 아이디어 요약과 실험 로그는 마크다운이고, 실험 로그에는 표 수치와 그림 내용을 풀어 쓴 사실 관찰이 들어간다. 템플릿은 .tex/.sty 파일이고 그림은 이미지 파일이다. 그림이 없으면 파이프라인이 직접 만든다.

1단계 Outline Agent는 1회 호출로 JSON 아웃라인을 만든다. 아웃라인은 세 키로 구성된다. plotting_plan은 plot 또는 diagram 구분, 데이터 출처, 종횡비를 담는다. intro_related_work_plan은 서론용 거시 문헌 10-20편과 관련연구용 2-4개 방법론 클러스터 30-50편, 클러스터별 한계 가설과 검색 쿼리를 담는다. section_plan은 절별 bullet과, 데이터셋·지표·옵티마이저마다 붙는 citation_hints를 담는다(F.1 프롬프트).

2단계 Plotting Agent와 3단계 Literature Review Agent는 병렬로 돈다. 플롯은 PaperBanana의 원 프롬프트에 캡션 재생성 단계 하나만 붙여 쓴다(4장, F.1). 공개 코드는 이 프롬프트를 utils/paper_banana_utils.py 안에 재구현했다. 처리 순서는 참조 그림 few-shot 검색(Top 10), 상세 설명 작성, gemini-3-pro-image-preview 이미지 생성 또는 matplotlib 코드 실행, VLM critic 검토 후 재생성(코드 기본 max_critic_rounds=3), 캡션 재생성이다. 문헌 에이전트는 Gemini-3-Flash에 Google Search grounding을 붙여 10개 병렬 워커로 후보를 모은다. 그다음 Semantic Scholar API로 초당 1건씩 순차 검증한다(App. B). 통과 조건은 제목 퍼지 매칭(Levenshtein 비율, 연도 일치 시 가점), 초록 존재, 연구 cutoff 이전 발행이다(D.3). 임계값은 논문에 없고, 코드에서는 S2 검색 상위 3건 중 최고 thefuzz 비율(연도 일치 시 +10)이 70을 넘어야 한다(utils/scholar_utils.py). S2 ID로 중복을 제거한 뒤 BibTeX와 citation_map을 자동 생성한다. 이후 검증된 논문만 인용하되 풀의 90% 이상을 인용하라는 제약 아래 서론과 관련연구를 쓴다(D.3).

4단계 Section Writing Agent는 단일 멀티모달 호출로 나머지 절을 채운다. 실험 로그 수치로 booktabs 표를 만들고, 제공된 그림을 모두 넣고, citation_map의 키만 쓰도록 지시받는다. LaTeX 컴파일은 pdflatex-bibtex-pdflatex-pdflatex 순서의 subprocess 호출이다(utils/pdf_utils.py).

5단계 Content Refinement Agent는 AgentReview의 시뮬레이션 리뷰를 받아 원고를 고친다. 채택 규칙은 다음과 같다. 전체 점수가 오르면 채택한다. 같으면 하위 축 순이득이 0 이상일 때만 채택한다. 코드에서는 Overall과 Confidence를 뺀 축의 상승 합이 하락 합 이상인지 본다. 전체 점수가 내려가거나, 같은데 순이득이 음수이면 이전 버전으로 되돌리고 멈춘다. 반복 상한은 코드 기본 max_reflections=3이다. 에이전트는 새 실험 요청을 무시하고 '한계를 명시적으로 쓰지 말라'는 규칙을 따르도록 지시받는다. 저자들은 초기 실험에서 에이전트가 빠진 베이스라인을 한계로 나열해 자동 리뷰 점수를 올리는 reward hacking을 보였기 때문이라고 설명한다(F.1 말미). 공개 코드에는 논문에 서술되지 않은 VLM 서식 점검 루프(max_formatting_loops=1)가 추가로 있다.

작성 백본은 모든 시스템에서 Gemini-3.1-Pro로 고정된다. 논문 1편당 LLM 호출은 약 60-70회(Outline 1, 문헌 20-30, 플롯 20-30, 작성 1, 정제 5-7)이고 평균 39.6분이 걸린다(App. B). 모든 파이프라인에 같은 Anti-Leakage 프롬프트를 넣어 학습 데이터 기억 사용을 금지한다. 다만 LLM이 부정 제약을 완벽히 지키지 않을 수 있다는 점은 저자들도 인정한다(D.4).

실험 셋업

  • 벤치마크: PaperWritingBench, CVPR 2025와 ICLR 2025 채택 논문 각 100편, 총 200편을 OpenReview(ICLR)와 CVF Open Access(CVPR)에서 무작위 추출했다. MinerU로 PDF를 마크다운으로, PDFFigures 2.0으로 그림·캡션을 추출하고, 파싱 실패 샘플은 버렸다(3.2절).
  • 원자료 역생성: Gemini-3.1-Pro가 PDF 마크다운과 표·그림 이미지를 멀티모달로 받아 세 자료를 만들었다. Sparse idea는 평균 약 587-591단어, Dense idea는 약 1,057-1,083단어, Experimental Log는 CVPR 1,530단어, ICLR 2,387단어다. 저자·제목, 인용, URL, 그림·표 참조는 제거했다(App. C.2, Table 8).
  • 기본 설정: Sparse idea, F=F_GT(원 논문 그림 사용, PlotOff). 연구 cutoff는 CVPR 2024-11, ICLR 2024-10이다(5.1절, D.1).
  • 베이스라인 2종: (1) 모든 원자료를 한 번의 LLM 호출로 처리해 원고와 BibTeX를 함께 쓰는 Single Agent, (2) AI Scientist-v2(인용 수집은 Gemini-3-Flash로 교체). 둘 다 작성 백본은 Gemini-3.1-Pro이고 Anti-Leakage 프롬프트를 똑같이 넣었다. 제외한 시스템과 사유는 다음과 같다(D.2). OmniScientist는 재현 가능한 공개 코드가 없다. PaperRobot과 data-to-paper는 투고용 LaTeX 원고를 끝까지 생성하지 못한다. AI-Researcher는 구조화된 중간 산출물이 필요하다. CycleResearcher는 구조화된 BibTeX 입력이 필요하다. AutoSurvey2와 LiRA(Generic RAG pipelines로 표기)는 서베이 전용이다. AI Scientist-v2를 같은 입력에 맞게 이식한 코드는 공개 저장소 파일 트리에 없다.
  • 자동 평가기는 네 종류다(5.2절). (a) Citation F1: GT 참고문헌을 LLM이 P0 must-cite와 P1 good-to-cite로 나누고 Semantic Scholar ID로 매칭한다. (b) 문헌 검토 품질 LLM judge: 0-100점, 6개 축, 점수 상한과 감점 규칙을 둔다. (c) AI Scientist-v2 Reviewer와 ScholarPeer: ScholarPeer의 scouting agent는 끈다. (d) SxS 문헌 검토와 SxS 전체 품질: 두 순서로 평가해 위치 편향을 줄인다. judge는 Gemini-3.1-Pro와 GPT-5(gpt-5-2025-08-07)다.
  • 온도: 리뷰형 평가기 0.75(Gemini-3.1-Pro), SxS 0.0(Gemini-3.1-Pro), GPT-5는 고정값 1.0이다(D.1).
  • SxS 집계 규칙: 두 순서 결과가 2승이거나 1승 1무면 win, 1승 1패나 2무면 tie, 그 외는 loss로 친다(5.2절).
  • 사람 평가: AI 연구자 11명이 40편(학회당 20편)을 맡아 Streamlit UI에서 블라인드 SxS 180건(고유 쌍 120개)을 평가했다. 3점 척도(Win/Tie/Loss)로 답하고, 진단 질문 12개에 먼저 답한 뒤 최종 판단을 내렸다. 평가자 간 일치도(kappa 등)는 보고되지 않았다. 본문·부록에서 kappa, agreement, inter-annotator를 검색했고 inter-autorater 상관만 찾았다(5.4절, D.5).
  • 절대 승률 차 정의: PaperOrchestra 승률에서 베이스라인 승률을 뺀 값이고 tie는 양쪽 어디에도 넣지 않는다(1장 contributions 괄호). 사람 평가 결과는 두 학회를 합쳐 보고된다(Figure 3a).
  • Ablation: Sparse vs Dense idea(Table 5), PlotOff vs PlotOn(Table 6), 정제 전후(Figure 4, Gemini-3.1-Pro와 GPT-5 두 judge의 SxS와 AgentReview 지표). 문헌 에이전트나 아웃라인 에이전트를 하나씩 빼는 ablation은 없다. Single Agent가 시스템 전체 ablation 역할을 한다.
  • 비용 측정: CVPR 5편과 ICLR 5편, 총 10편을 단일 워커로 실행하고 최댓값·최솟값을 뺀 평균 지연을 냈다. 토큰 수나 달러 비용은 보고되지 않았다. 본문·부록에서 token, $, USD를 검색해 해당 수치가 없음을 확인했다(App. B, Table 7).

한계 · 비판

  • 그림 생성을 외부 모듈 PaperBanana에 맡기므로 그림 환각(figure hallucination)을 직접 통제하기 어렵다. 생성된 그림이 사실에 맞는지, LaTeX 레이아웃의 알맞은 위치에 들어갔는지 검증하려면 VLM 점검과 사람 평가가 따로 필요하다고 저자들이 적었다(Appendix A 첫째 항목). 관련 결과로, 자체 생성 그림(PlotOn)은 GT 그림(PlotOff)을 쓴 설정에 단독 승률이 대부분 밀린다(Table 6. PlotOn 승 26-34%, PlotOff 승 34-49%). 저자들은 GT 그림에 실험 로그에 없는 정보가 들어 있다는 점을 이유로 든다(5.5절). (저자 인정)
  • Content Refinement는 사람이 아니라 LLM이 만든 구조화 리뷰(AgentReview)에 의존한다. 연구자가 자연어 비평으로 초안을 조종하는 human-in-the-loop 시스템으로 옮겨 가는 것을 향후 과제로 둔다. 시스템은 독립 저자가 아니라 보조 도구라는 입장이다(Appendix A 둘째 항목, Ethics Statement). (저자 인정)
  • PaperWritingBench의 원 논문(CVPR 2025, ICLR 2025)이 사전학습 데이터에 들어 있을 수 있다(pretraining contamination). 대응은 입력 자료의 익명화와 탈맥락화, 그리고 모든 파이프라인에 똑같이 넣은 Anti-Leakage Prompt뿐이다. 저자들은 백본이 같으니 누출이 있어도 모든 시스템에 똑같이 작용하므로 상대 비교는 공정하다고 주장한다. 다만 LLM이 부정 제약을 완벽히 지키지 않을 수 있다는 점은 인정한다. 생성과 기억을 완전히 분리하려면 미발표 연구나 자동 생성 원자료가 필요하다고 적었다(Appendix A 셋째 항목, D.4). (저자 인정)
  • 문헌 검토 품질에서 자동 평가기와 사람 판단의 상관이 낮다. Pearson 기준 Gemini-3.1-Pro 0.0868, GPT-5 0.2764다. 저자들은 LLM의 self-bias를 원인으로 꼽는다. LLM이 'Problem-Gap-Solution' 같은 형식 단서에 점수를 주는 structural grader처럼 행동하고, 사람은 사실 밀도와 서사 흐름을 중시한다는 설명이다(5.4절, Figure 3b). (저자 인정)
  • 초기 실험에서 정제 에이전트가 reward hacking을 했다. 빠진 베이스라인을 한계로 나열해 자동 리뷰어의 채택 점수를 부풀렸다. 그래서 프롬프트에 '한계를 명시적으로 쓰지 말라'와 '새 실험 요청은 무시하라'는 규칙을 넣었다(Appendix F.1 Content Refinement Agent 프롬프트 뒤 설명). 이는 저자들이 직접 보고한 실패 사례다. (저자 인정)
  • 사람이 쓴 원본(GT)과의 품질 격차는 저자들도 인정한다. 5.3절은 전체 품질에서 'Human (GT) remains the upper bound'라고 쓰고, D.5와 Figure 7 캡션도 GT 대비 품질 격차가 남아 있다고 적는다. 동시에 문헌 검토에서 GT 대비 tie+win 43%를 'highly competitive'로 표현한다(5.4절). 이 GT 비교는 초록에는 나오지 않는다. (저자 인정)
  • 초록의 사람 평가 수치(문헌 50-68%p, 전체 14-38%p)는 AI 베이스라인 대비 값이다. 같은 사람 평가에서 인간 원본(GT)과 비교하면 결과가 다르다. 전체 품질은 GT 승 81%, tie 14%, PO 승 5%다. 문헌 검토는 GT 승 57%, tie 24%, PO 승 19%다. 이 수치는 Figure 3(a) 그림에서 직접 읽어 확인했다. 저자들도 본문에서 GT를 upper bound로 두고(5.3절) 격차가 남아 있다고 적는다(D.5). 하지만 초록에는 GT 비교가 빠져 있다. 비교별 건수는 논문에 없다. 40편에 비교 3개를 곱하면 고유 쌍 120개이고 평가는 180건이다. 따라서 비교당 약 60건이고 일부 쌍은 중복 평가됐다고 추정되며, 두 학회를 합친 값이다. 그런데도 평가자 간 일치도는 보고되지 않았다. 본문과 부록에서 kappa, agreement, inter-annotator를 검색했고 inter-autorater 상관만 찾았다. 따라서 '제출 가능한 원고'라는 표현은 AI 베이스라인과의 상대 우위로 읽어야 한다. 사람 원고 수준이라는 근거는 없다. (추가 의문)
  • 자동 평가 결과 일부가 사람 판단과 반대 방향으로 간다. Table 4(200편)에서 Gemini judge는 PO의 문헌 검토 점수(78.30 CVPR, 76.23 ICLR)를 GT(71.08, 75.18)보다 높게 줬다. GPT-5 judge도 CVPR에서는 PO 53.99, GT 53.66으로 PO를 약간 높게 줬다(ICLR은 GT 55.53이 PO 54.15보다 높다). 사람 평가(40편 표본)에서는 GT가 57% 대 19%로 이겼다. 표본과 형식이 다르므로 직접 대조에는 한계가 있다. 문헌 검토의 사람-자동 상관은 0.09-0.28이다. 그럼에도 저자들은 'relative rankings remain strictly consistent'라고 쓰는데, 이를 정량으로 보인 표는 찾지 못했다. 따라서 문헌 검토 자동 SxS 승률 차 88-99%p나 Table 4의 +32.87-33.25점 같은 큰 수치는 약한 근거로 다뤄야 한다. ScholarPeer 결과도 같은 신호를 준다. LLM을 한 번만 호출하는 Single Agent도 모의 채택률 71%(CVPR)와 72%(ICLR)를 얻고, PO는 84%와 81%다(Table 2). 이 평가기의 변별력이 제한적이라는 신호다. (추가 의문)
  • 인용 무결성은 측정된 결과가 아니라 구조로 보장한 것이다. Semantic Scholar 검증 단계는 있다. 코드상 thefuzz 비율 70 초과(연도 가점 포함), 초록 필수, cutoff 이전 발행을 확인한다(utils/scholar_utils.py, literature_review_agent.py). 그러나 최종 원고에서 존재하지 않거나 잘못 붙은 인용의 비율(hallucinated citation rate)은 PO와 베이스라인 모두 보고되지 않았다. 본문과 부록에서 hallucinat를 검색하면 관련연구 서술, App. A(그림 환각), D.3·D.4 설명, 프롬프트 지시문, 윤리 문단에서만 나오고 측정값은 없다. 제목 퍼지 매칭은 실존 여부만 확인할 뿐, 인용한 문장이 그 논문 내용을 정확히 대변하는지는 검증하지 않는다. 인용 지표는 엇갈린다. Overall Citation F1은 Single Agent와 CVPR 29.65 대 28.03으로 차이가 작고, ICLR은 27.76 대 23.16이다. 저자들은 베이스라인의 인용 수가 9-14개로 적어 F1이 부풀려진 착시라고 설명한다. 실제로 PO의 P1 Recall은 15.85-17.11%로 베이스라인 2.77-3.36%보다 크게 높다. 반면 P0 Recall은 54.48-65.17%라서 필수 인용의 약 35-46%가 빠진다(Table 3). '풀의 90% 이상 인용' 제약이 인용 수를 늘린 효과와 실제 문헌 이해의 효과는 분리되지 않았다. (추가 의문)
  • 정제 단계의 평가에 부분적인 순환성이 있다. 최적화 대상인 AgentReview가 Figure 4(b)에서 효과 지표로도 쓰인다(채택률 53->72%, 11->33%). 반면 Figure 4(a)의 SxS는 작성 백본과 같은 Gemini-3.1-Pro뿐 아니라 GPT-5로도 평가했고, 두 judge 모두 정제 후 승 79-81%, 패 0%였다. 그래서 같은 모델 judge만의 결과라고 볼 수는 없다. 다만 사람 평가로 정제 효과를 따로 확인한 실험은 없다. 또 '한계를 명시적으로 쓰지 말라'는 규칙은 평가기 해킹을 막는다. 그 대신 리뷰어가 지적한 약점(예: 빠진 베이스라인)을 원고에 한계로 반영하는 길도 막는다. 원고에서 한계 서술이 아예 사라지는 것은 아니다. Section Writing 프롬프트는 결론에서 한계와 향후 과제를 다루라고 권한다(F.1, 저장소 methods/prompts/section_writing_agent.py 54행의 'Nice to have'). 정제 프롬프트에는 'Never explicitly state a limitation' 한 줄만 있다. 저장소 prompts 폴더에서 limitation을 검색해 확인했다. 그래서 정제 과정에서 초안의 한계 문단이 유지되는지는 확인되지 않는다. (추가 의문)
  • ablation과 비용 보고가 부족하다. 문헌 에이전트나 아웃라인 에이전트를 하나씩 빼 보는 실험이 없고, Single Agent가 시스템 전체 ablation 역할만 한다. 베이스라인은 2종뿐이고, AI Scientist-v2를 같은 입력에 맞게 이식한 코드는 저장소에 없다(파일 트리 확인). 비용은 LLM 호출 수와 평균 지연(10편 측정)만 있다. 토큰과 달러 비용은 없다. 본문과 부록에서 token, USD, dollar를 검색해 확인했다(Table 7, App. B). Single Agent(1회, 3.3분) 대비 우위는 호출 수 차이(약 60-70배)와 분리되지 않는다. 다만 AI Scientist-v2와 비교하면 사정이 다르다. 호출 수는 약 40-45회로 PO의 약 1.3-1.75배 차이이고, 지연도 35.1분 대 39.6분으로 비슷하다. 그런데도 사람 평가에서 PO가 문헌 67% 대 17%, 전체 50% 대 36%로 이겼다(Figure 3a). 따라서 우위가 호출 수만으로 설명되지 않는다는 근거가 일부 있다. 그래도 토큰 기준 비용 대비 효과는 판단할 수 없다. (추가 의문)

재현 가능성

코드 공개. github.com/google-research/paper-orchestra를 git clone --depth 1로 받아 확인했다(최신 커밋 d9bae99, 2026-11-15). methods/agents/ 아래에 파이프라인 모듈 outline_agent, literature_review_agent, plotting_agent, section_writing_agent, content_refinement_agent가 있고 paper_writing_cli.py도 있다. autoraters/ 아래에 agent_review, citation_f1, lit_review_quality, sxs_lit_review_quality, sxs_paper_quality가 있고, Streamlit frontend도 있다. 논문에서 쓴 ScholarPeer 평가 코드, AI Scientist-v2 Reviewer 평가 코드, 베이스라인 이식 코드는 파일 트리에 없다. 플로팅(--use_plotting)의 PaperBanana 프롬프트는 저장소 안 utils/paper_banana_utils.py에 재구현돼 있다. few-shot 참조(PaperBananaBench)와 스타일 가이드는 ../../PaperBanana 경로에서 읽는다. 이 파일이 없으면 경고를 내고 few-shot과 스타일 가이드 없이 진행하므로, 논문 설정을 재현하려면 별도 PaperBanana 저장소가 사실상 필요하다.가중치 해당 없음. 학습한 모델이 없고 상용 API를 호출하는 구조다. 기본 모델은 gemini-3.1-pro-preview(작성)와 gemini-3-pro-image-preview(이미지)다. 문헌 후보 수집에는 Gemini-3-Flash와 Google Search grounding을 쓰고, 선택적으로 OpenAI 모델(평가용 GPT-5)을 쓸 수 있다.데이터 저장소 README의 Dataset 절(50행)은 지금도 데이터셋이 'not included'이고 추후 별도 공개한다고 적고 있다. 그러나 HuggingFace yiwen-song/PaperWritingBench는 이미 공개돼 있고, 프로젝트 페이지(yiwen-song.github.io/paper_orchestra)의 Dataset 링크가 이 저장소를 가리킨다. HF API로 확인한 내용은 다음과 같다. 파일은 README.md, datasets.zip, metadata.json이고, 라이선스 태그는 apache-2.0, gated는 false, lastModified는 2026-05-17이다. 내용은 CVPR 2025와 ICLR 2025 각 100편에서 Gemini-3.1-Pro로 역생성한 idea.md(Sparse/Dense), experimental_log.md, 템플릿, 그림이다(3.2절, C.2).라이선스 코드: Apache License 2.0(저장소 LICENSE 파일을 직접 확인). 데이터셋: HuggingFace 메타데이터의 license 태그가 apache-2.0. 논문: arXiv abs 페이지(2604.05018v1)의 라이선스 링크가 CC BY 4.0임을 확인했다. 원 논문들(CVPR 2025, ICLR 2025)의 저작권과 데이터셋 라이선스가 어떤 관계인지는 확인하지 않았다.

필요한 키는 Gemini(VERTEX_AI_PROJECT와 LOCATION, 또는 GEMINI_API_KEY)이고, 선택적으로 OPENAI_API_KEY와 SEMANTIC_SCHOLAR_API_KEY를 쓴다(README의 .env 예시). S2를 키 없이 호출하면 금방 막힌다. 이 분석 중 키 없이 citations 엔드포인트를 두 번째로 부르자 429 Too Many Requests가 돌아왔다. 코드에서 주의할 점이 두 가지 있다. utils/paper_banana_utils.py 308행은 LLM이 만든 matplotlib 코드를 exec()로 샌드박스 없이 실행한다. utils/scholar_utils.py 28행과 autoraters/citation_f1.py 41행은 S2 API 키를 stdout에 출력한다. LaTeX 컴파일은 pdflatex와 bibtex를 subprocess로 부른다. Windows에서는 실행해 보지 않았다. CLI는 TeX 배포판이 PATH에 있으면 돌 가능성이 있지만 paper_writing_cli.sh는 bash 전용이다. 프론트엔드는 Part A에 따르면 Linux 전용 호출을 써서 WSL이 현실적이다. 비용(토큰, 달러)은 논문에 없어 추정할 수 없다. 저자들이 보고한 수치는 논문 1편당 LLM 호출 약 60-70회, 평균 39.6분이다.

📌 내 학습 포인트

  • [인용 검증을 LLM 없이 스크립트로] PaperOrchestra는 웹 검색으로 후보를 모은 뒤 Semantic Scholar로 순차 검증한다. 통과 조건은 제목 퍼지 매칭 비율 70 초과(연도 일치 시 +10), 초록 존재, cutoff 이전 발행이다. 통과한 목록에 든 키만 인용하게 한다(D.3, utils/scholar_utils.py). 요약 카드 파이프라인에도 이 구조를 옮길 수 있다. 카드 JSON을 쓰는 Write 뒤에 PostToolUse hook으로 Python 스크립트를 건다. 스크립트는 카드에 나온 arXiv ID마다 export.arxiv.org API를 부르고, 반환된 제목과 카드 제목의 퍼지 비율을 계산한다(difflib이면 0.7, thefuzz이면 70 기준). 비율이 기준 이하이면 exit code 2로 끝내고 stderr에 이유를 적는다. 그러면 Claude가 그 메시지를 받아 카드를 고친다. PostToolUse는 이미 끝난 Write를 되돌리지 못한다. 쓰기 자체를 막으려면 PreToolUse hook에서 Write 입력 내용을 검사해야 한다. 날짜 조건을 '주차 범위 안'으로 걸면 안 된다. 주간 트렌딩에는 오래된 논문도 오른다. 이 논문만 해도 arXiv v1은 2026-04-06인데 W47 목록에 들었다. 날짜는 카드 작성일보다 뒤인 ID만 거르는 정도가 맞다. LLM 토큰은 0이고 Windows Python으로 돈다. S2는 키 없이 부르면 금방 429가 난다(이번 분석에서 실제로 발생). 그래서 1초 간격 순차 호출과 재시도가 필요하고, arXiv API도 연속 호출 사이에 간격을 두는 것이 안전하다. 다만 이 방식은 실존과 제목 일치만 확인한다. 카드 본문의 수치가 원문과 맞는지는 별도의 검증 subagent가 맡아야 한다.

방법 상세

R-SWA는 디코더 12층 전부의 어텐션 마스크를 바꾼다. 생성 토큰 t의 가시 집합은 N(t) = P U D_n(t)이다(식 1-2). P는 길이 L_m의 프리픽스, 즉 시각 토큰과 프롬프트 전체이며 디코딩 내내 전역으로 보인다. D_n(t)는 직전 n개 출력 토큰의 인과적 슬라이딩 윈도우로 n 기본값은 128이다(Figure 1, config.json sliding_window_size=128). KV 캐시는 C(T) = L_m + min(n,T) <= L_m + n(식 6)으로 MHA의 L_m + T(식 5)와 달리 출력 길이 T에 대해 상한이 있다. 단 L_m은 페이지 수에 비례하므로 '상수'는 한 요청 안에서 디코딩 길이에 대해 상수라는 뜻이다. 토큰당 어텐션 비용은 O(L_m + n), 전체 디코딩은 O(T(L_m+n))로 full attention의 O(T L_m + T^2/2)와 대비된다(논문에 FLOP 식은 없고 식 1-6에서 유도). 윈도우 128의 선택 근거나 다른 값 비교 실험은 본문에 없다.

공개 transformers 구현(HF modeling_deepseekv2.py SlidingWindowLlamaAttention)은 프리필을 일반 causal attention으로 계산해 그 길이를 기록하고, 디코딩에서는 프리픽스 KV 뒤 W=128 슬롯 링 버퍼의 가장 오래된 출력 KV를 덮어쓴다. RoPE 위치는 절대 위치로 계속 증가한다. Figure 2의 '용량 m+n 큐에서 m+1번째 KV 축출' 설명과 맞는다.

일반 SWA는 이미지 토큰도 윈도우 밖으로 밀려나 시각 정보가 출력 상태로만 전달되는데, 저자는 이를 state transition에 의한 흐려짐이라 부르고 R-SWA는 참조 토큰을 상태 전이에서 빼서 이를 피한다고 주장한다. 논문은 StreamingLLM을 인용하지 않는다(참고문헌 37개 확인). 구조는 'sink + 최근 윈도우'와 닮았지만 sink가 소수 초기 토큰이 아니라 수천 개의 시각 토큰 전체이고, 추론 시 트릭이 아니라 이 패턴으로 계속 학습했다는 점이 다르다(분석자 해석). 일반 SWA 대비 실험이나 참조 토큰 전역 유지 여부 ablation은 없다.

베이스는 DeepSeek OCR이다. DeepEncoder(SAM-ViT 윈도우 어텐션 -> 16x 압축 -> CLIP-ViT 글로벌 어텐션)를 그대로 쓰고 Base(1024x1024, 다중 페이지)와 Gundam(동적 해상도, 단일 페이지) 두 모드만 남겼다. 1024x1024 한 장은 256 토큰이며 코드상 줄바꿈·구분 토큰을 더해 페이지당 273토큰이 프리픽스에 들어간다. 디코더는 MoE 3B total, 500M activated(3.2절)이고 config상 hidden 1280, MHA 10헤드, routed expert 64개 중 6개 + shared 2개다.

학습은 DeepSeek OCR 체크포인트에서 DeepEncoder를 동결하고 LLM만 4,000 step 계속 학습했다(GBS 256, 32K, lr 1e-4, 8x16 A800). 데이터는 약 200만 샘플(단일:다중 9:1)이며 단일 페이지는 PaddleOCR 의사 라벨, 다중 페이지 약 20만은 단일 페이지 2-50장을 <page>로 이어 붙인 합성이다. 언어 구성, GPU 시간, 학습 시 R-SWA 마스크와 패킹 결합 방식은 기술되지 않았다.

'single forward pass'는 모든 페이지를 Base 모드로 인코딩해 한 프롬프트로 한 번 프리필하고, 하나의 generate 호출로 끝까지 디코딩한다는 뜻이다(infer_multi 코드). 공개 코드는 max_length=32768을 프리필+출력 합계에 적용하므로 32K에 들어가는 페이지 수는 출력 밀도에 달려 있다. 논문은 정확한 수를 밝히지 않고, 후속 UOCR2 보고서는 v1을 '40페이지 입력 한계'로 기술한다.

실험 셋업

  • 버전: arXiv에는 v1(2026-06-22)만 있다. abs 페이지의 Submission history에 v1 하나뿐이고, v2 URL은 'Article not found'를 반환한다. 저장소 태그 UnlimitedOCR1.0의 Unlimited-OCR.pdf는 arXiv 스탬프 한 줄을 빼면 arXiv v1과 텍스트가 같다. 따라서 이 카드의 논문 수치는 모두 v1 기준이다.
  • 학습(4.2절): DeepSeek OCR 체크포인트에서 4,000 step 계속 학습했다. 설정은 global batch 256, 최대 길이 32K, 8x16 A800(128장), random packing이다. DeepEncoder는 동결하고 LLM만 학습했다. 최적화는 AdamW + cosine annealing, 초기 lr 1e-4이고, DeepEP EP=4와 Megatron-LM을 썼다. 총 GPU 시간과 학습 기간은 적혀 있지 않다.
  • 데이터(4.1절): 문서 OCR 샘플 약 200만 개, 단일:다중 = 9:1. 단일 페이지 PDF는 PaddleOCR로 라벨링했다. 블록 좌표를 0-1000으로 정규화하고 내용과 이어 붙여 검출+파싱 정답을 만든다. 다중 페이지 약 20만 개는 단일 페이지 2-50장을 <page> 구분자로 이어 붙인 합성 데이터다. 전부 32K로 패킹했다. 언어 비율과 원천 도메인 구성은 적혀 있지 않다.
  • 단일 페이지 평가(5.1절, Table 1): OmniDocBench v1.5와 v1.6을 쓴다(v1.6은 v1.5보다 테스트 이미지 296장 많음). 지표는 Text Edit, Formula CDM, Table TEDS/TEDS-S, Reading-order Edit이고, Overall은 text·formula·table의 가중 평균이다. Table 1 캡션에 따르면 Unlimited OCR 외 모든 모델 수치는 OmniDocBench 저장소에서 가져왔다. 저자가 같은 조건으로 재실행했다는 서술은 없다. v1.6 블록에는 베이스라인 DeepSeek-OCR(v1)이 없고 DeepSeek-OCR 2만 있다. Table 1이 Gundam 모드로 측정됐는지는 명시되지 않았다. 다만 3.3절은 단일 페이지용으로 Gundam 모드를 남겼다고 쓴다.
  • 세부 유형 평가(5.3절, Table 2): OmniDocBench v1.5의 9개 문서 유형별로 text edit와 reading-order edit을 DeepSeek-OCR, DeepSeek-OCR 2와 비교한다.
  • 장문 평가(5.1, 5.4절, Table 3): 사내(in-house) 테스트셋을 쓴다. 소설·문서·논문을 페이지 수에 따라 2, 5, 10, 15, 20, 40+ 페이지 구간으로 나눴고, 구간당 10권 이상이다. 지표는 Distinct-20/35와 edit distance다. 이 표에는 비교 모델이 하나도 없다(DeepSeek OCR의 다중 페이지 결과 없음). 5.1절 본문은 15페이지 구간을 언급하지 않지만 표에는 있다. 테스트셋 공개 여부는 v1 태그 README와 현 README에서 찾지 못했다.
  • 디코딩 설정: 논문은 평가에 쓴 디코딩 설정(temperature, 반복 억제 여부)을 밝히지 않는다. arXiv v1 PDF 텍스트에서 repeat, gram, greedy, temperature, sampling, logit을 검색하면 Distinct-n 정의와 5.4절 서술 외에는 0건이다. 반면 공개 추론 예시는 반복 금지 logits processor를 켠다. v1 태그 README의 transformers 예시는 no_repeat_ngram_size=35에 ngram_window 128(단일)과 1024(다중)를 쓰고, SGLang 예시는 DeepseekOCRNoRepeatNGramLogitProcessor(ngram_size 35)를 쓴다. HF infer/infer_multi의 기본값은 temperature=0.0이다. Table 3의 Distinct-35가 이 설정으로 측정됐는지는 확인되지 않는다.
  • 처리량(5.2절): OmniDocBench에서 512 동시 요청, DeepEncoder 'Base' 모드로 쟀다. Unlimited OCR 5580 TPS vs DeepSeek OCR 4951 TPS(+12.7%)다. 3.3절이 단일 페이지용으로 Gundam 모드를 두었으므로 Table 1 정확도는 Gundam으로 쟀을 가능성이 높지만, 명시는 없다. 따라서 처리량과 정확도의 측정 모드가 다를 수 있다. 이 문단에는 GPU 종류와 추론 엔진이 명시되지 않았다(4.2절은 Transformers와 SGLang 구현을 함께 언급한다). 저자는 OmniDocBench의 평균 문서 길이가 짧고, 출력이 길수록 이점이 커진다고 덧붙인다.
  • 이론 상한(6절, Table 4): '이상적 동시성', 프리필 길이 10 고정, 출력 길이 256-6144 조건에서 TPS 상한을 비교한다. 하드웨어는 적혀 있지 않다. 프리필이 10토큰이라 순수하게 디코드 쪽 KV 증가 효과만 보는 설정이다.
  • 커널·메모리(3.4.3절, Figure 3): Flash Attention v3 커널의 호출당 지연을 디코딩 길이에 따라 그림으로만 보여 준다. GPU 메모리는 'DeepSeek OCR은 선형 증가, Unlimited OCR은 고정'이라는 서술뿐이다. v1 논문에 메모리 수치 표는 없다.
  • Ablation·분산: 윈도우 크기 비교, 참조 토큰 전역 유지 여부, 일반 SWA 대비 실험, 데이터만 추가해 학습한 대조군, seed·분산·신뢰구간이 모두 없다. HTML 전문과 PDF 텍스트에서 ablation/seed/variance/appendix를 검색한 결과 0건이었다. PDF는 14쪽이고 참고문헌으로 끝난다(부록 없음).

한계 · 비판

  • 유한한 컨텍스트(예: 32K)에서는 진정한 unlimited 파싱이 불가능하다고 저자가 직접 쓴다. DeepEncoder 압축률이 높아도 페이지가 쌓이면 프리필 자체가 길어지기 때문이다. 단기 계획으로 128K 학습을, 장기 계획으로 모델이 프리필 KV 청크를 골라 가져오는 prefill pool을 제시한다(v1 7절 Limitation and Future Work). (저자 인정)
  • 40+페이지 구간에서 반복·인식 오류가 늘어난다(Table 3: edit distance 0.1069, Distinct-20 96.08%, Distinct-35 96.90%). 저자는 반복 오류 사례를 살펴본 결과를 이렇게 설명한다. 대부분은 R-SWA가 진행 위치를 잃어서가 아니라, 다중 페이지에서 쓰는 Base 모드(1024x1024)로는 PDF의 작은 글씨를 판독하기 어려워서 생긴다는 것이다(v1 5.4절). 이 원인 귀속은 사례 관찰에 근거하며, 이를 확인하는 별도 실험은 없다. (저자 인정)
  • 출력이 짧으면 속도 이득이 없다. 이론 TPS 상한에서 출력 256토큰일 때 두 모델은 7229.52 vs 7229.32로 사실상 같다. 저자는 이득이 출력이 길어질수록만 커진다고 직접 적는다(v1 6절, Table 4). 5.2절에서도 OmniDocBench의 평균 문서 길이가 짧다는 단서를 단다. (저자 인정)
  • R-SWA를 ASR·번역 같은 참조 기반 과제로 옮기는 것은 향후 계획으로만 적혀 있고 실험은 없다(v1 1절, 7절). HTML 전문에서 ASR/translation을 검색해 해당 실험 절이 없음을 확인했다. (저자 인정)
  • [후속 문서, v1 논문 아님] 같은 팀의 Unlimited OCR Works 2 보고서(arXiv 2610.39308)는 R-SWA의 근본 병목을 이렇게 진단한다. R-SWA는 디코딩 중에도 모든 페이지의 시각 토큰에 dense하게 어텐션하므로, 페이지 수가 늘면 시각 컨텍스트도 커진다는 것이다(1-2절, Figure 1 캡션). MarathonDocBench 표(Table 2 캡션)에서는 v1을 '40-page input limitation' 때문에 보고하지 않았고, MPDocBench(Table 1)에서 v1은 Overall 61.89로 보고된다. (저자 인정)
  • 향상분의 원인이 분리되지 않았다. DeepSeek OCR 대비 OmniDocBench v1.5 +6.22점(87.01 -> 93.23)은 두 변화가 동시에 들어간 결과다. 하나는 R-SWA 교체이고, 다른 하나는 PaddleOCR 의사 라벨 약 200만 샘플로 한 4,000 step 추가 학습이다. 그런데 저자는 1절('R-SWA also yields a modest improvement'), 5.2절('demonstrates the effectiveness of R-SWA'), 5.3절('free lunch')에서 향상을 R-SWA에 직접 귀속한다. 같은 데이터로 full attention을 계속 학습한 대조군이 없다. 그래서 이 결과가 지지하는 것은 'R-SWA로 바꾸고 추가 학습해도 성능이 떨어지지 않았다'까지다. '향상이 R-SWA 덕분'이라는 저자 해석은 검증되지 않았다. 5.2절 스스로도 full attention이 발산할 수 있다는 설명을 'may'와 'could'로 추측한다. (추가 의문)
  • Ablation과 분산 보고가 전혀 없다. 윈도우 128을 고른 근거와 다른 폭과의 비교, 참조 토큰을 전역으로 두지 않는 일반 SWA 대비 실험, seed·신뢰구간이 모두 없다(HTML 전문과 PDF 텍스트에서 ablation/seed/variance/appendix 검색 0건, PDF 14쪽은 참고문헌으로 끝남). 따라서 R-SWA의 핵심 주장인 '참조 토큰을 상태 전이에서 빼야 시각 정보가 흐려지지 않는다'는 실험으로 검증되지 않은 저자 주장이다. Table 3은 단조롭지 않다(15p edit 0.0787 > 20p 0.0572, 10p Distinct-20 97.49% < 15p 99.92%). 구간당 10권 남짓의 작은 표본에서 생긴 잡음일 가능성을 배제할 수 없다. (추가 의문)
  • Table 3의 반복 지표는 디코딩 설정에 따라 해석이 달라진다. 공개 추론 예시는 다중 페이지에서 직전 1024토큰 안의 35-gram 반복을 금지하는 logits processor를 켠다(no_repeat_ngram_size=35, ngram_window=1024, v1 태그 README). 논문은 Table 3을 이 설정으로 쟀는지 밝히지 않는다. 같은 설정이 쓰였다면 Distinct-35의 99% 안팎 값에는 모델 자체의 반복 억제력뿐 아니라 디코딩 제약의 효과가 일부 섞여 있다. 1024토큰보다 멀리 떨어진 반복은 막히지 않으므로 40+페이지의 96.90%처럼 반복이 남을 수는 있다. 반복 억제를 R-SWA의 장점으로 읽으려면 processor를 끈 결과가 필요하다(분석자 해석). (추가 의문)
  • 장문 능력은 이 논문의 핵심 신규 기능인데 비교 기준이 없다. Table 3은 사내 테스트셋 하나에 Unlimited OCR만 실려 있다. 1절이 'engineering workaround'라고 비판한 페이지별 for-loop 처리(예: DeepSeek OCR로 페이지마다 따로 전사)와의 정확도·속도 비교도 없다. 저자 서술도 측정 범위를 넘는다. 1절은 책 한 권 전체를 one-shot으로 파싱한다고 쓰고, 5.4절은 수십-수백 페이지를 한 번에 프리필할 수 있다고 쓴다. 그러나 실측 최대 구간은 40+페이지이고, 7절은 32K 컨텍스트에서는 프리필 길이 때문에 진정한 unlimited가 불가능하다고 인정한다. 분석자 계산으로는 페이지당 273토큰일 때 100페이지 프리필만 약 27K로 32K의 대부분을 차지한다. 32K에 들어가는 페이지 수도 명시되지 않았다. 3.4절의 '시각 토큰 10K = 1024x1024 기준 약 20-30페이지'도 3.3절의 페이지당 256토큰으로 계산하면 약 39페이지라 논문 안에서 맞지 않는다. (추가 의문)
  • 속도·메모리 증거는 헤드라인보다 약하다. '35%'는 프리필 10토큰, 이상적 동시성, 출력 6,144토큰 조건의 이론 TPS 상한이다(Table 4, 정확히 +34.8%). 실측 end-to-end는 OmniDocBench 512 동시 요청, Base 모드에서 +12.7%(5580 vs 4951 TPS)이고, 그 문단에 GPU 종류와 추론 엔진이 없다. 메모리는 'DeepSeek OCR은 선형 증가, Unlimited OCR은 고정'이라는 서술과 Figure 3 커널 지연 그림뿐이고 수치 표가 없다. 실제 다중 페이지 입력에서는 프리필이 수천-1만 토큰이라 토큰당 어텐션 비용이 L_m에 지배된다. 그래서 Table 4 조건(프리필 10)의 이득이 그대로 옮겨지지 않는다(분석자 해석). UOCR2 보고서도 같은 방향을 가리킨다. R-SWA가 원거리 시각 토큰에 dense하게 어텐션해 페이지 수에 따라 비용이 커진다고 지적하고, 100페이지 규모에서 스텝당 디코딩 지연이 R-SWA 대비 5.6x 빠르다고 주장한다(Gundam 모드, batch 3, 페이지당 출력 1,024토큰, 저자 보고서 수치). (추가 의문)

📌 내 학습 포인트

  • R-SWA의 비용식 C = L_m + min(n,T)를 내 논문 분석 파이프라인의 토큰 비용에 그대로 대입해 본다. 서브에이전트 한 번 호출의 입력은 '참조(L_m: 논문 원문·지침)'와 '이전 출력(T: 누적 카드·이전 주 데이터)'으로 나뉜다. R-SWA처럼 이전 출력을 최근 몇 개로 자르면 T 쪽에는 상한이 생긴다. 하지만 Table 4에서 출력 256토큰일 때 이득이 0이었듯, T가 작으면 절감도 없다. L_m이 지배적이면 참조 쪽을 줄여야 한다. 같은 팀의 UOCR2가 바로 그렇게 했다. '참조가 커지면 그게 병목'이라며 참조를 고정 크기(README 예시 512토큰)의 작업 참조로 줄였고, 100페이지 규모에서 스텝당 디코딩이 R-SWA 대비 5.6x 빠르다고 주장한다(Gundam 모드, batch 3, 저자 보고서 수치). 실행 방법: ai-paper-trends 스킬의 서브에이전트 호출 몇 건에서 입력 토큰을 원문/지침/과거 카드로 나눠 기록한다. 과거 카드가 크면 '직전 1주 관련 카드만' 윈도우로 넘긴다. 원문이 크면 HTML 전체 대신 초록·방법·실험·표 절만 미리 추출해 넘긴다. 이 규칙을 SKILL.md에 적는다. GPU는 필요 없고, 측정만으로 어느 쪽을 줄일지 정할 수 있다.
  • 내 시스템의 카드에 그대로 옮겨지기 쉬운 수치 유형이 두 가지 있다. 하나는 '35% 빠름'이다. 이는 Table 4의 이론 상한(프리필 10토큰, 이상적 동시성, 출력 6,144토큰)이고, 실측은 +12.7%(512 동시 요청, Base 모드)다. 다른 하나는 '+6.22점 무손실'이다. 이 향상에는 R-SWA 교체와 200만 샘플 추가 학습이 섞여 있다. 같은 맥락에서 Distinct-35 같은 반복 지표는 공개 코드가 35-gram 반복 금지 processor를 켜 두었는지도 함께 봐야 한다. 실행 방법: 분석 스킬의 SKILL.md 체크리스트에 세 줄을 추가한다. (1) 속도·메모리 수치는 이론/실측, 동시성·배치, 입력·출력 길이, 하드웨어를 함께 적는다. (2) 'X 덕분에 향상' 주장에는 X만 뺀 같은 데이터 대조군이 있는지 적는다. (3) 생성 품질 지표는 디코딩 설정(반복 억제, temperature)이 논문이나 코드에 있는지 적는다. 자동 점검이 필요하면 settings.json의 PostToolUse 훅(matcher 'Write|Edit')에 작은 Python 스크립트를 붙인다. 이 스크립트는 _data/analysis/*.json이 저장될 때 '%'나 'x'가 붙은 속도 수치 문장에 '이론' 또는 '실측' 표기가 없으면 경고를 stderr에 쓰고 exit code 2로 끝낸다. PostToolUse에서 exit code 2의 stderr는 Claude에게 전달되지만 exit 0의 stdout은 전달되지 않으므로 이 방식이어야 Claude가 바로 고친다. 훅은 Write/Edit 도구 호출에만 걸리므로, 분석 JSON을 Bash의 Python 스크립트로 저장한다면 그 스크립트 끝에서 같은 검사 함수를 호출한다. 현재 저장 파일에는 key_numbers 필드가 없으므로(_data/analysis 검색 0건) 검사는 본문 문자열 기준으로 한다. 모델 호출이 없어 추가 토큰 비용은 경고가 났을 때의 짧은 메시지뿐이다.
  • 로컬 OCR이 필요한 경우는 텍스트 레이어가 없는 스캔 PDF·이미지 페이지뿐이다. arXiv 논문은 지금처럼 HTML/PDF 텍스트를 추출하는 쪽이 훨씬 싸므로 이 모델로 대체할 이유가 없다. 스캔 자료는 Claude에 이미지로 넘기는 대신 로컬에서 마크다운으로 바꾸면 토큰을 아낄 수 있다. 조건: NVIDIA GPU(BF16 지원)와 대략 12GB 이상 VRAM을 출발 가정으로 둔다(분석자 추정: v1 가중치 약 6.7GB + 40페이지 KV 약 0.68GB + 인코더 활성값). 저자는 Linux/A800 계열에서만 테스트했고 최소 VRAM과 Windows 지원을 밝히지 않았다. v1 transformers 경로는 순수 PyTorch eager 어텐션이라 flash-attn 없이 시도할 수 있다. 순서: 1페이지 Gundam 모드에서 시작해 5-10페이지 Base 모드로 늘리며, PyMuPDF 추출 결과나 원문과 직접 비교한다. 학습 데이터의 언어 구성이 공개되지 않았으므로 한국어 스캔 문서 성능은 반드시 1-2페이지로 먼저 확인한다. 작은 글씨가 많으면 Base 모드에서 오류가 늘어난다는 저자 설명(5.4절)을 고려해 페이지별 Gundam 처리와도 비교한다. GPU가 없거나 VRAM이 부족하면 기존 텍스트 추출로 대체한다. HF Spaces 데모는 문서를 외부 서버로 올리는 방식이므로 공개해도 되는 자료에만 쓴다.

Claude 종합 코멘트

이 논문에서 실제로 새로운 것은 디코더 12층 전부를 '시각·프롬프트 토큰은 전역, 출력 텍스트는 직전 128토큰만' 보는 마스크로 바꾸고 그 패턴으로 계속 학습해도 단일 페이지 OCR 정확도가 떨어지지 않았다는 관찰이다. 구조는 StreamingLLM류 'sink + 최근 윈도우'와 닮았다. 다만 sink 자리에 페이지 전체의 시각 토큰을 두고, 추론 시 트릭이 아니라 학습된 패턴이라는 점이 다르다. 논문은 StreamingLLM을 인용하지 않는다. 증거는 중간 이하 수준이다. OmniDocBench v1.5 +6.22점은 R-SWA 교체와 PaddleOCR 의사 라벨 200만 샘플 추가 학습이 섞인 결과다. 같은 데이터로 학습한 full attention 대조군, 윈도우 크기·참조 토큰 ablation, seed 분산이 모두 없다. v1.6 1위는 Qianfan-OCR보다 0.02점 앞선 것이고, TextEdit과 TableTEDS에서는 다른 모델에 진다. 장문 결과는 비교 모델이 없는 사내 셋 하나이고, 40+페이지에서 edit distance 0.1069로 나빠진다. 효율 헤드라인 '35%'는 프리필 10토큰·이상적 동시성 조건의 이론 상한이고, 실측은 512 동시 요청에서 +12.7%다. KV 캐시 '상수'는 출력 길이에 대해서만 상수이며, L_m은 페이지 수에 비례한다. 같은 팀의 UOCR2 보고서(arXiv 2610.39308)가 바로 이 점을 병목으로 지적하고 SR-SWA로 고쳤다. 인용할 때는 'arXiv 2606.23050v1(개정판 없음)'으로 표기하는 것이 정확하다. 단일 페이지 무손실은 추가 학습과 섞인 저자 주장이고, 속도 이득은 실측 12.7%(35%는 Table 4 이론치)라는 조건을 붙인다. 방법 상세

Depth Pro와의 관계: 논문은 Depth Pro(Bochkovskii et al., ICLR 2025, arXiv 2410.02073)를 '전작'이나 '후속'이라는 단어로 부르지 않는다. 대신 "Depth Pro 접근을 기반으로 한다"(2장)와 "Depth Pro를 따라 초점거리로 정규화한 역깊이를 예측한다"(3.1절)고 쓴다. 이어받은 것은 이 역깊이 표현, 별도 화각(FoV) 추정기로 미터 깊이를 되찾는 방식, DPT 디코더의 transposed conv 업샘플링, 다중 스케일 gradient 손실, 경계 F1 지표와 평가셋이다. 바뀐 것은 세 가지다. 다중 스케일 타일과 1536x1536 고정 입력을 버리고 ViT 한 번 통과로 원 해상도를 처리한다. 이미지 전용에서 이미지와 비디오 공용이 됐다. FoV 헤드는 독립 경량 추정기로 바뀌었다.

구조: DINOv3 ViT-S/B/L/H+(patch 16)로 초기화한 multi-view transformer와 DPT 디코더로 이뤄진다. 앞 1/3 블록은 프레임 내부 self-attention만 쓰고, 나머지 블록은 프레임 내부와 프레임 간 attention을 번갈아 쓴다. 공개 코드를 보면 프레임 간 블록은 모든 프레임의 패치 토큰을 한 시퀀스로 이어 사전학습 attention 가중치를 그대로 쓰고, cls와 register 토큰은 프레임 평균 하나만 문맥으로 넣는다. 그래서 새 파라미터가 없다. 프레임 순서 위치 인코딩도 없어 프레임 순서를 바꿔도 결과가 같고(permutation equivariant) 프레임 수가 자유롭다. 2D RoPE 좌표는 두 축 모두 긴 변으로 나눠 종횡비 정보를 남긴다. 입력은 리사이즈 없이 32의 배수로 replicate 패딩만 한다(코드 기준).

비디오 추론: buffered 모드는 N프레임 클립을 K프레임 겹쳐 처리하고 겹친 구간은 선형 가중으로 섞는다. 클립 안에서는 앞뒤 프레임을 모두 본다. unbuffered 모드는 causal이다. 현재 프레임과 직전 C-1프레임의 key/value를 FIFO 캐시에 두며, 이 캐시는 프레임 간 블록에서만 쓴다. 기본값은 N=16, K=4, C=16이다. 학습 클립은 최대 32프레임이지만 추론 길이에는 제한이 없다.

초점거리: DINOv3 ViT-S/16 기반의 23.5M 추정기를 따로 둔다. EXIF가 있는 Flickr 사진 약 9200만 장으로 학습했고, 짧은 변 512px 입력에서 짧은 변 FoV를 예측한다. 다중 프레임 입력에는 초점거리가 일정하다고 보고 프레임별 추정의 중앙값을 쓴다(3.1절). 공개 코드 기준으로 영상 파일은 첫 창 프레임들의 중앙값을 모든 프레임에 쓴다. 실시간 stream은 첫 창이 찰 때까지 그때까지의 중앙값을 쓰고, 그 뒤에는 값을 고정한다. EXIF 초점거리나 f_px가 주어지면 추정기를 건너뛴다.

학습: 19개 데이터셋에서 1~32프레임 클립을 섞는다. 데이터셋은 크기 n의 1/2 제곱에 비례해 뽑고, 작은 데이터셋에는 가중치 상한을 둔다. GPU당 토큰 예산은 73,728개다. GT 깊이는 보간하지 않고 크롭과 stride 2 서브샘플링만 한다. 손실은 네 항을 가중치 없이 더한다. mae는 metric GT 소스에만, ssi는 전 데이터에, mge(3 스케일)는 합성 데이터에만, mvc는 포즈가 있는 다중 프레임 소스에만 건다. mvc는 예측 깊이로 픽셀을 3D로 올린 뒤 GT 포즈로 다른 프레임에 재투영하고, 그 프레임의 예측과 역깊이 L1 차이를 벌한다. GT 깊이로 확인해 2% 넘게 어긋나는 가림과 움직이는 픽셀은 뺀다. 다단계 커리큘럼 없이 128개 B200에서 100K step을 학습한다(AdamW, 최대 lr 5e-5).

실험 셋업

  • 평가 틀(4장, F.2): 모두 zero-shot이다. metric 정확도는 11개 데이터셋(iBims, Middlebury, Booster, HAMMER, ETH3D, DIODE 전체 split, KITTI, nuScenes, Sintel, Spring, DyDToF)에서 delta1을 쟀다. 단일 이미지 설정은 시퀀스 첫 50프레임을 한 장씩 따로 채점했다. 비디오 설정은 KITTI, Sintel, Spring, DyDToF의 50프레임 클립을 한 번에 넣었다. GT intrinsics와 예측 intrinsics 두 조건으로 나눴다. 평가 데이터로 학습한 baseline 결과는 회색으로 칠하고 순위에서 뺐다. HTML을 확인하면 Spring에서 MapAnything, FoundationGeo, DA3-NGL, DAGE가 회색이고, 경계와 jitter 표에서는 FlashDepth-L도 회색이다. baseline과의 비교에는 H+만 썼다. metric 표(표 2, 3)의 baseline은 10-11개다
  • 경계 선명도(표 4, F.3): Depth Pro v1이 쓴 boundary F1을 그대로 썼다. 대상은 iBims, Middlebury, Sintel, Spring, DyDToF다. 프레임마다 scale과 shift를 맞춘 뒤 잰다. 출력 해상도가 GT와 다르면 nearest-neighbor로 맞춰 경계가 흐려지지 않게 했다
  • 시간적 일관성(표 5, F.1, B.3): jitter를 쟀다. GT point track을 따라 log-depth 잔차가 프레임마다 얼마나 변하는지의 평균 절대값이고, log 공간의 TEPE와 같다. Sintel과 Spring에서 영상마다 affine 정렬을 한 번만 하고 잰다. 보조 지표 TAE는 Sintel, Spring, ScanNet, Bonn, KITTI에서 쟀다. 저자들은 TAE가 정적 장면을 가정해 GT에도 0이 아닌 오차를 주고 흐린 예측을 유리하게 본다고 스스로 단서를 단다
  • baseline(표 2-5): 표 5 기준으로 24개 방법과 비교했다. 단일 이미지 계열은 Depth Pro, MoGe-2-L, MoGe-3-G, UniDepthV2-L, UniK3D-L, MetricAnything, FoundationGeo, InfiniDepth, Lotus-2, Marigold V2, Pixel-Perfect Depth, Lapis다. 다중 프레임 계열은 VGGT-1B, VGGT-Omega-1B, pi3, MapAnything, DA3-NGL, DAGE, VDA-L(Video Depth Anything), DepthCrafter, ChronoDepth, DVD, FlashDepth-L, VeloDepth다. 모두 공개 체크포인트를 공식 해상도로 돌렸다. 그래서 각 논문이 직접 보고한 수치와 다를 수 있다고 저자들이 밝힌다
  • 속도 측정(B.4 표 13, F.5 그림 12): 모두 B200 1장, bf16 autocast, eager 모드, torch.compile 없이 쟀다. 표 13은 같은 Spring 32프레임 클립을 VGA, 720p, 1080p, 4K로 넣었다. 비디오 방법은 32프레임을 한 번에, 단일 이미지 방법은 8프레임을 한 장씩 처리했다. 측정값은 warm-up 3회 뒤 11회의 중앙값이고, Depth Pro 2는 FoV 추정기 시간을 포함한다. 단일 이미지 방법의 peak 메모리는 1프레임 기준이라 32프레임을 한 번에 넣은 비디오 방법과 메모리를 바로 비교할 수 없다. VeloDepth 처리량에는 CPU에서 도는 optical flow가 들어가고, InfiniDepth 처리량은 MoGe-2 참조 계산을 빼서 상한값이다(B.4). 그림 12와 서론의 53 fps, 8 fps는 unbuffered C=16에서 초점거리를 주어 FoV 추정기를 뺀 조건이다
  • 통제 실험(E.1 표 19, F.4): 기준 A1은 ViT-L, 8 GPU, 100K step이다. held-out 시퀀스로 평가했다. Waymo 42개와 ARKitScenes 92개는 깊이 정확도, DynamicReplica 44개는 경계와 jitter를 본다. ARKitScenes는 D1 조건에서만 학습에 넣었으므로 나머지 조건에서는 처음 보는 데이터다. A1만 seed 3개로 평균과 표준편차를 냈고, 나머지 조건은 한 번씩만 돌렸다. 1 sigma보다 큰 차이에만 색을 칠했다
  • 추론 시점 분석(E.2, E.3): H+를 다시 학습하지 않고 두 가지를 봤다. 하나는 프레임 간 attention 연결을 무작위로 0-100% 끊는 실험이고 3회 반복했다. 다른 하나는 입력 짧은 변을 360, 540, 720, 원본으로 바꾸는 실험이다. 긴 영상은 DynamicReplica 300프레임, 720p, GT intrinsics로 buffered의 N, K와 unbuffered의 C를 훑었다
  • 응용(D장): RealBokeh 테스트 220장면에서 bokeh를 렌더링했다. BokehMe 렌더러는 고정했고, 전역 disparity 배율은 따로 떼어 둔 60장면 검증셋에서 골랐다. 2000x1500에서 PSNR, SSIM, LPIPS, Boundary LPIPS, DISTS를 쟀다. 비디오 bokeh(197프레임)와 novel-view synthesis(DIS5K 4장면, Tiled MPI 렌더러)는 정성 비교만 있다
  • 학습 자원(A.1, A.2): 깊이 모델 4종은 모두 128개 B200에서 100K step, AdamW 최대 lr 5e-5, warmup 5% 뒤 cosine으로 학습했다. FoV 추정기는 32개 B200에서 120k step, step당 약 3,050장, lr 1e-4다. 총 GPU 시간이나 학습 일수는 본문 전체에서 'hours', 'days', 'weeks', 'wall-clock'을 검색했지만 나오지 않았다
  • 한계 서술: 본문과 부록 전체에서 'limitation', 'fail', 'future work'를 검색했지만 별도 Limitations 절은 없다. 'limitation'은 TAE 지표의 한계(B.3)를 말할 때 한 번만 나온다. 저자가 직접 밝힌 약점은 표 8의 DIODE AbsRel 2.418이다. 레이저 GT가 맨 나뭇가지 깊이로 표시한 곳을 모델이 하늘로 예측했기 때문이라고 설명한다.   • 공개 범위와 실행 조건(README, LICENSE, pyproject): 추론 코드만 공개했고 학습, 평가 코드는 없다. 코드는 Apple 샘플 코드 스타일 라이선스(LICENSE)라 재배포를 허용한다. 가중치는 LICENSE_MODEL로, 비상업 'Research Purposes' 전용이다. 실행에는 Python 3.11 이상(.python-version은 3.12), torch 2.7 이상, timm 1.0.27 이상 1.1 미만, av, pillow-heif, huggingface-hub가 필요하다. 장치는 CUDA, MPS, CPU 순으로 자동 선택한다. 한계 · 비판

  • TAE 지표의 한계(B.3, 표 12 설명). 저자들은 깊이 GT가 희소하거나 품질이 낮은 데이터셋에서 TAE를 믿기 어렵다고 쓴다. TAE는 흐린 예측을 유리하게 보고, GT 깊이에도 0이 아닌 오차를 준다. 그래서 TAE는 보조 지표로만 쓰고, 주 지표는 point track 기반 jitter(표 5)로 잡았다. 이 TAE 기준으로 H+는 평균 순위 3.8로 3위다(VeloDepth 3.5, VDA-L 3.6). (저자 인정)
  • DIODE AbsRel 2.418(표 8 각주). 저자 설명에 따르면 DIODE 오차 대부분은 맨 나뭇가지 주변의 몇몇 실외 픽셀에서 생긴다. 레이저 GT는 이 픽셀을 나뭇가지 깊이로 표시하지만 모델은 하늘로 예측하고, 평가는 이를 최대 깊이로 둔다. AbsRel은 이런 과대 추정에 상한이 없다는 점도 저자가 직접 밝힌다. (저자 인정)
  • 실측 데이터와 경계 선명도의 충돌(E.1, 표 19 D1-D4). 실측 데이터를 더하면(D1) ARKitScenes metric delta1이 +14.3 오르지만 경계 F1은 -1.2 떨어진다. 저자들은 깊이 센서 GT가 가림 경계에서 부정확하기 때문이라고 본다. 내부 데이터를 빼면(D4) Waymo, 경계, jitter는 오히려 좋아지지만 ARKitScenes metric delta1이 45.2포인트 떨어진다고 스스로 보고한다. (저자 인정)
  • baseline 수치가 원 논문과 다를 수 있음(F.2). 모든 baseline을 공개 체크포인트로 저자들이 직접 돌렸다. 저자들은 intrinsics, 정렬 방식, 샘플링한 프레임이나 시퀀스, 평가 해상도가 연구마다 달라 published 결과와 다를 수 있다고 명시한다. (저자 인정)
  • 운용상 한계(README 'Interpreting the depth', 'Choosing settings'와 E.3). 작은 모델은 하늘을 수 km 거리로 예측할 수 있다. 초점거리가 10% 길면 모든 깊이가 10% 멀어진다. stream의 첫 프레임들은 참조할 이전 프레임이 적어 덜 안정적이다. 입력을 많이 줄이면 디테일을 잃고 깊이 스케일이 바뀔 수 있다. E.3에서는 jitter가 N=64, C=32에서 더 줄지 않고, overlap을 늘리면 jitter는 조금 줄지만 처리량이 떨어진다. (저자 인정)
  • '모든 차원에서 앞선다'는 초록 주장은 평균 순위 기준일 때만 맞다. 표 2를 HTML 셀 단위로 뽑고 PDF로 교차 확인했다. 회색(비 zero-shot)은 Spring 열의 MapAnything, FoundationGeo, DA3-NGL, DAGE뿐이었다. GT intrinsics 조건에서 H+가 단독 1위인 데이터셋은 11개 중 5개(HAMMER, ETH3D, DIODE, KITTI, Sintel)다. Middlebury는 DA3-NGL과 73.9로 같다. 나머지 5개에서는 진다. iBims 94.4는 DA3-NGL 96.1, UniK3D-L 95.3, UniDepthV2-L 94.5보다 낮다. Booster 65.7 대 DAGE 76.4, nuScenes 90.9 대 UniK3D-L 92.4, Spring 20.5 대 MoGe-2-L 27.2, DyDToF 80.5 대 DAGE 82.3이다. 예측 intrinsics 조건에서는 11개 중 7개에서 이긴다. iBims(86.6 대 UniDepthV2-L 94.6), Booster(43.1 대 DAGE 74.8), KITTI(87.9 대 UniDepthV2-L 97.6), nuScenes(87.7 대 UniK3D-L 92.1)에서는 진다. 경계 F1에서도 Sintel은 단일 이미지(40.2 대 InfiniDepth 44.8)와 비디오(43.4 대 44.8) 모두에서 지고, iBims는 MoGe-3-G(22.2)와 MoGe-2-L(20.6)보다 낮다(표 4). 평균 순위 2.4가 1위라는 사실은 그대로지만, 개별 데이터셋에서는 우세가 고르지 않다. (추가 의문)
  • 속도와 품질의 헤드라인이 서로 다른 모델에서 나온다. 53 fps는 S 모델(B200, unbuffered C=16, 초점거리 제공)이고, SOTA 품질은 8 fps인 H+다. S의 품질은 H+보다 크게 낮다. 비디오 Sintel metric delta1(GT)은 29.9 대 51.2(표 15)다. 단일 이미지 경계 F1은 Depth Pro v1보다도 5개 중 4개에서 낮다. S와 Depth Pro를 비교하면 iBims 12.6 대 19.5, Sintel 24.3 대 36.3, Spring 10.3 대 12.7, DyDToF 18.1 대 24.8이고, Middlebury만 14.9 대 7.9로 앞선다(표 16a, 표 4a). 반면 S의 jitter(Sintel 2.43)는 VDA-L(2.55)과 비슷하다. 'Pareto frontier'라는 말은 HTML과 PDF 전문에서 초록에만 나오고, baseline과 함께 속도와 품질을 그린 그림은 없다. 다만 결론 절은 S와 H+를 나눠서 서술한다. (추가 의문)
  • 데이터 기여와 구조 기여를 떼어 보기 어렵다. 표 7 데이터 풀의 프레임 수로 보면 약 49%(55,185,184프레임 중 27,196,737프레임)가 공개되지 않은 Apple 내부 데이터다. 실제 학습 샘플링은 데이터셋 크기의 제곱근에 비례하고 작은 데이터셋에 상한을 두므로, 학습에 실제로 뽑힌 비율은 이와 다르다(정확한 값은 원문에서 확인되지 않음). 저자들도 E.1에서 직접 밝힌다. 내부 데이터는 학습 혼합 밖의 유일한 검증셋인 ARKitScenes의 일반화를 높이지만(D4에서 빼면 -45.2), 경계 선명도와 jitter에는 비용이 따른다. 내부 데이터만 쓰면(D3) 모든 지표가 나빠지므로 외부 데이터도 필요하다. 문제는 이 일반화 근거가 검증셋 하나뿐이라는 점이다. 게다가 이 지표는 기준 A1에서도 seed 3개 표준편차가 3.8로 가장 흔들린다. A1을 뺀 모든 조건은 한 번씩만 돌렸고, 통제 실험은 최종 규모(H+, 128 GPU)가 아니라 ViT-L, 8 GPU에서 했다. D 조건들을 11개 zero-shot 벤치마크에서 평가한 결과는 본문과 부록에서 찾지 못했다. E.1은 모든 조건을 held-out 검증셋에서만 평가한다고 쓴다. 그래서 헤드라인 성능 중 어느 몫이 데이터에서 오는지 외부에서 확인할 수 없다. (추가 의문)
  • 단안 metric 깊이는 어려운 도메인에서 아직 절대 수준이 낮고, 초점거리 추정이 큰 오차원이 될 수 있다. H+조차 Spring GT 20.5, Booster 예측 43.1, Sintel 예측 43.4다(표 2). 예측 intrinsics로 바꾸면 크게 떨어지는 데이터셋이 있다. Booster는 65.7에서 43.1, KITTI는 98.2에서 87.9, Sintel은 60.2에서 43.4로 내려간다. 다만 방향이 고르지는 않다. Middlebury(73.9 -> 79.1)와 Spring(20.5 -> 37.0)은 예측 intrinsics에서 오히려 높다. FoV 추정기가 delta25 88.6%로 1위(표 6)여도, 데이터셋에 따라 metric 정확도가 초점거리 정보에 크게 좌우된다는 뜻이다. README의 '초점거리 10% 오차면 깊이도 10% 오차'와도 맞는다. (추가 의문)
  • 속도 비교는 측정 조건과 모델 크기를 함께 봐야 한다. 표 13은 모든 방법을 B200, bf16, eager 모드(torch.compile 없음)로 쟀다. 비디오 방법은 32프레임을 한 번에, 단일 이미지 방법은 8프레임을 한 장씩 처리했고, 단일 이미지 방법의 메모리는 1프레임 기준이다. 1080p에서 H+(5.3 fps)는 1536 고정 입력인 Depth Pro(23.4 fps)보다 느리다. FlashDepth-L(15.2), VeloDepth(16.8), MoGe-2-L(12.4)보다도 느리다. 반면 같은 1080p에서 H+는 다중 프레임 방법인 VGGT-1B(0.9), DA3-NGL(1.0), pi3(1.2), DepthCrafter(1.4), MapAnything(1.7)보다 빠르다. peak 메모리도 29.5 GiB로 DA3-NGL(114.6), VGGT-1B(68.0)보다 작다. S는 1080p에서 44.8 fps로 표 13의 원 해상도 방법 중 가장 빠르다. 그러나 4K에서는 VeloDepth(3.9)가 S(3.6)보다 빠르다. 소비자 GPU나 Windows 측정값은 논문과 저장소 어디에도 없다. 저장소에서 확인한 범위는 README, demo/README.md 전체, 'windows' grep이다. (추가 의문)

'Pareto'라는 말은 전문에서 초록에만 한 번 나온다. 적대적 검증 subagent에게 전문을 통째로 읽히면 토큰이 많이 든다. 대신 arXiv HTML 표를 셀 단위로 뽑는 짧은 Python 스크립트를 skill 폴더에 둔다. 이 스크립트는 회색(#808080) 셀을 비 zero-shot으로 표시하고, 제안 방법 행과 열별 최고 baseline만 출력한다. 연결 연구

Depth Pro 2는 Depth Pro(2410.02073)의 초점거리 정규화 역깊이와 별도 FoV 추정기 방식을 이어받는다. 그 위에 DINOv3 기반 multi-view transformer를 얹어 이미지와 비디오를 한 네트워크로, 원 해상도에서 처리한다. 새로운 점은 세 가지다. 첫째, 프레임 간 attention이 사전학습 블록을 그대로 써서 새 파라미터가 없다. 이는 VGGT와 Depth Anything 3의 교차 attention 발상을 따른 것이다. 둘째, 포즈가 있는 데이터에만 거는 multi-view consistency 손실을 쓴다. 셋째, 리사이즈나 타일 없이 토큰 예산으로 원 해상도 학습을 한다. 평가 범위는 넓다. metric 정확도는 11개 zero-shot 데이터셋에서 10-11개 baseline과 비교했고, jitter는 Sintel과 Spring에서 24개 baseline과 비교했다. 그러나 증거의 강도는 고르지 않다. 평균 순위로는 표 2-5에서 H+가 1위다. 하지만 단일 이미지 단독 1위는 GT intrinsics 조건에서 11개 중 5개, 예측 intrinsics 조건에서 7개이고, TAE는 3위다. 통제 실험은 기준 A1만 seed 3개를 썼고, 나머지는 1회씩만 돌렸다. ARKitScenes 표준편차는 3.8이다. 학습 데이터 풀 프레임 수의 약 49%는 공개되지 않은 내부 데이터다. 실제 샘플링은 크기의 제곱근에 비례하므로 학습 비중은 이와 다르다. 내부 데이터를 빼면 ARKitScenes 점수가 45.2포인트 떨어진다. 헤드라인 수치는 조건에 묶여 있다. 53 fps는 S 모델을 B200에서 unbuffered로 돌리고 초점거리를 준 조건이다. 최고 품질은 8 fps인 H+에서 나온다. 'Pareto frontier'는 초록에만 있고, 이를 그린 그림은 없다. 인용할 때는 기준을 함께 적는다. 예를 들면 'H+가 저자 측정 zero-shot 평균 순위에서 metric 정확도, 경계 F1, jitter 1위'라고 쓰고, 속도에는 모델 크기와 GPU를 붙인다. 가중치는 비상업 연구 전용이고 학습 코드가 없다. 그래서 재현 대상이 아니라 추론 도구로 보는 것이 맞다. 공개 5일째라 후속 연구는 확인하지 못했다.

방법 상세

저자는 miHoYo Honkai AI R&D Team이 주도하고 NUS, Tsinghua, UCAS, USTC, Xi'an Jiaotong 소속이 함께한다(일부 저자는 miHoYo 인턴). HSR 실험의 Gamer는 Qwen3-VL-8B에서 출발하고, 공개 벤치마크에는 Qwen3.5-35B-A3B MoE CPT 모델도 보고한다. 화면은 1280x720으로 캡처해 854x480으로 줄이고 5 Hz로 넣으며 최근 20개 관측 턴을 본다. 행동은 200 ms마다 누적 마우스 이동(X, Y, 스크롤 Z)과 33 ms 블록 6개의 눌린 키 집합으로 이루어진다. 이를 언어 모델 어휘로 직렬화하며(약 30 Hz) 별도 행동 헤드는 없다. GitHub README 기준으로 X, Y는 화면 너비와 높이의 1/1000 단위이고 키 어휘는 74개 토큰이다.

CPT는 게임별 키 명세를 입력에 넣고, 궤적마다 재바인딩 가능한 키를 무작위로 일대일 재매핑한다. 행동 스텝의 85% 넘게가 직전 행동 반복이라 n번째 반복 토큰에 gamma^(n-1)(gamma=0.9) 가중을 준다(Game-TARS의 감쇠 손실을 따름). 토큰 비율은 게임 85%, 일반 VL 15%다.

SFT 출력은 <think>r</think> 뒤 행동이며 r은 빈칸, 현재 판단, 메모리 요약 중 하나다. 별도 분류기나 라우터 없이 같은 정책이 언제 생각할지 배운다. GPT-5.6-Luna가 10초 창(관측 25장, 행동 50구간)에서 결정 지점만 골라 약 1.2M개의 Think 주석을 만들었다. 장기 메모리는 512 토큰, 단기 이력은 20턴이다. 요약은 단계 전환, 서브골 완료, 이력 퇴출 직전에 쓰고, 예산을 넘으면 오래된 요약부터 지운다. 초록의 unbounded-context 실행은 이 압축 구조를 말한다. 희소 사고가 계산을 얼마나 줄이는지는 본문에 수치가 없다.

TA-GRPO는 긴 롤아웃을 요약으로 이어진 최대 20턴 세그먼트로 자른다. 같은 과제 조건에서 롤아웃을 샘플하고(그룹 크기 G=8), 세그먼트 단계마다 그 단계에 도달한 롤아웃끼리 비교 그룹을 만든다. 따라서 그룹 크기는 G보다 작을 수 있다. 세그먼트가 같은 게임 상태에서 시작할 필요는 없다. 엔진 검증 이진 보상을 그룹 정규화해 advantage를 얻고, 이를 세그먼트 끝에 가까운 스텝일수록 크게(beta=0.9, 평균 1 유지) 나눠 준다. 갱신은 토큰 단위 clip 0.2로 한다. 게임 상태 복원, value critic, 학습된 PRM은 모두 쓰지 않는다.

Streaming-vLLM은 환경별 KV 캐시를 유지한다. 압축 시에는 퇴출된 페이지를 해제하고 남은 키의 RoPE 위상만 보정하며, Qwen3.5의 GDN 층은 고정 크기 상태를 그대로 이어 쓴다. 디코딩에서는 FSM이 구분자와 빈 키 그룹 같은 구조 토큰 초안을 내고 문법상 유효한 전이만 허용한다. BF16 본 모델이 이 초안을 검증하며, 첫 키 블록이 준비되면 먼저 클라이언트로 보낸다. RL에서는 32개 Windows VM을 H200 64장 풀로 서빙한다. Table 9는 H200과 Qwen3.5-35B-A3B로 고정된 짧은 상호작용 시퀀스를 처리한 결과다. TP1 기준선 1306 ms가 TP4, megakernel, 부분 W8A8 양자화, FSM 유도 디코딩을 누적한 뒤 65.12 ms가 된다. 반면 다중 턴 측정(App C.3, H200 TP4)에서는 35B-A3B가 BF16 110.08 ms, W8A8 92.19 ms이고, HSR 백본인 Qwen3-VL-8B는 BF16 75.66 ms다. 이 엔진 코드는 아직 공개되지 않았다(README TODO 미체크).

독자에게 옮길 만한 아이디어는 세 가지다. 첫째는 희소 사고다. 평소에는 정해진 형식만 내고 상황이 바뀔 때만 생각한다. Claude Code에서는 SKILL.md에 '기본은 짧은 구조화 출력, 검증 실패나 목표 변경 때만 상세 추론' 규칙을 두는 식으로 옮길 수 있다. 둘째는 메모리 압축이다. 단계 경계마다 완료 목표, 실패 시도, 남은 계획을 짧은 요약 파일에 쓰고, Stop hook이나 서브에이전트 종료 시점에 갱신한다. 셋째는 같은 과제의 여러 시도를 검증 가능한 점수로 상대 비교하는 그룹 평가다. 다만 뒤쪽 스텝 가중은 저자 스스로 인과 기여가 아닌 시간 prior라고 밝힌다. 직접 돌릴 수 있는 것은 GameScaling CPT 체크포인트 8종(Qwen3.5 0.8B-27B, Apache-2.0, 2.2-54.7 GB)뿐이다. 이 체크포인트는 vLLM 서빙을 전제로 하므로, Windows PC에서는 Linux 환경(WSL2 등)과 GPU 메모리(9B는 가중치만 18.8 GB)를 먼저 확인해야 한다.

실험 셋업

  • 공개 게임 벤치마크(Sec 8.1, Table 5): MCU, ViZDoom, OmniGameArena, GameWorld를 쓴다. 각 벤치마크의 원래 지표로 평가하며, 실시간(RT) 점수를 주값으로 두고 시간 정지(TP) 대비 차이(RT-TP)를 괄호로 보고한다. 저자는 MCU와 ViZDoom을 CPT에 포함된 도메인, OmniGameArena를 미지 3D 게임, GameWorld를 원거리 전이로 구분한다. 비교 대상은 GPT-5.6-Sol, GPT-5.6-Luna, Claude-Opus-5.0, GLM-5.3-Flash, DeepSeek-V4-Flash-Vision, Qwen3.5 0.8B/2B/9B/27B다. Gamer 쪽은 SFT/RL 모델 없이 CPT 체크포인트 두 개(Qwen3-VL-8B Dense, Qwen3.5-35B-A3B MoE)만 들어간다. GPT-6.1-Sol과 Gemini-3.8-Flash는 Table 5에 없다. MCU 기본 프로토콜은 600 step 상한이다(App B.6, Fig 17 캡션). 본문은 어느 벤치마크가 2D인지 밝히지 않는다. 다만 Gamer README가 링크한 GameScaling 평가 코드(github.com/THUSI-Lab/GameScaling, evaluation/README.md)는 GameWorld를 headless Chromium에서 도는 브라우저 게임 34종으로 설명한다. 카탈로그에는 2048, Tetris, Flappy Bird, Pacman 같은 2D 게임과 Temple Run 2, Wolf3D 같은 3D풍 게임이 함께 있다. 그래서 초록의 '2D 게임 벤치마크'는 GameWorld를 가리킬 가능성이 높다(우리 추정).
  • HSR 사이드 퀘스트(Sec 8.1, 8.3, Table 6, App D.3)는 두 개다. Opportunity Makes the Thief (Part I)는 마일스톤 30개, 부모 단계 22개이고, 마일스톤 유형별로는 항법 14, 대화 14, 전투 1, UI 1이다. 시간 예산은 30분이다. Bestial Ferocity는 마일스톤 55개, 부모 단계 40개이고, 유형별로는 항법 32, 대화 16, 전투 2, UI 2, 퍼즐 3이다. 시간 예산은 Sec 8.1에서 100분, App D.3 Table 14에서 6,040 s로 서로 조금 다르다. 과제마다 3회 평가한다. Acc는 검증된 마일스톤 통과 수를 (필요 마일스톤 수 x 시도 수)로 나눈 마일스톤 단위 통과율이다. 예를 들어 Gamer-RL의 퀘스트 1 값 80.0은 90개 중 72개 통과와 맞는다(우리 역산). 따라서 이 값은 중단 없는 end-to-end 완주율이 아니며, 본문도 'rather than uninterrupted end-to-end quest completion'이라고 밝힌다. 부록에 따르면 스크립트 전환으로 재개된 실행의 마일스톤 통과도 인정되고, 누락된 평가는 실패로 세지 않는다. 'The published report should state the exact number of valid attempts' 같은 미완성 문장이 남아 있고, 모델별 유효 시도 수는 보고되지 않았다.
  • HSR 미니게임(Sec 8.4, Table 7, Fig 10, App D.4)은 7개 유형 40개 과제다. PDF Figure 10 기준 개수는 Magflow Link 5, Navigation Compass 8, Abacus Circuitry 3, Hexanexus 3, Janus's Hidden Passage 7, Golden Scapegoat 7, Janus's Maze 7이다. 이 개수는 Table 7 값과 맞는다(예: NC 95.8 = 23/24, ML 53.3 = 8/15, 우리 역산). 그러나 Sec 8.1 본문은 'between one and sixteen evaluated instances'라고 적어 서로 충돌한다. 과제마다 3회 평가하며, 과제 점수는 유효 시도의 평균이다. 유형 안에서 평균한 뒤 7개 유형의 비가중 평균을 Acc로 쓴다. 평가 과제는 학습에서 제외했지만 같은 게임의 다른 플레이는 학습했다. 그래서 저자 스스로 미지 게임 zero-shot이 아니라고 밝힌다.
  • HSR 메인 스토리(App D.4 Extended Main-Story Evaluation): 스토리 아크 5개, 퀘스트 체인 19개, 메인 미션 항목 160개를 약 50시간 평가했고, 전체 시간의 95% 넘게 자율 동작했다고 보고한다. '자율 시간'의 정의, 개입 기준, 개입 횟수는 본문과 부록에서 찾지 못했다('intervention' 검색 0건).
  • 온라인 RL 설정(Sec 7.1, 7.3, Table 15, App F.2-F.3): Windows VM 32대를 H200 64장 기반 sharded Streaming-vLLM 풀로 서빙한다. 반복마다 rollout 128개를 모은다. 과제 수는 항법 8개, 퍼즐 16개이고, 과제당 rollout은 항법 16개, 퍼즐 8개다. 그룹 크기는 8이고, 배치당 2회 업데이트한다(서로 겹치지 않는 반쪽 배치). 옵티마이저는 Adam(MCore, beta 0.9/0.999)이고, LR 1e-6 상수, clip 0.2, beta 0.9, 세그먼트 20턴, 메모리 512 토큰, 최대 컨텍스트 23K를 쓴다. 학습 규모는 항법 61 iteration(약 7.8K rollout, 3.1e7 토큰), 퍼즐 53 iteration(약 6.8K rollout, 2.8e7 토큰)이다. 보상은 검증 가능한 이진 과제 보상이고, 추론 설정은 temperature 0.9, 최대 생성 512 토큰이다.
  • 실시간 대 저속 롤아웃 RL 비교(Sec 8.5, Fig 11): 항법 과제 8개에서 Streaming-vLLM 실시간 롤아웃과, 표준 vLLM 속도를 나타내는 0.6 FPS 대조군을 처음 50 iteration 동안 비교한다. 두 설정 모두 게임은 계속 진행된다. 수치는 그림에만 있고 본문 표는 없다.
  • GameScaling 통제 연구(Sec 2.3, 8.2, Table 3, App B, F.2): Qwen3.5 0.8B/2B/9B/27B, 게임플레이 50-1,600시간 6단계, 혼합 S1-S5(Minecraft 비율 100/51.4/27.1/2.8/0%)로 4x6x5=120개 구성을 학습했다. 비용은 약 45K H200 GPU-hours다. WSD 트렁크 20개를 두고, 짧은 예산 체크포인트는 여기서 분기해 각각 decay를 마친다. 검증 분포는 Minecraft, 학습에 포함된 게임, 제목이 겹치지 않는 미지 게임 28종 x 160 클립(4,480개)이다. 벤치마크 그림(Fig 14, 16)은 시간 정지 평가 기준이다.
  • 학습 하이퍼파라미터(Table 15, App F.2): CPT(GameScaling 기준 행)는 AdamW (0.9, 0.95), weight decay 0.01을 쓴다. LR은 LLM 1e-5, 비전 인코더 7e-6이고, WSD 비율은 3/87.3/9.7%다. 업데이트당 2.3e5 토큰, 6,839 iteration, 총 5.45e10 토큰, 최대 컨텍스트 45K이며, key remapping과 gamma 0.9를 쓴다. SFT는 CPT 체크포인트에서 시작한다. LR 1e-5(LLM과 비전 모두), weight decay 0.1, warmup-decay 5/95%로 1,696 iteration, 3.9e8 토큰을 학습한다. CPT는 H200 클러스터, SFT는 A800 클러스터에서 학습하고, RL은 Megatron/MCore BF16을 쓴다. HSR 보강 Gamer-CPT(Qwen3-VL-8B) 자체의 iteration 수와 GPU 시간은 따로 보고되지 않았다.
  • Streaming-vLLM 평가(Sec 8.6, Table 8, Table 9, App C.3-C.4): StreamingBench Real-Time 하위셋과 OVO-Bench(Real/Backward/Forward)로 정확도, 질의 지연, 최대 메모리를 H200에서 잰다. Streaming-vLLM 자체는 Qwen3-VL-8B와 Qwen3.5-9B에서만 돌렸다. 그래서 같은 백본으로 직접 비교한 상대는 DSCache뿐이다. ReKV, StreamingVLM, InfiniPot-V는 LLaVA-OV-7B와 Qwen2.5-VL-7B 백본 행에만 있다. 피크 메모리는 Streaming-vLLM 22 GB로 DSCache 21 GB보다 약간 크다. Table 9는 H200과 Qwen3.5-35B-A3B로 고정된 짧은 상호작용 시퀀스에 최적화를 하나씩 누적한 결과이고, 마지막 두 단계에는 부분 W8A8 양자화와 FSM 유도 디코딩이 들어간다. 저자는 일부 구성이 프로파일링 경계를 바꾸므로 단일 요인 효과가 아니라 누적 개선이라고 밝힌다. App C.3은 A800/H200, TP, BF16/W8A8를 바꿔 가며 다중 턴 지연을 측정한다.
  • 시드와 분산: HSR 과제는 3회 평균만 보고하고 표준편차는 없다. 스케일링 적합의 불확실성은 혼합 내 층화 bootstrap 300회로 추정했다. 저자는 이것이 학습 시드 간 분산이 아니라고 명시한다(App B.3-B.4). 부록 E 정성 사례는 체크포인트당 16회 시도다. 구성 요소 ablation(key remapping, repeat decay, 희소 사고 대 매 스텝 추론, 메모리 유무, 시간 가중 beta)은 없다. v3 HTML 전문에서 'ablat', 'w/o', 'without memory'를 검색해 확인했다. 'ablation'이라는 단어는 Table 9 시스템 누적 실험을 가리키는 곳(Sec 5.3, 8.6.1, App C.4)에만 나온다.

한계 · 비판

  • 평가 범위가 선택된 일부 환경과 과제 구조에 한정된다. 더 넓은 환경으로 확장했을 때의 이득은 학습 데이터의 커버리지와 구성에 달려 있다고 저자가 밝힌다(Sec 10 Limitations and Future Work, 첫째 항목). (저자 인정)
  • Streaming-vLLM의 실시간성은 평가한 GPU 플랫폼(A800, H200)에서만 확인되었다. 저자는 서빙 비용을 더 줄여야 하고 자원 제약 환경에는 모델 압축과 추가 런타임 최적화가 필요하다고 적는다(Sec 10, 둘째 항목). (저자 인정)
  • 빠르고 연속적인 상호작용만으로 복잡한 전략 문제를 풀 수 있는 것은 아니며, 깊은 숙고가 필요한 환경에서는 추론 능력이 병목으로 남을 수 있다고 인정한다. 대안으로 큰 System 2 모델과 빠른 System 1 모델을 결합하는 계층형 에이전트를 제안한다(Sec 10, 셋째 항목). (저자 인정)
  • HSR 평가는 같은 게임의 다른 플레이를 이미 학습한 상태에서 보류한 과제를 푸는 설정이라 미지 게임 zero-shot 전이가 아니라고 명시한다(Sec 8.1 평가 세트 설명). 또 스크립트 전환으로 재개된 실행의 마일스톤 통과는 무중단 자율 진행을 뜻하지 않고, 누락된 평가는 실패로 세지 않으며, 모델별 유효 시도 수는 최종 결과에서 밝혀야 한다는 미완성 문장이 남아 있다(App D.3, Table 13 직전 문단). (저자 인정)
  • TA-GRPO의 뒤쪽 스텝 가중은 시간 prior일 뿐 후반 행동이 결과에 더 기여한다는 뜻이 아니라고 밝힌다(Sec 4.2, Eq. 아래 문단). 스케일링 적합의 bootstrap 불확실성은 학습 시드 간 분산이 아니며(App B.3-B.4), 미지 원거리 게임에서는 데이터 지수 b가 0에 가깝고 within-mixture R^2가 0.079에 불과해 높은 nominal R^2(0.855)가 데이터 추가 시 지속 향상을 뜻하지 않는다고 적는다(Sec 8.2.3). (저자 인정)
  • 초록의 핵심 주장 일부는 본문 실험으로 뒷받침되지 않거나 약하게만 뒷받침된다. 먼저 'skilled'는 v3 HTML 전문에서 3회(초록, 서론, 기여 목록)만 나온다. 인간 플레이어와 비교한 실험(인원, 숙련도, 지표)은 찾지 못했다. '2D'도 초록과 서론, 기여 목록에만 나오고, 본문은 어느 벤치마크가 2D인지 밝히지 않는다. 다만 저자들이 링크한 GameScaling 평가 코드는 GameWorld를 브라우저 게임 34종(2048, Tetris, Flappy Bird 등 포함)으로 설명한다. 그래서 '2D 게임 벤치마크 경쟁력'은 GameWorld 결과를 가리킨다고 읽을 수 있다. 그렇게 읽으면 근거는 약하다. GameWorld RT에서 Gamer는 34.0/30.2로 Qwen3.5, GLM-5.3-Flash, DeepSeek-V4-Flash-Vision보다 높지만 GPT-5.6-Sol 44.3, Claude-Opus-5.0 42.0, GPT-5.6-Luna 41.6보다 낮다. 2D GUI(웹·데스크톱 앱) 평가는 없다. 데이터 규모는 사정이 다르다. 초록(v1-v3 동일)의 'a dataset constructed from tens of thousands of hours'는 원시 수집량을 가리키는 표현으로 읽을 수 있고, Sec 6의 '수만 시간 원시 게임플레이에서 필터링' 서술과 일관된다. 다만 실제 CPT 게임플레이는 Table 2 기준 약 2.4K시간이므로 '수만 시간으로 학습'이라고 줄여 쓰면 틀린다. 또 키보드·마우스 궤적은 모두 게임이나 데스크톱 데이터이고, 'embodied' 성분은 토큰 15%를 차지하는 일반 VL 데이터다. (추가 의문)
  • 공개 벤치마크 우위는 실시간(RT) 평가 조건에 크게 의존한다. Table 5의 RT 평균은 Gamer-8B-CPT 29.5, Gamer-35B-A3B-CPT 31.5로 GPT-5.6-Sol 17.6보다 높다. 그러나 괄호의 RT-TP 값으로 시간 정지 평균을 역산하면 순위가 달라진다. GPT-5.6-Sol 52.1, Claude-Opus-5.0 43.7, GPT-5.6-Luna 37.4가 Gamer-8B 33.9보다 높고, Gamer-35B 28.1은 GLM-5.3-Flash 30.9와 DeepSeek-V4-Flash-Vision 29.5보다도 낮다. GameWorld에서는 RT에서도 GPT-5.6-Sol 44.3이 Gamer 34.0을 앞선다. Gamer-35B의 평균 RT-TP는 +3.4이고, MCU에서는 +18.6이다. 저자는 이를 추론이 빨라 제때 상호작용할 수 있었고 그 결과 제어 오류 누적이 줄었기 때문이라고 설명한다. 그러나 TP에는 지연 페널티가 없으므로, RT 점수가 TP보다 높게 나온 이유는 이 설명으로 해명되지 않는다. Game-TARS, Lumine, NitroGen 같은 게임 에이전트와의 비교는 Table 1의 정성 비교뿐이고 수치 비교는 없다. Table 5에는 SFT/RL 모델 없이 CPT 체크포인트만 들어간다. HSR 평가에서 범용 베이스라인을 RT로 돌렸는지 TP로 돌렸는지는 Sec 8.1, App D, App F에서 확인되지 않았다. (추가 의문)
  • HSR 결과의 통계적 근거는 약하다. 과제당 3회 평가에 표준편차가 없다. 퀘스트 1의 Combat과 UI는 마일스톤이 1개, 퀘스트 2의 Combat과 UI는 2개, Puzzle은 3개뿐이어서 100%나 0%가 소수 실행으로 정해진다. 보고된 Acc도 퀘스트 완주율이 아니라 마일스톤 통과율이다. 퀘스트 2에서 Gamer-CPT 47.9는 Gemini-3.8-Flash 45.5와 거의 같다. 미니게임에서는 Gamer-CPT 15.0이 GPT-6.1-Sol 17.1보다 낮다. 큰 격차는 사내 데이터로 만든 SFT(69.1, 39.2)와 RL(83.6, 49.7)에서 나온다. RL은 항법 61, 퍼즐 53 iteration으로 짧다. 일부 항목은 RL 후 SFT보다 떨어졌다: Janus's Maze(52.4 -> 23.8), 퀘스트 2 Puzzle(22.2 -> 11.1), 퀘스트 1 Dialogue(92.9 -> 88.1). Table 7의 유형 값으로 다시 계산한 RL 매크로 평균은 49.6으로, 보고값 49.7과 반올림 차이가 있다. (추가 의문)
  • 구성 요소 ablation이 없다. key remapping, 반복 행동 감쇠(gamma 0.9), 희소 사고 대 매 스텝 추론, 메모리 유무, 시간 가중 beta 가운데 어느 것도 따로 끈 실험이 본문과 부록에 없다. v3 전문을 검색하면 'ablation'은 Table 9 시스템 누적 실험을 가리키는 곳에만 나오고, 'w/o'는 0건이다. 따라서 초록의 '희소 사고가 중복 계산을 크게 줄인다'는 주장은 정량 근거가 없다. Fig 11의 실시간 대 0.6 FPS 비교는 RL 알고리즘끼리의 비교가 아니다. 롤아웃 중 환경 동역학 자체를 바꾼 비교다. 그래서 저속 조건에서 나타난 reward collapse가 TA-GRPO의 안정성을 직접 보여 주지는 않는다. (추가 의문)
  • 재현성과 출처 구분에 문제가 있다. Sec 8.2의 스케일링 결과(120개 구성, 약 45K H200 GPU-hours)는 같은 팀의 별도 논문 GameScaling(arXiv 2610.28698)을 요약한 것이라고 본문이 밝힌다('We summarize ... reported in GameScaling'). 공개 가중치도 이 GameScaling 체크포인트다. Table 5의 Gamer-CPT나 HSR의 Gamer-SFT/RL은 공개되지 않았다. 공개 코드는 별도 저장소 THUSI-Lab/GameScaling에 있는 추론 클라이언트와 4개 벤치마크 평가 코드뿐이고, 학습 코드는 없다고 그 README가 밝힌다. v3 Table 1 각주는 추론 엔진을 공개한다고 적는다. 그러나 2026-11-24에 clone한 Gamer 저장소(커밋 69a4f98)에는 코드가 없고, README TODO의 Streaming-vLLM 항목도 미체크다. HSR 데이터의 녹화 주체와 동의 절차, 게임 봇과 이용약관 문제는 논문에서 다루지 않는다('ethic', 'terms of service', 'misuse', 'cheat', 'consent' 검색 0건). 책임 있는 사용 문구는 프로젝트 페이지에만 있다. (추가 의문)

재현 가능성

코드 Gamer 저장소 RainBowLuoCS/Gamer는 2026-11-24에 git clone --depth 1로 받았다(커밋 69a4f98, 2026-11-16). 파일은 readme.md, LICENSE, streaming-vllm/readme.md, 로고·배지 이미지, mp4 영상 2개를 합쳐 18개이고, 학습·추론 코드는 없다. README TODO에서 Streaming-vLLM만 미체크이고 'Coming soon'으로 적혀 있다. 이는 v3 Table 1 각주의 'we release our inference engine' 문장과 충돌한다. 실행 가능한 코드는 Gamer README 말미가 링크한 별도 저장소 THUSI-Lab/GameScaling에 있다(2026-11-24 clone, 커밋 b9c856b, 2026-11-19, 파일 1,420개). 이 저장소에는 다음이 들어 있다. 추론 클라이언트(gamescaling/prompt.py, policy.py, action.py, keymaps.py), 시스템 프롬프트 템플릿, README 기준 GPU 없이 도는 오프라인 테스트(tests/test_core.py), vLLM 서빙 스크립트(scripts/serve_vllm.sh), 4개 벤치마크 평가 코드(evaluation/, evaluation.zip)다. 평가 대상은 README 기준 MCU(OpenHA), ViZDoom, OmniGameArena, GameWorld다. README는 학습 코드가 없다고 명시한다. 코드는 읽기만 했고 실행하지 않았다.가중치 HF 컬렉션 THUSI-Lab/gamescaling-model에 GameScaling-0.8B/2B/9B/27B의 S1(Minecraft 전용)과 S3(혼합) 8종이 있다. 모델 카드 기준 bf16, 1,600시간 학습, 가중치 0.8B 2.2 GB, 2B 5.4 GB, 9B 18.8 GB(API 합계 18.84 GB로 확인), 27B 54.7 GB(GPU 2장 TP 권장)다. HSR 실험의 Gamer-CPT/SFT/RL(Qwen3-VL-8B)과 Table 5의 Gamer-8B-CPT, Gamer-35B-A3B-CPT는 컬렉션에 없다.데이터 Honkai: Star Rail 녹화 데이터, GPT-5.6-Luna 주석 SFT 데이터, RL 환경(GM 명령 기반 샌드박스)은 공개되지 않았다(v3 Table 1 각주: 데이터 보안을 이유로 HSR 데이터와 이를 학습한 체크포인트 비공개). 공개 출처인 VPT, D2E, OpenP2P와 일반 VL 데이터는 각 원 저자가 배포하는 외부 데이터다. HF 컬렉션 항목은 모델 9개와 논문 1개뿐이라 가공된 CPT 혼합 데이터셋은 올라와 있지 않다.라이선스 Gamer와 GameScaling GitHub 저장소의 LICENSE는 모두 Apache License 2.0이다. HF GameScaling 카드와 GameScaling-9B-S3 API의 license도 apache-2.0이다. GameScaling README는 백본 Qwen3.5도 Apache 2.0이라고 적는다(저자 서술이며 Qwen 측 원문은 확인하지 않았다). 두 README 모두 게임 화면, 영상, 이름, 로고 같은 게임 자산의 권리는 각 퍼블리셔에 있고 Apache-2.0이 그 권리를 주지 않는다고 밝힌다. GameScaling README는 순수 연구 목적이며 상업 활동을 하지 않는다고 적는다. HSR 게임 클라이언트는 상용 소프트웨어다.

이 논문의 헤드라인 결과(HSR 퀘스트·미니게임, Table 5의 Gamer-CPT, Streaming-vLLM 지연)는 지금 공개된 자료로 재현할 수 없다. 재현할 수 있는 것은 선행 논문 GameScaling 체크포인트로 4개 공개 벤치마크를 평가하는 정도다. 이 결과는 Gamer Table 5가 아니라 GameScaling 쪽 결과(Fig 14, 16, 시간 정지 평가)와 대응한다. Windows PC에 적용할 때의 조건은 다음과 같다. 추론 클라이언트의 의존성은 requests와 Pillow뿐이고, README에 따르면 tests/test_core.py는 GPU와 서버 없이 돈다. 따라서 프롬프트 형식과 행동 파서를 익히는 용도라면 Windows에서도 바로 시도할 수 있다(직접 실행하지는 않았다). 모델 서빙은 bash 스크립트로 vllm serve를 띄우는 방식이라 Linux 환경(WSL2 등)이 필요할 가능성이 높다. OmniGameArena 평가는 UE 5.5.4 Linux 빌드를 따로 받아야 하고, GameWorld 평가는 headless Chromium과 브라우저 게임 자산이 필요하다. 가중치 크기는 bf16 기준 0.8B 2.2 GB, 2B 5.4 GB여서 소비자 GPU에서 시도할 만하다. 9B는 18.8 GB라 24 GB급 이상이 필요하고, 27B는 GPU 2장(TP)이 필요하다. 서빙 스크립트는 최대 컨텍스트 32,768과 이미지 8장(이력 5프레임과 현재 프레임, 여유분 포함)을 쓰므로 Gamer의 20턴 이력 설정과 다르다. 또 이 체크포인트는 HSR 데이터나 SFT/RL을 거치지 않은 CPT 모델이어서 희소 사고나 메모리 요약 동작은 기대하기 어렵다.

📌 내 학습 포인트

  • 희소 사고를 카드 작성 skill의 출력 규칙으로 옮긴다. Gamer는 행동 스텝 85% 넘게가 직전 행동 반복이라는 점에 착안해, SFT에서 평소에는 빈 <think> 뒤 행동만 내고 결정 지점에만 추론을 붙인다. 결정 지점은 GPT-5.6-Luna가 10초 창(관측 25장, 행동 50구간)에서 골랐고, Think 주석은 약 1.2M개다. 독자의 SKILL.md에도 같은 원칙을 적을 수 있다. 기본은 정해진 JSON 필드만 채우고, 상세 추론 문단은 숫자 대조 실패, 초록과 본문 불일치, 이전 카드와 다른 판정 같은 사건이 있을 때만 쓰게 한다. 다만 Gamer는 학습된 정책이고 이쪽은 프롬프트 규칙이라 둘의 관계는 유비일 뿐이다. 논문도 계산 절감량을 수치로 보이지 않았다. 그러니 같은 논문 3-5편으로 규칙 적용 전후의 출력 길이와 검증 통과율을 직접 비교해 효과를 확인해야 한다.
  • 장기 세션에는 예산을 둔 단계 경계 메모리를 쓴다. Gamer는 원본 단기 이력 20턴과 512 토큰 장기 메모리를 둔다. 요약은 단계 전환, 서브골 완료, 이력 퇴출 직전에만 쓰고, 예산을 넘으면 가장 오래된 요약부터 지운다. 독자의 멀티 에이전트 워크플로에서는 단계 사이에 넘기는 상태 파일을 '완료 항목, 실패한 시도, 남은 할 일' 세 필드로 고정한다. 크기는 수백 토큰 수준의 상한으로 묶고, 갱신은 서브에이전트 종료나 Stop hook 같은 경계 시점에만 한다. 상한을 넘으면 오래된 항목부터 버린다. 이렇게 하면 전체 대화 기록을 넘길 때보다 입력 토큰이 줄어든다. Gamer가 최근 20턴을 원본으로 남기듯, 숫자 검증처럼 세부 근거가 필요한 단계는 요약 대신 원문 파일을 다시 읽게 한다. Gamer에는 메모리 ablation이 없으므로 이 설계의 이득은 논문이 아니라 독자 자신의 측정으로 확인해야 한다.
  • skill과 프롬프트 개선에 '같은 조건끼리 비교하는 검증 가능한 이진 점수'를 쓴다. TA-GRPO는 critic이나 학습된 PRM 없이, 같은 과제에서 같은 단계에 도달한 롤아웃 G=8개를 엔진이 검증한 이진 보상으로 그룹 정규화한다. RL을 돌리지 않는 독자도 이 구조를 개선 루프에 옮길 수 있다. 같은 논문에 기존 skill과 수정 skill을 각각 돌린다(토큰 비용을 고려해 G는 2-3). 점수는 기계적으로 확인 가능한 항목으로 매긴다. 예를 들어 카드의 숫자가 원문 텍스트에 있는지, 금지 문자가 있는지, 필수 필드가 있는지를 PostToolUse hook이나 스크립트로 통과/실패 채점한다. 그리고 비교는 같은 논문 안에서만 한다. 서로 다른 논문의 점수를 섞지 않는 것이 '같은 단계끼리 그룹' 원칙에 해당한다. 주의할 점이 두 가지 있다. 뒤쪽 스텝 가중(beta 0.9)은 저자 스스로 인과 기여가 아닌 시간 prior라고 밝혔으므로, 실패를 마지막 단계 탓으로 돌리는 근거가 되지 않는다. 또 Gamer RL에서 Janus's Maze가 52.4에서 23.8로 떨어졌듯 한 지표를 최적화하면 다른 항목이 나빠질 수 있으므로, 고정된 회귀 점검용 논문 세트를 함께 유지한다.

Claude 종합 코멘트

Gamer의 새로움은 개별 기법보다 통합과 실증에 있다. 하나의 자기회귀 정책이 평소에는 빈 <think> 뒤에 행동만 내고, 결정 지점에서만 추론하며, 512 토큰 메모리 요약을 쓴다. TA-GRPO는 이 요약으로 이어진 20턴 세그먼트를 같은 단계끼리 묶어 그룹 정규화한다. 이 RL은 상용 3D 게임 클라이언트 32대를 실시간으로 서빙하는 Streaming-vLLM 위에서 돌았다. 다만 GRPO, 반복 행동 감쇠, 압축 메모리, 투기적 디코딩은 모두 선행 연구에 있는 기법이다. 저자 구성은 miHoYo Honkai AI R&D Team이 주도하고 NUS, Tsinghua, UCAS, USTC, Xi'an Jiaotong이 참여했으며, 일부 저자는 miHoYo 인턴이다.

증거의 강도는 고르지 않다. HSR 사이드 퀘스트 80.0/83.6%와 미니게임 49.7%는 범용 모델과 차이가 크다. 그러나 앞의 두 값은 퀘스트 완주율이 아니라 마일스톤 통과율이다. 과제당 3회 평가에 표준편차가 없고, 마일스톤이 1-3개뿐인 범주가 있으며, 스크립트 재개도 허용한다. 평가 환경은 개발사 내부 데이터와 GM 명령에 의존하고, 일부 항목은 RL 후 오히려 떨어졌다. 공개 벤치마크에서 상위 프런티어 모델을 앞서는 것도 실시간 평가에서만이다. 시간 정지 평가로 역산하면 GPT-5.6-Sol(52.1)이 Gamer-8B-CPT(33.9)보다 높다. 구성 요소 ablation이 없어서 희소 사고의 계산 절감, key remapping, 메모리의 효과는 검증되지 않았다. 초록의 '숙련 플레이어 수준'은 본문 실험으로 확인되지 않는다. '2D 벤치마크 경쟁력'은 브라우저 게임 34종으로 된 GameWorld를 가리키는 것으로 보이는데, 이 벤치마크에서는 프런티어 모델이 RT에서도 앞선다. 초록의 'tens of thousands of hours'는 원시 수집량으로 읽어야 하며, 실제 CPT 게임플레이는 약 2.4K시간이다.

정확하게 인용하려면 이렇게 쓰는 것이 좋다. '사내 HSR 보류 과제에서 CPT, SFT, RL 단계별 향상을 보이고, H200 35B-A3B 고정 짧은 시퀀스 기준 누적 최적화로 지연을 1306 ms에서 65.12 ms로 줄인 시스템 논문(다중 턴 측정에서는 같은 모델 TP4 BF16 110.08 ms)'. 스케일링 결과는 원출처인 GameScaling(2610.28698)으로 인용한다. 지금 재현할 수 있는 것은 GameScaling 체크포인트와 그 GitHub 저장소의 추론 클라이언트, 평가 코드뿐이다.

정답 검증기 없이 대조적 제안-시험 실행-조합으로 하니스를 고치고, 그 경험을 다음 과제용 개선 하니스에 쌓는다.

LLM 에이전트의 능력은 모델뿐 아니라 실행 하니스에도 달려 있고, 재귀적 자기개선(RSI)은 이 하니스를 자동으로 진화시키는 유망한 방법이다. 그러나 열린 세계의 과제는 하니스 설계 단계에서 보지 못한 새 과제라 온라인 수정을 이끌 정답 검증기가 없고, RSI 과정 자체도 과제마다 특화돼 새 상황으로 일반화되지 않는다.

Harness²는 서로 연결된 두 단계의 재귀로 이 문제를 다루는 플러그인형 프레임워크다. 과제 수준 재귀(task-level recursion)는 대조적 Propose-Probe-Compose 단계로 정답 검증기 없이 현재 과제의 하니스 수정을 이끌고, 병렬 또는 순차 재귀로 더 늘릴 수 있다. 하니스 수준 재귀(harnessing-level recursion)는 이런 수정에서 경험을 뽑아 지속 개선 하니스(continual improvement harness)를 갱신해, 에이전트가 이후 과제에 더 잘 적응하게 한다.

  • 정답 검증기가 없는 열린 세계 과제를 위한 2단계 재귀 하니스 개선 프레임워크(과제 수준·하니스 수준)
  • 3개 전문 벤치마크와 4개 모델-하니스 구성에서 한 번의 단계(k=1)만으로 GLM-5와 Gemini 3.5 Flash를 기본 하니스보다 일관되게 개선했다고 보고. 단 k=1에도 과제당 실행 4회와 Claude Opus 4.8 편집 세션 3회가 들어간다(W43 심층 분석)

Codex 기반에서는 상시 텍스트가 AGENTS.md 하나로 합쳐지고, 훅은 Claude Code 훅 스키마를 따르는 .codex/hooks.json으로 바뀐다(저장소 prompts.py).

Propose: 먼저 현재 하니스로 참조 실행을 돌린다. 편집기(Claude Opus 4.8, OpenCode 위 에이전트 세션)는 과제·하니스·궤적·산출물·라이브러리를 파일로 받아 후보 2개를 만든다. INV 후보는 도구 오류·반복 작업·완료 확인 같은 도메인 무관 절차 결함을 맡고, DOM 후보는 산출물 구조·결정 규칙 같은 실무 지식을 맡는다. 프롬프트의 지시는 네 가지다. 모든 편집은 궤적의 특정 순간에 근거해야 한다. 우선순위는 실행 간 불일치, 반복 실패, 잠재 위험 순이다. 상시 텍스트보다 skill·script·plugin을 먼저 쓴다. 기본 실행이 발견한 이 작업공간의 검증된 사실(파일 간 키 매핑 등)은 하니스에 직접 적는다.

Probe: 각 후보를 같은 과제·모델·환경에서 1회 실행해 참조 실행과 궤적·산출물을 비교한다. 이때 쓰는 신호는 정답이 아니라 행동 대조(behavioral contrast)이고, 이를 판단하는 것은 실행 기록을 읽는 LLM 편집기다. 저자도 이 대조가 정답을 검증하지 않는다고 적는다(2.2.1). 구성기 프롬프트는 후보 간 일치를 독립 증거가 아니라 지지로만 보라고 하고, 불일치가 나오면 투표하지 말고 궤적을 다시 보라고 지시한다. 채점 결과는 guard가 컨텍스트에 들어오지 못하게 막는다.

Compose: 구성기는 참조·후보·diff·실행 기록을 보고 병합, 한 후보 채택, 수정, KEEP_BASE 중 하나를 고른다. 결정은 kept|revised|dropped -> 편집 -> 근거 형식으로 기록한다. 기본 실행에서 반복된 실패는 강한 근거로, 후보의 1회 실행 결과는 약한 근거로 본다. 산출물을 못 낸 실행과 엮인 편집은 위험(UNSAFE)으로 표시한다. 구성된 하니스를 다시 실행한 결과가 제출물이 된다.

예산 k: 병렬 재귀는 기본 실행 k개, INV·DOM 후보 각 k개, 전체 풀을 보는 독립 구성 k개를 만든다. 폭을 넓히는 방식이며 집단 갱신은 1회다. 순차 재귀는 PPC를 k번 이어 이전 체크포인트와 누적 증거를 넘긴다. 깊이를 늘리는 방식이다. 두 방식 모두 과제당 실행 4k회와 개선 세션 3k회를 쓴다(저장소 ledger.py). k>1이면 선택기가 익명화된 최종 산출물 k개 중 하나를 고르고, k=1은 선택 없이 실행 4회와 세션 3회다.

하니스 수준 재귀: 제출 후 Reflector가 전체 기록을 읽고, 변경된 구성요소마다 편집 효과를 helped/hurt/no observed effect/confounded로 판정한다. 그다음 cue·lesson·evidence·confidence로 된 교훈을 1개 쓰거나 NO_ENTRY를 낸다. 도메인별 라이브러리에는 채택된 하니스의 전체 트리, EXPERIENCE.md, INDEX.md가 쌓인다. 코드에서는 교훈이 없으면 항목 자체를 추가하지 않는다(library.py has_experience). 다음 과제는 다시 H0에서 시작하고, 편집기는 라이브러리 구성요소를 복사해 수정할 수 있지만 이전 과제의 사실은 다시 검증해야 한다. 모델 가중치와 단계 프롬프트는 고정되고 라이브러리만 바뀐다.

실험 셋업

  • 구성은 4개로, 실행기(executor) 2개(Gemini 3.5 Flash, GLM-5, 가중치 고정)와 기본 하니스 2개(OpenCode, Codex CLI)의 조합이다. 편집기와 선택기는 Claude Opus 4.8이고 OpenCode 안에서 high reasoning effort로 돈다(D.2). 메인 표(Table 1, 2)의 Harness²는 k=1이다. '+ Recursion' 행은 병렬 재귀 k=5에서 평균이 얼마나 바뀌었는지를 적은 것이다(3.1).
  • 반복 실행: 독립 스트림 3회의 평균과 SD를 보고하며, 스트림마다 과제 순서를 섞는다. 라이브러리는 벤치마크 도메인마다 빈 상태에서 시작해 과제가 끝날 때마다 갱신된다(3.1, 부록 B, D.2). 저장소 문서에 따르면 --seed는 과제 순서만 섞고 모델 샘플링은 통제하지 않는다(docs/EXPERIMENTS.md). 본문과 부록에서 'significan', 'p-value', 'confidence interval'을 검색했지만 유의성 검정은 없었다.
  • 실행 상한: 롤아웃 1회는 200 model turns, 3,600초까지다. WorkBuddy는 컨테이너 타임아웃을 기본값의 2배로 쓴다. 롤아웃은 다른 과제의 기억 없이 돈다(D.1). 편집 세션 상한은 논문에서 확인되지 않는다. 코드 기본값은 steps=120, timeout=3600이다(core/spec.py ChannelSpec).
  • 베이스라인(부록 C)은 모두 같은 실행기, 초기 하니스, 테스트 스트림, 심사기를 쓰고, 수정과 반성에는 Opus 4.8을 쓴다. 비교 대상은 다섯 가지다. - Base harness. - ReasoningBank: gemini-embedding-001로 같은 도메인에서 가장 비슷한 과거 과제의 기억 항목을 최대 3개 꺼내 쓰고, 정답 없는 self-judge를 둔다. - Meta-Harness: 오프라인 방식이다. WB/JB에서는 train half로 10 iterations x 2 candidates x 3 replicates, margin 0.01을 쓰고, LAB에서는 24-task dev set을 쓴다. - Harness Scaling: 과제별로 수정 루프를 돌리고 상태를 다음 과제로 넘기지 않는다. k=1에서는 기본 롤아웃 1회, 수정 세션 1회, 배포 롤아웃 1회다. - Best-of-k: 기본 하니스를 k회 실행하고 같은 선택기로 하나를 고르며, 그림 5에만 나온다.
  • 비용 측정: 그림 6은 Gemini/OpenCode 구성의 JobBench와 WB에서 최종 제출 전까지 쓴 전체 토큰(실행 + 개선)을 로그축으로 그린다. ReasoningBank, Harness Scaling, Harness²는 k=1과 k=5 두 점씩, Meta-Harness는 한 점이 표시된다. 본문에는 방법별 토큰 절대값, 과제당 시간, USD가 없다. 'hour', 'minute', 'latency', 'cost', 'USD'로 검색했을 때 찾은 것은 지연에 대한 정성 문장뿐이다. 코드 ledger는 세션별 usd를 기록하지만 논문은 이 값을 보고하지 않는다. 모델 호출 수는 저장소 기준으로 과제당 롤아웃 4k회와 에이전트 개선 세션 3k회이고, 여기에 선택 1회(k>1일 때)와 반성 1회가 더해진다. 세션 안의 턴 수는 보고되지 않는다.
  • Ablation(Table 3)은 Gemini 3.5 Flash/OpenCode, k=1 조건에서 WB 3개 도메인 평균과 JobBench로 세 가지를 비교한다. - w/o library - w/o scoping: INV/DOM 대신 일반 편집기 2개를 쓴다. - w/o composition: 구성 없이 근거가 더 나은 후보 하나만 반환한다. 구성요소 제거(Table 6)는 k=5로 개선한 하니스에서 prompt*, skills, scripts를 빼고, 개선 과정을 다시 돌리지 않은 채 재평가한다.
  • 추가 분석은 다음과 같다. - 그림 5: k=1..5에서 병렬 재귀와 순차 재귀를 ReasoningBank, Harness Scaling, Best-of-k와 비교한다. WB-code와 WB-office만 다루며, 수치로 보아 Gemini/OpenCode 구성이다. - 그림 7: 실행 없는 직접 편집에서 라이브러리 없음, k=1 라이브러리, k=5 라이브러리를 비교하고, JB -> WB 라이브러리 전이도 다룬다. - 그림 8: 같은 모델을 실행기이자 편집기로 쓴 5개 모델 결과다(k=2). - 그림 11: leave-one-out 재실행. - 그림 12: 다른 실행기로의 전이. - 그림 13: 상용 하니스(CodeBuddy, OpenCode, Codex, Claude Code) 비교. - Table 7: 도구 호출 수와 오류율. - 그림 14: 실패 사례 9건.

WB-code subset에서만 편집기에게 산출물 파일 본문을 숨기고 파일 목록만 보여 준다(workbuddy.py proposer_deliverables). 편집기에게 주는 안내 문자열은 이 경로로 예전에 채점기의 pass rate가 노출된 적이 있다고 적고 있다. 릴리스에서 실행기의 네트워크 접근은 제한되지 않는다. 논문 실험의 네트워크 정책은 본문과 부록에서 'network', 'internet', 'egress'로 검색했지만 기술이 없었다.
  • 저장소 공개 범위: Apache-2.0, v0.1.0이고 Python 3.12-3.13과 POSIX 환경을 요구하며 README는 Linux를 명시한다. 실행기는 OpenCode와 Codex만 지원하고, 모델 경로는 Vertex AI(ADC 인증)가 기본이다. 편집기 채널은 코드에 opencode와 claude_cli 두 가지가 있다. claude_cli는 'claude --dangerously-skip-permissions -p'를 Vertex 환경변수로 부르고 ANTHROPIC_API_KEY 등을 환경에서 지운다. 기본 채널은 opencode다(config.py DEFAULT_PROPOSER_CHANNEL). 자격 증명이 필요 없는 결정론적 데모(harness2-demo)가 있다. WorkBuddy setup은 실행기가 google-vertex/gemini 계열일 때만 진행된다(install.py). 'glm'을 grep했을 때 README의 결과 문장 말고는 GLM-5 실행 경로나 설정을 저장소 텍스트 파일에서 찾지 못했다.

한계 · 비판

  • 재귀 정제 비용(부록 F 'Cost of recursive refinement'): 후보를 제안·탐침·구성하려면 실행과 편집 세션이 추가로 필요하고, 재귀 예산을 늘리면 추론 비용도 커진다. 병렬 세션으로 지연은 줄일 수 있지만 계산량 자체는 줄지 않는다. 실험은 제한된 예산 범위에서 trade-off를 보여 줄 뿐이고, 보편적인 최적 배분을 확립하지는 않았다고 저자가 적는다. (저자 인정)
  • 실행 기반 피드백의 한계(부록 F 'Execution-based feedback', 2.2.1): 정답 감독이 없어서 정제는 행동 대조와 모델 판단에 기댄다. 이 신호는 실행 간 변동성과 모델들이 공유하는 편향에 민감하다. 또 채택한 변경이 옳다는 것도, 다른 과제로 전이된다는 것도 보장하지 않는다. (저자 인정)
  • Leave-one-out 재실행(E.2, 그림 11)의 WB 77.5 -> 79.4, JB 36.0 -> 37.7에 대해 저자는 두 가지 단서를 단다. 재실행은 이후 과제의 항목까지 볼 수 있으므로 온라인 이득의 추정치가 아니라 오프라인 재사용 분석이다. 반복 실행 자체가 차이에 기여했을 수도 있다. (저자 인정)
  • 구성요소 제거(E.1, Table 6)에서 skills -5.3, scripts -3.7, prompt* -1.5가 나왔다. 저자는 이 결과가 여러 구성요소 그룹의 기여를 지지할 뿐 효과가 합산된다는 근거는 아니라고 적는다. 상용 하니스 비교(E.5, 그림 13)의 +4.6/+5.8/+4.9에도 정제가 추가 test-time compute를 쓴다는 단서를 붙인다. (저자 인정)
  • 실패 분석(E.6, 그림 14): 저자는 참조 실행보다 점수가 낮아진 9건을 세 유형으로 나눈다. 첫째, 선택기가 약한 후보를 고른 경우다(WB-code에서 95점 후보 대신 55점 후보, LAB에서 coverage가 좁아져 54 -> 26). 둘째, 잘못된 전제가 모든 후보로 퍼진 경우로 2-11점을 잃었다. 셋째, 결과 변동, 심사기 판정 누락, 평가 기준과 무관한 편집 때문에 원인을 가리기 어려운 경우다. 저자는 coverage와 정밀도의 균형을 맞춘 선택, 공유된 가정을 흔드는 probe, 편집 효과와 결과 변동을 구분하기 위한 반복 실행이 필요하다고 적는다. 다른 실행기로의 전이(E.3)에서도 이득이 실행기와 도메인에 따라 크게 다르다고 밝힌다.   • test-time compute와 하니스 개선 효과가 섞여 있다. k=1이어도 같은 과제를 기본 실행 1회와 후보 실행 2회로 미리 돌린 뒤 최종 실행 결과를 제출한다(롤아웃 4회, Opus 4.8 세션 3회). 편집기 프롬프트는 기본 실행에서 알아낸 작업공간 사실을 하니스에 적으라고 요구한다. 그런데 메인 표의 Base는 실행 1회이고, 표 안의 test-time 대조군인 Harness Scaling k=1도 롤아웃 2회와 세션 1회로 Harness²보다 적게 쓴다. 계산량 비교 근거는 두 가지다. 첫째, 그림 6(Gemini/OpenCode, JB·WB)은 실행과 개선을 모두 센 토큰 기준 비교다. 저자는 Harness² k=1과 k=5가 모두 경험적 Pareto frontier 위에 있다고 적는다. 그림을 읽으면 k=1은 토큰 규모가 비슷하거나 더 큰 ReasoningBank k=5, Harness Scaling k=5보다 이득이 크고, Meta-Harness보다 훨씬 적은 토큰으로 이득이 더 크다. 이는 저자에게 유리한 근거다. 둘째, 그림 5의 Best-of-k는 같은 k에서 롤아웃을 k회만 쓰므로 계산량을 맞춘 대조가 아니다. 저자는 k=2의 두 재귀 형태가 두 도메인 모두에서 k=5의 모든 베이스라인보다 높다고 적는다(4장, Best-of-5 포함). 다만 롤아웃 수를 4회로 맞추면 WB-code에서 Best-of-4(판독 약 77.0)가 Harness² k=1(76.5)과 비슷하거나 약간 높다. 재현 가능성

코드 공개. https://github.com/google-research/harness2 main 브랜치(확인한 커밋 1cfe254)이고, 버전은 pyproject 기준 v0.1.0이다. GitHub Releases 페이지에는 릴리스가 없다(2026-10-19 확인). PPC 재귀(core/recursion.py), 선택(selection.py), 라이브러리(library.py), 누출 guard(context.py), 단계별 프롬프트(prompts.py), WorkBuddy·JobBench·LAB 어댑터, 자격 증명 없이 도는 결정론적 데모(harness2-demo)가 들어 있다. 논문의 test split 파일은 저장소에서 찾지 못했다(파일 트리에서 split·EXPERIENCE·INDEX 이름 검색). scripts/split_tasks.py로 직접 만들어야 하고, 문서도 생성된 분할이 release asset이 아니라고 밝힌다.가중치 해당 없음. 이 방법은 모델 가중치를 고정한 채 하니스 파일만 바꾸며, 학습된 가중치나 체크포인트를 배포하지 않는다. 실행기(Gemini 3.5 Flash, GLM-5)와 개선기(Claude Opus 4.8)는 외부 모델을 API로 부르고, 기본 경로는 Vertex AI(ADC 인증)다. 저장소(커밋 1cfe254)에서 'glm'을 grep하면 텍스트 파일 중 README의 결과 문장만 걸린다. 그래서 GLM-5 실행 설정은 저장소에서 찾지 못했다. 논문 실험에서 채택된 하니스나 라이브러리 산출물이 공개 자산으로 올라와 있는지도 확인되지 않았다. assets 폴더에는 이미지와 영상만 있다.데이터 세 벤치마크 모두 외부에서 만든 것이고 setup 스크립트가 받아 온다. WorkBuddy-Bench(Tencent)는 업스트림 자체 라이선스로 EU 지역 제한이 있다. JobBench는 Hugging Face에 공개돼 있고 RUBRICS.json도 공개라서 다운로드 시점 revision이 기록된다. LAB은 harveyai/harvey-labs다.라이선스 Apache License 2.0 (LICENSE 파일에서 직접 확인). 논문 HTML의 라이선스 표기는 CC BY 4.0이다. 벤치마크 데이터는 각 업스트림 라이선스를 따른다.

Linux와 Python 3.12-3.13만 지원한다(README 'Use Linux, Python 3.12', pyproject 'Operating System :: POSIX'). 그래서 Windows에서는 WSL2 같은 Linux 환경이 필요할 것으로 추정한다. WorkBuddy-Bench는 Docker Engine도 요구한다(docs/BENCHMARKS.md, docs/SETUP.md). 실행기 하니스는 OpenCode와 Codex만 지원하고, Claude Code는 실행기로 지원하지 않는다. 편집기 채널은 opencode(기본)와 claude_cli 두 가지다. claude_cli는 'claude --dangerously-skip-permissions'를 Vertex를 거쳐 부르고 ANTHROPIC_API_KEY는 환경에서 지운다(core/proposer.py). 실행기 네트워크가 제한되지 않으므로, 문서(docs/EXPERIMENTS.md 'Web access')는 평가 전에 huggingface.co, github.com 등으로 나가는 egress를 도구 설정이 아니라 네트워크 수준에서 차단하라고 권고한다. 비용 기록은 코드 ledger에 남지만, 논문에는 USD와 시간이 보고되지 않는다.

📌 내 학습 포인트

  • 스킬 개선 루프의 제안 단계를 '범위가 다른 서브에이전트 2개와 구성 서브에이전트 1개'로 나눠 볼 수 있다. 첫 번째 서브에이전트는 도구 오류·반복 작업·완료 확인 같은 절차 결함(INV)만 고친다. 두 번째는 산출물 구조·도메인 규칙(DOM)만 고친다. 두 서브에이전트에는 '편집마다 실행 로그의 특정 순간을 근거로 적어라'라는 조건을 단다. 세 번째 서브에이전트는 두 diff와 실행 기록을 보고 병합, 한쪽 채택, 수정, KEEP_BASE 중 하나를 고르고, 결정을 kept|revised|dropped -> 편집 -> 근거 형식으로 남긴다. 근거: Table 3에서 scoping을 빼면 -2.9/-3.7, composition을 빼면 -1.6/-1.9다(Gemini/OpenCode 단일 구성, SD 없음). 적용 조건: k=1이어도 실행 4회와 세션 3회가 들고, 토큰은 Base의 약 6-8배다(그림 6 판독). 따라서 매주 돌리는 핵심 스킬처럼 반복 가치가 큰 것에만 쓰는 편이 현실적이다.
  • 스킬이나 프롬프트를 자동으로 고칠 때는 두 가지를 지킨다. 편집에 실행 근거나 축적된 경험을 붙이고, 채점 기준이 새지 않게 막는다. 근거: 실행·후보·라이브러리 없이 직접 편집하면 WB-code가 73.4 -> 63.2, Web이 69.9 -> 65.0으로 떨어졌다(그림 7). 다만 같은 조건에서 Office는 74.0 -> 77.1로 올랐다. 실행 없이 편집해도 k=5 라이브러리를 주면 세 도메인 모두 기본보다 높았다(그림 7 막대 수치). 그러니 '실행 없는 편집은 항상 해롭다'가 아니라 '근거도 경험도 없는 편집은 위험할 수 있다'로 읽는 것이 정확하다. 누출 쪽으로는, 릴리스 검증에서 Codex 롤아웃이 지시 없이 JobBench rubric을 내려받은 사례가 있다(docs/EXPERIMENTS.md). Claude Code에서는 두 가지를 설정할 수 있다. 첫째, settings.json permissions의 deny에 정답·평가 파일 경로의 Read와 huggingface.co·github.com 대상 WebFetch를 넣는다. 둘째, PreToolUse hook으로 평가용 디렉터리 접근과 Bash의 curl·wget 호출을 차단한다. 다만 WebFetch deny만으로는 Bash를 통한 우회를 막지 못한다. 저장소 문서도 도구 설정보다 네트워크 수준(egress 방화벽, DNS 정책)에서 막으라고 권한다. 심사 모델은 편집 모델과 다른 회사 계열로 두는 편이 낫다. 논문에서는 JobBench(Opus 4.8)와 LAB(Sonnet 4.6) 심사기가 모두 편집기와 같은 Claude 계열이다. 적용 조건: hook과 permissions는 Windows에서도 동작하지만, 완전한 네트워크 차단에는 Windows 방화벽 규칙 같은 별도 설정이 필요할 수 있다.
  • 파일 메모리에 교훈을 쌓을 때 Reflector 형식을 빌려 쓸 수 있다. 먼저 편집 효과를 helped/hurt/no observed effect/confounded로 판정하게 한다. 근거가 있을 때만 cue·lesson·evidence·confidence 4필드로 된 항목을 1개 쓰게 하고, 근거가 없으면 NO_ENTRY를 내게 해서 메모리가 부풀지 않게 한다(core/prompts.py, library.py). 다음 작업에서는 이전 항목을 '재검증이 필요한 힌트'로만 주입한다. 근거: 라이브러리를 빼면 -3.1/-1.8이다(Table 3, 실행 포함 k=1). 실행 없이 직접 편집하는 조건(그림 7 왼쪽)에서 k=5 라이브러리는 기본 대비 +0.9/+4.4/+5.1을 준다. k=1 라이브러리는 저자 표현으로 기본 수준을 회복하는 정도다(그림 막대 수치 Code 73.8, Web 72.6, Office 77.5). 또 라인의 절반 이상을 라이브러리 항목에서 가져온 파일은 2-10%뿐이다(그림 10). 그러니 통째로 복사하기보다 참고해서 고쳐 쓰는 방식이 맞다. 적용 조건: 대규모 계산 없이 텍스트 파일과 서브에이전트 1회 호출로 구현할 수 있다.

  • ← : 과제별로 하니스 수정에 계산을 할당하는 베이스라인이다. 상태를 다음 과제로 넘기지 않는다는 점에서 Harness²의 하니스 수준 재귀와 대비된다. 메인 표에서는 12개 비교 중 7개에서 기본 하니스보다 낮다.
  • ← : 하니스를 파일 구성요소로 나누는 분해 방식의 출처다. Harness²는 여기에 구성요소 1개를 더해 8개로 만든다(2.1, Table 5).
  • ← : pairwise output judgment를 쓰는 온라인 하니스 RSI 선행 연구로 인용된다(1장, 2.1, 5장, A.1, Table 4). 실험 비교 대상은 아니다. 이름이 비슷한 RRSI(2609.24972)는 본문과 참고문헌에서 'RRSI', '2609.24972'로 검색했지만 인용되지 않았다.

Claude 종합 코멘트

새로운 점은 세 가지다. 첫째, 하니스 편집을 고를 때 정답 검증기 대신 행동 대조를 쓴다. 같은 과제의 기본 실행과, 범위가 다른 후보 2개의 실행을 비교한다. 둘째, 제안을 INV와 DOM으로 범위를 나눠 받고, 구성기가 병합, 채택, 수정, KEEP_BASE 중 하나로 정리한다. 셋째, 채택된 하니스 트리와 근거 있는 교훈만 도메인 라이브러리에 쌓아 다음 과제로 넘긴다. 하니스를 8개 파일 구성요소로 다루는 방식은 Claude Code의 skills, subagents, hooks, 상시 메모리 구조와 거의 그대로 대응해서 실무에 옮기기 쉽다.

증거는 평균 기준으로 일관되지만 강하지 않다. 독립 스트림은 3개이고 유의성 검정이 없으며, 일부 JB 이득은 SD 안에 든다. Ablation과 라이브러리 분석은 단일 구성에서만 했다. LAB의 일부 구성에서는 Meta-Harness나 ReasoningBank와 비슷하거나 더 낮다.

제출물은 같은 과제를 미리 3회 돌려 본 뒤 다시 실행한 결과다. 그래서 이득에는 재시도에 따른 test-time compute 효과와 더 강한 Opus 4.8 편집기의 기여가 섞여 있을 수 있다. 계산량 측면의 근거는 대체로 저자에게 유리하지만 완전하지 않다. 토큰 기준 비교(그림 6, Gemini/OpenCode의 JB·WB)에서 Harness²의 두 점은 Pareto frontier 위에 있고, k=1이 ReasoningBank k=5, Harness Scaling k=5, Meta-Harness보다 효율적이다. 저자는 k=2가 k=5의 모든 베이스라인(Best-of-5 포함)보다 높다고도 적는다. 반면 롤아웃 수를 맞춘 Best-of-4와 비교하면 WB-code에서 k=1의 뚜렷한 우위가 보이지 않는다(그림 5 판독). LAB과 GLM-5·Codex 구성에는 이런 비교가 없다. 같은 모델이 스스로 편집한 결과(그림 8)도 벤치마크마다 Opus 편집보다 크거나 작아서, 증류 효과의 크기는 판단하기 어렵다.

'검증기 없이'라는 주장은 파이프라인 안에 rubric과 점수를 들이지 않는다는 뜻으로는 대체로 맞다. 다만 심사기가 개선기나 실행기와 같은 계열인 경우가 많다(JB Opus 4.8, LAB Sonnet 4.6, Gemini 구성의 WB Gemini 3.5 Flash). 예외인 GLM-5 구성의 WB는 심사기가 실행기·편집기와 계열이 다르고 결정론적 검사도 섞여 있는데, 여기서 향상이 가장 크다(+11.5/+10.9). 이는 같은 계열 심사기의 편향만으로 결과를 설명하기 어렵다는 근거가 된다. 그 밖에 JobBench 선택 프롬프트에 coverage 우선 지시가 있고(k>1에만 해당), 논문 실험의 네트워크 정책은 보고되지 않았다. 그래서 신호가 완전히 독립적이라고 보기는 어렵다.

인용할 때는 이렇게 적는 것이 정확하다. 'Opus 4.8 편집기를 쓰고 과제당 롤아웃 4k회를 들이는 test-time 하니스 정제로, 고정 실행기 2종과 하니스 2종 조합에서 기본 하니스 대비 WB +3.0~11.5점, JB +1.2~4.5점, LAB +2.0~11.8%p(k=1)를 보고함.' 토큰 비용이 Base 대비 k=1에서 약 6-8배, k=5에서 약 30-40배(그림 6 판독)라는 점도 함께 밝혀야 한다.

방법 상세

TradingAgents는 실제 트레이딩 회사를 모사한 LLM 멀티에이전트 프레임워크로, 7개 역할을 5개 팀으로 조직한다. (1) 애널리스트 팀(Analyst Team)은 펀더멘털(fundamental)·감성(sentiment)·뉴스(news)·기술적(technical) 분석가가 각자 구조화 리포트를 생성한다. (2) 리서처 팀(Researcher Team)은 강세(bull)/약세(bear) 연구자가 자연어 토론(natural language debate)을 n라운드 진행하고, 진행자(facilitator) 에이전트가 토론 이력을 검토해 우세 관점을 선택·기록한다(원문 표현 'facilitator ... selects the prevailing perspective'). (3) 트레이더(Trader)가 이를 종합해 매매 신호를 도출한다. (4) 리스크 관리 팀(Risk Management Team)은 공격적(aggressive)·중립(neutral)·보수(conservative) 세 관점이 토론해 노출을 조정한다. (5) 펀드 매니저(Fund Manager)가 최종 승인·집행한다. 에이전트 간 통신은 '구조화 리포트'를 1차 채널로, '자연어 대화'를 2차 채널로 쓰는 하이브리드 방식이며, 공유 글로벌 에이전트 상태(global agent state)와 메모리로 과거 결정 맥락을 유지한다(명시적 reflection 모듈 여부는 본문 확인 필요). 모델은 2계층(two-tier) 전략으로, 추론 집약 노드(분석·연구·트레이딩)에는 심층사고(deep-thinking) o1-preview를, 요약·데이터 변환·검색 등에는 신속사고(quick-thinking) gpt-4o/gpt-4o-mini를 배정하고, 전 에이전트는 ReAct 프롬프팅 프레임워크를 따른다(논문 명시). LangGraph는 논문 본문이 아니라 공식 오픈소스 레포/문서에서 구현 스택으로 명시된다('built with LangGraph').

재현 가능성

코드 공개 (github.com/TauricResearch/TradingAgents, Python, CLI+패키지, 조회 시점 약 94.6k 스타 — 변동값)가중치 해당 없음 — 자체 학습 가중치 없이 OpenAI/Anthropic/Google/xAI/DeepSeek/Qwen/Ollama 등 상용·로컬 LLM API를 호출하는 구조데이터 부분 공개 — Yahoo/FinnHub/EODHD/Reddit 등 공개 API로 수집(API 키 필요), 정제·전처리 세부는 재현 시 재구성 필요라이선스 Apache-2.0 (레포 확인)

코드는 완전 공개이며 레포/문서에 LangGraph 기반 구현, 다중 LLM 프로바이더·Ollama 로컬 모델, CLI가 명시됨. 상용 LLM API 키가 필요해 비용·모델 버전에 따라 결과 재현이 달라질 수 있고, 레포에 '연구 목적이며 금융/투자/트레이딩 조언 아님' 면책이 명시됨. 논문 성과 수치(Table 1)는 원문과 1:1 대조해 일치 확인함.

  • 화려한 수익률(SR 8.21)을 액면 그대로 믿지 말고 재현 실험을 설계할 것: 종목·기간을 넓히고 거래비용을 넣은 뒤, 특히 뉴스/지표 검색을 시점정합(point-in-time)으로 잠근 out-of-sample 백테스트를 돌려 미래정보 유입을 통제하는 검증 습관을 기른다.
