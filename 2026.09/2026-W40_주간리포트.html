실제 트레이딩 회사처럼 역할을 나눈 LLM 에이전트들이 토론으로 주식 매매를 결정한다.

금융 분야의 LLM 활용은 단일 에이전트가 한 가지 작업을 처리하거나 여러 에이전트가 자료를 따로 모으는 수준에 머무는 경우가 많다. 실제 트레이딩 조직처럼 서로 다른 관점이 충돌하고 위험을 통제하는 협업 구조는 충분히 탐구되지 않았다.

펀더멘털·감성·기술 분석가와 강세(Bull)·약세(Bear) 리서처, 리스크 관리자, 트레이더를 각각 LLM 에이전트로 구현한다. 강세와 약세 에이전트가 시장 상황을 토론하고, 트레이더가 그 논쟁과 과거 데이터를 종합해 행동을 선택한다. 별도의 리스크 관리 팀이 노출 수준을 점검해 공격적·중립적·보수적 관점을 의사결정에 반영한다.

  • 실제 트레이딩 회사의 역할 분담과 토론 구조를 재현한 멀티에이전트 프레임워크
  • 베이스라인보다 높은 누적 수익률과 Sharpe Ratio를 보고

방법 상세

TradingAgents는 실제 트레이딩 회사를 모사한 LLM 멀티에이전트 프레임워크로, 7개 역할을 5개 팀으로 조직한다. (1) 애널리스트 팀(Analyst Team)은 펀더멘털(fundamental)·감성(sentiment)·뉴스(news)·기술적(technical) 분석가가 각자 구조화 리포트를 생성한다. (2) 리서처 팀(Researcher Team)은 강세(bull)/약세(bear) 연구자가 자연어 토론(natural language debate)을 n라운드 진행하고, 진행자(facilitator) 에이전트가 토론 이력을 검토해 우세 관점을 선택·기록한다(원문 표현 'facilitator ... selects the prevailing perspective'). (3) 트레이더(Trader)가 이를 종합해 매매 신호를 도출한다. (4) 리스크 관리 팀(Risk Management Team)은 공격적(aggressive)·중립(neutral)·보수(conservative) 세 관점이 토론해 노출을 조정한다. (5) 펀드 매니저(Fund Manager)가 최종 승인·집행한다. 에이전트 간 통신은 '구조화 리포트'를 1차 채널로, '자연어 대화'를 2차 채널로 쓰는 하이브리드 방식이며, 공유 글로벌 에이전트 상태(global agent state)와 메모리로 과거 결정 맥락을 유지한다(명시적 reflection 모듈 여부는 본문 확인 필요). 모델은 2계층(two-tier) 전략으로, 추론 집약 노드(분석·연구·트레이딩)에는 심층사고(deep-thinking) o1-preview를, 요약·데이터 변환·검색 등에는 신속사고(quick-thinking) gpt-4o/gpt-4o-mini를 배정하고, 전 에이전트는 ReAct 프롬프팅 프레임워크를 따른다(논문 명시). LangGraph는 논문 본문이 아니라 공식 오픈소스 레포/문서에서 구현 스택으로 명시된다('built with LangGraph').

재현 가능성

코드 공개 (github.com/TauricResearch/TradingAgents, Python, CLI+패키지, 조회 시점 약 94.6k 스타 — 변동값)가중치 해당 없음 — 자체 학습 가중치 없이 OpenAI/Anthropic/Google/xAI/DeepSeek/Qwen/Ollama 등 상용·로컬 LLM API를 호출하는 구조데이터 부분 공개 — Yahoo/FinnHub/EODHD/Reddit 등 공개 API로 수집(API 키 필요), 정제·전처리 세부는 재현 시 재구성 필요라이선스 Apache-2.0 (레포 확인)

코드는 완전 공개이며 레포/문서에 LangGraph 기반 구현, 다중 LLM 프로바이더·Ollama 로컬 모델, CLI가 명시됨. 상용 LLM API 키가 필요해 비용·모델 버전에 따라 결과 재현이 달라질 수 있고, 레포에 '연구 목적이며 금융/투자/트레이딩 조언 아님' 면책이 명시됨. 논문 성과 수치(Table 1)는 원문과 1:1 대조해 일치 확인함.

📌 내 학습 포인트

  • 역할 분리 + 하이브리드 통신 패턴을 직접 모사해볼 것: 구조화 리포트(1차)와 자연어 토론(2차)을 상태 그래프(예: LangGraph)로 분리하면 '데이터 수집 → 관점 토론 → 리스크 조정 → 승인/집행' 파이프라인을 재사용 가능한 템플릿으로 만들 수 있다.
  • 2계층 모델 라우팅(deep-thinking o1-preview vs quick-thinking gpt-4o/mini)을 벤치마크할 것: 추론 노드에만 고비용 모델을 쓰고 요약·검색은 저비용 모델로 돌려 비용/성능 트레이드오프를 직접 측정하면 실전 에이전트 설계 감각을 얻는다.
  • 화려한 수익률(SR 8.21)을 액면 그대로 믿지 말고 재현 실험을 설계할 것: 종목·기간을 넓히고 거래비용을 넣은 뒤, 특히 뉴스/지표 검색을 시점정합(point-in-time)으로 잠근 out-of-sample 백테스트를 돌려 미래정보 유입을 통제하는 검증 습관을 기른다.

RRSI: Regularized Recursive Self-Improvement of Agent Harnesses

Peng Xia, Rujun Han, Zifeng Wang 외 11명

▲ 218💬 2★ 966
agent-harnessself-refinementagentic-workflowout-of-distribution-generalizationregularization

하니스를 스스로 고치며 진화하는 에이전트가 학습 과제에 과적합하지 않도록 제안과 선택에 정규화를 건다.

에이전트의 능력은 고정된 백본 모델을 둘러싼 프롬프트·제어 흐름·도구·메모리·컨텍스트 관리, 즉 하니스(harness)에 크게 좌우된다. 최근에는 하니스의 구성요소별 수정안을 반복 제안·선택하는 자동화, 곧 시스템 수준의 재귀적 자기개선(RSI)이 늘고 있다. 그러나 이런 진화는 학습 과제를 암기해, 분포 내에서는 크게 오르다가 분포 밖 벤치마크에서는 이득이 줄거나 사라지는 과적합을 일으킨다.

하니스 자기개선의 후보 제안(proposal)과 선택(selection) 양쪽에 정규화(regularization) 원리를 넣는다. 제안기(proposer)는 시간에 따라 줄어드는(temporally annealed) 예산으로 한 후보가 묶을 수 있는 수정 개수를 제한하고, 진화 이력을 보고 아직 탐색하지 않은 경로를 장려한다. 선택기(selector)에는 벤치마크 특화 제안을 걸러내는 비평가(critic)와, 너무 작거나 비싸거나 더는 쓸모없어진 변경을 제거하는 가지치기기(pruner)가 붙는다. 이 제약들이 벤치마크 전용 트릭이나 잡음보다 재사용 가능한 에이전트 메커니즘을 선호하게 만든다.

  • 하니스 자기개선의 과적합(분포 내 이득이 분포 밖에서 소멸)을 문제로 명시하고 정규화로 다루는 프레임 제시
  • 코딩·에이전틱 워크스페이스·엔지니어링 설계 8개 벤치마크에서, 진화 대상 분할 최대 +14.1점, 분포 밖 5개 벤치마크 최대 +4.7점

방법 상세

OpenHands(구 OpenDevin)는 코딩·명령줄·웹 브라우징을 사람 개발자처럼 수행하는 AI 에이전트를 만들기 위한 오픈 플랫폼으로, 핵심 추상화는 단일 step(self, state: State) 함수와 이벤트 스트림(event stream)이다. 이벤트 스트림은 과거 행동(Action)과 관찰(Observation)을 시간순으로 누적한 State의 핵심 요소로, 사용자 지시/피드백·멀티에이전트 위임 메타데이터까지 담는다. 행동 원시 타입은 IPythonRunCellAction(샌드박스 내 Python 실행), CmdRunAction(bash 실행), BrowserInteractiveAction(BrowserGym DSL 기반 웹 조작), 그리고 AgentDelegateAction·MessageAction·AgentFinishAction 등으로 정의된다. 실행 격리는 Agent Runtime으로, Docker 샌드박스 위에서 bash 쉘, Jupyter IPython 서버, Playwright 기반 Chromium을 제공한다. AgentSkills는 기본 bash/Python으로 얻기 어려운 유틸리티 툴박스로 edit_file, scroll_up/scroll_down, parse_image(비전-언어 모델 기반), parse_pdf 등을 제공한다. 멀티에이전트 협업은 AgentDelegateAction으로 구현되어 범용 CodeActAgent가 웹 태스크를 BrowsingAgent에게 위임할 수 있으며, 커뮤니티 에이전트 구현은 AgentHub에 모인다. 이 이벤트 스트림 + Docker 런타임 + AgentSkills + 위임 구조가 새 에이전트 구현·평가를 표준화하는 프레임워크를 이룬다.

  • 버전이 빠르게 바뀌어(v1.5 vs v1.8) 논문 수치와 현재 레포 성능/설계가 어긋날 수 있어 재현 시 커밋+모델 버전 고정 필요 (추가 의문)
  • 도메인별 최고점은 여전히 전문 에이전트/전용 학습 모델에 미달 - '제너럴리스트'의 대가로서 범용성-성능 트레이드오프가 명시적으로 존재 (추가 의문)

Efficient Memory Management for Large Language Model Serving with PagedAttention

Woosuk Kwon, Zhuohan Li, Siyuan Zhuang 외 6명

▲ 75💬 1★ 86.1k
kv-cachellm-servingpaged-attentionmemory-management

운영체제의 가상 메모리·페이징을 KV 캐시에 적용해 메모리 낭비를 거의 없애고 LLM 서빙 처리량을 2~4배 올린다.

LLM을 높은 처리량으로 서빙하려면 많은 요청을 한 번에 배치해야 한다. 그런데 요청마다 KV 캐시 메모리가 매우 크고 동적으로 늘었다 줄어, 비효율적으로 관리하면 단편화(fragmentation)와 중복 복제로 메모리가 크게 낭비되고 배치 크기가 제한된다.

운영체제의 고전적 가상 메모리와 페이징 기법에서 착안한 어텐션 알고리즘 PagedAttention을 제안한다. KV 캐시를 고정 크기 블록 단위로 나눠 연속 메모리가 아니어도 저장할 수 있게 하고, 그 위에 LLM 서빙 시스템 vLLM을 구축한다. vLLM은 KV 캐시 메모리 낭비를 거의 0으로 줄이고, 요청 내부와 요청 간에 KV 캐시를 유연하게 공유해 메모리 사용을 더 줄인다.

  • 가상 메모리·페이징 개념을 KV 캐시 관리에 이식한 PagedAttention 알고리즘
  • KV 캐시 낭비를 거의 없애고 요청 내·간 공유를 지원하는 서빙 시스템 vLLM
  • 같은 지연 수준에서 FasterTransformer·Orca 대비 처리량 2~4배 향상
  • 긴 시퀀스, 큰 모델, 복잡한 디코딩 알고리즘일수록 이득이 커짐

정답 보기

KV 캐시를 고정 크기 블록으로 나눠 비연속 메모리에 저장하는 페이징 방식으로 단편화와 중복을 줄이고, 아낀 메모리만큼 더 많은 요청을 한 배치에 넣을 수 있어 처리량이 오른다.

02 이번 주 동향 인사이트

📋 이번 주 요약

이번 주 6편은 에이전트 3편(50%), 효율·추론최적화 2편, 비전 1편으로 나뉜다. 가장 큰 관심(▲218)을 받은 RRSI는 하니스 자동 진화가 진화 대상 분할에서 최대 +14.1점을 얻는 동안 분포 밖 5개 벤치마크에서는 최대 +4.7점에 그치는 격차 자체를 문제로 삼고, 제안 예산 감쇠·비평가·가지치기기로 이를 억제하면서 정책 토큰을 30% 줄였다고 보고한다. 효율·추론최적화는 관측 이래 처음으로 한 주에 2편이 올랐는데, vLLM의 토대인 PagedAttention(같은 지연에서 처리량 2~4배)과 그 vLLM·TensorRT-LLM 위에서 추측 디코딩을 재며 합성 입력이 처리량을 과대평가한다고 지적한 SPEED-Bench다. 여기에 수집 14주 중 13주째 등장한 TradingAgents(▲148)와 7주째인 OpenDevin(▲89)이 기준점 자리를 지켰고, UniMate는 임의 골격 모션 생성으로 W32·W35의 3D 흐름을 이었다. 두 흐름의 공통분모는 '헤드라인 수치가 어떤 조건에서 나왔는가'를 연구 대상으로 끌어올렸다는 점이다.

🌊 최근 동향

누적 14회 관측(W25~W36, W38, W40) 기준, LLM/Agents는 14주 전부 등장한 유일한 카테고리이고 agentic-workflow도 누적 33회로 14주 모두 등장했다. 부상 신호는 두 갈래다. 첫째, agent-harness가 W36(Prime Agent·Apodex 1.1)과 W40(RRSI) 서로 다른 두 주에 등장해, 질문이 '하니스를 어떻게 설계하나'에서 '자동으로 고친 하니스가 일반화되나'로 한 단계 나아갔다. 둘째, 효율·추론최적화는 최근 4회 관측(W35·W36·W38·W40) 중 3회 등장해 지속 기준을 충족했고 이번 주 2편은 관측 이래 한 주 최다다. 반대로 1차 카테고리 기준 임바디드·월드모델은 W31 이후 7회 관측, document-parsing 키워드는 W34 이후 4회 관측 동안 등장하지 않아 식어가는 쪽이다. W37·W39를 수집하지 않았으므로 직전 비교는 2주 간격인 W38 대비이며, 연속 등장 배지는 달력 주 기준이라 이번 주에는 붙지 않는다.
