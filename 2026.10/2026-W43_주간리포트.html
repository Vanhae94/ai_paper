정답 검증기 없이 대조적 제안-시험 실행-조합으로 하니스를 고치고, 그 경험을 다음 과제용 개선 하니스에 쌓는다.

LLM 에이전트의 능력은 모델뿐 아니라 실행 하니스에도 달려 있고, 재귀적 자기개선(RSI)은 이 하니스를 자동으로 진화시키는 유망한 방법이다. 그러나 열린 세계의 과제는 하니스 설계 단계에서 보지 못한 새 과제라 온라인 수정을 이끌 정답 검증기가 없고, RSI 과정 자체도 과제마다 특화돼 새 상황으로 일반화되지 않는다.

Harness²는 서로 연결된 두 단계의 재귀로 이 문제를 다루는 플러그인형 프레임워크다. 과제 수준 재귀(task-level recursion)는 대조적 Propose-Probe-Compose 단계로 정답 검증기 없이 현재 과제의 하니스 수정을 이끌고, 병렬 또는 순차 재귀로 더 늘릴 수 있다. 하니스 수준 재귀(harnessing-level recursion)는 이런 수정에서 경험을 뽑아 지속 개선 하니스(continual improvement harness)를 갱신해, 에이전트가 이후 과제에 더 잘 적응하게 한다.

  • 정답 검증기가 없는 열린 세계 과제를 위한 2단계 재귀 하니스 개선 프레임워크(과제 수준·하니스 수준)
  • 3개 전문 벤치마크와 4개 모델-하니스 구성에서 한 번의 단계(k=1)만으로 GLM-5와 Gemini 3.5 Flash를 기본 하니스보다 일관되게 개선했다고 보고. 단 k=1에도 과제당 실행 4회와 Claude Opus 4.8 편집 세션 3회가 들어간다(W43 심층 분석)
  • WorkBuddy-Bench 최대 +11.5점, JobBench 최대 +4.5점, LAB 최대 +11.8%p를 보고했고, 과제 수준 재귀 예산을 늘리면 추가로 개선된다고 밝힘
  • Google Research 코드 공개(GitHub 약 6.5천 스타)와 프로젝트 페이지

방법 상세

하니스 편집(harness edit)은 고정된 모델을 둘러싼 8개 파일 구성요소의 diff다(Table 5). AHE의 파일 분해에 1개를 더해 다음 8개로 이뤄진다. - 매 호출 상시 주입: systemprompt.md, guardrails.md, LongTermMEMORY.md, tool_guidance.md - 호출 시 로드: skills/<n>/SKILL.md - bash로 실행: scripts/*.py - 별도 컨텍스트: sub_agents/<n>/AGENT.md - 도구 루프 안의 훅: plugin/*.ts 즉 프롬프트·도구·제어 흐름·메모리를 모두 포함한다. Codex 기반에서는 상시 텍스트가 AGENTS.md 하나로 합쳐지고, 훅은 Claude Code 훅 스키마를 따르는 .codex/hooks.json으로 바뀐다(저장소 prompts.py).

Propose: 먼저 현재 하니스로 참조 실행을 돌린다. 편집기(Claude Opus 4.8, OpenCode 위 에이전트 세션)는 과제·하니스·궤적·산출물·라이브러리를 파일로 받아 후보 2개를 만든다. INV 후보는 도구 오류·반복 작업·완료 확인 같은 도메인 무관 절차 결함을 맡고, DOM 후보는 산출물 구조·결정 규칙 같은 실무 지식을 맡는다. 프롬프트의 지시는 네 가지다. 모든 편집은 궤적의 특정 순간에 근거해야 한다. 우선순위는 실행 간 불일치, 반복 실패, 잠재 위험 순이다. 상시 텍스트보다 skill·script·plugin을 먼저 쓴다. 기본 실행이 발견한 이 작업공간의 검증된 사실(파일 간 키 매핑 등)은 하니스에 직접 적는다.

Probe: 각 후보를 같은 과제·모델·환경에서 1회 실행해 참조 실행과 궤적·산출물을 비교한다. 이때 쓰는 신호는 정답이 아니라 행동 대조(behavioral contrast)이고, 이를 판단하는 것은 실행 기록을 읽는 LLM 편집기다. 저자도 이 대조가 정답을 검증하지 않는다고 적는다(2.2.1). 구성기 프롬프트는 후보 간 일치를 독립 증거가 아니라 지지로만 보라고 하고, 불일치가 나오면 투표하지 말고 궤적을 다시 보라고 지시한다. 채점 결과는 guard가 컨텍스트에 들어오지 못하게 막는다.

Compose: 구성기는 참조·후보·diff·실행 기록을 보고 병합, 한 후보 채택, 수정, KEEP_BASE 중 하나를 고른다. 결정은 kept|revised|dropped -> 편집 -> 근거 형식으로 기록한다. 기본 실행에서 반복된 실패는 강한 근거로, 후보의 1회 실행 결과는 약한 근거로 본다. 산출물을 못 낸 실행과 엮인 편집은 위험(UNSAFE)으로 표시한다. 구성된 하니스를 다시 실행한 결과가 제출물이 된다.

예산 k: 병렬 재귀는 기본 실행 k개, INV·DOM 후보 각 k개, 전체 풀을 보는 독립 구성 k개를 만든다. 폭을 넓히는 방식이며 집단 갱신은 1회다. 순차 재귀는 PPC를 k번 이어 이전 체크포인트와 누적 증거를 넘긴다. 깊이를 늘리는 방식이다. 두 방식 모두 과제당 실행 4k회와 개선 세션 3k회를 쓴다(저장소 ledger.py). k>1이면 선택기가 익명화된 최종 산출물 k개 중 하나를 고르고, k=1은 선택 없이 실행 4회와 세션 3회다.

하니스 수준 재귀: 제출 후 Reflector가 전체 기록을 읽고, 변경된 구성요소마다 편집 효과를 helped/hurt/no observed effect/confounded로 판정한다. 그다음 cue·lesson·evidence·confidence로 된 교훈을 1개 쓰거나 NO_ENTRY를 낸다. 도메인별 라이브러리에는 채택된 하니스의 전체 트리, EXPERIENCE.md, INDEX.md가 쌓인다. 코드에서는 교훈이 없으면 항목 자체를 추가하지 않는다(library.py has_experience). 다음 과제는 다시 H0에서 시작하고, 편집기는 라이브러리 구성요소를 복사해 수정할 수 있지만 이전 과제의 사실은 다시 검증해야 한다. 모델 가중치와 단계 프롬프트는 고정되고 라이브러리만 바뀐다.

실험 셋업

  • 구성은 4개로, 실행기(executor) 2개(Gemini 3.5 Flash, GLM-5, 가중치 고정)와 기본 하니스 2개(OpenCode, Codex CLI)의 조합이다. 편집기와 선택기는 Claude Opus 4.8이고 OpenCode 안에서 high reasoning effort로 돈다(D.2). 메인 표(Table 1, 2)의 Harness²는 k=1이다. '+ Recursion' 행은 병렬 재귀 k=5에서 평균이 얼마나 바뀌었는지를 적은 것이다(3.1).
  • 반복 실행: 독립 스트림 3회의 평균과 SD를 보고하며, 스트림마다 과제 순서를 섞는다. 라이브러리는 벤치마크 도메인마다 빈 상태에서 시작해 과제가 끝날 때마다 갱신된다(3.1, 부록 B, D.2). 저장소 문서에 따르면 --seed는 과제 순서만 섞고 모델 샘플링은 통제하지 않는다(docs/EXPERIMENTS.md). 본문과 부록에서 'significan', 'p-value', 'confidence interval'을 검색했지만 유의성 검정은 없었다.
  • 실행 상한: 롤아웃 1회는 200 model turns, 3,600초까지다. WorkBuddy는 컨테이너 타임아웃을 기본값의 2배로 쓴다. 롤아웃은 다른 과제의 기억 없이 돈다(D.1). 편집 세션 상한은 논문에서 확인되지 않는다. 코드 기본값은 steps=120, timeout=3600이다(core/spec.py ChannelSpec).
  • 베이스라인(부록 C)은 모두 같은 실행기, 초기 하니스, 테스트 스트림, 심사기를 쓰고, 수정과 반성에는 Opus 4.8을 쓴다. 비교 대상은 다섯 가지다. - Base harness. - ReasoningBank: gemini-embedding-001로 같은 도메인에서 가장 비슷한 과거 과제의 기억 항목을 최대 3개 꺼내 쓰고, 정답 없는 self-judge를 둔다. - Meta-Harness: 오프라인 방식이다. WB/JB에서는 train half로 10 iterations x 2 candidates x 3 replicates, margin 0.01을 쓰고, LAB에서는 24-task dev set을 쓴다. - Harness Scaling: 과제별로 수정 루프를 돌리고 상태를 다음 과제로 넘기지 않는다. k=1에서는 기본 롤아웃 1회, 수정 세션 1회, 배포 롤아웃 1회다. - Best-of-k: 기본 하니스를 k회 실행하고 같은 선택기로 하나를 고르며, 그림 5에만 나온다.
  • 비용 측정: 그림 6은 Gemini/OpenCode 구성의 JobBench와 WB에서 최종 제출 전까지 쓴 전체 토큰(실행 + 개선)을 로그축으로 그린다. ReasoningBank, Harness Scaling, Harness²는 k=1과 k=5 두 점씩, Meta-Harness는 한 점이 표시된다. 본문에는 방법별 토큰 절대값, 과제당 시간, USD가 없다. 'hour', 'minute', 'latency', 'cost', 'USD'로 검색했을 때 찾은 것은 지연에 대한 정성 문장뿐이다. 코드 ledger는 세션별 usd를 기록하지만 논문은 이 값을 보고하지 않는다. 모델 호출 수는 저장소 기준으로 과제당 롤아웃 4k회와 에이전트 개선 세션 3k회이고, 여기에 선택 1회(k>1일 때)와 반성 1회가 더해진다. 세션 안의 턴 수는 보고되지 않는다.
  • Ablation(Table 3)은 Gemini 3.5 Flash/OpenCode, k=1 조건에서 WB 3개 도메인 평균과 JobBench로 세 가지를 비교한다. - w/o library - w/o scoping: INV/DOM 대신 일반 편집기 2개를 쓴다. - w/o composition: 구성 없이 근거가 더 나은 후보 하나만 반환한다. 구성요소 제거(Table 6)는 k=5로 개선한 하니스에서 prompt*, skills, scripts를 빼고, 개선 과정을 다시 돌리지 않은 채 재평가한다.
  • 추가 분석은 다음과 같다. - 그림 5: k=1..5에서 병렬 재귀와 순차 재귀를 ReasoningBank, Harness Scaling, Best-of-k와 비교한다. WB-code와 WB-office만 다루며, 수치로 보아 Gemini/OpenCode 구성이다. - 그림 7: 실행 없는 직접 편집에서 라이브러리 없음, k=1 라이브러리, k=5 라이브러리를 비교하고, JB -> WB 라이브러리 전이도 다룬다. - 그림 8: 같은 모델을 실행기이자 편집기로 쓴 5개 모델 결과다(k=2). - 그림 11: leave-one-out 재실행. - 그림 12: 다른 실행기로의 전이. - 그림 13: 상용 하니스(CodeBuddy, OpenCode, Codex, Claude Code) 비교. - Table 7: 도구 호출 수와 오류율. - 그림 14: 실패 사례 9건.
  • 누출 방지(D.2, 부록 H, 저장소 core/context.py): 채점 판정, rubric, 점수가 든 작업 디렉터리는 넘기지 않도록 guard가 막는다. 모든 프롬프트에는 rubric이 없다는 문장이 들어간다. WB-code subset에서만 편집기에게 산출물 파일 본문을 숨기고 파일 목록만 보여 준다(workbuddy.py proposer_deliverables). 편집기에게 주는 안내 문자열은 이 경로로 예전에 채점기의 pass rate가 노출된 적이 있다고 적고 있다. 릴리스에서 실행기의 네트워크 접근은 제한되지 않는다. 논문 실험의 네트워크 정책은 본문과 부록에서 'network', 'internet', 'egress'로 검색했지만 기술이 없었다.
  • 저장소 공개 범위: Apache-2.0, v0.1.0이고 Python 3.12-3.13과 POSIX 환경을 요구하며 README는 Linux를 명시한다. 실행기는 OpenCode와 Codex만 지원하고, 모델 경로는 Vertex AI(ADC 인증)가 기본이다. 편집기 채널은 코드에 opencode와 claude_cli 두 가지가 있다. claude_cli는 'claude --dangerously-skip-permissions -p'를 Vertex 환경변수로 부르고 ANTHROPIC_API_KEY 등을 환경에서 지운다. 기본 채널은 opencode다(config.py DEFAULT_PROPOSER_CHANNEL). 자격 증명이 필요 없는 결정론적 데모(harness2-demo)가 있다. WorkBuddy setup은 실행기가 google-vertex/gemini 계열일 때만 진행된다(install.py). 'glm'을 grep했을 때 README의 결과 문장 말고는 GLM-5 실행 경로나 설정을 저장소 텍스트 파일에서 찾지 못했다.

데이터셋

  • WorkBuddy-Bench (Tencent, Team et al. 2026, arXiv 2607.20911) — Code 80, Web 70, Office 50 과제를 범주별로 반으로 나누고, 테스트 절반 40/35/25 = 100과제만 보고한다. 채점은 벤치마크의 복합 verifier로, 결정론적 검사(숨겨진 테스트, 파일·구조 검사)에 LLM/VLM 심사 항목을 섞는다. 심사 모델은 Gemini 3.5 Flash이고 과제 점수는 통과한 검사의 비율이다. 저자가 만든 벤치마크가 아니며, 업스트림 라이선스는 EU 지역 제한이 있는 Tencent 자체 라이선스다(부록 B, 저장소 BENCHMARKS.md). (사무형 산출물: Code(개발자·알고리즘·제품·운영·QA 5개 역할), Web(페이지 상호작용·시각화·문서 변환 등 7개 범주), Office(데이터 파일·문서·워크스페이스 자동화))
  • JobBench (Li et al. 2026, arXiv 2605.26329, Job-Bench/job-bench-eval) — 65과제를 31/34로 고정 분할하고 테스트 34과제를 보고한다. 산출물은 가중치가 있는 rubric으로 Claude Opus 4.8이 LLM 심사한다(편집기·선택기와 같은 모델). 점수는 가중 합계를 최대 점수로 나눈 값이다. 저자가 만든 벤치마크가 아니며, RUBRICS.json은 Hugging Face에 공개돼 있다(부록 B, 저장소 EXPERIMENTS.md). (입력 문서를 받아 요청된 산출물을 만드는 7개 직업군의 전문 업무)
  • LAB, Harvey Legal Agent Benchmark (Harvey AI 2026, harveyai/harvey-labs) — 논문 기준 1,251과제다(저장소 EXPERIMENTS.md는 전체 스트림을 1,143과제로 적어 수치가 다르며 이유는 확인되지 않음). Niklaus(2026)의 분할을 따라 100과제 held-out test만 보고하고, 24과제 dev set은 Meta-Harness 탐색에만 쓴다. 실행 가능한 검사 없이 Claude Sonnet 4.6이 과제별 기준으로 LLM 심사하고, 지표는 기준별 통과율인 Partial이다. 저자가 만든 벤치마크가 아니다(부록 B). (법률 업무: 24개 실무 분야, 4개 작업 유형(analyse, draft, review, research))

한계 · 비판

  • 재귀 정제 비용(부록 F 'Cost of recursive refinement'): 후보를 제안·탐침·구성하려면 실행과 편집 세션이 추가로 필요하고, 재귀 예산을 늘리면 추론 비용도 커진다. 병렬 세션으로 지연은 줄일 수 있지만 계산량 자체는 줄지 않는다. 실험은 제한된 예산 범위에서 trade-off를 보여 줄 뿐이고, 보편적인 최적 배분을 확립하지는 않았다고 저자가 적는다. (저자 인정)
  • 실행 기반 피드백의 한계(부록 F 'Execution-based feedback', 2.2.1): 정답 감독이 없어서 정제는 행동 대조와 모델 판단에 기댄다. 이 신호는 실행 간 변동성과 모델들이 공유하는 편향에 민감하다. 또 채택한 변경이 옳다는 것도, 다른 과제로 전이된다는 것도 보장하지 않는다. (저자 인정)
  • Leave-one-out 재실행(E.2, 그림 11)의 WB 77.5 -> 79.4, JB 36.0 -> 37.7에 대해 저자는 두 가지 단서를 단다. 재실행은 이후 과제의 항목까지 볼 수 있으므로 온라인 이득의 추정치가 아니라 오프라인 재사용 분석이다. 반복 실행 자체가 차이에 기여했을 수도 있다. (저자 인정)
  • 구성요소 제거(E.1, Table 6)에서 skills -5.3, scripts -3.7, prompt* -1.5가 나왔다. 저자는 이 결과가 여러 구성요소 그룹의 기여를 지지할 뿐 효과가 합산된다는 근거는 아니라고 적는다. 상용 하니스 비교(E.5, 그림 13)의 +4.6/+5.8/+4.9에도 정제가 추가 test-time compute를 쓴다는 단서를 붙인다. (저자 인정)
  • 실패 분석(E.6, 그림 14): 저자는 참조 실행보다 점수가 낮아진 9건을 세 유형으로 나눈다. 첫째, 선택기가 약한 후보를 고른 경우다(WB-code에서 95점 후보 대신 55점 후보, LAB에서 coverage가 좁아져 54 -> 26). 둘째, 잘못된 전제가 모든 후보로 퍼진 경우로 2-11점을 잃었다. 셋째, 결과 변동, 심사기 판정 누락, 평가 기준과 무관한 편집 때문에 원인을 가리기 어려운 경우다. 저자는 coverage와 정밀도의 균형을 맞춘 선택, 공유된 가정을 흔드는 probe, 편집 효과와 결과 변동을 구분하기 위한 반복 실행이 필요하다고 적는다. 다른 실행기로의 전이(E.3)에서도 이득이 실행기와 도메인에 따라 크게 다르다고 밝힌다. (저자 인정)
  • 릴리스 단서와 향후 과제(README 'Web access', docs/EXPERIMENTS.md, 부록 G): 실행기 네트워크는 제한되지 않고 Codex는 sandbox를 끈 채 돈다. 릴리스 검증 실행에서는 Codex 롤아웃이 지시 없이 JobBench rubric을 내려받았다고 문서에 적혀 있다. 부록 G는 라이브러리가 단순한 색인 구조라 커지면 통합·갱신이 필요하다고 쓰고, 재귀 형태와 예산을 미리 고정한다는 점도 앞으로 풀 과제로 든다. (저자 인정)
  • test-time compute와 하니스 개선 효과가 섞여 있다. k=1이어도 같은 과제를 기본 실행 1회와 후보 실행 2회로 미리 돌린 뒤 최종 실행 결과를 제출한다(롤아웃 4회, Opus 4.8 세션 3회). 편집기 프롬프트는 기본 실행에서 알아낸 작업공간 사실을 하니스에 적으라고 요구한다. 그런데 메인 표의 Base는 실행 1회이고, 표 안의 test-time 대조군인 Harness Scaling k=1도 롤아웃 2회와 세션 1회로 Harness²보다 적게 쓴다. 계산량 비교 근거는 두 가지다. 첫째, 그림 6(Gemini/OpenCode, JB·WB)은 실행과 개선을 모두 센 토큰 기준 비교다. 저자는 Harness² k=1과 k=5가 모두 경험적 Pareto frontier 위에 있다고 적는다. 그림을 읽으면 k=1은 토큰 규모가 비슷하거나 더 큰 ReasoningBank k=5, Harness Scaling k=5보다 이득이 크고, Meta-Harness보다 훨씬 적은 토큰으로 이득이 더 크다. 이는 저자에게 유리한 근거다. 둘째, 그림 5의 Best-of-k는 같은 k에서 롤아웃을 k회만 쓰므로 계산량을 맞춘 대조가 아니다. 저자는 k=2의 두 재귀 형태가 두 도메인 모두에서 k=5의 모든 베이스라인보다 높다고 적는다(4장, Best-of-5 포함). 다만 롤아웃 수를 4회로 맞추면 WB-code에서 Best-of-4(판독 약 77.0)가 Harness² k=1(76.5)과 비슷하거나 약간 높다. WB-office에서는 Best-of-4(약 78.3)가 k=1(79.5)보다 낮다. Best-of-k 막대는 Code에서 k=4에서 k=5로 가며 약 77.0 -> 74.9로 떨어질 만큼 자체 변동도 크다. k=5 병렬(80.8/83.4)은 Best-of-5(판독 약 75/80)보다 분명히 높다. LAB과 GLM-5·Codex 구성에서는 계산량 비교가 없다. (추가 의문)
  • 심사기가 개선기나 실행기와 같은 계열인 경우가 많다. JobBench 심사기 Claude Opus 4.8은 편집기·구성기·선택기와 같은 모델이다. LAB 심사기 Claude Sonnet 4.6도 편집기와 같은 Claude 계열이다. WB 심사기 Gemini 3.5 Flash는 Gemini 구성의 실행기와 같은 모델이다. 예외는 GLM-5 실행기의 WB 결과다. 이 구성에서는 심사기(Gemini)가 실행기(GLM-5)와도 편집기(Opus)와도 계열이 다르고, WB 채점에는 숨겨진 테스트 같은 결정론적 검사도 섞여 있다(부록 B). 그런데도 이 구성의 향상이 가장 크다(+11.5/+10.9). 따라서 같은 계열 심사기 문제는 JB·LAB 전체와 Gemini 구성의 WB에 해당한다. 저장소의 JobBench 선택기 블록(harness2/benchmarks/jobbench.py)에는 'material beyond what was asked costs nothing here'라는 coverage 우선 지시가 있다. 다만 선택은 k>1에서만 실행되므로, 이 지시가 영향을 줄 수 있는 것은 + Recursion(k=5) 같은 결과이고 k=1 메인 수치는 아니다. 논문은 이 겹침을 따로 분석하지 않으며, 이것만으로 편향을 입증할 수는 없다. (추가 의문)
  • 통계 근거가 약하다. 독립 스트림은 3개이고, seed는 과제 순서만 섞는다(docs/EXPERIMENTS.md). 유의성 검정은 없다. Gemini/Codex JB의 +1.4(SD 2.6/3.5)와 GLM-5/Codex JB의 +1.2(SD 2.3/0.2)는 SD 안에 든다. Gemini/OpenCode에서 Meta-Harness와의 차이도 WB 1.1, JB 0.2에 그친다. Ablation(Table 3)과 하니스 수준 재귀 분석(그림 7, 11)은 모두 Gemini 3.5 Flash/OpenCode 단일 구성이고 SD도 없다. 따라서 '일관된 향상'은 평균 기준으로만 성립한다. (추가 의문)
  • 논문 실험의 누출 통제가 보고되지 않았다. 본문과 부록에서 'network'를 검색하면 Figure 17 사례 설명의 1건만 나오고, 'internet', 'sandbox', 'firewall'은 0건이다. 실험 네트워크 정책은 기술되지 않는다. 릴리스 문서는 rubric을 내려받은 사례를 인정하고 사용자에게 egress 차단을 권한다. 저장소 core/context.py의 안내 문자열에는 과거 WB-code 산출물 경로로 채점기 pass rate가 노출된 적이 있다는 기록이 있다. 논문 수치가 이런 경로를 막은 뒤에 나온 것인지는 원문만으로 확인할 수 없다. (추가 의문)
  • 메인 결과의 편집기는 실행기보다 강한 Opus 4.8이다. 따라서 이득의 일부는 강한 모델의 지식이 하니스 파일로 증류된 결과일 수 있다. 그런데 같은 모델이 스스로 편집한 그림 8(k=2)의 근거는 엇갈린다. Gemini 3.5 Flash는 JB +0.9로 Opus가 편집한 k=1의 +4.5보다 작지만, WB에서는 +5.9로 +5.1보다 크고 LAB에서는 +1.7 대 +2.0이다. GLM-5는 WB +4.1로 Opus 편집 +11.5보다 훨씬 작지만 LAB에서는 +13.7로 +11.8보다 크다. k가 2와 1로 달라 직접 비교도 아니다. 이 밖에 논문과 코드가 어긋나는 점이 세 가지 있다. 첫째, 선택 풀이 논문 프롬프트에서는 수정하지 않은 실행을 포함하지만 selection.py에서는 최종 k개뿐이다. 둘째, LAB 과제 수가 논문 1,251개, 문서 1,143개로 다르다. 셋째, 논문의 정확한 test split 파일을 저장소에서 찾지 못했다(scripts/split_tasks.py만 있고, 문서는 생성된 분할이 release asset이 아니라고 밝힌다). 그래서 수치를 정확히 재현하려면 split을 다시 만들어야 한다. 증거는 평균 기준으로 일관되지만 강하지 않다. 독립 스트림은 3개이고 유의성 검정이 없으며, 일부 JB 이득은 SD 안에 든다. Ablation과 라이브러리 분석은 단일 구성에서만 했다. LAB의 일부 구성에서는 Meta-Harness나 ReasoningBank와 비슷하거나 더 낮다.

제출물은 같은 과제를 미리 3회 돌려 본 뒤 다시 실행한 결과다. 그래서 이득에는 재시도에 따른 test-time compute 효과와 더 강한 Opus 4.8 편집기의 기여가 섞여 있을 수 있다. 계산량 측면의 근거는 대체로 저자에게 유리하지만 완전하지 않다. 토큰 기준 비교(그림 6, Gemini/OpenCode의 JB·WB)에서 Harness²의 두 점은 Pareto frontier 위에 있고, k=1이 ReasoningBank k=5, Harness Scaling k=5, Meta-Harness보다 효율적이다. 저자는 k=2가 k=5의 모든 베이스라인(Best-of-5 포함)보다 높다고도 적는다. 반면 롤아웃 수를 맞춘 Best-of-4와 비교하면 WB-code에서 k=1의 뚜렷한 우위가 보이지 않는다(그림 5 판독). '검증기 없이'라는 주장은 파이프라인 안에 rubric과 점수를 들이지 않는다는 뜻으로는 대체로 맞다. 다만 심사기가 개선기나 실행기와 같은 계열인 경우가 많다(JB Opus 4.8, LAB Sonnet 4.6, Gemini 구성의 WB Gemini 3.5 Flash). 예외인 GLM-5 구성의 WB는 심사기가 실행기·편집기와 계열이 다르고 결정론적 검사도 섞여 있는데, 여기서 향상이 가장 크다(+11.5/+10.9). 이는 같은 계열 심사기의 편향만으로 결과를 설명하기 어렵다는 근거가 된다. 그 밖에 JobBench 선택 프롬프트에 coverage 우선 지시가 있고(k>1에만 해당), 논문 실험의 네트워크 정책은 보고되지 않았다. 그래서 신호가 완전히 독립적이라고 보기는 어렵다.

방법 상세

Edge0는 MoE의 routed expert 가중치를 RAM이 아니라 SSD에 두고, int4 per-layer stacked safetensors를 mmap으로 열어 필요한 byte range만 읽는 스트리밍 추론 엔진이다(3.1절). 35B 티어(Qwen3.6-35B-A3B 기반, 40층 x 256 experts)는 층당 expert 가중치가 453 MB(expert 1개 1.77 MB), routed expert 전체가 18 GB로 19.5 GB 체크포인트의 대부분을 차지한다. 핫 데이터는 OS page cache가 들고, 피크 메모리는 파라미터 수가 아니라 active set을 따른다.

실행 경로는 네 가지다. exact(on-demand 번들 빌드, 정확성 기준), staged(고정 슬롯 double buffering, decode 주력. 라우팅 인덱스를 slot table로 매핑하고 incr_stack으로 바뀐 expert만 제자리 갱신), hot(층별 LRU 상주 hot expert, miss 시 exact로 fallback), whole-layer(prefill에서 층 전체 expert를 9번의 직접 read로 일괄 로드)다. 모든 경로는 down(silu(gate(x))·up(x))를 같은 quantized gather 커널로 계산하며 dequantized reference 대비 relative L2 1% 미만(측정 잔차 약 0.24%)으로 테스트된다.

핵심은 prerouter다. 층 N+1의 expert 선택은 층 N 출력이 있어야 정해지므로 순진한 스트리밍은 매 층마다 디스크 지연에 막힌다. Edge0는 '이중 shift'를 쓴다. 층 N이 소유한 head가 토큰 t에서 층 N의 post-attention norm 출력을 보고 토큰 t+1의 층 N+1 라우팅을 예측한다. 한 스텝당 한 번의 flush로 모든 staged 층(35B 32개, 8B 16개)을 한꺼번에 예측하므로 SSD read가 한 decode step 전체와 겹친다. 같은 토큰 안에서 미리 고르는 Pre-gated MoE 방식은 이 엔진에서 스텝당 30-100 ms의 동기화 비용이 들어 plain LRU보다도 느렸다고 저자들은 보고한다. head 구조는 fc1 -> erf-gelu -> fc2에 linear residual을 더한 것이며, residual은 다음 층 router 가중치로 warm-start한다. 입력은 hidden state와 두 개의 top-k one-hot(이번 토큰과 이전 토큰에서 이 층이 실제 고른 expert)을 이어 붙인 것으로 35B는 2048+2x256=2560차원, hidden 512, fp16이다. 35B는 head 33개(owner 6-38), 8B는 16개다.

Prediction-as-routing이 가장 중요한 설계다. decode 시 MoE 층은 원래 router 대신 prerouter logits를 같은 softmax-topk 또는 sigmoid-group 수식에 넣어 라우팅한다. 예측 집합이 곧 라우팅 집합이므로 staged 슬롯과 정확히 일치하고 drop이나 fallback load가 없다. 즉 '오예측'이라는 사건 자체가 런타임에 존재하지 않고, 원본 모델과 다른 expert를 쓰는 근사 오차가 그대로 모델 동작에 반영된다. 이 비용은 학습에서 갚는다. head 입력은 학습 때는 실제 라우팅, 추론 때는 자기 예측이라는 feature drift가 있는데 head를 재학습하지 않고 LoRA가 흡수하게 둔다. 예측 정확도(hit rate, top-k overlap)는 본문 전체에서 수치로 보고되지 않으며, 저자들은 router 일치도를 더 쫓는 것은 잘못된 목표이고 학생 라우팅에서 언어모델이 좋은 텍스트를 내는지가 중요하다고 주장한다.

Recovery LoRA(r=16, alpha=32)는 attention, linear-attention, shared-expert projection에만 붙고 routed expert에는 붙지 않는다(스트리밍되며 교체 가능해야 하므로). 서빙은 unmerged로 y = W_int4(x) + (alpha/r)·B·A·x 병렬 delta다. LoRA delta(RMS 약 1e-3)가 4-bit group step보다 작아 병합 후 재양자화하면 효과가 attention projection에서 34%, dense projection에서 2%, logits 수준에서 18%만 남기 때문이다. unmerged 비용은 어댑터 42 MB, decode 시간 차이는 측정되지 않을 정도라고 한다. 양자화는 expert 가중치 int4 affine group-64다.

학습은 3단계이며 모두 4-bit 배포 체크포인트를 dequantize한 bf16 재구성 위에서 base를 고정한 채 진행한다. Phase 1은 head만 다음 층의 실제 router logits를 모방하도록 distill한다. Phase 2는 prerouter 라우팅을 켠 student path 전체 forward로 약 2M행의 teacher 생성 텍스트에 SFT한다(distill만 한 체크포인트는 반복·붕괴된 텍스트를 냈다고 함). Phase 3은 on-policy distillation으로 학생이 생성하고 원래 fp16 base가 teacher로 채점하며, teacher top-k 토큰에 reverse KL과 tail 항을 쓴다. 약 200k행(Phase 2의 1/10)에서 수렴한다. 이 구조 덕에 35B 티어는 base의 K=8 대신 K=4로 재학습해 출시됐다.

Edge0는 20.4 tok/s, 2.9 GiB로 '5배 빠르고 메모리는 1/6-1/7'이라고 주장한다. 단 resident baseline의 routing K는 명시되지 않았고 Edge0는 K=4 재학습 프로파일이다. 저자들은 resident 쪽이 메모리 부족으로 paging한다고 설명한다. llama.cpp --cpu-moe, PowerInfer, Mixtral-offloading, MoE-Infinity, FlexGen은 관련연구에서 인용만 하고 수치 비교는 없다.

한계 · 비판

  • 단일 요청 직렬 처리: Edge0는 한 번에 한 요청만 FIFO로 처리하며 배치 서빙을 하지 않는다. 배치는 expert working set을 바꾸는데 이는 per-request 프로파일이 모델링하지 않는다고 저자들이 적는다. 20.4 tok/s를 포함한 모든 처리량 수치가 batch 1 조건이다 (6장, Table 1 캡션). (저자 인정)
  • CPU측 하한: 40층 forward의 graph building이 스텝당 44 ms이고 이는 스토리지 쪽 최적화로 줄일 수 없는 decode 하한이라고 저자들이 명시한다 (6장). (저자 인정)
  • prefetch 이득의 조건 의존성과 메모리 대가: prerouter 이득은 제거하는 대기 시간에 비례하므로 hot cache나 빠른 스토리지에서는 줄어들고, 인접 토큰이 한 층의 expert 중 약 1/4만 공유하므로 재사용에 상한이 있다. 대가는 page cache에서 가져오는 unreclaimable residency로, K=8에서 prerouter arm이 MLX 메모리를 1.43 GiB 더 쥐고 page cache는 1.15 GiB 줄었다. 실제로 24GB Mac mini에서는 prerouter off 19.9 vs on 20.4 tok/s다 (6장, 5.3절, Table 1 캡션). (저자 인정)
  • 측정 구성의 미완 최적화: stager가 같은 가중치의 bundle과 stacked view 두 사본을 들고 있어 K=8에서 약 0.45 GiB가 낭비되고, incremental stacking fill이 메인 스레드에서 동기 실행되어 K=8에서 스텝당 62.5 ms가 든다고 저자들이 'Two levers not yet pulled'로 밝힌다. 두 개선 모두 측정 구성에 포함되지 않았다 (5.3절). (저자 인정)
  • 품질 손실이 긴 추론에 집중: 35B 티어 AIME -6.1점(86.6 vs 92.7), 8B 티어 AIME -10.0점, 8B IFBench -6.7점을 저자들이 직접 한계로 적는다. HF 모델 카드 두 개는 별도로 tool use와 multi-step planning 등 agent 능력이 약하고, 성능 수치는 MLX Apple Silicon 측정이며 iOS/Android/Windows 엔진은 아직 성숙 중이라고 경고한다. 35B 카드는 긴 context에서 KV cache로 3 GiB를 넘는다고도 적는다 (6장, Table 2, HF 모델 카드 Limitations). (저자 인정)
  • 구현 범위와 측정 신뢰성: MLX가 유일한 구현 백엔드이고 CUDA는 아키텍처만 있고 코드는 없다(6장, README 로드맵상 2026 Q4). 또 이 하드웨어에서 single-shot 벤치마크는 run 간 +-40%, 16GB 머신은 세션 간 최대 2.3배 편차가 있어 같은 세션 교차 A/B만 증거로 쓴다고 밝힌다 (5.1절). (저자 인정)
  • 헤드라인 성능의 원인 귀속이 흐리다. abstract는 prerouter가 SSD 지연을 숨긴다는 서사를 쓰지만, 20.4 tok/s를 낸 24GB Mac mini에서 prerouter를 끄면 19.9 tok/s로 측정 기여는 약 0.5 tok/s(약 2.5%)다. off arm이 정확히 어떤 구성인지는 원문에 없다. +80-84% 이득(Table 3)은 가중치가 메모리에 들어가지 않는 16GB MacBook M2에서, 절대 속도 3.3-8.6 tok/s 수준으로만 나온다. 같은 16GB 머신에서 K=8을 K=4로 줄이면 decode가 3.3 -> 6.4 tok/s로 거의 2배가 되고(4장, Table 3), incr_stack도 +34%를 보인다(Appendix B, 다른 측정 캠페인). 그래서 출시 티어 속도의 상당 부분은 routing width 축소와 스트리밍 경로 최적화에서 온다고 보는 것이 논문 자체 데이터와 맞는다. 다만 24GB Mac mini에서 각 요소의 기여를 분해한 측정은 없고, 저자들은 정확한 집합을 공급할 prerouter 없이는 staging만으로 배포 가능한 구성이 아니라고 반론한다(5.3절). (추가 의문)
  • 외부 baseline이 사실상 하나다. 비교 대상은 같은 Mac mini에서 19.5 GB를 전부 상주시켜 paging이 일어나는 vanilla mlx-lm(3.9 tok/s, 18.2 GiB)뿐이다. 저자 각주는 같은 머신, 같은 decode protocol이라고만 밝히고 routing K는 명시하지 않아 K=4 Edge0와 동일 조건인지 알 수 없다. llama.cpp --cpu-moe, MoE-Infinity, PowerInfer, Mixtral-offloading은 인용만 있고 수치 비교가 없다. Pre-gated MoE 계열은 자기 엔진 안에서 same-token 변형을 측정해 스텝당 30-100 ms 비용으로 plain LRU보다 느렸다고 서술하지만, 표나 원 시스템 수치는 제시하지 않는다. '5배 빠르다'는 이 단일 비교에 한정해 읽어야 한다. 다만 저자들이 resident baseline이 이 하드웨어에서 빠른 기준이 아닌 이유를 3.1절에서 직접 설명한다는 점은 공정하게 밝혀 둔다. (추가 의문)
  • Prediction-as-routing의 동작 변화 평가가 부족하다. 35B는 40층 중 32층, 8B는 24층 중 16층이 이전 토큰 시점의 예측으로 라우팅되고, 35B는 K도 8 -> 4로 바뀐다. 그런데 router 일치도, top-k overlap, 출력 분포 KL 같은 지표는 본문 전체에서 수치로 보고되지 않고, 평가는 5개 벤치마크 점수뿐이다. 저자들은 router 일치도를 쫓는 것이 잘못된 목표라고 근거를 들어 주장하지만, 그렇다면 언어모델 출력 수준의 차이를 더 넓게 측정해야 한다. 원본 대비 편차는 벤치마크 밖(장문 생성, 다국어, agent 작업)에서 드러날 수 있으나 이를 측정한 결과는 없고, HF 카드도 agent 능력이 약하다고 인정한다. 벤치마크의 sampling, temperature, max tokens, AIME 반복 횟수도 원문에서 확인되지 않아 -6.1 같은 격차의 분산을 판단할 수 없다. (추가 의문)
  • 재현성 공백. 저장소 전체 파일 트리(1131 경로)를 train, distill, sft, opencompass로 검색한 결과, 추론 엔진, 벤치 스크립트(python/examples/bench.py), 학습된 어댑터와 head만 있고 prerouter head distill, LoRA SFT, on-policy distillation, OpenCompass 평가 코드는 없다. docs/prerouter.md는 heads.py가 별도의 training implementation에서 가져온 것이라고 적어 학습 구현이 비공개임을 시사한다. Phase 2 약 2M행 데이터의 프롬프트 출처, 학습 compute, learning rate와 step 수도 원문에서 확인되지 않는다. 따라서 다른 MoE에 prerouter를 새로 학습시키려면 논문 서술만 보고 재구성해야 한다. (추가 의문)
  • 측정 조건과 공개 자료의 불일치. SSD 모델·대역폭과 macOS 버전이 명시되지 않아, SSD에 의존하는 시스템인데도 하드웨어 일반화가 어렵다. README와 HF 카드는 다른 프로토콜(약 3.3k 토큰 프롬프트 후 200 decode 토큰, 2 runs)로 35B 14.9-17.7 tok/s, 8B 23.9-25.3 tok/s, 8B peak 1.0 GiB를 적어 논문의 20.4, 28.0 tok/s, 1.5 GiB와 다르다. 차이의 일부는 조건 차이로 보이지만 두 수치를 조정하는 설명은 없다. 📌 내 학습 포인트

  • 로컬 모델 속도는 single-shot으로 측정하지 말 것. 저자들은 같은 하드웨어에서 single-shot 벤치마크가 run 간 +-40%, 16GB 머신에서 세션 간 최대 2.3배 차이가 난다고 보고한다. 그래서 각 arm을 별도 프로세스로 띄우고, arm 순서를 회전하고, 두 arm이 같은 토큰 시퀀스를 재생하게 한 뒤 warm 상태 3라운드 median을 내는 같은 세션 교차 A/B만 증거로 쓴다. 같은 저자들의 README 수치(3.3k 프롬프트 후 200 토큰, 2 runs)가 논문 수치보다 2.7-5.5 tok/s 낮은 것 자체가 프로토콜 차이의 영향을 보여 준다. Windows PC에서 llama.cpp 옵션(예: -cmoe, -ngl)이나 양자화 포맷을 비교할 때 이 절차를 작은 PowerShell 스크립트로 만들어 두면, 트렌드 시스템이 논문의 tok/s 주장을 검증할 때도 같은 기준을 쓸 수 있다.
  • offloading·prefetch 기법의 효과는 먼저 '모델이 메모리에 들어가느냐'로 갈린다. 같은 prerouter가 가중치를 다 담지 못하는 16GB MacBook M2에서는 decode +80-84%(K=4 기준 3.5 -> 6.4 tok/s)지만, 24GB Mac mini에서는 19.9 -> 20.4 tok/s로 약 2.5%다. 반면 같은 16GB 머신에서 routing width를 K=8에서 K=4로 줄이자 decode가 거의 2배가 됐다. 활성 expert 수가 토큰마다 옮겨야 할 바이트 양을 직접 정하기 때문이다. 따라서 35B급 MoE를 로컬에서 돌리려면 먼저 RAM(또는 unified memory) 용량과 int4 체크포인트 크기(35B 약 19.5 GB)를 비교하고, 모자랄 때만 SSD 스트리밍류 기법을 고려하는 것이 순서다. repo의 Windows 참고 수치(35B decode 약 27.7 tok/s)도 48GB RAM에 모델이 다 올라간 warm-RAM 조건이며, README는 16GB 이하에서 35B가 paging-bound라고 적는다. GPU 유무와 SSD 속도는 본인 환경에서 직접 측정해야 하며, 논문은 SSD 사양을 명시하지 않았다.
  • 양자화 모델에 LoRA를 붙일 때 병합 후 재양자화를 기본값으로 쓰지 말 것. 저자들은 LoRA delta(RMS 약 1e-3)가 int4 group-64 step보다 작아서, 병합·재양자화하면 효과가 attention projection 34%, dense projection 2%, logits 18%만 남는다고 측정했다. unmerged 병렬 delta(어댑터 42 MB)는 decode 시간 차가 측정되지 않을 정도라고 보고한다. repo의 Windows 앱도 MLX LoRA를 별도 GGUF adapter로 변환해 llama.cpp에 런타임 adapter로 넘기므로(windows/tools/lora_mlx_to_gguf.py) 같은 원칙을 따른다. 로컬에서 GGUF 등 4-bit 모델에 자체 LoRA를 쓸 때는 런타임 어댑터 로딩(llama.cpp의 --lora 인자)을 먼저 시도하고, 병합본과 품질을 같은 프롬프트 세트로 비교하는 습관을 들이면 된다. 단 Windows 앱은 prerouter를 advisory prefetch로만 쓰므로(기본 비활성) student routing 경로에서 학습한 LoRA가 원래 gate 위에서 돌게 되고, 이때 Table 2 품질이 유지되는지는 확인되지 않았다(코드 주석과 논문 서술을 비교한 추론). HF 카드도 agent 능력(tool use, multi-step planning)이 약하다고 경고하므로, Claude Code 서브에이전트의 로컬 대체 모델로 쓰기 전에 별도 검증이 필요하다.

연결 연구

  • ← : 같은 토큰 안에서 다음 층 expert를 미리 고르는 pre-gating 방식이다. Edge0는 이런 same-token 변형이 자기 엔진에서 스텝당 30-100 ms의 동기화 비용 때문에 plain LRU보다 느렸다고 보고하고, 다음 토큰을 예측하는 이중 shift로 대체한다.
  • ← : 저자들이 접근법상 가장 가깝다고 꼽은 연구다. 사후 학습한 MoE가 그에 맞춰 학습되면 expert 수를 절반으로 줄여도 견딘다는 관찰이며, Edge0의 routing 대체 학습과 K=8 -> 4 재학습이 같은 관찰을 prediction-as-routing에 적용한 것이라고 저자들은 설명한다.
  • ← : Mixtral expert를 LRU 캐시와 speculative expert loading으로 offload하는 선행 시스템이다. Edge0는 자기 hot 경로가 같은 popularity 캐시 계열이라며 인용만 하고 수치 비교는 하지 않는다.
  • ← : 개인 기기용 expert 캐시·prefetch 시스템으로 문제 설정이 같다. Edge0와의 수치 비교는 없다.
  • ← : hot/cold neuron 분리로 소비자 GPU와 CPU에 가중치를 나누는 접근이다. Edge0의 hot expert 경로가 같은 hot/cold 분리라고 저자들이 직접 적는다. 인용만 있고 수치 비교는 없다.
  • ← : GPU/CPU/디스크 계층으로 가중치와 KV를 offload하는 처리량 지향 배치 서빙의 대표 선행 연구다. Edge0는 배치 1 지연 지향이라 목표가 다르다.

Claude 종합 코멘트

이 논문의 진짜 새로운 점은 prerouter 예측을 prefetch 힌트가 아니라 실제 라우팅으로 쓰는 prediction-as-routing이다. 예측 집합이 곧 사용 집합이므로 오예측 fallback 경로가 사라지고, 그 대가인 원본 모델과의 동작 차이는 recovery LoRA와 on-policy distillation으로 학습 단계에서 갚는다. 4-bit 위에 LoRA를 병합하지 않는 이유를 잔존율(34%, 2%, 18%)로 측정해 보인 점도 실용적이다. 반면 증거의 강도는 헤드라인보다 약하다. '단일 24GB 머신'은 GPU VRAM이 아니라 Mac mini M4 Pro의 unified memory다. 20.4 tok/s는 batch 1, short context, warm, 3라운드 median이고, base의 K=8이 아닌 K=4 재학습 프로파일 조건이다. 이 머신에서 prerouter의 측정 기여는 약 2.5%뿐이고, +80% 이상은 16GB 기기에서만 나온다. 같은 16GB 기기에서는 K=8을 K=4로 줄이는 것만으로 decode가 약 2배가 됐다. '3 GiB'는 MLX allocator peak로 page cache를 뺀 값이다. 외부 비교는 paging이 일어나는 vanilla mlx-lm 하나뿐이고, router 일치도나 출력 분포 차이는 보고되지 않는다. 품질 격차는 평균 3.9/2.8점이지만 AIME에서는 -6.1/-10.0점으로 크다. 그밖에 SSD 사양 미공개, 학습 코드 부재(저장소 전체 트리 확인), README·HF 카드·저장소 문서와의 수치·구성 불일치(8B staged decode 비활성 등)가 남는다. Windows 앱은 prerouter를 advisory prefetch로만 쓰므로 논문 방법을 Windows에서 재현한 것으로 볼 수 없다. 인용할 때는 'Apple Silicon 24GB unified memory Mac mini에서 Qwen3.6-35B-A3B를 K=4로 재학습한 int4 변형이 배치 1 decode 약 20 tok/s를 냈고, 다섯 벤치마크 평균 약 4점 하락(AIME는 6점 이상)'처럼 조건과 손실을 함께 적는 것이 정확하다.

방법 상세

TradingAgents는 실제 트레이딩 회사를 모사한 LLM 멀티에이전트 프레임워크로, 7개 역할을 5개 팀으로 조직한다. (1) 애널리스트 팀(Analyst Team)은 펀더멘털(fundamental)·감성(sentiment)·뉴스(news)·기술적(technical) 분석가가 각자 구조화 리포트를 생성한다. (2) 리서처 팀(Researcher Team)은 강세(bull)/약세(bear) 연구자가 자연어 토론(natural language debate)을 n라운드 진행하고, 진행자(facilitator) 에이전트가 토론 이력을 검토해 우세 관점을 선택·기록한다(원문 표현 'facilitator ... selects the prevailing perspective'). (3) 트레이더(Trader)가 이를 종합해 매매 신호를 도출한다. (4) 리스크 관리 팀(Risk Management Team)은 공격적(aggressive)·중립(neutral)·보수(conservative) 세 관점이 토론해 노출을 조정한다. (5) 펀드 매니저(Fund Manager)가 최종 승인·집행한다. 에이전트 간 통신은 '구조화 리포트'를 1차 채널로, '자연어 대화'를 2차 채널로 쓰는 하이브리드 방식이며, 공유 글로벌 에이전트 상태(global agent state)와 메모리로 과거 결정 맥락을 유지한다(명시적 reflection 모듈 여부는 본문 확인 필요). 모델은 2계층(two-tier) 전략으로, 추론 집약 노드(분석·연구·트레이딩)에는 심층사고(deep-thinking) o1-preview를, 요약·데이터 변환·검색 등에는 신속사고(quick-thinking) gpt-4o/gpt-4o-mini를 배정하고, 전 에이전트는 ReAct 프롬프팅 프레임워크를 따른다(논문 명시). LangGraph는 논문 본문이 아니라 공식 오픈소스 레포/문서에서 구현 스택으로 명시된다('built with LangGraph').

방법 상세

Kronos는 금융 K-line(캔들스틱) 데이터를 위한 2단계 파운데이션 모델로, 연속형 시장 정보를 이산 토큰으로 바꾸는 전용 토크나이저와 그 위에 얹은 자기회귀(autoregressive) 디코더 트랜스포머로 구성된다. 토크나이저는 3층 트랜스포머 오토인코더(d_model 256, d_ff 512, head 4)에 BSQ(Binary Spherical Quantization)를 결합해, 연속 잠재벡터를 학습 가능한 초평면에 사영하여 k비트 이진코드로 양자화한다(k=20, 총 어휘 2^20 = 1,048,576). 2^20을 그대로 예측하면 비용이 크므로 k비트를 동일 길이의 coarse/fine 두 서브토큰(k_c = k_f = k/2 = 10비트, 각 2^10)으로 인수분해하고, coarse 서브토큰만으로 복원하는 coarse loss, coarse+fine 전체 토큰으로 복원하는 fine loss, BSQ 정칙화용 양자화 loss(commitment weight beta = 0.05)를 합친 복합 목적함수로 학습해 coarse가 주요 구조를, fine이 잔차를 담도록 강제한다. 입력은 시점당 OHLCVA 6차원(Open, High, Low, Close, Volume, Amount)이며 차원별 z-score 정규화 후 [-5, 5]로 클리핑하고, 패치가 아니라 K-line 레코드 단위로 시점당 2개 서브토큰을 생성한다. 백본은 causal self-attention 기반 디코더로 RoPE 위치인코딩, Pre-LayerNorm + RMSNorm을 쓰고 최대 컨텍스트는 512 토큰이며, minute-of-day / hour-of-day / day-of-week / day-of-month / month-of-year 다섯 개 시간 특징을 각각 임베딩해 합산 후 입력 표현에 더한다. 예측은 dual-head 순차 방식으로, coarse head가 먼저 로짓을 내고 예측된 coarse 토큰 임베딩을 쿼리로 하는 cross-attention을 거쳐 fine head가 조건부 분포를 내며, 손실은 L_ar = -E[sum_t (log p(b_t^c | b_<t) + log p(b_t^f | b_<t, b_t^c))] 형태의 두 항 합이다. 모델 크기는 Kronos_small(8층, d_model 512, d_ff 1024, head 8, 24.7M), Kronos_base(12층, 832, 2048, head 16, 102.3M), Kronos_large(18층, 1664, 3072, head 32, 499.2M) 세 가지이며, AdamW + cosine 스케줄, peak LR 1e-3 / 5e-4 / 2e-4, weight decay 0.01-0.10으로 사전학습했다(총 학습 토큰 수, 스텝 수, 사용 하드웨어는 원문에 명시되지 않아 본문 확인 필요). 추론 시에는 temperature와 top-p를 둔 Monte Carlo 샘플링으로 복수 미래 경로를 뽑아 평균내는 앙상블을 쓴다(가격/수익률/투자시뮬레이션은 temp 0.6, top-p 0.90, 10 샘플; 변동성은 temp 0.9, top-p 0.90, 1 샘플; K-line 생성은 temp 1.0, top-p 0.95, 1 샘플).

실험 셋업

  • 평가 과제 5종: (1) 가격 시계열 예측(IC, RankIC), (2) 수익률 예측(IC, RankIC), (3) 실현변동성 예측(MAE, R2), (4) 합성 K-line 생성(다양성은 t-SNE 및 KDE 비교, 충실도는 LSTM 판별기 기반 discriminative score, 유용성은 TSTR(Train-on-Synthetic, Test-on-Real)의 IC/RankIC), (5) 투자 시뮬레이션(연율화 초과수익 AER, 정보비율 IR).
  • 핵심 헤드라인 수치(초록 기준): zero-shot 가격 예측 RankIC가 최강 TSFM 대비 +93%, 최강 비사전학습 베이스라인 대비 +87%; 변동성 예측 MAE 약 9% 감소; 합성 K-line 생성 충실도 22% 개선. 개별 모델별 IC/RankIC 절대값 표는 부록 F(Full Experiment Results)로 넘겨져 있어 본문 확인 필요.
  • 비교군 총 25개: 비사전학습 8종(iTransformer, TimesNet, PatchTST, NSTransformer, DLinear, FEDformer, TimeMixer, TimeXer), zero-shot TSFM 5종(TimeMOE, Moirai, TimesFM, Moment, Chronos), 계량경제 2종(ARCH, GARCH), 생성모형 3종(DiffusionTS, TimeVAE, TimeGAN), 그리고 ablation 변형 3종(Direct-AR, Prob-AR, Kronos-Parallel).
  • Ablation(Table 2, Kronos_small 기준) - 가격예측 IC 0.0431 / RankIC 0.0254, 수익률예측 IC 0.0665 / RankIC 0.0622, 변동성 MAE 0.0384 / R2 0.2490. 비교: Kronos-Parallel IC 0.0345 / RankIC 0.0226, Prob-AR IC 0.0179 / RankIC 0.0102. Direct-AR(연속공간 MSE 회귀) 수치는 본문 확인 필요.
  • Ablation 결론 3가지: (a) 이산 토큰 모델링이 연속형(Direct-AR의 MSE 회귀, Prob-AR의 Student-t 혼합분포)보다 뚜렷하게 우수, (b) coarse -> fine 순차 예측이 동시(parallel) 인수분해 예측보다 우수, (c) 어휘 크기를 키운 k=20 설정이 복원 품질과 다운스트림 예측 모두 개선.
  • 스케일링: 24.7M -> 102.3M -> 499.2M로 모델을 키울수록 가격 예측, 변동성 예측, 생성 품질 전반에서 성능이 일관되게 개선되어 시계열 파운데이션 모델에서도 scaling law가 경험적으로 성립한다고 주장.
  • 시간적 분리 프로토콜: 사전학습 데이터는 2024년 6월까지, 평가 구간은 2024년 7월 이후로 잘라 leakage를 차단. 다운스트림은 태스크별 파인튜닝 없이 zero-shot으로 평가.
  • 룩백/예측 구간은 주기별로 다르게 설정(Table 8) - 예: 5분봉은 lookback 480 / horizon 96, 일봉은 lookback 40 / horizon 12.
  • 투자 시뮬레이션: 중국 A주 대상 롱온리 전략, CSI 300에서 top-k=50 / n=5, CSI 800에서 top-k=200 / n=10, 일별 리밸런싱 제한과 거래당 0.15%의 보수적 거래비용 적용. Kronos가 AER과 IR 모두에서 최고라고 서술되나 구체 수치는 본문 확인 필요.
  • 데이터 정제 파이프라인: 주기별 임계값(점프 0.10-0.50)으로 이상 가격 급등락 구간 제거, 거래량 0 또는 near-zero가 지속되는 저유동성 구간 제거, 종가가 장기간 고정된 정체 구간 제거. 가격 필드의 결측은 시퀀스 하드 경계로 처리하고 거래량/거래대금 결측은 0으로 대치.

  • 논문에 독립된 Limitations 섹션이 없다. 5장 Conclusion도 성과 요약만 하고 한계나 Future Work를 서술하지 않는다. 저자가 인정한 제약은 부록 곳곳에 흩어져 있다. (저자 인정)
  • 컨텍스트 길이 512 토큰 제한을 저자가 명시적으로 인정한다. 본문에 '자원 제약과 실제 배포 시나리오를 고려해' 최대 컨텍스트를 512로 제한했다고 적었고, 대신 주기(frequency)를 바꿔 임의 예측 지평을 커버할 수 있다고 주장한다(단기는 1분봉, 주간/월간은 일봉). 즉 긴 룩백은 아키텍처가 아니라 데이터 샘플링으로 우회한다. (저자 인정)
  • 서브토큰 분해 개수 n=2는 최적 탐색 결과가 아니라 파라미터 절감 대 추론 지연의 트레이드오프로 고른 값이다(Appendix H Q3, Table 12). n=4, n=5도 표에 있고 오히려 총 파라미터가 더 적지만(각각 100.5M, 101.1M 대 n=2의 102.3M), 성능 비교 없이 토큰당 추론 스텝 4배/5배라는 지연 비용만으로 배제했다. (저자 인정)
  • Q1(K-line만으로 단기 가격 변동을 설명할 정보가 충분한가)에 대해 저자는 선행 문헌 인용에 그치고 '위 실증 증거에 대한 상세 논의는 본 논문의 범위를 벗어난다'고 명시적으로 회피한다. 모델의 근본 전제가 논증되지 않은 채로 남는다. (저자 인정)
  • 크립토와 외환 평가에서는 volume/amount를 의도적으로 제외하고 OHLC만 사용한다고 밝힌다. 다만 이를 단순한 설계 결함 자인으로 읽으면 과하다. 원문 Appendix C는 학습 중 volume과 amount를 전체 샘플의 5%에서 무작위로 0으로 만드는 정규화를 두어 '가격 정보만으로도 예측하도록' 명시적으로 훈련시킨다고 밝힌다. 따라서 OHLC 전용 평가는 신뢰할 volume 데이터가 없는 상황을 겨냥해 의도적으로 학습시킨 능력의 검증에 가깝다. 남는 한계는 6차원 OHLCVA 입력 설계가 모든 자산군에 동일하게 적용되지는 않는다는 점 자체다.   • 계층적(coarse/fine) 복원 손실은 표준 손실 대비 복원 품질을 개선하지 않는다. Table 9에서 MAE 0.0785 대 0.0781, MSE 0.0203 대 0.0202로 오히려 미세하게 나쁘다. 저자도 '거의 동일'(nearly identical)하다고 서술하며, 계층 구조의 목적은 정확도가 아니라 후속 자기회귀 모델의 편의라고 인정한다. (저자 인정)
  • 코드북 사용률이 coarse 97.66%, fine 85.25%로 fine 레벨은 14.75%가 미사용이다(Table 11, 각 서브코드북 크기 2^10). 어휘가 완전히 활용되지 않는다는 점을 저자가 표로 공개했다. 다만 저자는 이를 한계가 아니라 코드북 붕괴가 없다는 근거로 제시한다. (저자 인정)

Table 14의 Kronos_large 평균 RankIC는 0.0267이다. 0.0138 x 1.93 = 0.0266으로 헤드라인 93%가 정확히 재현되고, 87%도 최고 full-shot 베이스라인 0.0143 x 1.87 = 0.0267로 재현된다. 즉 0.0138 -> 0.0267이라는 절대 0.013%p 수준의 이동을 93%로 표기한 것이다. 분모가 0에 가까운 상대 비율은 불안정하며 실무 의사결정에서의 의미는 완전히 별개다. (추가 의문)
  • 가격 시계열 IC/RankIC의 정의 자체가 퀀트 실무의 IC와 다르다. 원문 Appendix D는 '각 샘플에 대해 예측 시계열과 실제 시계열 사이의 IC/RankIC를 OHLC 4개 가격 채널 각각에 대해 계산하고 4채널 평균을 최종 지표로 보고한다'고 명시한다. 가격 레벨은 자기상관이 매우 높아 추세가 지속되기만 해도 높은 상관이 나온다. 실무의 횡단면 IC(같은 시점 종목 간 랭킹 상관)와 혼동될 여지가 큰데, 하필 헤드라인 93%가 붙은 지표가 이것이다. 반면 return forecasting 쪽은 예측 수익률 벡터와 실제 수익률 벡터 사이로 계산해 실무 IC에 훨씬 가까운데도 헤드라인에서 빠져 있다. 다만 이쪽도 '자산군-주기 내 전체 샘플 풀링'이라 엄밀한 시점별 횡단면 IC는 아니다. (추가 의문)
  • 실현변동성 예측이 전용 헤드가 아니라 예측된 종가 경로의 로그수익 제곱합으로 유도된다(원문 식 12). 게다가 Table 6에 따르면 이 태스크는 샘플 수 N=1, T=0.9로 단일 경로를 쓴다. 즉 변동성 추정치가 한 번의 확률적 샘플링 노이즈에 그대로 노출되고, 생성 경로의 변동성이 실제 변동성을 대리한다는 가정이 검증되지 않았다. (추가 의문)
  • 변동성 베이스라인이 ARCH와 GARCH뿐이다(둘 다 p,q in {1,2,3} 그리드에서 BIC로 선택). 원문 전체를 검색해도 HAR, HAR-RV, Log-HAR, EWMA는 단 한 번도 등장하지 않는다. 실현변동성 예측의 사실상 표준 벤치마크가 통째로 빠진 것이다. HAR은 GARCH보다 실현변동성에서 훨씬 강한 것으로 알려져 있어 '9% 낮은 MAE'는 약한 상대에게 얻은 우위일 수 있다. 독립 연구(arXiv 2607.05291)가 9개 TSFM을 8개 계량 벤치마크와 비교해 TTM만이 Log-HAR을 일관되게 이겼다고 보고한 점이 이 우려를 뒷받침한다(단 이 연구는 Kronos 자체를 다룬 후속 연구가 아니라 일반 TSFM 연구다). (추가 의문)
  • 통계적 유의성 검정과 신뢰구간이 사실상 없다. 메인 결과 표는 전부 단일 실행 점추정이다. 시드 5개와 표준편차가 등장하는 곳은 Figure 7(추론 샘플 수 절제)뿐이며 캡션에 '5회 실행 평균, 음영은 표준편차'라고 명시된다. 신호 대 잡음비가 낮다고 저자 스스로 강조한 도메인에서 이는 치명적이다. Diebold-Mariano 같은 예측 비교 검정도 없다. (추가 의문)
  • 백테스트 창이 짧고 단일 시장이다. 원문은 'Kronos의 사전학습 데이터가 2024년 6월까지이므로 모든 태스크의 테스트 기간은 2024년 7월에 시작한다'고만 적고 백테스트 종료일을 어디에도 명시하지 않는다(원문 확인 완료). 11개월이라는 기간은 오직 저장소 finetune/config.py의 backtest_time_range = 2024-07-01 ~ 2025-06-05에서만 나온다. 이 구간에는 중국 A주의 2024년 9-10월 급등 국면이 포함된다. 단일 시장(CSI300/CSI800), 단일 경로, 11개월로 산출한 연율화 초과수익과 IR은 레짐 의존성이 크다. (추가 의문)
  • 백테스트 현실성 가정이 얕다. 롱온리 top-k/drop-n에 최소 보유기간 5일과 일일 최대 n종목 매매 제한을 두고(CSI300은 k=50/n=5, CSI800은 k=200/n=10), 단일 거래비용 0.15%만 적용한다. 회전율 통제 장치는 있으나 슬리피지, 마켓 임팩트, 거래정지, A주 상하한가(+-10%) 제약은 모델링하지 않는다. 원문 전체 검색에서 slippage, market impact, price limit 관련 서술은 0건이다. 상한가 종목은 실제로 살 수 없는데 시그널 상위에 몰리기 쉬워 성과가 과대평가될 구조다. 참고로 README 면책은 포트폴리오 최적화와 리스크 팩터 중립화 부재만 인정할 뿐 이 미시구조 제약들은 언급하지 않는다. (추가 의문)
  • 예측 지표의 격차와 실제 포트폴리오 성과의 격차가 크게 어긋난다. Table 10에서 Kronos_large 평균 AER 0.2084 / IR 1.6491인데 Moment_large는 0.1681 / 1.3677, Moirai_large는 0.1577 / 1.2481이다. AER 기준 최고 베이스라인 대비 약 24% 우위로, 예측 단계의 93%가 투자 단계에서는 20-30% 수준으로 줄어든다. 이는 '예측 정확도가 투자 성과로 직결된다'는 본문 주장의 강도를 스스로 약화시킨다. 한편 Chronos_large는 평균 AER -0.0302 / IR -0.3384로 손실을 낸다. (추가 의문)
  • 이산화의 인과 기여가 분리되지 않았다. Table 2의 Kronos 대 Direct-AR/Prob-AR 비교에서 Kronos만 앙상블 샘플링(N=10)과 태스크별 T/top-p 튜닝의 혜택을 받는다. 연속형 베이스라인에 동등한 추론 예산을 준 통제 실험이 없어, 이득 중 얼마가 이산 토큰화 자체이고 얼마가 테스트타임 앙상블인지 알 수 없다. 실제로 독립 연구 VAIOM(arXiv 2607.13929)은 동일한 카테고리형 출력 목적함수 아래에서 연속 입력이 이산 토큰 입력보다 낫다고 보고한다. (추가 의문)
  • Kronos 사전학습의 컴퓨트 예산이 보고되지 않는다. Table 5는 드롭아웃/LR/weight decay만 주고, 본문은 워밍업 15,000스텝과 AdamW + 코사인 스케줄, 하드웨어(3 pod x 8장 = RTX 4090D 24장)만 밝힌다. 주의할 점은 Appendix D에 'batch size 256'과 '최대 12 에폭'이 등장하지만 이는 베이스라인 모델 학습 설정이지 Kronos 사전학습 설정이 아니라는 것이다(원문 확인 완료). Kronos 자체의 총 학습 스텝, 총 학습 토큰, 배치 크기, 에폭 수, 학습 소요 시간은 전부 누락됐다. 코퍼스 규모 120억 봉만으로는 컴퓨트 대비 성능을 계산할 수 없고, 세 크기 점 3개만으로 '스케일링 법칙을 실증했다'(empirically validating the scaling laws)고 말하기에는 근거가 얇다. 각 크기가 동일 토큰 예산으로 학습됐는지도 불명이다. (추가 의문)
  • 누출과 생존 편향 통제가 2024년 6월 시점 컷오프 하나에 전적으로 의존한다. 원문은 이 시간 분리만 서술할 뿐 상장폐지 종목 포함 여부, 수정주가 처리 방식, 지수 구성종목의 point-in-time 반영 여부를 전혀 언급하지 않는다(원문 확인 완료, 누락 확정). 사전학습 코퍼스에 CSI300/CSI800 종목의 과거 일봉이 들어 있었을 가능성이 매우 높은데(상하이 XSHG가 in-distribution 거래소로 명시됨), 이 경우 백테스트 유니버스는 새롭지 않다. (추가 의문)
  • 정규화 통계의 산출 범위가 논문에 없다. 원문 Appendix C는 'D개 특징 차원 각각에 독립적으로 z-score 정규화를 적용한 뒤 [-5,5]로 클리핑한다'고만 적고, 평균/표준편차를 룩백 윈도우 내부에서 계산하는지 시계열 전체에서 계산하는지 명시하지 않는다(원문 확인 완료, 누락 확정). 전자면 문제없고 후자면 미래 정보 누출이다. 논문만으로는 판별 불가이며 코드 확인이 필요하다. (추가 의문)
  • 어휘 크기 결론과 실제 실험 설정이 어긋난다. 배포 토크나이저는 k=20(2^20)인데 Table 9의 토크나이저 아키텍처 절제는 명시적으로 2^18 어휘에서 수행됐다. Figure 6의 어휘-성능 곡선도 '어휘를 키우면 복원과 예측이 모두 개선된다'는 단조 개선만 서술할 뿐 포화점을 보여주지 않아 2^20이 최적이라는 근거가 되지 못한다. (추가 의문)
  • 저장소와 논문이 어긋난다. 논문에 없는 Kronos-mini(4.1M, 컨텍스트 2048, Kronos-Tokenizer-2k)가 저장소에 있고(원문 전체 검색에서 mini 변종 언급 0건), 논문 최고 성능인 large는 미공개다. 논문 표를 그대로 재현하려면 base까지만 가능하다. (추가 의문)
  • 실패 사례 분석이 전무하다. 어떤 자산군, 어떤 변동성 레짐, 어떤 유동성 구간에서 모델이 무너지는지에 대한 서술이 없다. Appendix H는 왜 잘 되는지의 사후 정당화(노이즈 억제, 이산 상태공간, 초구 기하)에 집중하고, 레짐 전환이나 극단 이벤트에서의 성능 저하는 다루지 않는다. (추가 의문)
  • 라이선스는 MIT지만 사전학습 데이터의 출처와 라이선스가 전혀 명시되지 않는다. 45개 거래소, 120억 봉 규모라면 유료 벤더 데이터가 섞였을 개연성이 높다. 코드/가중치가 MIT라는 사실이 데이터 유래 리스크까지 정리해주지는 않는다. (추가 의문)

코드 부분 공개. github.com/shiyu-coder/Kronos (MIT). 공개 범위는 추론 코드(model/kronos.py, KronosPredictor), 파인튜닝 파이프라인(finetune/config.py, train_tokenizer.py, train_predictor.py, qlib_data_preprocess.py, qlib_test.py), 예제 스크립트, Web UI, Qlib 기반 A주 백테스트 스크립트다. torchrun 다중 GPU 파인튜닝을 지원한다. 반면 사전학습 코드는 공개되지 않았다(저장소 최상위 디렉터리는 examples, figures, finetune, finetune_csv, model, tests, webui로 pretrain 계열 경로가 없음). 즉 파인튜닝은 재현 가능하지만 사전학습은 재현 불가.가중치 부분 공개. Hugging Face NeoQuasar 조직에서 Kronos-mini(4.1M, 컨텍스트 2048, Kronos-Tokenizer-2k), Kronos-small(24.7M, 512, Kronos-Tokenizer-base), Kronos-base(102.3M, 512, Kronos-Tokenizer-base)와 각 토크나이저가 공개되어 있다. 논문 최고 성능 모델인 Kronos-large(499.2M)는 저장소 Model Zoo에 미공개로 표시되어 있어 논문 상단 수치(예: 가격 시계열 평균 RankIC 0.0267, 투자 시뮬레이션 평균 AER 0.2084 / IR 1.6491)를 그대로 재현할 수 없다. 참고로 Kronos-mini는 논문 본문에 전혀 등장하지 않는 저장소 전용 변종이다.데이터 핵심 데이터 비공개. 45개 거래소, 7개 주기, 120억+ K-line 사전학습 코퍼스는 공개되지 않았고 출처 벤더도 명시되지 않는다. 저자 스스로 본문에서 '일반 시계열 파운데이션 모델 연구와 달리 잘 정제된 공개 금융 데이터가 제한적이어서 처음부터 구축했다'고 밝힌다. 평가용 데이터셋(9개 주식 거래소 = in-distribution XSHG/XNAS/XJPX/XNSE/XKRX/XHKG + OOD XIDX/XKLS/XTAI, Binance 전 현물 페어, 1000+ 외환 페어)도 비공개다. 재현 가능한 부분은 투자 시뮬레이션뿐으로, 이는 오픈소스 Qlib의 중국 A주 일봉 데이터를 사용하며 백테스트도 Qlib 엔진 안에서 수행한다. 저장소 config.py 기준 학습 2011-01-01~2022-12-31, 검증 2022-09-01~2024-06-30, 테스트 2024-04-01~2025-06-05, 백테스트 2024-07-01~2025-06-05, instrument=csi300, lookback_window=90. 주의: 논문 본문은 '테스트 기간이 2024년 7월에 시작한다'고만 적고 종료일을 명시하지 않으므로, 11개월이라는 백테스트 길이는 논문이 아니라 저장소에서만 확인된다.라이선스 코드 및 저장소: MIT License. 공개 체크포인트도 HF 모델 카드 기준 MIT. 사전학습 데이터의 라이선스와 출처는 논문/저장소 어디에도 명시되지 않음 -> 상업적 활용 시 데이터 유래 리스크는 별도 검토 필요.

  • 비전 도메인의 양자화 기법(BSQ)을 금융 시계열로 이식한 것이 이 논문의 실질 기여다. 이산화가 회귀보다 나은 이유로 저자가 든 논거 - BSQ는 임베딩을 단위 초구에 사영한 뒤 이진화하므로 기대 왜곡이 상한으로 묶이고, 따라서 플래시 크래시 같은 이상치가 무한대 근사 오차를 만들지 못한다 - 는 노이즈가 큰 어떤 도메인에도 재사용 가능한 사고틀이다. 회귀 문제를 분류 문제로 바꾸면 이상치의 영향력에 천장이 생긴다.
  • 대어휘 실용화 트릭: 2^20 어휘를 2^10 두 개로 인수분해하면 어휘 의존 파라미터가 1744.8M -> 3.4M로 99.8% 줄고 총 모델 크기가 1842.3M -> 102.3M으로 약 95% 감소한다(Table 12). 대가는 토큰당 추론 스텝 2배. 큰 어휘를 쓰고 싶은데 임베딩/출력 행렬이 감당 안 될 때 바로 꺼내 쓸 카드다.
  • 서브토큰을 병렬로 예측하면 손해다. Kronos-Parallel의 RankIC 0.0226 대 순차 coarse->fine의 0.0254. 인수분해로 나눈 조각들은 조건부 의존성을 유지해야 하고, 이를 위해 예측된 coarse 토큰 임베딩을 쿼리로 하는 cross-attention을 끼워 넣었다. 인수분해는 공짜가 아니라 의존성 복원 장치를 요구한다.
  • 계층적 손실이 복원 정확도를 올리지 않는다는 사실(Table 9: 0.0785 대 0.0781)이 오히려 교훈이다. 손실 설계의 목적이 항상 성능일 필요는 없다. 여기서는 'coarse만으로도 대략 복원되는' 표현 구조를 강제하기 위한 장치이고, 그 이득은 토크나이저가 아니라 후속 자기회귀 모델에서 회수된다. 손실 함수로 표현의 구조를 조각하는 사례로 기억해둘 만하다.
  • Test-time scaling이 시계열에도 통한다. 샘플 경로 N을 늘려 평균내면 IC/RankIC가 단조 개선된다(Figure 7). 생성형 예측기는 재학습 없이 추론 예산과 정확도를 맞바꿀 수 있다. 실서비스에서 지연 예산 대비 정확도 곡선을 그릴 수 있다는 뜻이라 실무적으로 가치가 크다.
  • 샘플링 파라미터가 사실상 태스크 헤드 역할을 한다. 예측은 T=0.6/top-p 0.9/N=10, 변동성은 T=0.9/N=1, 생성은 T=1.0/top-p 0.95. 정밀도가 필요하면 분포를 날카롭게, 다양성이 필요하면 무디게. 하나의 사전학습 모델로 다목적을 커버하려면 이 축을 반드시 태스크별로 잡아야 한다. 저자는 top-p의 하드 절단보다 temperature의 전역 재조정이 더 효과적이라고 관찰했다.
  • 사전학습 코퍼스의 도메인 혼합비를 명시적으로 조정했다. 원 코퍼스가 주식에 쏠려 있어 크립토/선물/외환의 샘플링 가중치를 올렸다. 파운데이션 모델에서 데이터 혼합비는 아키텍처만큼 중요한 하이퍼파라미터라는 점을 다시 확인.
  • 데이터 클리닝 파이프라인이 논문의 숨은 자산이다. 주기별로 임계값을 다르게 둔다: 가격 점프 임계는 1분봉 0.10에서 주봉 0.50까지, 비유동/정체 연속 봉 허용치는 1분봉 15/45에서 주봉 0/2까지. 구조적 단절(전일 종가 대비 당일 시가 점프)로 시계열을 분할해 액면분할, 배당, 선물 롤오버 아티팩트를 격리한다. 금융 시계열 전처리 설계 시 그대로 참고할 수 있는 표다.
  • 결측치 처리 철학이 인상적이다. 가격 필드의 결측을 채우지 않고 '경계'로 간주해 시계열을 유효 부분수열들로 쪼갠다. 부당한 보간으로 없는 패턴을 만들지 않겠다는 선택이며, 사전학습처럼 데이터가 남아도는 상황에서는 채우기보다 버리기가 옳다는 판단이다.
  • RoPE로 상대 위치를 주면서도, 캘린더 정보(minute/hour/weekday/day/month 다섯 개)는 별도 임베딩으로 합산해 주입한다. 금융처럼 절대 시각의 계절성(개장/폐장 효과, 월말 효과)이 실재하는 도메인에서는 상대 위치만으로 부족하다는 설계 판단.
  • 평가 설계에서 배울 점과 반면교사가 함께 있다. 배울 점: in-distribution 거래소 6개와 OOD 거래소 3개(인도네시아, 말레이시아, 대만)를 나눠 일반화를 측정하고, 크립토/외환에서는 volume을 일부러 빼 OHLC만으로 테스트한 점. 반면교사: 메인 표 전부가 단일 실행 점추정이고 유의성 검정이 없다는 점.
  • 헤드라인 퍼센트는 항상 절대값과 함께 읽어야 한다. RankIC 0.0254 같은 수준에서의 +93%와, 투자 시뮬레이션에서 AER 0.2084 대 0.1681(약 +24%)의 격차가 같은 모델에서 나온다. 예측 지표의 상대 개선은 포트폴리오 단계로 갈수록 급격히 희석된다는 사실 자체가 중요한 실무 지식이다.
  • 실전 적용 시 컨텍스트 512가 첫 번째 제약이다. K-line 레코드 하나당 서브토큰 2개를 만들므로 유효 룩백은 대략 256봉 수준으로 봐야 한다(정확한 카운팅 방식은 코드 확인 필요). 5분봉 480봉 룩백 설정은 이 한계에 부딪히고, 저장소의 KronosPredictor는 초과분을 자동 절단한다. 긴 룩백이 필요하면 더 낮은 주기를 쓰거나 컨텍스트 2048인 Kronos-mini를 고려해야 한다.
  • 재현성 실무 교훈: 코드와 가중치를 MIT로 풀어도 사전학습 코퍼스와 사전학습 코드가 없으면 '오픈'의 범위는 파인튜닝과 추론까지다. 오픈소스 파운데이션 모델을 평가할 때 확인할 체크리스트는 (1) 사전학습 코드, (2) 코퍼스, (3) 최상위 체크포인트, (4) 학습 예산 보고 네 가지이며 Kronos는 이 중 어느 것도 완전히 충족하지 않는다.

연결 연구

  • ← : Kronos 토크나이저의 핵심 부품. 잠재벡터를 단위 초구에 사영 후 이진화해 암묵적 코드북을 만들고 기대 왜곡의 상한을 보장한다. Kronos는 저자 공식 구현의 하이퍼파라미터(commitment 0.05, entropy weight 1.0/1.1, entropy scale 0.05, group size 5)를 거의 그대로 가져왔다. 어휘가 커질수록 좋아진다는 관찰도 이 계열에서 물려받은 것.
  • ← : 룩업 없는 양자화(LFQ)의 원류. BSQ의 직전 세대이며, Kronos는 LFQ가 정규화 없이 부호 기반 양자화를 해 이상치에 대한 오차 상한이 없다는 점을 BSQ 채택 근거로 든다. 어휘 인수분해 아이디어의 출처이기도 하다.
  • ← : 이산 잠재 표현 학습의 원점. Kronos 관련연구 절이 시계열 토큰화 계보를 여기서 시작한다.
  • ← : 시계열을 스케일링 + 균등 양자화로 토큰화한 TSFM. Kronos의 직접 선행이자 베이스라인. 흥미롭게도 Kronos의 투자 시뮬레이션에서 Chronos_large는 평균 AER -0.0302로 유일하게 음수를 기록해, 일반 시계열 토큰화가 금융에 그대로 이식되지 않음을 보여주는 대조군 역할을 한다.
  • ← : 논문이 '가장 강한 TSFM 베이스라인'으로 지목한 모델. 헤드라인 +93% RankIC의 비교 기준점이 바로 이 모델이다. 결측 가격 처리 시 시계열을 유효 부분수열로 분할하는 아이디어도 Time-MoE에서 차용했다고 밝힌다.
  • ← : 제로샷 TSFM 베이스라인. 투자 시뮬레이션에서 Moirai_large가 평균 AER 0.1577 / IR 1.2481로 상위권에 들어, Kronos와의 실제 포트폴리오 성과 격차가 예측 지표 격차보다 훨씬 작다는 사실을 드러낸다.
  • ← : 디코더 온리 TSFM 베이스라인. Kronos가 Table 3에서 지적하는 '기존 TSFM 사전학습 코퍼스 중 금융 데이터 비중이 1% 미만'이라는 논거의 대상 중 하나.
  • ← : 제로샷 TSFM 베이스라인. 투자 시뮬레이션에서 Moment_large가 평균 AER 0.1681 / IR 1.3677로 제로샷 baseline 중 최고 성능을 냈다.
  • ← : 논문이 '가장 강한 비사전학습 모델'로 지목한 풀샷 베이스라인. 헤드라인 +87%의 비교 기준점.
  • ← : 패치 기반 시계열 트랜스포머. Kronos는 의도적으로 패치가 아니라 K-line 레코드 단위 토큰화를 택했으므로, 설계상 대조점이 되는 선행 연구다.
  • ← : VQ-VAE 기반 시계열 토큰화. Kronos 관련연구에서 코드북 기반 접근의 대표로 인용되며, Kronos가 명시적 코드북 대신 암묵적 코드북(BSQ)을 택한 이유의 비교 대상이다.
  • ← : 투자 시뮬레이션의 데이터 소스이자 백테스트 엔진. 저장소의 파인튜닝 데모 파이프라인도 전적으로 Qlib에 의존한다. 표준화된 평가라는 장점과 동시에 슬리피지/마켓임팩트 미모델링이라는 한계를 함께 물려받는다.
  • ← : 백본의 위치 인코딩. Pre-LN + RMSNorm과 함께 현대 LLM 표준 구성을 그대로 이식한 부분.
  • ← : 생성 태스크 베이스라인이자 평가 프로토콜(diversity/fidelity/usefulness, discriminative score, TSTR)의 출처. Kronos의 '생성 충실도 22% 개선' 주장이 이 프로토콜 위에서 계산된다.
  • ← : 확산 기반 생성 베이스라인. TimeVAE(Desai et al. 2021)와 함께 생성 비교군을 이룬다.
  • → : Kronos의 핵심 전제에 대한 가장 직접적인 반례. 입력 표현과 출력 우도를 분리해, 연속 다변량 금융 이벤트 벡터를 입력으로 쓰되 출력은 변동성 정규화 수익률 버킷에 대한 범주형 분포로 둔다. 검증 실험에서 '동일한 범주형 출력 목적함수 아래에서 연속 입력이 이산 토큰 입력보다 낫다'고 보고한다. 즉 Kronos의 이득이 이산 출력에서 오는지 이산 입력에서 오는지를 분리해 답한 셈이고, 결론은 입력까지 이산화할 필요는 없다는 쪽이다. 1시간 FX 봉, 0.9M 파라미터, 3시드, 2025년 두 구간 아웃오브샘플로 LightGBM 대비 이벤트당 0.029~0.043비트 개선.
  • → : Kronos의 '변동성 예측 MAE 9% 개선' 주장을 재평가하게 만드는 연구. 9개 제로샷 TSFM 대 8개 계량경제 모델(HAR 계열 포함)을 주식/외환/선물 50자산, 3개 지평에서 형식적 예측 비교 검정과 함께 비교했다. 결론은 TSFM의 우위가 균일하지 않고 소수 아웃라이어 자산에 집중되며, 자산별 손실비를 평균하면 Tiny Time Mixers 하나만 근소하게 Log-HAR을 이긴다는 것. 게다가 단기 지평 우위의 상당 부분이 실제 동역학 예측이 아니라 스케일 보정 효과였다고 지적한다. Kronos가 HAR 계열을 베이스라인에서 뺀 것이 왜 문제인지를 보여준다.
  • → : Kronos의 고정 컨텍스트 512 제약을 정면으로 문제 삼는 후속 방향. 비정상 가격 프로세스에서는 최적 룩백이 시변하므로 고정 컨텍스트 윈도우가 구조적으로 부적합하다고 지적하고, 중첩 가변 길이 윈도우를 전문가에게 라우팅하는 MoE를 제안한다. Kronos가 '주기를 바꿔 우회하면 된다'고 넘어간 지점을 아키텍처로 푸는 시도.
  • → : Kronos의 '금융을 토큰 생성으로 본다'는 관점을 예측을 넘어 자산배분까지 확장. 별도 회귀/랭킹/정책 헤드 없이 인과 언어모델의 제약된 토큰 생성만으로 3스텝 수익률 예측과 5개 ETF 동적 배분을 수행한다. 2023-2025 테스트에서 5bp 거래비용 반영 순 샤프를 1.394 -> 1.494로 개선했다고 보고. Kronos가 예측에서 멈춘 지점을 의사결정까지 밀고 간 계열.
  • → : Kronos가 금융 전용으로 만든 토크나이저를 범용 시계열로 일반화하려는 방향. Kronos의 도메인 특화 전략과 범용 토크나이저 전략 중 어느 쪽이 옳은지에 대한 후속 논쟁의 한 축.

Kronos는 '금융 K-line 전용 파운데이션 모델'이라는 빈칸을 처음으로 제대로 채운 논문이고, 그 점에서 가치가 분명하다. 비전 양자화(BSQ)를 금융 시계열로 옮긴 선택, 2^20 어휘를 2^10 두 개로 인수분해해 파라미터를 99.8% 줄인 엔지니어링, coarse->fine 순차 예측으로 서브토큰 의존성을 유지한 설계, 그리고 추론 샘플 수로 정확도를 사는 test-time scaling은 모두 재사용 가치가 높다. 데이터 클리닝 파이프라인(주기별 임계값 표)과 결측을 보간하지 않고 시계열을 분할하는 처리 철학도 실무에서 그대로 가져다 쓸 만하다. 다만 검증한 결과, 이 논문의 신뢰도는 헤드라인 수치보다 상당히 낮게 잡아야 한다. 첫째, 독립된 Limitations 섹션이 아예 없고 Conclusion도 성과 요약만 한다. 저자가 인정한 한계는 컨텍스트 512 제약, n=2 인수분해가 비용 기반 선택이라는 점, 계층적 손실이 복원 품질을 개선하지 않는다는 점(Table 9), 크립토/외환에서는 volume을 빼야 한다는 점 정도로, 대부분 부록에 흩어져 있다. 오히려 GitHub README의 면책 문구가 논문보다 정직하다. 둘째, 헤드라인 '+93% RankIC'는 절대값이 0.02~0.05 수준인 지표 위의 상대 개선이고, 해당 지표(가격 시계열의 시간축 IC)는 가격 레벨의 자기상관 때문에 추세 지속만으로도 높게 나올 수 있어 퀀트 실무의 횡단면 IC와 성격이 다르다. 같은 모델의 투자 시뮬레이션에서는 Kronos_large 평균 AER 0.2084 대 Moment_large 0.1681로 격차가 20%대로 축소되는데, 이 대비가 헤드라인의 실질을 잘 보여준다. 셋째, 메인 결과가 전부 단일 실행 점추정이고 유의성 검정이 없다. 시드 5개는 Figure 7 한 곳뿐이다. 저자 스스로 신호 대 잡음비가 낮다고 강조한 도메인에서 이건 방법론적 결함에 가깝다. 넷째, 변동성 태스크는 실현변동성의 사실상 표준인 HAR 계열을 베이스라인에서 통째로 빼고 ARCH/GARCH만 썼다. 후속 연구 2607.05291이 9개 TSFM을 Log-HAR과 비교해 대부분 이기지 못한다고 보고한 것을 보면, '9% 낮은 MAE'는 약한 상대에게 얻은 우위일 개연성이 있다. 다섯째, 이산화의 인과 기여가 분리되지 않았다. Kronos만 N=10 앙상블과 태스크별 T/top-p 튜닝의 혜택을 받고 연속형 베이스라인에는 동등한 추론 예산이 주어지지 않았다. 후속 연구 VAIOM(2607.13929)이 동일한 범주형 출력 목적함수 아래에서 연속 입력이 이산 토큰 입력보다 낫다고 보고한 것은 이 의심에 실증을 붙인다. 여섯째, 백테스트가 단일 시장(중국 A주), 롱온리, 약 11개월(저장소 config 기준 2024-07-01~2025-06-05, 논문 본문에는 기간 명시 없음 -> 본문 확인 필요)이며 그 구간에 2024년 9-10월 급등이 포함된다. 상하한가와 거래정지를 모델링하지 않은 점은 A주에서 특히 성과를 부풀릴 수 있다. 재현성은 '부분 오픈'이 정확한 표현이다. MIT 라이선스로 추론과 파인튜닝 코드, mini/small/base 가중치가 풀렸고 Qlib 기반 A주 실험은 재현 가능하다. 반면 사전학습 코드는 저장소에 존재하지 않고(pretrain 경로 404 확인), 120억 봉 코퍼스와 9개 거래소 평가셋은 비공개이며, 논문 최고 성능인 large(499.2M)는 미공개다. 총 학습 스텝/토큰/배치/에폭이 전부 누락되어 컴퓨트 대비 성능도 역산할 수 없다(하드웨어는 RTX 4090D 24장으로 명시). 결국 세 크기 점 3개로 '스케일링 법칙 실증'을 주장하는 것은 과하다. 개인 학습 목적이라면 이 논문은 두 가지로 쓰는 게 좋다. 하나는 도메인 특화 토크나이저 설계의 교과서적 사례로 - BSQ 채택 논거, 어휘 인수분해 트릭, 손실로 표현 구조를 조각하는 발상 - 읽는 것. 다른 하나는 금융 ML 논문을 읽을 때의 체크리스트를 벼리는 반면교사로 읽는 것이다. 상대 % 뒤의 절대값, IC의 정확한 정의(시간축인가 횡단면인가), 베이스라인에 도메인 표준(HAR)이 들어 있는가, 시드와 신뢰구간이 있는가, 백테스트 기간과 시장이 몇 개인가, 거래 제약이 모델링되었는가. 이 여섯 개만 물어도 이 논문의 주장 강도는 상당히 조정된다. AAAI 2026 채택과 GitHub 별 37.5k는 이 모델의 실용적 수요를 보여주지만, 그것이 위 방법론적 공백을 메워주지는 않는다.

방법 상세

ATAS의 중심 객체는 월드 상태 W_t=(S_t, E_t)다. 화면각본 u는 Compile(u, W_t)를 거쳐 bounded shot request q=(d, s, xi, c, tau, e)로 바뀐다. 각 필드는 로컬 설명, 장면 ID, 장면 좌표계 안의 공간 앵커, 목표 카메라, 요청 시간 구간, 선택적 사건 ID다(3.2절, 부록 B). 컴파일러는 장면 전환, 시간 관계, 과거 사건 참조, 카메라 요구를 하나씩 풀어 내면서 각 요청이 짧은 영상 예산에 들어갈 때까지 재귀적으로 분해한다. 요청은 순서대로 처리되고, 검증된 W_{t+1}이 다음 요청의 조건이 된다. 저장소 구현은 LLM 2단계다(기본값 gpt-5.1). 먼저 skeleton 단계가 캐스트, 장면, 내러티브 샷, 전환을 한 번에 계획한다. 이어 segment 단계가 실행이 도달한 샷만 4-15초 요청으로 확장하고, 이때 현재 월드 상태 요약을 입력으로 받는다.

장면 기억은 동적 영역을 뺀 정적 point cloud다. 장면의 첫 관측이 좌표계를 정한다. 본문은 재구성 모델 이름을 밝히지 않고, 판정 근거로 Umeyama, VGGT, CUT3R, Vista4D만 인용한다. 저장소(docs/design.md)를 보면 Vista4D에서 가져온 Pi3X로 RGB-D와 카메라를 복원하고, SAM3로 동적 마스크를 만든다. 첫 관측은 클립 전체에서 13개 프레임을 샘플해 만든 프레임 쌍의 일관성을 검사한다(허용치 t는 median depth의 2%). 이후 클립은 신뢰된 과거 프레임 최대 6장을 Pi3X 창에 주입해 재구성한다. 그중 4장은 depth/pose를 제공하고, 2장은 검증용으로 held-out 해 둔다. 그다음 잔차 similarity transform을 맞춘다. held-out 프레임, chunk-overlap 정적 점, SIFT 대응점 30개 이상의 세 조건이 모두 맞으면 등록 성공(r=1)이다. 신뢰 참조는 최대 2개까지 시도한다. 새 점은 기존 점과 겹치지 않는 곳에만 append하고, 기존 점은 수정하지 않는다. 버전은 장면 단위로 관리한다.

사건 기억은 레코드 (s, e, b, tau, D)의 집합이다. D는 프레임별 RGB-D, 마스크, 동적 point cloud다. 검색은 (장면, 사건 ID, 시간 구간)으로 바로 찾는 키 조회다. 저장소에서 embedding, faiss 같은 유사도 검색 코드는 찾지 못했다. 사건 기억은 정적 기억에 융합하지 않는다. 재포착 때는 원본 클립에서 요청 시각의 동적 점을 꺼내, 정적 점과 하나의 depth buffer로 합성 렌더한다.

조건 주입에 대해 논문은 장면·사건 참조가 context-dependent prompt를 이룬다고만 쓴다. 저장소에서는 기억을 목표 카메라 궤적으로 렌더한 point-splat 영상을 Wan의 reference video로 넣는다(include_geometry_reference=True). 여기에 gpt-image-2로 만든 첫 프레임 또는 인물 참조 이미지와 텍스트가 더해진다. 카메라 제어는 생성기 파라미터가 아니라 이 렌더 영상으로 전달된다. VGGT dense condition 경로는 기본값에서 꺼져 있다(use_dense_vggt_condition=False). 렌더 coverage의 역할은 이렇다. 설정 파일에 min_dense_target_coverage=0.45가 정의되어 있지만, repo 전체 grep에서 이 값을 읽는 코드는 찾지 못했다. 설계 문서는 coverage를 카메라 경로의 soft ranking 신호로만 쓰고 거부 기준으로는 쓰지 않는다고 적는다.

생성 후에는 세 가지 판정을 차례로 거친다. f(film review)는 VLM이 원 각본을 기준으로 subject, framing, motion, action, event, world_consistency 6개 항목을 본다. confidence 0.75 이상의 critical fail이 나오면 재생성한다(기본 최대 2회). r은 위의 등록 판정이다. a는 provenance, 장면 범위, parent 버전을 검사한다. f, r, a가 모두 1일 때만 W가 갱신된다. f=1이면 r이나 a가 실패해도 클립은 영화에 남지만, 이후 요청의 증거로는 쓰이지 않는다. 저장소에서는 수리 횟수를 다 써도 best-available 클립을 납품하고, 그 클립은 기억에 넣지 않는다. 납품과 기억 반영을 분리한 이유는 두 가지다. 영화 진행을 막지 않으면서, 정렬이 안 된 관측이 다음 샷을 오염시키지 않게 하려는 것이다.

  • 사건 재포착(Tab. 3, 부록 A.1): 고정 VLM judge 하나와 버전 관리되는 rubric을 쓴다. judge 입력은 샘플된 원본 사건 프레임, 사건 설명과 구간, 목표 카메라 요청, 선택적 memory render, 생성 클립 프레임이다. 5개 축(event identity, action/state, temporal order, char/object, viewpoint)을 쓰며, binary 판정은 0/1로, 5점 척도는 (r-1)/4로 정규화한다. 요청 안에서 먼저 평균을 내고, 그다음 요청 간 평균을 낸다. 생성 클립이 없는 요청은 해당 축에서 0점을 받는다. 동기화된 정답 영상은 없다. judge 모델 이름과 요청 수는 원문에서 확인되지 않는다.
  • Ablation(4.3절): Tab. 4는 Wan 3.0으로 고정하고, 같은 요청, 카메라, candidate budget, retry policy에서 구성요소를 누적 추가한다. Tab. 5는 저장 증거를 바꾼다(없음, frame history, static scene, updated scene, scene+event, full state). Tab. 5 캡션과 4.1절은 'ATAS와 Wan 3.0 고정'만 적고, candidate budget과 retry policy 고정은 명시하지 않는다. 부록 Tab. F/G/H는 용량, 갱신 간격, 신선도, 상태 검사 엄격도에 대한 민감도 분석이다. 부록 D는 이 분석들에서 prompt package, 카메라, 생성기, candidate budget, retry policy를 고정한다고 적는다.
  • 효율(Fig. 6): 6개 메모리 설정에서 다음을 측정한다. 스토리당 wall-clock, real-time factor, candidate lifecycle, 샷당 재시도, retry-adjusted delivery, throughput, 메모리 오버헤드다. GPU 종류와 개수, API 비용(달러)은 본문과 부록 어디에도 없다. README는 geometry 서비스에 NVIDIA GPU 약 20GB가 필요하다고 적는다.
  • 인간평가(Fig. 5, 부록 E, Fig. F/G/H): 6개 방법의 익명화된 전체 영상을 6개 기준(visual appeal, script faithfulness, character consistency, background consistency, physical law, narrative coherence)에 대해 1-5점으로 평가한다. 평가자 수는 본문, 부록, 인터페이스 그림을 모두 확인했지만 보고되지 않았다. 인터페이스 스크린샷(Fig. F)에는 '1 / 240' 페이지 표시, Framework A-F 탭, 'Videos are grouped by framework' 안내가 보인다. 부록 E는 'randomized order'라고만 쓰고 무엇을 무작위화했는지(프레임워크 순서, 묶음 안의 영상 순서)는 설명하지 않는다.
  • 자동 지표와 인간 평가의 일치도(Fig. H): matched clip에서 Spearman rho를 구해 human-human ceiling과 비교한다. 평가자 간 일치 계수 alpha는 0.58-0.72다(Fig. G).

데이터셋

  • VBench (official prompt suite/evaluator) — 공개 벤치마크. 이 논문에서 사용한 prompt 수는 원문에서 확인되지 않음 (single-clip video quality: aesthetic, subject/background consistency, flicker, smoothness, dynamic degree)
  • ST-Bench (from StoryMem [61]) — 공개 벤치마크. 사용 스토리 수는 원문에서 확인되지 않음 (multi-shot storytelling: aesthetic, PF-G, PF-S, cross-shot C-All, C-Top10)
  • ViStoryBench (ViStory-Self / ViStory-Cross) [62] — 공개 벤치마크. 사용 규모는 원문에서 확인되지 않음 (story visualization: within-story identity/appearance/temporal, cross-shot identity/appearance/scene consistency)
  • Spatial revisit set (자체 구성) — 요청 수 미보고. 본문, 부록, 표 캡션을 확인함 (target-image return view comparison under common-visibility mask)
  • Source-grounded event recapture set (자체 구성) — 요청 수 미보고. Tab. 3 값이 1/60, 1/56, 1/16 단위로 떨어져 요청 수가 수십 개 이하로 작을 가능성이 있다(분석자 추정, 저자 미확인) (historical event replay from a new camera, VLM-judged)
  • Human study stimuli (자체) — 인터페이스 표시 기준 240개 영상 페이지(Fig. F 스크린샷). 평가자 수 미보고 (whole long videos (about 2 min, e.g. 1:50 laundry film) from 6 methods)

한계 · 비판

  • 사건 재포착 평가는 source-grounded 판정이다. 생성 클립이 공급된 사건 증거와 카메라 요청에 맞는지는 판단하지만, 관측되지 않은 목표 영상과 pixel 수준에서 일치하는지는 확인할 수 없다. 저자는 동기화된 목표 영상이 있을 때의 재구성 평가를 이 점수로 대신할 수 없다고 명시한다(부록 A.1, Tab. 3 캡션 'No synchronized target video is used'). (저자 인정)
  • 정확한 action-state 재현이 남은 과제다. 사건 재포착에서 action/state 점수가 ReCA보다 약간 낮다(0.688 vs 0.700). 저자는 남은 어려움이 요청한 사건이나 뷰를 찾는 일이 아니라 동작·상태를 그대로 재현하는 일이라고 쓴다(4.2절, Tab. 3). 3.3절은 사건 기억이 identity-resolved motion model이 아니라 frame-local dynamic evidence만 보관한다고 밝힌다. (저자 인정)
  • 인간평가에서 ATAS 안에서도 background consistency(3.62)와 narrative coherence(3.77)가 낮다. 저자는 환경 전체의 일관성과 이야기 전체의 일관성이 덜 해결되었다고 쓴다. 부록 E는 narrative coherence와 physical law 판정이 script faithfulness보다 어렵다고 덧붙인다(4.2절, Fig. 5, 부록 E, Fig. G). (저자 인정)
  • 메모리는 총 compute를 줄이지 않는다. full state는 no memory 대비 스토리당 시간이 51.9분에서 64.9분으로 늘고, 메모리 오버헤드가 샷당 98초 붙으며, throughput은 7.28에서 6.21 shots/h로 떨어진다. 저자는 이득이 재시도 감소(1.00 -> 0.54)와 retry-adjusted delivery 단축(359 -> 339초/샷)이지 총 compute 절감이 아니라고 명시한다(4.2절, Fig. 6). (저자 인정)
  • 기본 상태 검사 threshold가 보편적으로 최적인 것은 아니다. permissive(반영률 90.0%)와 strict(반영률 36.0%) 둘 다 품질이 떨어진다. 저자는 이 검사가 통제된 admission 장치일 뿐 재구성이나 검색 품질 개선을 대신하지 못한다고 쓴다(부록 D, Tab. H). Tab. G는 마지막 반영 이후 샷이 0에서 5+로 늘면 C-Top10이 0.736에서 0.651로 떨어지는 신선도 저하도 보고한다. 저자는 이 구간 분석이 저하 원인(장면 변화, 사건 밀도, 누적 등록 오차)을 식별하지 못한다고 적는다(부록 D). (저자 인정)
  • 결과의 해석 범위에 대한 저자 단서도 있다. 자동 진단 지표와 인간 평가의 상관(0.41-0.61)이 human-human ceiling(0.67-0.80)보다 낮다. 그래서 저자는 자동 지표를 인간 판정의 완전한 대체가 아니라 구조화된 진단으로 써야 한다고 쓴다(부록 E, Fig. H). 메모리 통계(Tab. E)는 보고 설정의 operating profile이지 일반 scaling law가 아니라고 적는다(부록 C). ViStory-Self에서는 identity preservation에 개선 여지가 남았다고 쓴다(부록 Tab. C 설명). (저자 인정)
  • 통계적 근거가 얇다. 공간 재방문(Tab. 2)과 사건 재포착(Tab. 3)은 요청 수, 장면 수, 백본을 표기하지 않는다. 사건 judge VLM의 모델명도 원문에서 확인되지 않는다. Tab. 1의 +- 값은 그 정의(시드, 스토리, 반복)가 캡션과 4.1절에 없고, Tab. 2-5에는 산포 표시 자체가 없다. 인간평가는 Fig. 5에 standard-error whisker가 있지만 평가자 수가 보고되지 않았다(HTML 전문을 rater, participant, annotator로 grep했고, 감사의 글에 'participants'만 나온다). 이런 상태에서 일부 우위는 매우 작다. Tab. 2 LPIPS_C는 0.284 vs Mora 0.288이고, Tab. 5에서 scene+event로부터 full state로 가는 이득은 C-Top10 +0.016이다. 이 차이들은 유의성을 판단할 수 없다. 설명되지 않은 수치 일치도 있다. Tab. A의 VBench aesthetic과 Tab. B의 ST-Bench aesthetic이 네 백본 모두에서 소수 넷째 자리까지 같다(0.6387/0.6731/0.6945/0.6792). 두 벤치마크는 공식 입력이 다르다고 서술되어 있어서, 같은 클립에서 계산했는지 원문으로는 확인할 수 없다. (추가 의문)
  • 베이스라인 대비 우위가 어디서 오는지 분리가 불완전하다. Tab. 1-3의 블록 안에서 통제한 항목은 생성기, prompt package, duration budget, 평가(집계) 프로토콜뿐이다(Tab. 1 캡션, 4.1절). 베이스라인에도 같은 VLM film review와 재시도 예산을 주었는지는 명시되지 않았다. ATAS 내부 비교를 보면, Tab. 4는 candidate budget과 retry policy 고정을 캡션에 적지만 Tab. 5 캡션과 4.1절은 Wan 3.0 고정만 적는다. 단 Fig. 6의 샷당 재시도 차이(1.00 vs 0.54)는 같은 policy 아래의 결과일 수 있으므로, 그 자체를 예산 불일치의 증거로 볼 수는 없다. 메모리를 뺀 ATAS의 C-Top10은 0.536이고 frame history 조건은 0.598이다(Tab. 5). 이는 Tab. 1 Wan 3.0 블록 ReCA의 ST-Bench 0.602보다 낮거나 비슷하다. Tab. B-D의 ReCA reference 값(C-Top10 0.6015, ViStory-Self 0.6609, ViStory-Cross 0.4810)이 Tab. 1 Wan 3.0 블록의 ReCA 값(0.602, 0.661, 0.481)과 일치하므로, reference는 같은 Wan 3.0 비교로 보인다(분석자 대조). 따라서 ATAS가 베이스라인을 앞서는 폭의 대부분은 3D 정합 기억(렌더된 기억 영상이라는 추가 시각 조건)과 재귀 컴파일을 함께 쓸 때 나온다고 읽어야 한다. frame history(0.598)와 full state(0.719)의 차이 +0.121은 여러 요소의 합이다. 장면 기억(updated scene 0.658까지 +0.060), 사건 기억(scene+event 0.703, +0.045), 상태 검사(+0.016)가 모두 들어 있다. 부록 Tab. B-D는 비교 열로 ReCA reference 하나만 두므로, 블록별 베이스라인의 세부 지표는 없다. Wan 2.7 ATAS는 이 reference보다 몇몇 세부 지표에서 낮다. Tab. C identity(0.5494 vs 0.5608)와 appearance(0.6836 vs 0.7034), Tab. D cross-shot appearance(0.4871 vs 0.5013), Tab. B PF-G(0.2174 vs 0.2216)다. reference가 Wan 3.0이라면 백본이 달라 직접 비교는 아니다. 그래도 초록의 'all reported cross-shot consistency measures'는 블록별 aggregate 수준의 주장으로 읽는 것이 정확하다. (추가 의문)
  • 평가 설계에 독립성 문제가 있다. ReCA [64](arXiv 2605.26525)는 Tab. 1, Tab. 3, 인간평가에서 가장 강한 베이스라인이다. 이 논문은 같은 그룹의 선행 연구로, 저자 목록(A. Liu, Y. Li, Z. Zhang, Y. He, W. Wang, B. Zhuang 등)이 ATAS 저자와 이니셜 기준으로 상당 부분 겹친다. 인간평가 프로토콜도 ReCA를 따른다. 인간평가 인터페이스 그림(Fig. F)에는 'Videos are grouped by framework' 안내, Framework A-F 탭, '1 / 240' 페이지 표시가 보인다(이미지를 직접 확인함). 부록 E는 'randomized order'라고만 적고 무엇을 무작위화했는지 밝히지 않는다. 방법별로 묶어 보여 주면, 이름을 가려도 평가자는 같은 방법의 영상을 연달아 보게 된다. 따라서 두 서술이 어떻게 양립하는지 설명이 필요하다. 또 사건 재포착은 VLM judge가 채점하는데, 파이프라인 자체도 VLM(저장소 기본 gpt-5.1)으로 film review를 한다. judge가 같은 계열 모델이라면 평가와 최적화가 같은 기준을 공유할 수 있다. judge 이름이 없어 이 점은 확인할 수 없다. Fig. H의 자동 지표-인간 Spearman rho는 0.41-0.61로, human-human ceiling 0.67-0.80보다 낮다. (추가 의문)
  • 4개 생성기 일반화 주장은 검증하기 어렵다. MiniMax-H3, HappyHorse 1.0, Wan 2.7, Wan 3.0은 참고문헌에 인용이 없고, 해상도와 호출 방식도 본문에 없다. 논문은 MiniMax-H3를 open-source로 분류하지만 근거를 제시하지 않는다. 3D-guided 비교 대상인 FlexWorld도 참고문헌에서 찾지 못했다. 저장소에는 DashScope Wan 어댑터(wan2.7-r2v/i2v/t2v 설정, 기본값 wan3.0-video)만 있다. MiniMax와 HappyHorse 문자열은 코드 전체 grep에서 나오지 않았다. 따라서 4개 백본 중 2개 블록은 공개 코드로 재현할 수 없다. (추가 의문)
  • 비용 보고가 불완전하다. 스토리당 wall-clock(64.9분)과 샷당 시간은 있다. 그러나 GPU 종류·개수, DashScope 영상 API 비용, gpt-5.1과 gpt-image 호출 비용(달러)은 본문과 부록 어디에도 없다. 영상 생성 API는 샷마다 과금되고, film-rejected 후보가 36.8%다(Fig. 6b). 이를 생각하면 실사용 비용을 추정할 근거가 부족하다. 별도 failure case 절도 없다(목차와 부록 A-G 확인). 부록 G 갤러리는 성공 사례만 보여 준다. (추가 의문)

재현 가능성

코드 공개(https://github.com/ziplab/ATAS). main 브랜치 tarball로 확인했고, 디렉터리를 빼면 파일 422개다. 구성은 두 부분이다. client는 재귀 컴파일러, DashScope Wan 어댑터, VLM film review, best-available 선택, runner를 담는다. geometry 서비스는 Pi3X·SAM3 기반 재구성·등록 HTTP 서비스이고 run_geometry_service.sh로 실행한다. 예제 screenplay 3개(bookstore, clockshop, record)와 pytest 테스트가 있다. 반면 다음 코드는 찾지 못했다. 벤치마크 평가 코드(VBench, ST-Bench, ViStory, PSNR_C/LPIPS_C, 사건 judge rubric), 베이스라인 재현 코드, MiniMax-H3·HappyHorse 어댑터다. VBench, ViStory, LPIPS, PSNR 문자열은 geometry/backbones를 제외한 repo 전체(README 포함)에서 grep되지 않았다.가중치 ATAS 자체는 학습 가중치가 없는 inference-time 에이전트다. 외부 가중치로 Pi3X(yyfz/Pi3)와 SAM3(facebook/sam3, sam3.pt)를 별도로 내려받아 GEOMETRY_MODEL_ROOT에 둬야 한다. repo에는 포함되지 않는다(geometry/backbones/SOURCE_SNAPSHOT.md에 'Weights are not included'). 영상 생성은 DashScope API(Wan, DASHSCOPE_API_KEY), 계획·리뷰·이미지는 OpenAI 호환 API(기본 gpt-5.1, gpt-image)라서 유료 API 키가 필요하다.데이터 표준 벤치마크(VBench, ST-Bench from StoryMem, ViStoryBench)는 공개되어 있다. 자체 구성한 spatial revisit set, event recapture set, 인간평가 영상(인터페이스 기준 240 페이지)과 점수 데이터는 repo에서 찾지 못했다. 논문에도 공개 링크가 없다(HTML 전문과 프로젝트 페이지 확인).라이선스 MIT License(LICENSE 파일: 'Copyright (c) 2026 The ATAS Authors'). geometry/backbones/는 Vista4D 서브셋으로 Apache-2.0이고, 그 안의 Pi3와 SAM3는 각자의 upstream 라이선스를 따른다(SOURCE_SNAPSHOT.md, README License 절).

README 기준 client는 GPU가 필요 없다(Python 3.12, ffmpeg). geometry 서비스는 NVIDIA GPU 약 20GB가 필요하다. 저VRAM 기본 설정에서 피크가 약 20GB이고, 재구성 시작에 free 24576 MiB가 권장되며, whole-clip 모드는 80GB 카드 기준이다(geometry/.env.example). geometry는 bash 스크립트와 Linux 경로를 전제하고 torch+CUDA 환경이 필요하다. Windows PC에서는 client만 API로 돌리고 geometry는 원격 Linux GPU나 WSL2에 두는 구성이 현실적으로 보이지만, 직접 실행해 보지는 않았다. client는 --memory none 옵션으로 기억 없는 비교 실행을 지원하고, 재실행 시 유료 생성을 반복하지 않고 resume한다고 README에 적혀 있다. 실행마다 client/atas/film/report.py가 report.md를 쓴다. 여기에는 첫 리뷰 film-rejected 비율, 샷당 재생성, 상태 반영률(f=r=a=1), 스토리당 시간, 메모리 오버헤드, 단계별 GPU peak가 논문 값(Wan 3.0 full state: 0.368, 0.54, 0.674, 64.9분, 98초)과 나란히 표시된다. 따라서 Fig. 6과 Tab. H 계열의 process 지표는 실행 단위로 대조할 수 있다. 코드 주석은 이 값이 단일 스토리의 목표치가 아니라 참고용이라고 적는다. 반면 Tab. 1-3 수치 재현에 필요한 벤치마크 평가 코드는 없다. 생성은 외부 API에 의존하고, gpt-image-2 경로에는 결정적 seed가 없다는 코드 주석이 있다. 따라서 같은 입력으로도 결과가 달라질 수 있다. 공개 코드로 재현 가능한 범위는 Wan 블록의 파이프라인과 그 process 지표까지다. GitHub star 수는 API rate limit 때문에 이번에 확인하지 못했다(로컬 tier1 카드에는 280으로 기록됨).

📌 내 학습 포인트

  • '납품'과 '기억 반영'을 분리하는 admission gate를 논문 트렌드 시스템에 적용한다. ATAS는 film review(f)를 통과한 클립을 영화에 넣는다(수리 횟수를 다 쓰면 best-available을 넣는다). 반면 W에는 등록(r)과 상태 검사(a)까지 통과한 관측만 쓴다. 엄격도 실험(Tab. H, Wan 3.0 한 설정에서 3개 수준)에서 C-Top10은 반영률 90.0%일 때 0.696, 36.0%일 때 0.668, 기본값 67.4%일 때 0.719였다. 너무 느슨해도, 너무 엄격해도 손해였다. 단 저자는 기본 threshold가 보편적으로 최적이라는 뜻은 아니라고 적는다. 적용 방법은 이렇다. 주간 리포트 HTML에는 형식·문자 규칙 검사 같은 1차 검토(f에 해당)를 통과한 카드를 싣는다. 누적 트렌드 기억(_data/index.json이나 월간 종합 입력)에는 검증 subagent가 숫자 출처와 버전 URL까지 확인한 필드만 merge한다(r, a에 해당). 기각된 필드는 candidates 파일에 사유와 함께 남긴다. 매주 반영률과 기각 사유를 기록한다. 적정 반영률 구간은 논문이 정해 주지 않으므로, 몇 주치 기록을 보고 검증 프롬프트가 너무 느슨한지 엄격한지 판단한다. GPU가 필요 없고, Claude Code skill 안에서 subagent를 2단계로 호출하는 것만으로 구현된다.
  • 기억을 명시적 키로 조회하고, 신선도를 기록한다. ATAS 사건 기억은 (장면, 사건 ID, 시간 구간) 키로 바로 찾고, 저장소에서도 embedding 유사도 검색 코드는 찾지 못했다. 실험에서는 최근 프레임을 넘기는 frame history(C-Top10 0.598)보다 장면 좌표계에 정합한 scene+event 기억(0.703)이 나았다(Tab. 5). 다만 이 비교는 키 조회와 임베딩 검색의 비교가 아니다. 비구조 이력과 구조화·정합된 기억의 비교이므로, 키 조회 자체가 낫다는 근거는 아니다. 또 마지막 반영 이후 샷이 0개에서 5개 이상으로 늘면 C-Top10이 0.736에서 0.651로 떨어졌다(Tab. G). 저자는 이 저하의 원인을 구분하지 못한다고 적는다. 적용 방법은 이렇다. 파일 memory나 _data/analysis 카드를 '최근 N주를 통째로 붙여 넣기' 방식으로 쓰지 않는다. 대신 arxiv_id, 주차, topic_tag 키로 필요한 카드만 꺼내도록 skill 지시문에 조회 규칙을 적는다. 그리고 각 사실(star 수, 코드 공개 여부 등)에 last_verified 날짜를 붙여, 4주 이상 지난 항목은 재확인 대상으로 표시한다. 4주는 임의로 정한 출발값이다. 이번 분석에서는 API rate limit 때문에 star 수를 재확인하지 못했다. 이런 경우를 위해 확인하지 못한 값을 '미확인'으로 남기는 필드도 함께 둔다. 카드 수가 수백 개 수준이면 grep과 JSON 키 조회로 충분하고, 벡터 DB는 필요 없다.
  • 계획을 2단계 lazy compilation으로 나누고, 리뷰 루프에 상한을 둔다. Tab. 4 누적 ablation에서 재귀 컴파일 단계는 C-Top10(0.568 -> 0.684)과 Event score(0.508 -> 0.711)를 가장 크게 올렸다. 반면 ViStory average는 그 앞 단계인 장면·사건 기억 추가(0.478 -> 0.612)에서 더 크게 올랐다. 누적 추가 방식이라 기여 크기는 추가 순서에 따라 달라질 수 있다. 저장소 구현은 skeleton 단계에서 전체 샷 구조를 한 번 잡는다. 그다음 실행이 도달한 샷만, 현재 월드 상태 요약을 넣어 4-15초 요청으로 펼친다. 리뷰는 6개 항목 중 confidence 0.75 이상의 critical fail이 나올 때만 재생성하고(최대 2회), 그래도 실패하면 best-available을 납품한다. 적용 방법은 이렇다. 주간 리포트 skill을 두 단계로 나눈다. 먼저 skeleton(6편 목록, 섹션 구조, 주제 흐름)을 잡고, 그다음 섹션별로 확장하면서 직전까지 완성된 섹션 요약을 입력으로 넣는다. 검토 subagent에는 다음 규칙을 명시한다. 사실 오류나 규칙 위반 같은 명백한 critical만 fail로 판정하고, 문체 취향으로는 fail을 주지 않는다. 재작성은 최대 2회까지 하고, 그 뒤에는 최선본을 채택하고 사유를 기록한다. 이렇게 하면 무한 수정 루프와 토큰 낭비를 막을 수 있다. 단 ATAS에서 이 효과는 기억과 결합했을 때 컸다(Tab. 4에서 재귀 컴파일은 메모리 다음에 추가됨). 따라서 2단계 계획만으로 같은 이득을 기대하기보다, 앞의 키 기반 기억과 함께 적용하는 것이 근거에 맞다.

Claude 종합 코멘트

ATAS의 새로운 점은 다중 샷 영상 에이전트의 기억을 프롬프트나 최근 프레임이 아니라 '주소 지정 가능한 월드 상태'로 바꾼 데 있다. 장면 좌표계에 등록된 정적 point cloud와 (장면, 사건, 시간) 키로 찾는 동적 증거를 분리하고, 생성된 클립은 신뢰된 상태가 아니라 후보 관측으로 다룬다. 영화 납품(f)과 기억 반영(r, a)을 분리한 설계는 명확하고, 저장소 코드로도 확인된다. 기억은 목표 카메라로 렌더한 point-splat 영상을 Wan의 reference video로 주입하는 방식이다. 저장소는 MIT로 공개되어 있고, 실행마다 retry·반영률·시간 같은 process 지표를 논문 값과 나란히 보여 주는 report.md를 만든다. 근거의 강도는 중간이다. 메모리 ablation(Tab. 5, Wan 3.0 고정)은 C-Top10이 0.536 -> 0.719로 단조 증가함을 보여 준다. 구성요소 ablation(Tab. 4)은 같은 candidate budget과 retry policy를 캡션에 명시하므로 설득력이 있다. 단 Tab. 5 캡션에는 그 조건이 명시되지 않았다. 베이스라인과의 비교에서는 재시도·리뷰 예산의 동등성이 명시되지 않았다. Tab. 1의 ST-Bench 열은 Tab. B의 C-Top10과 같은 값이어서, Avg.가 cross-shot 지표 쪽에 무게가 실린 점도 감안해야 한다(분석자 대조). 사건 재포착과 공간 재방문은 요청 수, judge 모델, 분산이 없다. 인간평가는 평가자 수가 없다. 인터페이스에는 'grouped by framework'가 표시되는데, randomized order가 무엇을 무작위화했는지는 설명이 없다. 최강 베이스라인 ReCA(Tab. 1, 3, 인간평가 기준)가 같은 그룹의 연구라는 점도 감안해야 한다. 4개 생성기 중 MiniMax-H3와 HappyHorse 1.0은 인용도 코드도 없어 일반화 주장을 검증할 수 없다. 헤드라인 주장에는 다음 단서가 붙는다. 방법 상세

JEPA-Anything은 같은 그룹의 직전 연구다(arXiv 2609.20800, 2026-09-17, 제1저자 Taoyong Cui 포함 저자 7명 중복). JEPA를 확장해 잠재 목표를 상보적 요인으로 나누는 직교 예측 분해(OPF)를 쓰고, 요인별 예측기를 따로 학습한 뒤 완전한 잠재 상태로 다시 합성한다. 학습 목표는 요인 예측에 직교성·표현 정규화를 더한 형태다(2.2절). 본 논문은 이를 z_t=E(s_t,c), z_hat=F(z_t,a_t,c)와 점 예측 또는 분포를 내는 판독 R로 일반화하고 도메인마다 어댑터를 붙인다. 코드 수리의 W1은 Qwen2.5-Coder-3B-Instruct에 LoRA를 달아 후보-테스트 쌍마다 실행 결과 5개 클래스 확률을 낸다. 저장소 기준 GUI 월드모델은 같은 3B 인코더(LoRA rank 16), EMA 타깃(0.996), OPF(폭 256, 64x4 그룹), 판독 헤드로 이뤄지고 실제 다음 상태와 전문가 후속 궤적으로 학습된다.

행동 선택은 이렇게 돈다. 정책이 후보를 제안하면 각 후보에 결과 예측(지원 시 제한된 롤아웃)을 붙이고, 검증기가 유효성·효용 성분·출처·불확실성을 기록한다. 무효 후보를 빼고 R=sum(w*r)-lambda*U(불확실성 벌점은 선택)로 순위를 매겨 남은 피드백 예산에 맞는 후보만 실제로 실행하며, 실행된 후보만 예측-관측 쌍을 남긴다. 저장소 구현을 보면 코드 수리는 'P(전체 테스트 통과)+0.25x예측 통과 비율'로 수정안 4개와 현재 프로그램을 비교해 엄격히 높을 때만 교체하고, 실험실 계획은 4B 정책이 낸 후보 4개(탐욕 1개, 샘플 3개)를 월드모델이 예측 품질·개선·위험·불확실성으로 고른다. GUI는 정책 점수에 월드모델 값을 alpha 비율로 섞는데, 보고된 컨트롤러는 개발 집합에서 alpha=0이 골라져 월드모델을 아예 호출하지 않는다. 학습 데이터 선택은 증거를 E0(규칙 검사)·E1(모델 예측)·E2(시뮬레이터)·E3(외부 측정)로 표시하고, 상상 궤적은 유효성·최소 효용·불확실성 상한·허용 증거 조건을 모두 통과해야 학습에 들어간다(식 8). 다만 이 경로를 쓴 실험은 보고되지 않는다.

조건부 월드모델 적응은 현재 버전이 낸 예측(저장본 또는 재계산)만으로 오차·보정·드리프트·커버리지를 평가해 reliable, unreliable, insufficient 중 하나로 판정한다. 적응은 unreliable이고 적응 데이터가 충분하며 남은 예산이 예상 비용 이상일 때만 시도하고, 커버리지가 부족하면 insufficient로 보고 적응하지 않는다(식 10-12). 어느 실험도 이 판정 결과를 보고하지 않고, 저장소 코드에도 이 트리거는 없다. GUI는 제안마다 월드모델을 늘 재학습하고, 코드 수리는 4단계를 판정 없이 차례로 학습한다.

유지 단계에서 구성요소 검사는 후보 정책의 과제 효용·제약 또는 후보 예측기의 예측 품질을 현재 버전과 게이트 데이터로 비교하고, 쌍 검사는 조립된 새 쌍의 의사결정과 새 정책 후보에서의 예측기 적합성을 현재 쌍과 같은 조건에서 비교한다. 구성요소 검사에 실패하면 그 구성요소만, 쌍 검사에 실패하면 쌍 전체를 현재 버전으로 유지한다(식 13-18). 논문에는 수치 임계값이 없고, GUI 저장소 프로토콜에만 '개발 집합 50개에서 성공률 +0.04 이상이고 비용 1.2배 이하면 승격, 월드모델 혼합 제어는 +0.04 이상이고 비용 4배 이하일 때만 켜고 아니면 alpha=0으로 후퇴'라는 값이 있다. 코드상 GUI 승격은 새 정책·새 월드모델·선택 컨트롤러를 한 묶음으로 개발 집합에서 비교하는 단일 판정이며, 월드모델만 따로 보는 구성요소 검사는 없다(rsi.py).

개선 방식은 도메인마다 다르다. 코드 수리는 코더를 고정하고 W1만 학습 과제의 실행 기록으로 4단계 오프라인 학습(초기 32,920건 뒤 7,872, 41,088, 22,192건으로 순차 갱신)하며 평가 중 최적화 갱신은 없다(저장소). GUI는 ReasonFlux-Coder-7B LoRA를 성공 에피소드 행동만으로 SFT(신규 최대 256개 행동과 같은 수의 재생, 1 epoch)하고 월드모델을 재학습한 제안 2개를 차례로 승격했다. 실험실 계획의 4B 정책 갱신 방법은 논문에도 저장소에도 없다. 반응 최적화는 저장소 기준 같은 스크린의 다른 반응군 4,709행으로 판독기를 미리 맞춘 뒤 예측을 고정하고 기대 개선(EI)으로 다음 조건을 고른다. 면역학은 선행 연구의 Agent Genesis 워크플로 탐색을 재정리한 것이다.

  • 면역학 응용(3.5절, 6.1절, 6.2절): Agent Genesis가 과학 에이전트 워크플로를 탐색해 행동 조건부 면역 월드모델을 만들고, 분석 에이전트가 고정 파라미터로 시뮬레이션과 자기수정을 수행해 SIRP-alpha 억제와 IL-36-gamma 축 조절 병용을 전향적 가설로 지명했다. 이 논문에는 정량 평가가 없고 평가 설정은 Cui et al. 2026a(arXiv 2609.14709)로 넘기며, 가설은 실험 검증 전이다(5장).
  • 통계와 절제(6.2절): 구간 추정은 코드 수리의 고정 월드모델 대 정적 검증기 1건뿐이고, APPS/LCB는 3시드 평균(3,000/3,165회), LabHorizon은 200과제 평균, 화학은 실행별 누적 최고값을 보고한다. 전문을 ablat, variance, GPU, hour로 검색한 결과 별도 절제 절과 계산 비용 보고는 없었다. 코드 수리의 4개 비교가 예측 선택과 적응의 부분 절제 역할을 할 뿐, 유지 검사(구성요소·쌍)를 끈 비교는 어느 도메인에도 없다.

한계 · 비판

  • 정책과 월드모델이 한 과제 안에서 지속적으로 서로를 개선한다는 점을 입증하려면 합동 다회차 평가가 더 필요하다고 명시한다. 즉 저자도 지속적 상호 개선은 아직 입증되지 않았다고 본다(5장 Discussion). (저자 인정)
  • 실험들이 전체 프로토콜의 서로 다른 부분만 구현한다고 밝힌다. 코드 수리는 코더 고정 상태에서 예측 선택과 예측기 적응만, 실험실 계획은 정책 버전 추적만, GUI는 정책과 월드모델을 함께 갱신하며 완료율과 행동 지표를, 화학은 피드백 유도 탐색만, 면역학은 하류 분석에서 예측기를 고정한 채 다룬다(6장 서두, 표 4). (저자 인정)
  • 실험실 결과는 프로토콜 정합 계획만 평가하며, 신뢰할 만한 물리적 실행은 해당 장비와 워크플로에서 따로 평가해야 한다고 적는다(5장). (저자 인정)
  • 화학 결과는 보고된 실험 예산 아래 Suzuki-Miyaura 두 스크린에 한정되고, 면역학 응용의 치료 가설은 실험 검증을 기다린다고 명시한다(5장). (저자 인정)
  • 피드백이 선택된 후보에서만 나오므로 신뢰도 결론은 관측·커버된 후보 범위로 제한되고, 커버리지가 부족하면 신뢰 근거가 아니라 insufficient로 처리한다고 적는다(2.4절). GUI 1차 갱신 구성이 행동 수는 2.93으로 가장 적었지만 오제출 에피소드가 21개로 늘었다는 불리한 결과도 함께 보고한다(3.2절, 그림 4g). (저자 인정)
  • 저장소 문서도 한계를 스스로 밝힌다. 반응 최적화 README는 96.15%가 한 반응 맥락과 그 스크린 후보 풀에 한정된 평가라고 쓰고, 코드 수리 재현 문서는 전체 에폭 재학습을 패키징 중 돌리지 않았으며 기준 체크포인트가 엄격한 직교성·요인 독립성 검사를 통과하지 못했다고 적는다. GUI VERIFICATION.md도 공개 패키지로 전체 GPU 재학습은 하지 않았다고 쓴다. (저자 인정)
  • GUI 헤드라인은 월드모델이 행동을 고른 결과가 아니다. 저장소 RESULTS.md에 따르면 보고된 51% -> 79% -> 99%는 개발 집합에서 고른 alpha=0 컨트롤러(정책 순위만 사용)의 값이고, 코드상 alpha=0이면 월드모델을 호출하지 않으며 갱신용 경험 수집도 같은 컨트롤러로 했다(experiment.py, rsi.py). 신구 월드모델을 바꿔 끼운 교차 평가에서 이 컨트롤러의 변화는 0.00%p이고 상승은 성공 에피소드 SFT(+28%p, +20%p)에서 왔다. 같은 과제 템플릿의 다른 100개 인스턴스에서 규칙 컨트롤러가 100%(평균 2.87행동)를 내므로 과제 자체도 쉽다. OSWorld는 절대 성공률·기반 모델·과제 수·코드가 없어 검증할 수 없다. 공정하게 보면 월드모델 갱신 자체는 효과가 컸고(세 고정 OPF 모델의 순수 월드모델 제어가 630개 확인 집합에서 43.81% -> 97.04%, +53.23%p [50.26, 56.30]), 월드모델 혼합 여부를 개발 집합 이득과 비용으로 정하는 절차가 alpha=0을 고른 것은 유지 규칙이 작동한 사례로도 읽힌다. 개발 집합 50개로 고르고 두 제안을 시험 전에 고정한 설계도 시험 집합 선택 편향을 막는다. (추가 의문)
  • 화학의 96.15% 대 82.16%는 RSI 루프보다 사전 정보(보조 데이터로 학습해 고정한 예측)의 효과가 크다고 읽는 것이 타당하다. 저장소 evaluation.json상 이는 측정된 스크린의 오프라인 재생이고, 판독기는 같은 스크린의 다른 14개 반응군 4,709행으로 학습됐으며, 예측은 탐색 중 고정이고, 100회 모두 10번째 관측까지(96회는 정확히 10번째) 후보 풀 최댓값을 찾았다. 즉 대부분 모델이 고른 두 번째 조건이 최적이었다. 베이지안 최적화가 같은 보조 데이터를 받았는지는 논문과 저장소 어디에도 없고(reaction_optimization 폴더에 BO 코드도 없음) 정보량이 다른 비교일 수 있으며, JEPA 특징을 뺀 one-hot 조건 ExtraTrees 같은 단순 기준선과의 절제도 없다. 목표 반응군 321행을 학습과 보정 선택에서 뺀 점과 100회 재생을 봉인 기록으로 다시 계산해 검증한 점은 인정할 만하다. 재현 가능성

코드 공개, 단 도메인마다 범위가 다르다. GitHub Gen-Verse/RSI-Anything의 tasks/ 아래 code_repair(4단계 학습, 기록 입력 평가, 자산 검증), gui(MiniWoB++ 수집·학습·교차 평가·통계 재계산 전체 파이프라인), laboratory_planning(추론 전용), reaction_optimization(고정 예측표 기반 EI 추천과 검증 스크립트), immune_science_v2(README만, 'Coming soon')가 있다. 전체 파일 트리를 확인한 결과 OSWorld 코드, 베이지안 최적화 기준선 코드, 정적 검증기·Random-K 기준선 구현, GC 스크린 자산, 4B 계획 정책 학습 코드는 없다. 공용 CLI(rsi plan/run/report)는 code_repair와 gui만 지원하고, 코드 수리 실행기는 Linux namespace(runuser, unshare, nobody 계정)를 요구한다.가중치 Hugging Face Gen-Verse/RSI-Anything에 공개되지만 모델 저장소가 아니라 dataset 저장소다(논문 머리말 'Models' 링크가 이곳). 코드 수리 codecontests_final과 transfer_final(3B 인코더용 LoRA 약 29.5MB와 판독 헤드), GUI 정책 LoRA(약 40.4MB)와 월드모델 LoRA, 실험실 계획 월드모델 앙상블 3개(seed 1401-1403, 각 약 1.6MB, CPU 실행), ReactionT5-JEPA 체크포인트(약 807MB)가 있다. 실험실 계획 4B 정책 어댑터(P4)는 없고, 반응 체크포인트는 HF 설명상 C-N coupling용이며, 면역학은 MODEL_INDEX에서 'planned'다. 기반 모델 ReasonFlux-Coder-7B와 Qwen2.5-Coder-3B-Instruct는 고정 리비전으로 따로 내려받는다(GUI 전체 약 22GB).데이터 코드 수리 자산(평가용 약 64MB, 학습 보충 약 236MB; CodeContests 200과제 판정 자료, 기록된 후보·실행 기록, 학습 전이 기록, 월드모델 체크포인트 4개 포함), GUI 보고 통계 재계산용 엔드포인트 롤아웃 기록 7,980개, Suzuki 후보 321개 예측표(측정 수율 라벨 미포함), LabHorizon Level-1 사본(학습 3,000, 시험 200)이 공개된다. 재현 수준이 도메인별로 갈린다. GUI는 코호트 시드, 임계값, 교차 평가, 부트스트랩 구간과 엔드포인트 기록 7,980개가 공개돼 보고 통계를 CPU로 재계산할 수 있지만, 공개 패키지로 전체 GPU 재학습은 하지 않았다고 VERIFICATION.md가 밝힌다. 코드 수리는 기록 입력으로 600개 결정을 재현해 188/600(31.33%)을 얻는데 논문의 31.2%와 1건 다르고, 전체 에폭 재학습은 패키징 중 실행되지 않았으며, 기준 체크포인트가 엄격 직교성·요인 독립성 검사를 통과하지 못했다고 적혀 있다. 반응 최적화는 고정 예측표로 다음 조건 추천은 돌릴 수 있지만 측정 수율이 공개 자산에 없어 96.15% 재생 평가 자체는 다시 돌릴 수 없다. 기록 환경은 A800 80GB GPU(코드 수리 8장, GUI 3-6장)다. GPU 없이 CPU로 바로 돌릴 수 있는 것은 실험실 계획 후보 선택, Suzuki EI 추천, GUI 보고 통계 재계산과 브라우저 스모크 검사, HF 반응 수율 예측기 추론 정도이고, 코드 수리와 GUI 전체 파이프라인은 Linux와 CUDA GPU가 필요하며 Windows 네이티브 지원은 문서에 없다. OSWorld, 실험실 정책 학습, GC 스크린, 면역학은 공개 자산으로 재현할 수 없다.

📌 내 학습 포인트

  • 스킬·프롬프트 개정에 GUI 구현식 승격 게이트를 본떠 걸어라. 이 규칙은 논문 본문이 아니라 저장소 tasks/gui/docs/PROTOCOL.md에 있다. 개발 집합 50개에서 성공률이 +0.04 이상 오르고 비용이 현 버전의 1.2배 이하일 때만 새 버전을 승격하고, 탈락 후보도 교차 평가해 기록하며, 두 제안을 시험 집합을 열기 전에 고정했다. 실행: ai-paper-trends 스킬을 고칠 때마다 과거 주차 논문으로 고정 개발 묶음과 별도 보류 묶음을 정하고, 같은 논문을 구·신 버전으로 돌려 체크리스트 통과율과 세션 토큰을 짝지어 비교한 뒤 통과율이 오르고 토큰이 1.2배 이하일 때만 SKILL.md를 교체하며, 탈락안은 git 브랜치로 남겨라. 50개 중 0.04는 2건 차이라 잡음에 약하고, 스킬 전체를 수십 번 다시 돌리는 것은 비용이 크다. 그러니 스키마 검증·금지 문자 검사·수치 출처 대조처럼 싼 결정적 검사를 개발 묶음 판정에 먼저 쓰고, 차이가 애매하면 현 버전을 유지하라.
  • 개선 원인을 2x2 교차 평가로 분리하고, 자동화 루프보다 규칙 기준선을 먼저 재라. GUI 저장소(RESULTS.md)는 구·신 정책 x 구·신 월드모델 4조합을 같은 100개 인스턴스에서 돌려, 보고 컨트롤러(alpha=0)의 상승은 전부 정책 SFT(+28%p, +20%p)에서 왔고 월드모델 교체 효과는 0.00%p임을 보였다. 같은 표에서 월드모델 값으로 고르는 컨트롤러는 반대로 월드모델 교체가 이득을 냈다(1차 갱신에서 구 정책 고정 시 49% -> 95%). 어느 구성요소의 공인지는 그 구성요소를 실제로 쓰는 경로가 정한다는 뜻이다. 같은 과제 템플릿의 다른 100개 인스턴스에서 규칙 컨트롤러는 100%였다. 실행: 메인 프롬프트(정책 역할)와 검토 서브에이전트(검증기 역할)를 함께 바꿨다면 4조합을 같은 입력으로 돌려 이득의 출처를 확인하고, 이득이 없는 쪽은 되돌려라. 새 자동화 루프를 평가하기 전에는 grep·정규식·스키마 검사 같은 결정적 기준선 점수를 먼저 기록해 루프가 그 선을 넘는지부터 보라.
  • 예측과 관측을 분리하고 출처와 버전을 기록하라. 이 논문은 증거를 E0(규칙 검사)·E1(모델 예측)·E2(시뮬레이터)·E3(외부 측정)로 구분하고, 신뢰도 추정에는 현재 버전이 낸 예측만 쓰며 이전 버전 예측을 섞지 않는다(2.3-2.4절). 이번 분석에서도 초록의 96.15%가 측정 수율의 오프라인 재생이고 GUI 99%가 월드모델 값을 쓰지 않은 컨트롤러 값이라는 사실은 저장소 기록을 봐야 드러났다. 실행: 논문 정리 JSON의 각 수치에 출처 유형(초록/본문/그림 판독/저장소 기록/Claude 추론)과 그 수치를 만든 스킬 버전 필드를 붙이고, 스킬을 고친 뒤에는 고정 표본 논문을 새 버전으로 다시 돌려 출처 유형별 오류율을 비교하라. 검증 서브에이전트처럼 후보를 미리 거르는 단계를 더했다면 표 2처럼 항목당 실제 검증 호출 수를 성공률과 함께 기록해 이득이 검증을 더 쓴 결과인지 가려라. W1 같은 학습형 예측기(3B 인코더와 LoRA, 원 실험은 A800 80GB)를 로컬에서 만드는 일은 GPU 사양을 확인한 뒤로 미루고, 먼저 규칙 검사 결과와 Claude 판정을 구분해 쌓는 기록부터 시작하라.
