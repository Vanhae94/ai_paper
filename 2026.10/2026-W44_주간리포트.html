정답 검증기 없이 대조적 제안-시험 실행-조합으로 하니스를 고치고, 그 경험을 다음 과제용 개선 하니스에 쌓는다.

LLM 에이전트의 능력은 모델뿐 아니라 실행 하니스에도 달려 있고, 재귀적 자기개선(RSI)은 이 하니스를 자동으로 진화시키는 유망한 방법이다. 그러나 열린 세계의 과제는 하니스 설계 단계에서 보지 못한 새 과제라 온라인 수정을 이끌 정답 검증기가 없고, RSI 과정 자체도 과제마다 특화돼 새 상황으로 일반화되지 않는다.

Harness²는 서로 연결된 두 단계의 재귀로 이 문제를 다루는 플러그인형 프레임워크다. 과제 수준 재귀(task-level recursion)는 대조적 Propose-Probe-Compose 단계로 정답 검증기 없이 현재 과제의 하니스 수정을 이끌고, 병렬 또는 순차 재귀로 더 늘릴 수 있다. 하니스 수준 재귀(harnessing-level recursion)는 이런 수정에서 경험을 뽑아 지속 개선 하니스(continual improvement harness)를 갱신해, 에이전트가 이후 과제에 더 잘 적응하게 한다.

  • 정답 검증기가 없는 열린 세계 과제를 위한 2단계 재귀 하니스 개선 프레임워크(과제 수준·하니스 수준)
  • 3개 전문 벤치마크와 4개 모델-하니스 구성에서 한 번의 단계(k=1)만으로 GLM-5와 Gemini 3.5 Flash를 기본 하니스보다 일관되게 개선했다고 보고. 단 k=1에도 과제당 실행 4회와 Claude Opus 4.8 편집 세션 3회가 들어간다(W43 심층 분석)
  • WorkBuddy-Bench 최대 +11.5점, JobBench 최대 +4.5점, LAB 최대 +11.8%p를 보고했고, 과제 수준 재귀 예산을 늘리면 추가로 개선된다고 밝힘
  • Google Research 코드 공개(Apache-2.0, GitHub 약 2.0만 스타)와 프로젝트 페이지

방법 상세

하니스 편집(harness edit)은 고정된 모델을 둘러싼 8개 파일 구성요소의 diff다(Table 5). AHE의 파일 분해에 1개를 더해 다음 8개로 이뤄진다. - 매 호출 상시 주입: systemprompt.md, guardrails.md, LongTermMEMORY.md, tool_guidance.md - 호출 시 로드: skills/<n>/SKILL.md - bash로 실행: scripts/*.py - 별도 컨텍스트: sub_agents/<n>/AGENT.md - 도구 루프 안의 훅: plugin/*.ts 즉 프롬프트·도구·제어 흐름·메모리를 모두 포함한다. Codex 기반에서는 상시 텍스트가 AGENTS.md 하나로 합쳐지고, 훅은 Claude Code 훅 스키마를 따르는 .codex/hooks.json으로 바뀐다(저장소 prompts.py).

Propose: 먼저 현재 하니스로 참조 실행을 돌린다. 편집기(Claude Opus 4.8, OpenCode 위 에이전트 세션)는 과제·하니스·궤적·산출물·라이브러리를 파일로 받아 후보 2개를 만든다. INV 후보는 도구 오류·반복 작업·완료 확인 같은 도메인 무관 절차 결함을 맡고, DOM 후보는 산출물 구조·결정 규칙 같은 실무 지식을 맡는다. 프롬프트의 지시는 네 가지다. 모든 편집은 궤적의 특정 순간에 근거해야 한다. 우선순위는 실행 간 불일치, 반복 실패, 잠재 위험 순이다. 상시 텍스트보다 skill·script·plugin을 먼저 쓴다. 기본 실행이 발견한 이 작업공간의 검증된 사실(파일 간 키 매핑 등)은 하니스에 직접 적는다.

Probe: 각 후보를 같은 과제·모델·환경에서 1회 실행해 참조 실행과 궤적·산출물을 비교한다. 이때 쓰는 신호는 정답이 아니라 행동 대조(behavioral contrast)이고, 이를 판단하는 것은 실행 기록을 읽는 LLM 편집기다. 저자도 이 대조가 정답을 검증하지 않는다고 적는다(2.2.1). 구성기 프롬프트는 후보 간 일치를 독립 증거가 아니라 지지로만 보라고 하고, 불일치가 나오면 투표하지 말고 궤적을 다시 보라고 지시한다. 채점 결과는 guard가 컨텍스트에 들어오지 못하게 막는다.

Compose: 구성기는 참조·후보·diff·실행 기록을 보고 병합, 한 후보 채택, 수정, KEEP_BASE 중 하나를 고른다. 결정은 kept|revised|dropped -> 편집 -> 근거 형식으로 기록한다. 기본 실행에서 반복된 실패는 강한 근거로, 후보의 1회 실행 결과는 약한 근거로 본다. 산출물을 못 낸 실행과 엮인 편집은 위험(UNSAFE)으로 표시한다. 구성된 하니스를 다시 실행한 결과가 제출물이 된다.

예산 k: 병렬 재귀는 기본 실행 k개, INV·DOM 후보 각 k개, 전체 풀을 보는 독립 구성 k개를 만든다. 폭을 넓히는 방식이며 집단 갱신은 1회다. 순차 재귀는 PPC를 k번 이어 이전 체크포인트와 누적 증거를 넘긴다. 깊이를 늘리는 방식이다. 두 방식 모두 과제당 실행 4k회와 개선 세션 3k회를 쓴다(저장소 ledger.py). k>1이면 선택기가 익명화된 최종 산출물 k개 중 하나를 고르고, k=1은 선택 없이 실행 4회와 세션 3회다.

하니스 수준 재귀: 제출 후 Reflector가 전체 기록을 읽고, 변경된 구성요소마다 편집 효과를 helped/hurt/no observed effect/confounded로 판정한다. 그다음 cue·lesson·evidence·confidence로 된 교훈을 1개 쓰거나 NO_ENTRY를 낸다. 도메인별 라이브러리에는 채택된 하니스의 전체 트리, EXPERIENCE.md, INDEX.md가 쌓인다. 코드에서는 교훈이 없으면 항목 자체를 추가하지 않는다(library.py has_experience). 다음 과제는 다시 H0에서 시작하고, 편집기는 라이브러리 구성요소를 복사해 수정할 수 있지만 이전 과제의 사실은 다시 검증해야 한다. 모델 가중치와 단계 프롬프트는 고정되고 라이브러리만 바뀐다.

실험 셋업

  • 구성은 4개로, 실행기(executor) 2개(Gemini 3.5 Flash, GLM-5, 가중치 고정)와 기본 하니스 2개(OpenCode, Codex CLI)의 조합이다. 편집기와 선택기는 Claude Opus 4.8이고 OpenCode 안에서 high reasoning effort로 돈다(D.2). 메인 표(Table 1, 2)의 Harness²는 k=1이다. '+ Recursion' 행은 병렬 재귀 k=5에서 평균이 얼마나 바뀌었는지를 적은 것이다(3.1).
  • 반복 실행: 독립 스트림 3회의 평균과 SD를 보고하며, 스트림마다 과제 순서를 섞는다. 라이브러리는 벤치마크 도메인마다 빈 상태에서 시작해 과제가 끝날 때마다 갱신된다(3.1, 부록 B, D.2). 저장소 문서에 따르면 --seed는 과제 순서만 섞고 모델 샘플링은 통제하지 않는다(docs/EXPERIMENTS.md). 본문과 부록에서 'significan', 'p-value', 'confidence interval'을 검색했지만 유의성 검정은 없었다.
  • 실행 상한: 롤아웃 1회는 200 model turns, 3,600초까지다. WorkBuddy는 컨테이너 타임아웃을 기본값의 2배로 쓴다. 롤아웃은 다른 과제의 기억 없이 돈다(D.1). 편집 세션 상한은 논문에서 확인되지 않는다. 코드 기본값은 steps=120, timeout=3600이다(core/spec.py ChannelSpec).
  • 베이스라인(부록 C)은 모두 같은 실행기, 초기 하니스, 테스트 스트림, 심사기를 쓰고, 수정과 반성에는 Opus 4.8을 쓴다. 비교 대상은 다섯 가지다. - Base harness. - ReasoningBank: gemini-embedding-001로 같은 도메인에서 가장 비슷한 과거 과제의 기억 항목을 최대 3개 꺼내 쓰고, 정답 없는 self-judge를 둔다. - Meta-Harness: 오프라인 방식이다. WB/JB에서는 train half로 10 iterations x 2 candidates x 3 replicates, margin 0.01을 쓰고, LAB에서는 24-task dev set을 쓴다. - Harness Scaling: 과제별로 수정 루프를 돌리고 상태를 다음 과제로 넘기지 않는다. k=1에서는 기본 롤아웃 1회, 수정 세션 1회, 배포 롤아웃 1회다. - Best-of-k: 기본 하니스를 k회 실행하고 같은 선택기로 하나를 고르며, 그림 5에만 나온다.
  • 비용 측정: 그림 6은 Gemini/OpenCode 구성의 JobBench와 WB에서 최종 제출 전까지 쓴 전체 토큰(실행 + 개선)을 로그축으로 그린다. ReasoningBank, Harness Scaling, Harness²는 k=1과 k=5 두 점씩, Meta-Harness는 한 점이 표시된다. 본문에는 방법별 토큰 절대값, 과제당 시간, USD가 없다. 'hour', 'minute', 'latency', 'cost', 'USD'로 검색했을 때 찾은 것은 지연에 대한 정성 문장뿐이다. 코드 ledger는 세션별 usd를 기록하지만 논문은 이 값을 보고하지 않는다. 모델 호출 수는 저장소 기준으로 과제당 롤아웃 4k회와 에이전트 개선 세션 3k회이고, 여기에 선택 1회(k>1일 때)와 반성 1회가 더해진다. 세션 안의 턴 수는 보고되지 않는다.
  • Ablation(Table 3)은 Gemini 3.5 Flash/OpenCode, k=1 조건에서 WB 3개 도메인 평균과 JobBench로 세 가지를 비교한다. - w/o library - w/o scoping: INV/DOM 대신 일반 편집기 2개를 쓴다. - w/o composition: 구성 없이 근거가 더 나은 후보 하나만 반환한다. 구성요소 제거(Table 6)는 k=5로 개선한 하니스에서 prompt*, skills, scripts를 빼고, 개선 과정을 다시 돌리지 않은 채 재평가한다.
  • 추가 분석은 다음과 같다. - 그림 5: k=1..5에서 병렬 재귀와 순차 재귀를 ReasoningBank, Harness Scaling, Best-of-k와 비교한다. WB-code와 WB-office만 다루며, 수치로 보아 Gemini/OpenCode 구성이다. - 그림 7: 실행 없는 직접 편집에서 라이브러리 없음, k=1 라이브러리, k=5 라이브러리를 비교하고, JB -> WB 라이브러리 전이도 다룬다. - 그림 8: 같은 모델을 실행기이자 편집기로 쓴 5개 모델 결과다(k=2). - 그림 11: leave-one-out 재실행. - 그림 12: 다른 실행기로의 전이. - 그림 13: 상용 하니스(CodeBuddy, OpenCode, Codex, Claude Code) 비교. - Table 7: 도구 호출 수와 오류율. - 그림 14: 실패 사례 9건.
  • 누출 방지(D.2, 부록 H, 저장소 core/context.py): 채점 판정, rubric, 점수가 든 작업 디렉터리는 넘기지 않도록 guard가 막는다. 모든 프롬프트에는 rubric이 없다는 문장이 들어간다. WB-code subset에서만 편집기에게 산출물 파일 본문을 숨기고 파일 목록만 보여 준다(workbuddy.py proposer_deliverables). 편집기에게 주는 안내 문자열은 이 경로로 예전에 채점기의 pass rate가 노출된 적이 있다고 적고 있다. 릴리스에서 실행기의 네트워크 접근은 제한되지 않는다. 논문 실험의 네트워크 정책은 본문과 부록에서 'network', 'internet', 'egress'로 검색했지만 기술이 없었다.

데이터셋

  • WorkBuddy-Bench (Tencent, Team et al. 2026, arXiv 2607.20911) — Code 80, Web 70, Office 50 과제를 범주별로 반으로 나누고, 테스트 절반 40/35/25 = 100과제만 보고한다. 채점은 벤치마크의 복합 verifier로, 결정론적 검사(숨겨진 테스트, 파일·구조 검사)에 LLM/VLM 심사 항목을 섞는다. 심사 모델은 Gemini 3.5 Flash이고 과제 점수는 통과한 검사의 비율이다. 저자가 만든 벤치마크가 아니며, 업스트림 라이선스는 EU 지역 제한이 있는 Tencent 자체 라이선스다(부록 B, 저장소 BENCHMARKS.md). Niklaus(2026)의 분할을 따라 100과제 held-out test만 보고하고, 24과제 dev set은 Meta-Harness 탐색에만 쓴다. 실행 가능한 검사 없이 Claude Sonnet 4.6이 과제별 기준으로 LLM 심사하고, 지표는 기준별 통과율인 Partial이다. 저자가 만든 벤치마크가 아니다(부록 B). (법률 업무: 24개 실무 분야, 4개 작업 유형(analyse, draft, review, research))

한계 · 비판

  • 재귀 정제 비용(부록 F 'Cost of recursive refinement'): 후보를 제안·탐침·구성하려면 실행과 편집 세션이 추가로 필요하고, 재귀 예산을 늘리면 추론 비용도 커진다. 병렬 세션으로 지연은 줄일 수 있지만 계산량 자체는 줄지 않는다. 실험은 제한된 예산 범위에서 trade-off를 보여 줄 뿐이고, 보편적인 최적 배분을 확립하지는 않았다고 저자가 적는다. (저자 인정)
  • 실행 기반 피드백의 한계(부록 F 'Execution-based feedback', 2.2.1): 정답 감독이 없어서 정제는 행동 대조와 모델 판단에 기댄다. 이 신호는 실행 간 변동성과 모델들이 공유하는 편향에 민감하다. 또 채택한 변경이 옳다는 것도, 다른 과제로 전이된다는 것도 보장하지 않는다. (저자 인정)
  • Leave-one-out 재실행(E.2, 그림 11)의 WB 77.5 -> 79.4, JB 36.0 -> 37.7에 대해 저자는 두 가지 단서를 단다. 재실행은 이후 과제의 항목까지 볼 수 있으므로 온라인 이득의 추정치가 아니라 오프라인 재사용 분석이다. 반복 실행 자체가 차이에 기여했을 수도 있다. (저자 인정)
  • 구성요소 제거(E.1, Table 6)에서 skills -5.3, scripts -3.7, prompt* -1.5가 나왔다. 저자는 이 결과가 여러 구성요소 그룹의 기여를 지지할 뿐 효과가 합산된다는 근거는 아니라고 적는다. 상용 하니스 비교(E.5, 그림 13)의 +4.6/+5.8/+4.9에도 정제가 추가 test-time compute를 쓴다는 단서를 붙인다. (저자 인정)
  • 실패 분석(E.6, 그림 14): 저자는 참조 실행보다 점수가 낮아진 9건을 세 유형으로 나눈다. 첫째, 선택기가 약한 후보를 고른 경우다(WB-code에서 95점 후보 대신 55점 후보, LAB에서 coverage가 좁아져 54 -> 26). 둘째, 잘못된 전제가 모든 후보로 퍼진 경우로 2-11점을 잃었다. 셋째, 결과 변동, 심사기 판정 누락, 평가 기준과 무관한 편집 때문에 원인을 가리기 어려운 경우다. 저자는 coverage와 정밀도의 균형을 맞춘 선택, 공유된 가정을 흔드는 probe, 편집 효과와 결과 변동을 구분하기 위한 반복 실행이 필요하다고 적는다. 다른 실행기로의 전이(E.3)에서도 이득이 실행기와 도메인에 따라 크게 다르다고 밝힌다. (저자 인정)
  • 릴리스 단서와 향후 과제(README 'Web access', docs/EXPERIMENTS.md, 부록 G): 실행기 네트워크는 제한되지 않고 Codex는 sandbox를 끈 채 돈다. 릴리스 검증 실행에서는 Codex 롤아웃이 지시 없이 JobBench rubric을 내려받았다고 문서에 적혀 있다. 부록 G는 라이브러리가 단순한 색인 구조라 커지면 통합·갱신이 필요하다고 쓰고, 재귀 형태와 예산을 미리 고정한다는 점도 앞으로 풀 과제로 든다. (저자 인정)
  • test-time compute와 하니스 개선 효과가 섞여 있다. k=1이어도 같은 과제를 기본 실행 1회와 후보 실행 2회로 미리 돌린 뒤 최종 실행 결과를 제출한다(롤아웃 4회, Opus 4.8 세션 3회). 편집기 프롬프트는 기본 실행에서 알아낸 작업공간 사실을 하니스에 적으라고 요구한다. 그런데 메인 표의 Base는 실행 1회이고, 표 안의 test-time 대조군인 Harness Scaling k=1도 롤아웃 2회와 세션 1회로 Harness²보다 적게 쓴다. 계산량 비교 근거는 두 가지다. 첫째, 그림 6(Gemini/OpenCode, JB·WB)은 실행과 개선을 모두 센 토큰 기준 비교다. 저자는 Harness² k=1과 k=5가 모두 경험적 Pareto frontier 위에 있다고 적는다. 그림을 읽으면 k=1은 토큰 규모가 비슷하거나 더 큰 ReasoningBank k=5, Harness Scaling k=5보다 이득이 크고, Meta-Harness보다 훨씬 적은 토큰으로 이득이 더 크다. 이는 저자에게 유리한 근거다. 둘째, 그림 5의 Best-of-k는 같은 k에서 롤아웃을 k회만 쓰므로 계산량을 맞춘 대조가 아니다. 저자는 k=2의 두 재귀 형태가 두 도메인 모두에서 k=5의 모든 베이스라인보다 높다고 적는다(4장, Best-of-5 포함). 다만 롤아웃 수를 4회로 맞추면 WB-code에서 Best-of-4(판독 약 77.0)가 Harness² k=1(76.5)과 비슷하거나 약간 높다. WB-office에서는 Best-of-4(약 78.3)가 k=1(79.5)보다 낮다. Best-of-k 막대는 Code에서 k=4에서 k=5로 가며 약 77.0 -> 74.9로 떨어질 만큼 자체 변동도 크다. k=5 병렬(80.8/83.4)은 Best-of-5(판독 약 75/80)보다 분명히 높다. LAB과 GLM-5·Codex 구성에서는 계산량 비교가 없다. (추가 의문)
  • 심사기가 개선기나 실행기와 같은 계열인 경우가 많다. JobBench 심사기 Claude Opus 4.8은 편집기·구성기·선택기와 같은 모델이다. LAB 심사기 Claude Sonnet 4.6도 편집기와 같은 Claude 계열이다. WB 심사기 Gemini 3.5 Flash는 Gemini 구성의 실행기와 같은 모델이다. 예외는 GLM-5 실행기의 WB 결과다. 이 구성에서는 심사기(Gemini)가 실행기(GLM-5)와도 편집기(Opus)와도 계열이 다르고, WB 채점에는 숨겨진 테스트 같은 결정론적 검사도 섞여 있다(부록 B). 그런데도 이 구성의 향상이 가장 크다(+11.5/+10.9). 따라서 같은 계열 심사기 문제는 JB·LAB 전체와 Gemini 구성의 WB에 해당한다. 저장소의 JobBench 선택기 블록(harness2/benchmarks/jobbench.py)에는 'material beyond what was asked costs nothing here'라는 coverage 우선 지시가 있다. 다만 선택은 k>1에서만 실행되므로, 이 지시가 영향을 줄 수 있는 것은 + Recursion(k=5) 같은 결과이고 k=1 메인 수치는 아니다. 논문은 이 겹침을 따로 분석하지 않으며, 이것만으로 편향을 입증할 수는 없다. (추가 의문)
  • 통계 근거가 약하다. 독립 스트림은 3개이고, seed는 과제 순서만 섞는다(docs/EXPERIMENTS.md). 유의성 검정은 없다. Gemini/Codex JB의 +1.4(SD 2.6/3.5)와 GLM-5/Codex JB의 +1.2(SD 2.3/0.2)는 SD 안에 든다. Gemini/OpenCode에서 Meta-Harness와의 차이도 WB 1.1, JB 0.2에 그친다. Ablation(Table 3)과 하니스 수준 재귀 분석(그림 7, 11)은 모두 Gemini 3.5 Flash/OpenCode 단일 구성이고 SD도 없다. 따라서 '일관된 향상'은 평균 기준으로만 성립한다. (추가 의문)

(추가 의문)
  • 메인 결과의 편집기는 실행기보다 강한 Opus 4.8이다. 따라서 이득의 일부는 강한 모델의 지식이 하니스 파일로 증류된 결과일 수 있다. 그런데 같은 모델이 스스로 편집한 그림 8(k=2)의 근거는 엇갈린다. Gemini 3.5 Flash는 JB +0.9로 Opus가 편집한 k=1의 +4.5보다 작지만, WB에서는 +5.9로 +5.1보다 크고 LAB에서는 +1.7 대 +2.0이다. GLM-5는 WB +4.1로 Opus 편집 +11.5보다 훨씬 작지만 LAB에서는 +13.7로 +11.8보다 크다. k가 2와 1로 달라 직접 비교도 아니다. 이 밖에 논문과 코드가 어긋나는 점이 세 가지 있다. 첫째, 선택 풀이 논문 프롬프트에서는 수정하지 않은 실행을 포함하지만 selection.py에서는 최종 k개뿐이다. 둘째, LAB 과제 수가 논문 1,251개, 문서 1,143개로 다르다. 셋째, 논문의 정확한 test split 파일을 저장소에서 찾지 못했다(scripts/split_tasks.py만 있고, 문서는 생성된 분할이 release asset이 아니라고 밝힌다). 그래서 수치를 정확히 재현하려면 split을 다시 만들어야 한다. 코드 공개. https://github.com/google-research/harness2 main 브랜치(확인한 커밋 1cfe254)이고, 버전은 pyproject 기준 v0.1.0이다. GitHub Releases 페이지에는 릴리스가 없다(2026-10-19 확인). LAB은 harveyai/harvey-labs다.라이선스 Apache License 2.0 (LICENSE 파일에서 직접 확인). 논문 HTML의 라이선스 표기는 CC BY 4.0이다. 벤치마크 데이터는 각 업스트림 라이선스를 따른다.

Linux와 Python 3.12-3.13만 지원한다(README 'Use Linux, Python 3.12', pyproject 'Operating System :: POSIX'). 그래서 Windows에서는 WSL2 같은 Linux 환경이 필요할 것으로 추정한다. WorkBuddy-Bench는 Docker Engine도 요구한다(docs/BENCHMARKS.md, docs/SETUP.md). 실행기 하니스는 OpenCode와 Codex만 지원하고, Claude Code는 실행기로 지원하지 않는다. 편집기 채널은 opencode(기본)와 claude_cli 두 가지다. claude_cli는 'claude --dangerously-skip-permissions'를 Vertex를 거쳐 부르고 ANTHROPIC_API_KEY는 환경에서 지운다(core/proposer.py). 실행기 네트워크가 제한되지 않으므로, 문서(docs/EXPERIMENTS.md 'Web access')는 평가 전에 huggingface.co, github.com 등으로 나가는 egress를 도구 설정이 아니라 네트워크 수준에서 차단하라고 권고한다. 비용 기록은 코드 ledger에 남지만, 논문에는 USD와 시간이 보고되지 않는다.

  • 스킬이나 프롬프트를 자동으로 고칠 때는 두 가지를 지킨다. 편집에 실행 근거나 축적된 경험을 붙이고, 채점 기준이 새지 않게 막는다. 근거: 실행·후보·라이브러리 없이 직접 편집하면 WB-code가 73.4 -> 63.2, Web이 69.9 -> 65.0으로 떨어졌다(그림 7). 다만 같은 조건에서 Office는 74.0 -> 77.1로 올랐다. 실행 없이 편집해도 k=5 라이브러리를 주면 세 도메인 모두 기본보다 높았다(그림 7 막대 수치). 그러니 '실행 없는 편집은 항상 해롭다'가 아니라 '근거도 경험도 없는 편집은 위험할 수 있다'로 읽는 것이 정확하다. 누출 쪽으로는, 릴리스 검증에서 Codex 롤아웃이 지시 없이 JobBench rubric을 내려받은 사례가 있다(docs/EXPERIMENTS.md). Claude Code에서는 두 가지를 설정할 수 있다. 첫째, settings.json permissions의 deny에 정답·평가 파일 경로의 Read와 huggingface.co·github.com 대상 WebFetch를 넣는다. 둘째, PreToolUse hook으로 평가용 디렉터리 접근과 Bash의 curl·wget 호출을 차단한다. 다만 WebFetch deny만으로는 Bash를 통한 우회를 막지 못한다. 저장소 문서도 도구 설정보다 네트워크 수준(egress 방화벽, DNS 정책)에서 막으라고 권한다. 심사 모델은 편집 모델과 다른 회사 계열로 두는 편이 낫다. 논문에서는 JobBench(Opus 4.8)와 LAB(Sonnet 4.6) 심사기가 모두 편집기와 같은 Claude 계열이다. 적용 조건: hook과 permissions는 Windows에서도 동작하지만, 완전한 네트워크 차단에는 Windows 방화벽 규칙 같은 별도 설정이 필요할 수 있다.
  • 파일 메모리에 교훈을 쌓을 때 Reflector 형식을 빌려 쓸 수 있다. 먼저 편집 효과를 helped/hurt/no observed effect/confounded로 판정하게 한다. 근거가 있을 때만 cue·lesson·evidence·confidence 4필드로 된 항목을 1개 쓰게 하고, 근거가 없으면 NO_ENTRY를 내게 해서 메모리가 부풀지 않게 한다(core/prompts.py, library.py). 다음 작업에서는 이전 항목을 '재검증이 필요한 힌트'로만 주입한다. 근거: 라이브러리를 빼면 -3.1/-1.8이다(Table 3, 실행 포함 k=1). 실행 없이 직접 편집하는 조건(그림 7 왼쪽)에서 k=5 라이브러리는 기본 대비 +0.9/+4.4/+5.1을 준다. k=1 라이브러리는 저자 표현으로 기본 수준을 회복하는 정도다(그림 막대 수치 Code 73.8, Web 72.6, Office 77.5). 또 라인의 절반 이상을 라이브러리 항목에서 가져온 파일은 2-10%뿐이다(그림 10). 그러니 통째로 복사하기보다 참고해서 고쳐 쓰는 방식이 맞다. 적용 조건: 대규모 계산 없이 텍스트 파일과 서브에이전트 1회 호출로 구현할 수 있다.

새로운 점은 세 가지다. 첫째, 하니스 편집을 고를 때 정답 검증기 대신 행동 대조를 쓴다. 같은 과제의 기본 실행과, 범위가 다른 후보 2개의 실행을 비교한다. 둘째, 제안을 INV와 DOM으로 범위를 나눠 받고, 구성기가 병합, 채택, 수정, KEEP_BASE 중 하나로 정리한다. 셋째, 채택된 하니스 트리와 근거 있는 교훈만 도메인 라이브러리에 쌓아 다음 과제로 넘긴다. 하니스를 8개 파일 구성요소로 다루는 방식은 Claude Code의 skills, subagents, hooks, 상시 메모리 구조와 거의 그대로 대응해서 실무에 옮기기 쉽다.

증거는 평균 기준으로 일관되지만 강하지 않다. 독립 스트림은 3개이고 유의성 검정이 없으며, 일부 JB 이득은 SD 안에 든다. Ablation과 라이브러리 분석은 단일 구성에서만 했다. LAB의 일부 구성에서는 Meta-Harness나 ReasoningBank와 비슷하거나 더 낮다.

제출물은 같은 과제를 미리 3회 돌려 본 뒤 다시 실행한 결과다. 그래서 이득에는 재시도에 따른 test-time compute 효과와 더 강한 Opus 4.8 편집기의 기여가 섞여 있을 수 있다. 계산량 측면의 근거는 대체로 저자에게 유리하지만 완전하지 않다. 토큰 기준 비교(그림 6, Gemini/OpenCode의 JB·WB)에서 Harness²의 두 점은 Pareto frontier 위에 있고, k=1이 ReasoningBank k=5, Harness Scaling k=5, Meta-Harness보다 효율적이다. 저자는 k=2가 k=5의 모든 베이스라인(Best-of-5 포함)보다 높다고도 적는다. 반면 롤아웃 수를 맞춘 Best-of-4와 비교하면 WB-code에서 k=1의 뚜렷한 우위가 보이지 않는다(그림 5 판독). LAB과 GLM-5·Codex 구성에는 이런 비교가 없다. 같은 모델이 스스로 편집한 결과(그림 8)도 벤치마크마다 Opus 편집보다 크거나 작아서, 증류 효과의 크기는 판단하기 어렵다.

'검증기 없이'라는 주장은 파이프라인 안에 rubric과 점수를 들이지 않는다는 뜻으로는 대체로 맞다. 다만 심사기가 개선기나 실행기와 같은 계열인 경우가 많다(JB Opus 4.8, LAB Sonnet 4.6, Gemini 구성의 WB Gemini 3.5 Flash). 예외인 GLM-5 구성의 WB는 심사기가 실행기·편집기와 계열이 다르고 결정론적 검사도 섞여 있는데, 여기서 향상이 가장 크다(+11.5/+10.9). 이는 같은 계열 심사기의 편향만으로 결과를 설명하기 어렵다는 근거가 된다. 그 밖에 JobBench 선택 프롬프트에 coverage 우선 지시가 있고(k>1에만 해당), 논문 실험의 네트워크 정책은 보고되지 않았다. 그래서 신호가 완전히 독립적이라고 보기는 어렵다.

인용할 때는 이렇게 적는 것이 정확하다. 'Opus 4.8 편집기를 쓰고 과제당 롤아웃 4k회를 들이는 test-time 하니스 정제로, 고정 실행기 2종과 하니스 2종 조합에서 기본 하니스 대비 WB +3.0~11.5점, JB +1.2~4.5점, LAB +2.0~11.8%p(k=1)를 보고함.' 토큰 비용이 Base 대비 k=1에서 약 6-8배, k=5에서 약 30-40배(그림 6 판독)라는 점도 함께 밝혀야 한다.

방법 상세

TradingAgents는 실제 트레이딩 회사를 모사한 LLM 멀티에이전트 프레임워크로, 7개 역할을 5개 팀으로 조직한다. (1) 애널리스트 팀(Analyst Team)은 펀더멘털(fundamental)·감성(sentiment)·뉴스(news)·기술적(technical) 분석가가 각자 구조화 리포트를 생성한다. (2) 리서처 팀(Researcher Team)은 강세(bull)/약세(bear) 연구자가 자연어 토론(natural language debate)을 n라운드 진행하고, 진행자(facilitator) 에이전트가 토론 이력을 검토해 우세 관점을 선택·기록한다(원문 표현 'facilitator ... selects the prevailing perspective'). (3) 트레이더(Trader)가 이를 종합해 매매 신호를 도출한다. (4) 리스크 관리 팀(Risk Management Team)은 공격적(aggressive)·중립(neutral)·보수(conservative) 세 관점이 토론해 노출을 조정한다. (5) 펀드 매니저(Fund Manager)가 최종 승인·집행한다. 에이전트 간 통신은 '구조화 리포트'를 1차 채널로, '자연어 대화'를 2차 채널로 쓰는 하이브리드 방식이며, 공유 글로벌 에이전트 상태(global agent state)와 메모리로 과거 결정 맥락을 유지한다(명시적 reflection 모듈 여부는 본문 확인 필요). 모델은 2계층(two-tier) 전략으로, 추론 집약 노드(분석·연구·트레이딩)에는 심층사고(deep-thinking) o1-preview를, 요약·데이터 변환·검색 등에는 신속사고(quick-thinking) gpt-4o/gpt-4o-mini를 배정하고, 전 에이전트는 ReAct 프롬프팅 프레임워크를 따른다(논문 명시). LangGraph는 논문 본문이 아니라 공식 오픈소스 레포/문서에서 구현 스택으로 명시된다('built with LangGraph').

방법 상세

Kronos는 금융 K-line(캔들스틱) 데이터를 위한 2단계 파운데이션 모델로, 연속형 시장 정보를 이산 토큰으로 바꾸는 전용 토크나이저와 그 위에 얹은 자기회귀(autoregressive) 디코더 트랜스포머로 구성된다. 토크나이저는 3층 트랜스포머 오토인코더(d_model 256, d_ff 512, head 4)에 BSQ(Binary Spherical Quantization)를 결합해, 연속 잠재벡터를 학습 가능한 초평면에 사영하여 k비트 이진코드로 양자화한다(k=20, 총 어휘 2^20 = 1,048,576). 2^20을 그대로 예측하면 비용이 크므로 k비트를 동일 길이의 coarse/fine 두 서브토큰(k_c = k_f = k/2 = 10비트, 각 2^10)으로 인수분해하고, coarse 서브토큰만으로 복원하는 coarse loss, coarse+fine 전체 토큰으로 복원하는 fine loss, BSQ 정칙화용 양자화 loss(commitment weight beta = 0.05)를 합친 복합 목적함수로 학습해 coarse가 주요 구조를, fine이 잔차를 담도록 강제한다. 입력은 시점당 OHLCVA 6차원(Open, High, Low, Close, Volume, Amount)이며 차원별 z-score 정규화 후 [-5, 5]로 클리핑하고, 패치가 아니라 K-line 레코드 단위로 시점당 2개 서브토큰을 생성한다. 백본은 causal self-attention 기반 디코더로 RoPE 위치인코딩, Pre-LayerNorm + RMSNorm을 쓰고 최대 컨텍스트는 512 토큰이며, minute-of-day / hour-of-day / day-of-week / day-of-month / month-of-year 다섯 개 시간 특징을 각각 임베딩해 합산 후 입력 표현에 더한다. 예측은 dual-head 순차 방식으로, coarse head가 먼저 로짓을 내고 예측된 coarse 토큰 임베딩을 쿼리로 하는 cross-attention을 거쳐 fine head가 조건부 분포를 내며, 손실은 L_ar = -E[sum_t (log p(b_t^c | b_<t) + log p(b_t^f | b_<t, b_t^c))] 형태의 두 항 합이다. 모델 크기는 Kronos_small(8층, d_model 512, d_ff 1024, head 8, 24.7M), Kronos_base(12층, 832, 2048, head 16, 102.3M), Kronos_large(18층, 1664, 3072, head 32, 499.2M) 세 가지이며, AdamW + cosine 스케줄, peak LR 1e-3 / 5e-4 / 2e-4, weight decay 0.01-0.10으로 사전학습했다(총 학습 토큰 수, 스텝 수, 사용 하드웨어는 원문에 명시되지 않아 본문 확인 필요). 추론 시에는 temperature와 top-p를 둔 Monte Carlo 샘플링으로 복수 미래 경로를 뽑아 평균내는 앙상블을 쓴다(가격/수익률/투자시뮬레이션은 temp 0.6, top-p 0.90, 10 샘플; 변동성은 temp 0.9, top-p 0.90, 1 샘플; K-line 생성은 temp 1.0, top-p 0.95, 1 샘플).

Table 14의 Kronos_large 평균 RankIC는 0.0267이다. 0.0138 x 1.93 = 0.0266으로 헤드라인 93%가 정확히 재현되고, 87%도 최고 full-shot 베이스라인 0.0143 x 1.87 = 0.0267로 재현된다. 즉 0.0138 -> 0.0267이라는 절대 0.013%p 수준의 이동을 93%로 표기한 것이다. 분모가 0에 가까운 상대 비율은 불안정하며 실무 의사결정에서의 의미는 완전히 별개다. (추가 의문)

(추가 의문)
  • 예측 지표의 격차와 실제 포트폴리오 성과의 격차가 크게 어긋난다. Table 10에서 Kronos_large 평균 AER 0.2084 / IR 1.6491인데 Moment_large는 0.1681 / 1.3677, Moirai_large는 0.1577 / 1.2481이다. AER 기준 최고 베이스라인 대비 약 24% 우위로, 예측 단계의 93%가 투자 단계에서는 20-30% 수준으로 줄어든다. 이는 '예측 정확도가 투자 성과로 직결된다'는 본문 주장의 강도를 스스로 약화시킨다. 한편 Chronos_large는 평균 AER -0.0302 / IR -0.3384로 손실을 낸다. (추가 의문)
  • 이산화의 인과 기여가 분리되지 않았다. Table 2의 Kronos 대 Direct-AR/Prob-AR 비교에서 Kronos만 앙상블 샘플링(N=10)과 태스크별 T/top-p 튜닝의 혜택을 받는다. 연속형 베이스라인에 동등한 추론 예산을 준 통제 실험이 없어, 이득 중 얼마가 이산 토큰화 자체이고 얼마가 테스트타임 앙상블인지 알 수 없다. 실제로 독립 연구 VAIOM(arXiv 2607.13929)은 동일한 카테고리형 출력 목적함수 아래에서 연속 입력이 이산 토큰 입력보다 낫다고 보고한다. (추가 의문)
  • Kronos 사전학습의 컴퓨트 예산이 보고되지 않는다. Table 5는 드롭아웃/LR/weight decay만 주고, 본문은 워밍업 15,000스텝과 AdamW + 코사인 스케줄, 하드웨어(3 pod x 8장 = RTX 4090D 24장)만 밝힌다. 주의할 점은 Appendix D에 'batch size 256'과 '최대 12 에폭'이 등장하지만 이는 베이스라인 모델 학습 설정이지 Kronos 사전학습 설정이 아니라는 것이다(원문 확인 완료). Kronos 자체의 총 학습 스텝, 총 학습 토큰, 배치 크기, 에폭 수, 학습 소요 시간은 전부 누락됐다. 코퍼스 규모 120억 봉만으로는 컴퓨트 대비 성능을 계산할 수 없고, 세 크기 점 3개만으로 '스케일링 법칙을 실증했다'(empirically validating the scaling laws)고 말하기에는 근거가 얇다. 각 크기가 동일 토큰 예산으로 학습됐는지도 불명이다. (추가 의문)
  • 누출과 생존 편향 통제가 2024년 6월 시점 컷오프 하나에 전적으로 의존한다. 원문은 이 시간 분리만 서술할 뿐 상장폐지 종목 포함 여부, 수정주가 처리 방식, 지수 구성종목의 point-in-time 반영 여부를 전혀 언급하지 않는다(원문 확인 완료, 누락 확정). 사전학습 코퍼스에 CSI300/CSI800 종목의 과거 일봉이 들어 있었을 가능성이 매우 높은데(상하이 XSHG가 in-distribution 거래소로 명시됨), 이 경우 백테스트 유니버스는 새롭지 않다. (추가 의문)
  • 정규화 통계의 산출 범위가 논문에 없다. 원문 Appendix C는 'D개 특징 차원 각각에 독립적으로 z-score 정규화를 적용한 뒤 [-5,5]로 클리핑한다'고만 적고, 평균/표준편차를 룩백 윈도우 내부에서 계산하는지 시계열 전체에서 계산하는지 명시하지 않는다(원문 확인 완료, 누락 확정). 전자면 문제없고 후자면 미래 정보 누출이다. 논문만으로는 판별 불가이며 코드 확인이 필요하다. (추가 의문)
  • 어휘 크기 결론과 실제 실험 설정이 어긋난다. 배포 토크나이저는 k=20(2^20)인데 Table 9의 토크나이저 아키텍처 절제는 명시적으로 2^18 어휘에서 수행됐다. Figure 6의 어휘-성능 곡선도 '어휘를 키우면 복원과 예측이 모두 개선된다'는 단조 개선만 서술할 뿐 포화점을 보여주지 않아 2^20이 최적이라는 근거가 되지 못한다. (추가 의문)
  • 저장소와 논문이 어긋난다. 논문에 없는 Kronos-mini(4.1M, 컨텍스트 2048, Kronos-Tokenizer-2k)가 저장소에 있고(원문 전체 검색에서 mini 변종 언급 0건), 논문 최고 성능인 large는 미공개다. 논문 표를 그대로 재현하려면 base까지만 가능하다. (추가 의문)
  • 실패 사례 분석이 전무하다. 어떤 자산군, 어떤 변동성 레짐, 어떤 유동성 구간에서 모델이 무너지는지에 대한 서술이 없다. Appendix H는 왜 잘 되는지의 사후 정당화(노이즈 억제, 이산 상태공간, 초구 기하)에 집중하고, 레짐 전환이나 극단 이벤트에서의 성능 저하는 다루지 않는다. (추가 의문)
  • 라이선스는 MIT지만 사전학습 데이터의 출처와 라이선스가 전혀 명시되지 않는다. 45개 거래소, 120억 봉 규모라면 유료 벤더 데이터가 섞였을 개연성이 높다. 코드/가중치가 MIT라는 사실이 데이터 유래 리스크까지 정리해주지는 않는다. (추가 의문)

재현 가능성

코드 부분 공개. github.com/shiyu-coder/Kronos (MIT). 공개 범위는 추론 코드(model/kronos.py, KronosPredictor), 파인튜닝 파이프라인(finetune/config.py, train_tokenizer.py, train_predictor.py, qlib_data_preprocess.py, qlib_test.py), 예제 스크립트, Web UI, Qlib 기반 A주 백테스트 스크립트다. torchrun 다중 GPU 파인튜닝을 지원한다. 반면 사전학습 코드는 공개되지 않았다(저장소 최상위 디렉터리는 examples, figures, finetune, finetune_csv, model, tests, webui로 pretrain 계열 경로가 없음). 즉 파인튜닝은 재현 가능하지만 사전학습은 재현 불가.가중치 부분 공개. Hugging Face NeoQuasar 조직에서 Kronos-mini(4.1M, 컨텍스트 2048, Kronos-Tokenizer-2k), Kronos-small(24.7M, 512, Kronos-Tokenizer-base), Kronos-base(102.3M, 512, Kronos-Tokenizer-base)와 각 토크나이저가 공개되어 있다. 논문 최고 성능 모델인 Kronos-large(499.2M)는 저장소 Model Zoo에 미공개로 표시되어 있어 논문 상단 수치(예: 가격 시계열 평균 RankIC 0.0267, 투자 시뮬레이션 평균 AER 0.2084 / IR 1.6491)를 그대로 재현할 수 없다. 참고로 Kronos-mini는 논문 본문에 전혀 등장하지 않는 저장소 전용 변종이다.데이터 핵심 데이터 비공개. 45개 거래소, 7개 주기, 120억+ K-line 사전학습 코퍼스는 공개되지 않았고 출처 벤더도 명시되지 않는다. 저자 스스로 본문에서 '일반 시계열 파운데이션 모델 연구와 달리 잘 정제된 공개 금융 데이터가 제한적이어서 처음부터 구축했다'고 밝힌다. 평가용 데이터셋(9개 주식 거래소 = in-distribution XSHG/XNAS/XJPX/XNSE/XKRX/XHKG + OOD XIDX/XKLS/XTAI, Binance 전 현물 페어, 1000+ 외환 페어)도 비공개다. 재현 가능한 부분은 투자 시뮬레이션뿐으로, 이는 오픈소스 Qlib의 중국 A주 일봉 데이터를 사용하며 백테스트도 Qlib 엔진 안에서 수행한다. 저장소 config.py 기준 학습 2011-01-01~2022-12-31, 검증 2022-09-01~2024-06-30, 테스트 2024-04-01~2025-06-05, 백테스트 2024-07-01~2025-06-05, instrument=csi300, lookback_window=90. 주의: 논문 본문은 '테스트 기간이 2024년 7월에 시작한다'고만 적고 종료일을 명시하지 않으므로, 11개월이라는 백테스트 길이는 논문이 아니라 저장소에서만 확인된다.라이선스 코드 및 저장소: MIT License. 공개 체크포인트도 HF 모델 카드 기준 MIT. 사전학습 데이터의 라이선스와 출처는 논문/저장소 어디에도 명시되지 않음 -> 상업적 활용 시 데이터 유래 리스크는 별도 검토 필요.

Ubuntu 24.04.1 LTS, Python 3.13.2, PyTorch 2.7.0, NumPy 1.26.2, Pandas 2.2.2, Matplotlib 3.9.3, huggingface_hub 1.57.4. 하이퍼파라미터는 Table 5(드롭아웃, LR, weight decay: small 1e-3/0.01, base 5e-4/0.05, large 2e-4/0.10)와 Table 6(추론 T/top-p/N)에 공개. 옵티마이저는 AdamW + 코사인 스케줄, 워밍업은 피크의 10%에서 시작해 15,000스텝. 그러나 Kronos 사전학습의 총 스텝 수, 총 토큰 수, 배치 크기, 에폭 수, 학습 소요 시간이 모두 누락되어 컴퓨트 예산을 역산할 수 없다(원문 확인 완료). 주의: Appendix D에 나오는 'batch size 256'과 '최대 12 에폭, patience 3 조기종료'는 베이스라인 모델 학습 설정이지 Kronos 사전학습 설정이 아니다. 논문은 AAAI 2026에 채택되었고(저장소 뉴스 2025.11.10), arXiv v1은 2025.08.02 게재, 파인튜닝 스크립트는 2025.08.17 공개. 저장소는 별 약 37.5k, 포크 약 6.2k 규모다(수치는 조회 시점 의존).

📌 내 학습 포인트

  • 비전 도메인의 양자화 기법(BSQ)을 금융 시계열로 이식한 것이 이 논문의 실질 기여다. 이산화가 회귀보다 나은 이유로 저자가 든 논거 - BSQ는 임베딩을 단위 초구에 사영한 뒤 이진화하므로 기대 왜곡이 상한으로 묶이고, 따라서 플래시 크래시 같은 이상치가 무한대 근사 오차를 만들지 못한다 - 는 노이즈가 큰 어떤 도메인에도 재사용 가능한 사고틀이다. 회귀 문제를 분류 문제로 바꾸면 이상치의 영향력에 천장이 생긴다.
  • 대어휘 실용화 트릭: 2^20 어휘를 2^10 두 개로 인수분해하면 어휘 의존 파라미터가 1744.8M -> 3.4M로 99.8% 줄고 총 모델 크기가 1842.3M -> 102.3M으로 약 95% 감소한다(Table 12). 대가는 토큰당 추론 스텝 2배. 큰 어휘를 쓰고 싶은데 임베딩/출력 행렬이 감당 안 될 때 바로 꺼내 쓸 카드다.
  • 서브토큰을 병렬로 예측하면 손해다. Kronos-Parallel의 RankIC 0.0226 대 순차 coarse->fine의 0.0254. 인수분해로 나눈 조각들은 조건부 의존성을 유지해야 하고, 이를 위해 예측된 coarse 토큰 임베딩을 쿼리로 하는 cross-attention을 끼워 넣었다. 인수분해는 공짜가 아니라 의존성 복원 장치를 요구한다.
  • 계층적 손실이 복원 정확도를 올리지 않는다는 사실(Table 9: 0.0785 대 0.0781)이 오히려 교훈이다. 손실 설계의 목적이 항상 성능일 필요는 없다. 여기서는 'coarse만으로도 대략 복원되는' 표현 구조를 강제하기 위한 장치이고, 그 이득은 토크나이저가 아니라 후속 자기회귀 모델에서 회수된다. 손실 함수로 표현의 구조를 조각하는 사례로 기억해둘 만하다.
  • Test-time scaling이 시계열에도 통한다. 샘플 경로 N을 늘려 평균내면 IC/RankIC가 단조 개선된다(Figure 7). 생성형 예측기는 재학습 없이 추론 예산과 정확도를 맞바꿀 수 있다. 실서비스에서 지연 예산 대비 정확도 곡선을 그릴 수 있다는 뜻이라 실무적으로 가치가 크다.
  • 샘플링 파라미터가 사실상 태스크 헤드 역할을 한다. 예측은 T=0.6/top-p 0.9/N=10, 변동성은 T=0.9/N=1, 생성은 T=1.0/top-p 0.95. 정밀도가 필요하면 분포를 날카롭게, 다양성이 필요하면 무디게. 하나의 사전학습 모델로 다목적을 커버하려면 이 축을 반드시 태스크별로 잡아야 한다. 저자는 top-p의 하드 절단보다 temperature의 전역 재조정이 더 효과적이라고 관찰했다.
  • 사전학습 코퍼스의 도메인 혼합비를 명시적으로 조정했다. 원 코퍼스가 주식에 쏠려 있어 크립토/선물/외환의 샘플링 가중치를 올렸다. 파운데이션 모델에서 데이터 혼합비는 아키텍처만큼 중요한 하이퍼파라미터라는 점을 다시 확인.
  • 데이터 클리닝 파이프라인이 논문의 숨은 자산이다. 주기별로 임계값을 다르게 둔다: 가격 점프 임계는 1분봉 0.10에서 주봉 0.50까지, 비유동/정체 연속 봉 허용치는 1분봉 15/45에서 주봉 0/2까지. 구조적 단절(전일 종가 대비 당일 시가 점프)로 시계열을 분할해 액면분할, 배당, 선물 롤오버 아티팩트를 격리한다. 금융 시계열 전처리 설계 시 그대로 참고할 수 있는 표다.
  • 결측치 처리 철학이 인상적이다. 가격 필드의 결측을 채우지 않고 '경계'로 간주해 시계열을 유효 부분수열들로 쪼갠다. 부당한 보간으로 없는 패턴을 만들지 않겠다는 선택이며, 사전학습처럼 데이터가 남아도는 상황에서는 채우기보다 버리기가 옳다는 판단이다.
  • RoPE로 상대 위치를 주면서도, 캘린더 정보(minute/hour/weekday/day/month 다섯 개)는 별도 임베딩으로 합산해 주입한다. 금융처럼 절대 시각의 계절성(개장/폐장 효과, 월말 효과)이 실재하는 도메인에서는 상대 위치만으로 부족하다는 설계 판단.
  • 평가 설계에서 배울 점과 반면교사가 함께 있다. 배울 점: in-distribution 거래소 6개와 OOD 거래소 3개(인도네시아, 말레이시아, 대만)를 나눠 일반화를 측정하고, 크립토/외환에서는 volume을 일부러 빼 OHLC만으로 테스트한 점. 반면교사: 메인 표 전부가 단일 실행 점추정이고 유의성 검정이 없다는 점.
  • 헤드라인 퍼센트는 항상 절대값과 함께 읽어야 한다. RankIC 0.0254 같은 수준에서의 +93%와, 투자 시뮬레이션에서 AER 0.2084 대 0.1681(약 +24%)의 격차가 같은 모델에서 나온다. 예측 지표의 상대 개선은 포트폴리오 단계로 갈수록 급격히 희석된다는 사실 자체가 중요한 실무 지식이다.
  • 실전 적용 시 컨텍스트 512가 첫 번째 제약이다. K-line 레코드 하나당 서브토큰 2개를 만들므로 유효 룩백은 대략 256봉 수준으로 봐야 한다(정확한 카운팅 방식은 코드 확인 필요). 5분봉 480봉 룩백 설정은 이 한계에 부딪히고, 저장소의 KronosPredictor는 초과분을 자동 절단한다. 긴 룩백이 필요하면 더 낮은 주기를 쓰거나 컨텍스트 2048인 Kronos-mini를 고려해야 한다.
  • 재현성 실무 교훈: 코드와 가중치를 MIT로 풀어도 사전학습 코퍼스와 사전학습 코드가 없으면 '오픈'의 범위는 파인튜닝과 추론까지다. 오픈소스 파운데이션 모델을 평가할 때 확인할 체크리스트는 (1) 사전학습 코드, (2) 코퍼스, (3) 최상위 체크포인트, (4) 학습 예산 보고 네 가지이며 Kronos는 이 중 어느 것도 완전히 충족하지 않는다.

연결 연구

  • ← : Kronos 토크나이저의 핵심 부품. 잠재벡터를 단위 초구에 사영 후 이진화해 암묵적 코드북을 만들고 기대 왜곡의 상한을 보장한다. Kronos는 저자 공식 구현의 하이퍼파라미터(commitment 0.05, entropy weight 1.0/1.1, entropy scale 0.05, group size 5)를 거의 그대로 가져왔다. 어휘가 커질수록 좋아진다는 관찰도 이 계열에서 물려받은 것.
  • ← : 룩업 없는 양자화(LFQ)의 원류. BSQ의 직전 세대이며, Kronos는 LFQ가 정규화 없이 부호 기반 양자화를 해 이상치에 대한 오차 상한이 없다는 점을 BSQ 채택 근거로 든다. 어휘 인수분해 아이디어의 출처이기도 하다.
  • ← : 이산 잠재 표현 학습의 원점. Kronos 관련연구 절이 시계열 토큰화 계보를 여기서 시작한다.
  • ← : 시계열을 스케일링 + 균등 양자화로 토큰화한 TSFM. Kronos의 직접 선행이자 베이스라인. 흥미롭게도 Kronos의 투자 시뮬레이션에서 Chronos_large는 평균 AER -0.0302로 유일하게 음수를 기록해, 일반 시계열 토큰화가 금융에 그대로 이식되지 않음을 보여주는 대조군 역할을 한다.
  • ← : 논문이 '가장 강한 TSFM 베이스라인'으로 지목한 모델. 헤드라인 +93% RankIC의 비교 기준점이 바로 이 모델이다. 결측 가격 처리 시 시계열을 유효 부분수열로 분할하는 아이디어도 Time-MoE에서 차용했다고 밝힌다.
  • ← : 제로샷 TSFM 베이스라인. 투자 시뮬레이션에서 Moirai_large가 평균 AER 0.1577 / IR 1.2481로 상위권에 들어, Kronos와의 실제 포트폴리오 성과 격차가 예측 지표 격차보다 훨씬 작다는 사실을 드러낸다.
  • ← : 디코더 온리 TSFM 베이스라인. Kronos가 Table 3에서 지적하는 '기존 TSFM 사전학습 코퍼스 중 금융 데이터 비중이 1% 미만'이라는 논거의 대상 중 하나.
  • ← : 제로샷 TSFM 베이스라인. 투자 시뮬레이션에서 Moment_large가 평균 AER 0.1681 / IR 1.3677로 제로샷 baseline 중 최고 성능을 냈다.
  • ← : 논문이 '가장 강한 비사전학습 모델'로 지목한 풀샷 베이스라인. 헤드라인 +87%의 비교 기준점.
  • ← : 패치 기반 시계열 트랜스포머. Kronos는 의도적으로 패치가 아니라 K-line 레코드 단위 토큰화를 택했으므로, 설계상 대조점이 되는 선행 연구다.
  • ← : VQ-VAE 기반 시계열 토큰화. Kronos 관련연구에서 코드북 기반 접근의 대표로 인용되며, Kronos가 명시적 코드북 대신 암묵적 코드북(BSQ)을 택한 이유의 비교 대상이다.
  • ← : 투자 시뮬레이션의 데이터 소스이자 백테스트 엔진. 저장소의 파인튜닝 데모 파이프라인도 전적으로 Qlib에 의존한다. 표준화된 평가라는 장점과 동시에 슬리피지/마켓임팩트 미모델링이라는 한계를 함께 물려받는다.
  • ← : 백본의 위치 인코딩. Pre-LN + RMSNorm과 함께 현대 LLM 표준 구성을 그대로 이식한 부분.
  • ← : 생성 태스크 베이스라인이자 평가 프로토콜(diversity/fidelity/usefulness, discriminative score, TSTR)의 출처. Kronos의 '생성 충실도 22% 개선' 주장이 이 프로토콜 위에서 계산된다.
  • ← : 확산 기반 생성 베이스라인. TimeVAE(Desai et al. 2021)와 함께 생성 비교군을 이룬다.
  • → : Kronos의 핵심 전제에 대한 가장 직접적인 반례. 입력 표현과 출력 우도를 분리해, 연속 다변량 금융 이벤트 벡터를 입력으로 쓰되 출력은 변동성 정규화 수익률 버킷에 대한 범주형 분포로 둔다. 검증 실험에서 '동일한 범주형 출력 목적함수 아래에서 연속 입력이 이산 토큰 입력보다 낫다'고 보고한다. 즉 Kronos의 이득이 이산 출력에서 오는지 이산 입력에서 오는지를 분리해 답한 셈이고, 결론은 입력까지 이산화할 필요는 없다는 쪽이다. 1시간 FX 봉, 0.9M 파라미터, 3시드, 2025년 두 구간 아웃오브샘플로 LightGBM 대비 이벤트당 0.029~0.043비트 개선.
  • → : Kronos의 '변동성 예측 MAE 9% 개선' 주장을 재평가하게 만드는 연구. 9개 제로샷 TSFM 대 8개 계량경제 모델(HAR 계열 포함)을 주식/외환/선물 50자산, 3개 지평에서 형식적 예측 비교 검정과 함께 비교했다. 결론은 TSFM의 우위가 균일하지 않고 소수 아웃라이어 자산에 집중되며, 자산별 손실비를 평균하면 Tiny Time Mixers 하나만 근소하게 Log-HAR을 이긴다는 것. 게다가 단기 지평 우위의 상당 부분이 실제 동역학 예측이 아니라 스케일 보정 효과였다고 지적한다. Kronos가 HAR 계열을 베이스라인에서 뺀 것이 왜 문제인지를 보여준다.
  • → : Kronos의 고정 컨텍스트 512 제약을 정면으로 문제 삼는 후속 방향. 비정상 가격 프로세스에서는 최적 룩백이 시변하므로 고정 컨텍스트 윈도우가 구조적으로 부적합하다고 지적하고, 중첩 가변 길이 윈도우를 전문가에게 라우팅하는 MoE를 제안한다. Kronos가 '주기를 바꿔 우회하면 된다'고 넘어간 지점을 아키텍처로 푸는 시도.
  • → : Kronos의 '금융을 토큰 생성으로 본다'는 관점을 예측을 넘어 자산배분까지 확장. 별도 회귀/랭킹/정책 헤드 없이 인과 언어모델의 제약된 토큰 생성만으로 3스텝 수익률 예측과 5개 ETF 동적 배분을 수행한다. 2023-2025 테스트에서 5bp 거래비용 반영 순 샤프를 1.394 -> 1.494로 개선했다고 보고. Kronos가 예측에서 멈춘 지점을 의사결정까지 밀고 간 계열.
  • → : Kronos가 금융 전용으로 만든 토크나이저를 범용 시계열로 일반화하려는 방향. Kronos의 도메인 특화 전략과 범용 토크나이저 전략 중 어느 쪽이 옳은지에 대한 후속 논쟁의 한 축.
  • → : Kronos의 레시피(도메인 전용 토크나이저 + 자기회귀 사전학습 + 제로샷 다태스크)를 풍력 발전 예측으로 이식한 사례. 'K-line 전용'이라는 형식을 벗기면 이 방법론이 특정 도메인 시계열 일반에 적용 가능한 템플릿임을 보여준다.
  • → : 금융 파운데이션 모델 서베이. Kronos를 K-line 전용 FM의 대표 사례로 위치시키며, 이 분야의 공통 난점(데이터 비공개, 백테스트 신뢰성, 레짐 의존성)을 정리한다. Kronos를 큰 지형도 안에서 볼 때 참고할 문헌.
  • → : 금융 파운데이션 모델의 실효성을 회의적으로 검증하는 계열. Kronos류의 낙관적 주장에 대한 균형추 역할.
  • → : 시장 레짐/모드 변화를 명시적으로 모델링하는 방향. Kronos가 다루지 않은 레짐 전환 하 성능 저하 문제에 대응하는 후속 흐름.
  • → : Kronos가 단일 종목 시계열만 보고 종목 간 상관(횡단면 구조)을 모델링하지 않는다는 공백을 겨냥한 계열. 실제 퀀트 시그널은 횡단면 랭킹이므로 이 방향이 실무적으로 중요하다.

Claude 종합 코멘트

Kronos는 '금융 K-line 전용 파운데이션 모델'이라는 빈칸을 처음으로 제대로 채운 논문이고, 그 점에서 가치가 분명하다. 비전 양자화(BSQ)를 금융 시계열로 옮긴 선택, 2^20 어휘를 2^10 두 개로 인수분해해 파라미터를 99.8% 줄인 엔지니어링, coarse->fine 순차 예측으로 서브토큰 의존성을 유지한 설계, 그리고 추론 샘플 수로 정확도를 사는 test-time scaling은 모두 재사용 가치가 높다. 데이터 클리닝 파이프라인(주기별 임계값 표)과 결측을 보간하지 않고 시계열을 분할하는 처리 철학도 실무에서 그대로 가져다 쓸 만하다. 다만 검증한 결과, 이 논문의 신뢰도는 헤드라인 수치보다 상당히 낮게 잡아야 한다. 첫째, 독립된 Limitations 섹션이 아예 없고 Conclusion도 성과 요약만 한다. 저자가 인정한 한계는 컨텍스트 512 제약, n=2 인수분해가 비용 기반 선택이라는 점, 계층적 손실이 복원 품질을 개선하지 않는다는 점(Table 9), 크립토/외환에서는 volume을 빼야 한다는 점 정도로, 대부분 부록에 흩어져 있다. 오히려 GitHub README의 면책 문구가 논문보다 정직하다. 둘째, 헤드라인 '+93% RankIC'는 절대값이 0.02~0.05 수준인 지표 위의 상대 개선이고, 해당 지표(가격 시계열의 시간축 IC)는 가격 레벨의 자기상관 때문에 추세 지속만으로도 높게 나올 수 있어 퀀트 실무의 횡단면 IC와 성격이 다르다. 같은 모델의 투자 시뮬레이션에서는 Kronos_large 평균 AER 0.2084 대 Moment_large 0.1681로 격차가 20%대로 축소되는데, 이 대비가 헤드라인의 실질을 잘 보여준다. 셋째, 메인 결과가 전부 단일 실행 점추정이고 유의성 검정이 없다. 시드 5개는 Figure 7 한 곳뿐이다. 저자 스스로 신호 대 잡음비가 낮다고 강조한 도메인에서 이건 방법론적 결함에 가깝다. 넷째, 변동성 태스크는 실현변동성의 사실상 표준인 HAR 계열을 베이스라인에서 통째로 빼고 ARCH/GARCH만 썼다. 후속 연구 2607.05291이 9개 TSFM을 Log-HAR과 비교해 대부분 이기지 못한다고 보고한 것을 보면, '9% 낮은 MAE'는 약한 상대에게 얻은 우위일 개연성이 있다. 다섯째, 이산화의 인과 기여가 분리되지 않았다. Kronos만 N=10 앙상블과 태스크별 T/top-p 튜닝의 혜택을 받고 연속형 베이스라인에는 동등한 추론 예산이 주어지지 않았다. 후속 연구 VAIOM(2607.13929)이 동일한 범주형 출력 목적함수 아래에서 연속 입력이 이산 토큰 입력보다 낫다고 보고한 것은 이 의심에 실증을 붙인다. 여섯째, 백테스트가 단일 시장(중국 A주), 롱온리, 약 11개월(저장소 config 기준 2024-07-01~2025-06-05, 논문 본문에는 기간 명시 없음 -> 본문 확인 필요)이며 그 구간에 2024년 9-10월 급등이 포함된다. 상하한가와 거래정지를 모델링하지 않은 점은 A주에서 특히 성과를 부풀릴 수 있다. 재현성은 '부분 오픈'이 정확한 표현이다. MIT 라이선스로 추론과 파인튜닝 코드, mini/small/base 가중치가 풀렸고 Qlib 기반 A주 실험은 재현 가능하다. 반면 사전학습 코드는 저장소에 존재하지 않고(pretrain 경로 404 확인), 120억 봉 코퍼스와 9개 거래소 평가셋은 비공개이며, 논문 최고 성능인 large(499.2M)는 미공개다. 총 학습 스텝/토큰/배치/에폭이 전부 누락되어 컴퓨트 대비 성능도 역산할 수 없다(하드웨어는 RTX 4090D 24장으로 명시). 결국 세 크기 점 3개로 '스케일링 법칙 실증'을 주장하는 것은 과하다. 개인 학습 목적이라면 이 논문은 두 가지로 쓰는 게 좋다. 하나는 도메인 특화 토크나이저 설계의 교과서적 사례로 - BSQ 채택 논거, 어휘 인수분해 트릭, 손실로 표현 구조를 조각하는 발상 - 읽는 것. 다른 하나는 금융 ML 논문을 읽을 때의 체크리스트를 벼리는 반면교사로 읽는 것이다. 상대 % 뒤의 절대값, IC의 정확한 정의(시간축인가 횡단면인가), 베이스라인에 도메인 표준(HAR)이 들어 있는가, 시드와 신뢰구간이 있는가, 백테스트 기간과 시장이 몇 개인가, 거래 제약이 모델링되었는가. 이 여섯 개만 물어도 이 논문의 주장 강도는 상당히 조정된다. 방법 상세

Edge0는 MoE의 routed expert 가중치를 RAM이 아니라 SSD에 두고, int4 per-layer stacked safetensors를 mmap으로 열어 필요한 byte range만 읽는 스트리밍 추론 엔진이다(3.1절). 35B 티어(Qwen3.6-35B-A3B 기반, 40층 x 256 experts)는 층당 expert 가중치가 453 MB(expert 1개 1.77 MB), routed expert 전체가 18 GB로 19.5 GB 체크포인트의 대부분을 차지한다. 핫 데이터는 OS page cache가 들고, 피크 메모리는 파라미터 수가 아니라 active set을 따른다.

실행 경로는 네 가지다. exact(on-demand 번들 빌드, 정확성 기준), staged(고정 슬롯 double buffering, decode 주력. 라우팅 인덱스를 slot table로 매핑하고 incr_stack으로 바뀐 expert만 제자리 갱신), hot(층별 LRU 상주 hot expert, miss 시 exact로 fallback), whole-layer(prefill에서 층 전체 expert를 9번의 직접 read로 일괄 로드)다. 모든 경로는 down(silu(gate(x))·up(x))를 같은 quantized gather 커널로 계산하며 dequantized reference 대비 relative L2 1% 미만(측정 잔차 약 0.24%)으로 테스트된다.

핵심은 prerouter다. 층 N+1의 expert 선택은 층 N 출력이 있어야 정해지므로 순진한 스트리밍은 매 층마다 디스크 지연에 막힌다. Edge0는 '이중 shift'를 쓴다. 층 N이 소유한 head가 토큰 t에서 층 N의 post-attention norm 출력을 보고 토큰 t+1의 층 N+1 라우팅을 예측한다. 한 스텝당 한 번의 flush로 모든 staged 층(35B 32개, 8B 16개)을 한꺼번에 예측하므로 SSD read가 한 decode step 전체와 겹친다. 같은 토큰 안에서 미리 고르는 Pre-gated MoE 방식은 이 엔진에서 스텝당 30-100 ms의 동기화 비용이 들어 plain LRU보다도 느렸다고 저자들은 보고한다. head 구조는 fc1 -> erf-gelu -> fc2에 linear residual을 더한 것이며, residual은 다음 층 router 가중치로 warm-start한다. 입력은 hidden state와 두 개의 top-k one-hot(이번 토큰과 이전 토큰에서 이 층이 실제 고른 expert)을 이어 붙인 것으로 35B는 2048+2x256=2560차원, hidden 512, fp16이다. 35B는 head 33개(owner 6-38), 8B는 16개다.

Prediction-as-routing이 가장 중요한 설계다. decode 시 MoE 층은 원래 router 대신 prerouter logits를 같은 softmax-topk 또는 sigmoid-group 수식에 넣어 라우팅한다. 예측 집합이 곧 라우팅 집합이므로 staged 슬롯과 정확히 일치하고 drop이나 fallback load가 없다. 즉 '오예측'이라는 사건 자체가 런타임에 존재하지 않고, 원본 모델과 다른 expert를 쓰는 근사 오차가 그대로 모델 동작에 반영된다. 이 비용은 학습에서 갚는다. head 입력은 학습 때는 실제 라우팅, 추론 때는 자기 예측이라는 feature drift가 있는데 head를 재학습하지 않고 LoRA가 흡수하게 둔다. 예측 정확도(hit rate, top-k overlap)는 본문 전체에서 수치로 보고되지 않으며, 저자들은 router 일치도를 더 쫓는 것은 잘못된 목표이고 학생 라우팅에서 언어모델이 좋은 텍스트를 내는지가 중요하다고 주장한다.

Recovery LoRA(r=16, alpha=32)는 attention, linear-attention, shared-expert projection에만 붙고 routed expert에는 붙지 않는다(스트리밍되며 교체 가능해야 하므로). 서빙은 unmerged로 y = W_int4(x) + (alpha/r)·B·A·x 병렬 delta다. LoRA delta(RMS 약 1e-3)가 4-bit group step보다 작아 병합 후 재양자화하면 효과가 attention projection에서 34%, dense projection에서 2%, logits 수준에서 18%만 남기 때문이다. unmerged 비용은 어댑터 42 MB, decode 시간 차이는 측정되지 않을 정도라고 한다. 양자화는 expert 가중치 int4 affine group-64다.

학습은 3단계이며 모두 4-bit 배포 체크포인트를 dequantize한 bf16 재구성 위에서 base를 고정한 채 진행한다. Phase 1은 head만 다음 층의 실제 router logits를 모방하도록 distill한다. Phase 2는 prerouter 라우팅을 켠 student path 전체 forward로 약 2M행의 teacher 생성 텍스트에 SFT한다(distill만 한 체크포인트는 반복·붕괴된 텍스트를 냈다고 함). Phase 3은 on-policy distillation으로 학생이 생성하고 원래 fp16 base가 teacher로 채점하며, teacher top-k 토큰에 reverse KL과 tail 항을 쓴다. 약 200k행(Phase 2의 1/10)에서 수렴한다. 이 구조 덕에 35B 티어는 base의 K=8 대신 K=4로 재학습해 출시됐다.

  • 유일한 외부 시스템 baseline(3.1절, 5.4절)은 같은 Mac mini에서 19.5 GB 4-bit 가중치를 전부 상주시킨 vanilla mlx-lm 서버다. 결과는 3.9 tok/s, 18.2 GiB 점유다. 저자 각주는 같은 머신, 같은 decode protocol, think-mode on이라고 밝힌다. Edge0는 20.4 tok/s, 2.9 GiB로 '5배 빠르고 메모리는 1/6-1/7'이라고 주장한다. 단 resident baseline의 routing K는 명시되지 않았고 Edge0는 K=4 재학습 프로파일이다. 저자들은 resident 쪽이 메모리 부족으로 paging한다고 설명한다. llama.cpp --cpu-moe, PowerInfer, Mixtral-offloading, MoE-Infinity, FlexGen은 관련연구에서 인용만 하고 수치 비교는 없다.
  • prerouter A/B(Table 3, MacBook M2 16GB): on-demand 대비 prerouter decode는 K=2 4.8 -> 8.6(+80%), K=4 3.5 -> 6.4(+82%), K=8 1.8 -> 3.3(+84%)이다. 메인 스레드의 expert load 대기 시간(스텝당, 층 합산)은 K=2 154.9 -> 46.5 ms, K=4 244.0 -> 101.9 ms, K=8 575.0 -> 211.6 ms다. K=8 on-demand 합 575.0 ms가 스텝 559.1 ms보다 큰데, 층 간 load가 겹치기 때문이다. 디스크 read는 스텝의 최대 12%, 프로세스는 8코어 중 약 1코어, GPU는 35-41%를 써서 어떤 자원도 포화되지 않았다고 보고한다. 3라운드 median이며 3/3 라운드가 일치했다(Figure 3 캡션).
  • routing width A/B(4장, Table 3): 같은 16GB 머신의 같은 세션에서, 같은 가중치로 K=8을 K=4로 줄이면 prerouter arm decode가 3.3 -> 6.4 tok/s로 거의 2배가 되고 peak active memory도 줄어든다. on-demand arm은 1.8 -> 3.5다. 저자들은 재학습한 K=4 티어가 Table 2 품질을 유지한다고 주장한다. 24GB Mac mini에서 35B를 K=8로 측정한 수치는 없다.
  • I/O 비용(Table 4): 스텝당 read 바이트(prerouter vs on-demand)는 K=2 29.5 vs 30.4 MiB, K=8 125.1 vs 126.9 MiB로 거의 같다. K=4만 58.9 vs 50.9 MiB로 16% 많다. prerouter는 더 적고 크고 차가운 load를 낸다. K=8 기준 load당 1.40 MiB·90% cold vs 0.32 MiB·20% cold이고, 스텝당 load 수는 89.5 vs 398.6이다. load 비용 모델은 1.17 ms + 1.33 ms x cold 비율로, 측정값을 0.13 ms 이내로 재현한다. 인접 토큰 간 expert 집합 겹침은 약 1/4이다.
  • 메모리 대가(5.3절): unreclaimable MLX 할당은 on-demand 1.72/1.73/1.79 GiB, prerouter 2.33/2.60/3.22 GiB다(K=2/4/8). Process RSS(파일 기반 expert 페이지 포함)는 on-demand 5.29/6.12/6.18 GiB, prerouter 4.91/5.61/6.39 GiB다. K=8에서 prerouter arm은 1.43 GiB를 더 쥐고 page cache는 1.15 GiB 줄어든다. 저자들이 밝힌 미적용 개선 여지는 두 가지다. bundle과 stacked view 이중 사본을 없애면 K=8에서 약 0.45 GiB를 돌려받고, 메인 스레드 동기 fill(K=8에서 62.5 ms/step)을 다른 스레드로 옮길 수 있다. 둘 다 측정 구성에는 반영되지 않았다.
  • 품질 평가(5.1-5.2절, Table 2): OpenCompass를 compute server에서 돌려 Edge0(int4 + adapters + prerouter routing)와 원래 fp16 base를 동일 설정으로 평가했다. sampling, temperature, max tokens, AIME 반복 횟수 등 세부 설정은 원문에서 확인되지 않는다. 35B: AIME 2026 86.6 vs 92.7(-6.1), HumanEval 90.9 vs 95.1(-4.2), GPQA-Diamond 79.8 vs 81.8(-2.0), MMLU-Pro 81.0 vs 84.6(-3.6), IFBench 57.9 vs 61.7(-3.8), 평균 79.2 vs 83.2. 8B: AIME 63.3 vs 73.3(-10.0), HumanEval 91.5 vs 92.7(-1.2), GPQA-D 70.7 vs 71.2(-0.5), MMLU-Pro 70.1 vs 65.8(+4.3), IFBench 53.9 vs 60.6(-6.7), 평균 69.9 vs 72.7.
  • 측정 신뢰성 주의(5.1절): 저자들은 이 하드웨어에서 single-shot 벤치마크가 run 간 +-40%, 16GB 머신에서는 세션 간 최대 2.3배 차이가 난다고 밝힌다. 그래서 같은 세션 교차 A/B만 증거로 쓴다.
  • Appendix B: incr_stack(sticky-slot 제자리 갱신)은 별도 A/B에서 decode를 +34% 올렸다. K=8 구성에서 native routing 대비 전체 출시 파이프라인은 6.8 -> 12.5 tok/s였다. 저자 스스로 이전 캠페인의 다른 구성이라 Table 3와 비교할 수 없다고 밝힌다. 6장에 따르면 40층 forward의 CPU측 graph building 44 ms/step이 decode 하한이다.
  • 저장소 문서와 논문의 구성 불일치: docs/models/edge0-8b.md는 8B 배포 프로파일에서 staged decode를 끈다고 적는다(staged=False). 이유는 deployment verification에서 staged decode가 출력을 저하시켰기 때문이며, 대신 prerouter가 다음 토큰 expert prefetch를 직접 구동한다. 논문 3.2절은 8B가 K=8, 층당 8개 staged slot으로 돈다고 적는다. docs/models/edge0-35b.md는 35B 프로파일이 on-demand prefill(full_layer_prefill=False)이라고 적지만, 논문은 두 티어 모두 prefill에 whole-layer 경로를 쓴다고 적는다. Table 1이 어느 구성으로 측정됐는지는 확인되지 않는다.

한계 · 비판

  • 단일 요청 직렬 처리: Edge0는 한 번에 한 요청만 FIFO로 처리하며 배치 서빙을 하지 않는다. 배치는 expert working set을 바꾸는데 이는 per-request 프로파일이 모델링하지 않는다고 저자들이 적는다. 20.4 tok/s를 포함한 모든 처리량 수치가 batch 1 조건이다 (6장, Table 1 캡션). (저자 인정)
  • CPU측 하한: 40층 forward의 graph building이 스텝당 44 ms이고 이는 스토리지 쪽 최적화로 줄일 수 없는 decode 하한이라고 저자들이 명시한다 (6장). (저자 인정)
  • prefetch 이득의 조건 의존성과 메모리 대가: prerouter 이득은 제거하는 대기 시간에 비례하므로 hot cache나 빠른 스토리지에서는 줄어들고, 인접 토큰이 한 층의 expert 중 약 1/4만 공유하므로 재사용에 상한이 있다. 대가는 page cache에서 가져오는 unreclaimable residency로, K=8에서 prerouter arm이 MLX 메모리를 1.43 GiB 더 쥐고 page cache는 1.15 GiB 줄었다. 실제로 24GB Mac mini에서는 prerouter off 19.9 vs on 20.4 tok/s다 (6장, 5.3절, Table 1 캡션). (저자 인정)
  • 측정 구성의 미완 최적화: stager가 같은 가중치의 bundle과 stacked view 두 사본을 들고 있어 K=8에서 약 0.45 GiB가 낭비되고, incremental stacking fill이 메인 스레드에서 동기 실행되어 K=8에서 스텝당 62.5 ms가 든다고 저자들이 'Two levers not yet pulled'로 밝힌다. 두 개선 모두 측정 구성에 포함되지 않았다 (5.3절). (저자 인정)
  • 품질 손실이 긴 추론에 집중: 35B 티어 AIME -6.1점(86.6 vs 92.7), 8B 티어 AIME -10.0점, 8B IFBench -6.7점을 저자들이 직접 한계로 적는다. HF 모델 카드 두 개는 별도로 tool use와 multi-step planning 등 agent 능력이 약하고, 성능 수치는 MLX Apple Silicon 측정이며 iOS/Android/Windows 엔진은 아직 성숙 중이라고 경고한다. 35B 카드는 긴 context에서 KV cache로 3 GiB를 넘는다고도 적는다 (6장, Table 2, HF 모델 카드 Limitations). (저자 인정)
  • 구현 범위와 측정 신뢰성: MLX가 유일한 구현 백엔드이고 CUDA는 아키텍처만 있고 코드는 없다(6장, README 로드맵상 2026 Q4). 또 이 하드웨어에서 single-shot 벤치마크는 run 간 +-40%, 16GB 머신은 세션 간 최대 2.3배 편차가 있어 같은 세션 교차 A/B만 증거로 쓴다고 밝힌다 (5.1절). (저자 인정)
  • 헤드라인 성능의 원인 귀속이 흐리다. abstract는 prerouter가 SSD 지연을 숨긴다는 서사를 쓰지만, 20.4 tok/s를 낸 24GB Mac mini에서 prerouter를 끄면 19.9 tok/s로 측정 기여는 약 0.5 tok/s(약 2.5%)다. off arm이 정확히 어떤 구성인지는 원문에 없다. +80-84% 이득(Table 3)은 가중치가 메모리에 들어가지 않는 16GB MacBook M2에서, 절대 속도 3.3-8.6 tok/s 수준으로만 나온다. 같은 16GB 머신에서 K=8을 K=4로 줄이면 decode가 3.3 -> 6.4 tok/s로 거의 2배가 되고(4장, Table 3), incr_stack도 +34%를 보인다(Appendix B, 다른 측정 캠페인). 그래서 출시 티어 속도의 상당 부분은 routing width 축소와 스트리밍 경로 최적화에서 온다고 보는 것이 논문 자체 데이터와 맞는다. 다만 24GB Mac mini에서 각 요소의 기여를 분해한 측정은 없고, 저자들은 정확한 집합을 공급할 prerouter 없이는 staging만으로 배포 가능한 구성이 아니라고 반론한다(5.3절). (추가 의문)
  • 외부 baseline이 사실상 하나다. 비교 대상은 같은 Mac mini에서 19.5 GB를 전부 상주시켜 paging이 일어나는 vanilla mlx-lm(3.9 tok/s, 18.2 GiB)뿐이다. 저자 각주는 같은 머신, 같은 decode protocol이라고만 밝히고 routing K는 명시하지 않아 K=4 Edge0와 동일 조건인지 알 수 없다. llama.cpp --cpu-moe, MoE-Infinity, PowerInfer, Mixtral-offloading은 인용만 있고 수치 비교가 없다. Pre-gated MoE 계열은 자기 엔진 안에서 same-token 변형을 측정해 스텝당 30-100 ms 비용으로 plain LRU보다 느렸다고 서술하지만, 표나 원 시스템 수치는 제시하지 않는다. '5배 빠르다'는 이 단일 비교에 한정해 읽어야 한다. 다만 저자들이 resident baseline이 이 하드웨어에서 빠른 기준이 아닌 이유를 3.1절에서 직접 설명한다는 점은 공정하게 밝혀 둔다. (추가 의문)
  • Prediction-as-routing의 동작 변화 평가가 부족하다. 35B는 40층 중 32층, 8B는 24층 중 16층이 이전 토큰 시점의 예측으로 라우팅되고, 35B는 K도 8 -> 4로 바뀐다. 그런데 router 일치도, top-k overlap, 출력 분포 KL 같은 지표는 본문 전체에서 수치로 보고되지 않고, 평가는 5개 벤치마크 점수뿐이다. 저자들은 router 일치도를 쫓는 것이 잘못된 목표라고 근거를 들어 주장하지만, 그렇다면 언어모델 출력 수준의 차이를 더 넓게 측정해야 한다. 원본 대비 편차는 벤치마크 밖(장문 생성, 다국어, agent 작업)에서 드러날 수 있으나 이를 측정한 결과는 없고, HF 카드도 agent 능력이 약하다고 인정한다. 벤치마크의 sampling, temperature, max tokens, AIME 반복 횟수도 원문에서 확인되지 않아 -6.1 같은 격차의 분산을 판단할 수 없다. (추가 의문)
  • 재현성 공백. 저장소 전체 파일 트리(1131 경로)를 train, distill, sft, opencompass로 검색한 결과, 추론 엔진, 벤치 스크립트(python/examples/bench.py), 학습된 어댑터와 head만 있고 prerouter head distill, LoRA SFT, on-policy distillation, OpenCompass 평가 코드는 없다. docs/prerouter.md는 heads.py가 별도의 training implementation에서 가져온 것이라고 적어 학습 구현이 비공개임을 시사한다. Phase 2 약 2M행 데이터의 프롬프트 출처, 학습 compute, learning rate와 step 수도 원문에서 확인되지 않는다. 따라서 다른 MoE에 prerouter를 새로 학습시키려면 논문 서술만 보고 재구성해야 한다. (추가 의문)
  • 측정 조건과 공개 자료의 불일치. SSD 모델·대역폭과 macOS 버전이 명시되지 않아, SSD에 의존하는 시스템인데도 하드웨어 일반화가 어렵다. README와 HF 카드는 다른 프로토콜(약 3.3k 토큰 프롬프트 후 200 decode 토큰, 2 runs)로 35B 14.9-17.7 tok/s, 8B 23.9-25.3 tok/s, 8B peak 1.0 GiB를 적어 논문의 20.4, 28.0 tok/s, 1.5 GiB와 다르다. 차이의 일부는 조건 차이로 보이지만 두 수치를 조정하는 설명은 없다. README의 35B 체크포인트 약 23 GB 표기도 논문 19.5 GB, HF 파일 합계 약 19.7 GB(어댑터와 head 포함)와 다르다. 또 저장소 문서는 8B에서 staged decode가 출력을 저하시켜 끈다고 적고(docs/models/edge0-8b.md) 35B는 on-demand prefill이라고 적어(docs/models/edge0-35b.md), 논문 3.2절의 배포 구성 서술과 충돌한다. '3 GiB peak active memory'는 MLX allocator peak로 page cache와 mmap 파일 페이지를 빼고 잰 값이며, 16GB 실험의 Process RSS는 4.91-6.39 GiB였다. (추가 의문)

📌 내 학습 포인트

  • 로컬 모델 속도는 single-shot으로 측정하지 말 것. 저자들은 같은 하드웨어에서 single-shot 벤치마크가 run 간 +-40%, 16GB 머신에서 세션 간 최대 2.3배 차이가 난다고 보고한다. 그래서 각 arm을 별도 프로세스로 띄우고, arm 순서를 회전하고, 두 arm이 같은 토큰 시퀀스를 재생하게 한 뒤 warm 상태 3라운드 median을 내는 같은 세션 교차 A/B만 증거로 쓴다. 같은 저자들의 README 수치(3.3k 프롬프트 후 200 토큰, 2 runs)가 논문 수치보다 2.7-5.5 tok/s 낮은 것 자체가 프로토콜 차이의 영향을 보여 준다. Windows PC에서 llama.cpp 옵션(예: -cmoe, -ngl)이나 양자화 포맷을 비교할 때 이 절차를 작은 PowerShell 스크립트로 만들어 두면, 트렌드 시스템이 논문의 tok/s 주장을 검증할 때도 같은 기준을 쓸 수 있다.
  • offloading·prefetch 기법의 효과는 먼저 '모델이 메모리에 들어가느냐'로 갈린다. 같은 prerouter가 가중치를 다 담지 못하는 16GB MacBook M2에서는 decode +80-84%(K=4 기준 3.5 -> 6.4 tok/s)지만, 24GB Mac mini에서는 19.9 -> 20.4 tok/s로 약 2.5%다. 반면 같은 16GB 머신에서 routing width를 K=8에서 K=4로 줄이자 decode가 거의 2배가 됐다. 활성 expert 수가 토큰마다 옮겨야 할 바이트 양을 직접 정하기 때문이다. 따라서 35B급 MoE를 로컬에서 돌리려면 먼저 RAM(또는 unified memory) 용량과 int4 체크포인트 크기(35B 약 19.5 GB)를 비교하고, 모자랄 때만 SSD 스트리밍류 기법을 고려하는 것이 순서다. repo의 Windows 참고 수치(35B decode 약 27.7 tok/s)도 48GB RAM에 모델이 다 올라간 warm-RAM 조건이며, README는 16GB 이하에서 35B가 paging-bound라고 적는다. GPU 유무와 SSD 속도는 본인 환경에서 직접 측정해야 하며, 논문은 SSD 사양을 명시하지 않았다.
  • 양자화 모델에 LoRA를 붙일 때 병합 후 재양자화를 기본값으로 쓰지 말 것. 저자들은 LoRA delta(RMS 약 1e-3)가 int4 group-64 step보다 작아서, 병합·재양자화하면 효과가 attention projection 34%, dense projection 2%, logits 18%만 남는다고 측정했다. unmerged 병렬 delta(어댑터 42 MB)는 decode 시간 차가 측정되지 않을 정도라고 보고한다. repo의 Windows 앱도 MLX LoRA를 별도 GGUF adapter로 변환해 llama.cpp에 런타임 adapter로 넘기므로(windows/tools/lora_mlx_to_gguf.py) 같은 원칙을 따른다. 로컬에서 GGUF 등 4-bit 모델에 자체 LoRA를 쓸 때는 런타임 어댑터 로딩(llama.cpp의 --lora 인자)을 먼저 시도하고, 병합본과 품질을 같은 프롬프트 세트로 비교하는 습관을 들이면 된다. 단 Windows 앱은 prerouter를 advisory prefetch로만 쓰므로(기본 비활성) student routing 경로에서 학습한 LoRA가 원래 gate 위에서 돌게 되고, 이때 Table 2 품질이 유지되는지는 확인되지 않았다(코드 주석과 논문 서술을 비교한 추론). HF 카드도 agent 능력(tool use, multi-step planning)이 약하다고 경고하므로, Claude Code 서브에이전트의 로컬 대체 모델로 쓰기 전에 별도 검증이 필요하다.

연결 연구

  • ← : 같은 토큰 안에서 다음 층 expert를 미리 고르는 pre-gating 방식이다. Edge0는 이런 same-token 변형이 자기 엔진에서 스텝당 30-100 ms의 동기화 비용 때문에 plain LRU보다 느렸다고 보고하고, 다음 토큰을 예측하는 이중 shift로 대체한다.
  • ← : 저자들이 접근법상 가장 가깝다고 꼽은 연구다. 사후 학습한 MoE가 그에 맞춰 학습되면 expert 수를 절반으로 줄여도 견딘다는 관찰이며, Edge0의 routing 대체 학습과 K=8 -> 4 재학습이 같은 관찰을 prediction-as-routing에 적용한 것이라고 저자들은 설명한다.
  • ← : Mixtral expert를 LRU 캐시와 speculative expert loading으로 offload하는 선행 시스템이다. Edge0는 자기 hot 경로가 같은 popularity 캐시 계열이라며 인용만 하고 수치 비교는 하지 않는다.
  • ← : 개인 기기용 expert 캐시·prefetch 시스템으로 문제 설정이 같다. Edge0와의 수치 비교는 없다.
  • ← : hot/cold neuron 분리로 소비자 GPU와 CPU에 가중치를 나누는 접근이다. Edge0의 hot expert 경로가 같은 hot/cold 분리라고 저자들이 직접 적는다. 인용만 있고 수치 비교는 없다.
  • ← : GPU/CPU/디스크 계층으로 가중치와 KV를 offload하는 처리량 지향 배치 서빙의 대표 선행 연구다. Edge0는 배치 1 지연 지향이라 목표가 다르다.

Claude 종합 코멘트

이 논문의 진짜 새로운 점은 prerouter 예측을 prefetch 힌트가 아니라 실제 라우팅으로 쓰는 prediction-as-routing이다. 예측 집합이 곧 사용 집합이므로 오예측 fallback 경로가 사라지고, 그 대가인 원본 모델과의 동작 차이는 recovery LoRA와 on-policy distillation으로 학습 단계에서 갚는다. 4-bit 위에 LoRA를 병합하지 않는 이유를 잔존율(34%, 2%, 18%)로 측정해 보인 점도 실용적이다. 반면 증거의 강도는 헤드라인보다 약하다. '단일 24GB 머신'은 GPU VRAM이 아니라 Mac mini M4 Pro의 unified memory다. 20.4 tok/s는 batch 1, short context, warm, 3라운드 median이고, base의 K=8이 아닌 K=4 재학습 프로파일 조건이다. 이 머신에서 prerouter의 측정 기여는 약 2.5%뿐이고, +80% 이상은 16GB 기기에서만 나온다. 같은 16GB 기기에서는 K=8을 K=4로 줄이는 것만으로 decode가 약 2배가 됐다. '3 GiB'는 MLX allocator peak로 page cache를 뺀 값이다. 외부 비교는 paging이 일어나는 vanilla mlx-lm 하나뿐이고, router 일치도나 출력 분포 차이는 보고되지 않는다. 품질 격차는 평균 3.9/2.8점이지만 AIME에서는 -6.1/-10.0점으로 크다. 그밖에 SSD 사양 미공개, 학습 코드 부재(저장소 전체 트리 확인), README·HF 카드·저장소 문서와의 수치·구성 불일치(8B staged decode 비활성 등)가 남는다. Windows 앱은 prerouter를 advisory prefetch로만 쓰므로 논문 방법을 Windows에서 재현한 것으로 볼 수 없다. 인용할 때는 'Apple Silicon 24GB unified memory Mac mini에서 Qwen3.6-35B-A3B를 K=4로 재학습한 int4 변형이 배치 1 decode 약 20 tok/s를 냈고, 다섯 벤치마크 평균 약 4점 하락(AIME는 6점 이상)'처럼 조건과 손실을 함께 적는 것이 정확하다.

방법 상세

MOSS-Image는 처음부터 사전학습한 5B single-stream DiT 렌더러와, 추론 시점에만 동작하는 GPT-6 기반 agentic prompt enhancer(논문 명칭 Layout PE)를 하나의 텍스트 조건 경로로 묶은 시스템이다. 5B는 diffusion generator만의 크기이며, frozen 텍스트 인코더 Qwen3.5-9B와 frozen FLUX.2 VAE(FLUX.2-klein-4B에서 로드, 32채널, 공간 8배 축소)는 제외된다(부록 A.1, PDF Table 5).

구조는 다음과 같다. Qwen3.5-9B 마지막 층 hidden state(4096차원)를 선형 투영(4096->3072)하고 텍스트 전용 Transformer 블록 2개를 거친 뒤, 2x2로 패치화한 이미지 latent 토큰(유효 stride 16픽셀, 1024x1024에서 4096토큰)과 한 시퀀스로 이어 붙인다. 42개 joint 블록(hidden 3072, 24 heads x 128, FFN 8192)은 joint self-attention, shared modulation, tanh soft-cap을 넣은 gated FFN인 SiTU-GLU를 쓴다. 이 값은 HF transformer/config.json(num_layers 42, dim 3072, num_heads 24, ffn_dim 8192, text_dim 4096)과도 일치한다. 위치 부호화는 4D RoPE(r 참조 인덱스, t 시퀀스 위치, w, h)이며 헤드 128차원 중 앞 32차원이 r 축이다. 참조 입력이 없으면 r=0이라 회전이 없는 partial RoPE가 되고, 이미지 위치는 텍스트 뒤에 이어지며 공간 좌표는 0 중심이다. 자연어 캡션과 bbox JSON 레이아웃이 별도 제어 모듈 없이 같은 텍스트 경로로 들어간다는 점이 핵심 설계다.

레시피는 ReLAION, OmniCorpus, DataComp 등 16개 공개 소스(PDF Table 8)를 SSCD 중복 제거와 자체 AI 이미지 탐지기로만 줄인다(본문은 약 50억->30억, 그림 3은 5.5B->3.2B로 표기). 그 이후 단계에서 추가 품질 필터는 일부러 쓰지 않는다. 다만 ReLAION의 NSFW, 워터마크 검사처럼 소스 구축 단계의 필터는 그대로 남는다고 저자가 밝힌다. 워터마크나 흐림 같은 결함은 걸러내지 않고 캡션에 적는다. gemma4로 short/medium/long 재캡션을 만들며 보이는 텍스트는 줄바꿈까지 그대로 전사한다. 고품질 부분집합에는 bbox와 타이포그래피를 담은 레이아웃 JSON을 붙이며, 스키마는 scene/element와 summary/items 두 가지다. 필드 dropout과 순서 셔플을 적용한다. 좌표 표현은 scene/element 분기에서 정규화/절대/중심기준 픽셀을 0.4/0.3/0.3으로 무작위 선택하고, 보조 item-level 분기는 0.2/0.4/0.4를 쓴다. summary/items는 [0,1000] 정규화 yxyx로 변환한다. 원 캡션과 재캡션의 비율은 20:80, 세 길이는 1:1:1이다. 합성 렌더링 텍스트 데이터를 따로 만들었다는 기술은 본문과 부록에 없다(PDF 전문에서 'synthetic' 검색 결과 0건). 다만 소스 중 text_atlas(TextAtlas5M)는 자체 초록에서 'generated and collected images'로 구성된다고 밝힌다. 따라서 생성된 텍스트 이미지가 간접적으로 포함되었을 수 있으며, 어떤 부분집합을 썼는지는 원문에서 확인되지 않는다. 저자들은 캡션이 주로 영어이며 중국어 전용 주석은 없다고 밝힌다. 학습은 flow matching 손실, 하이브리드 Muon-AdamW(lr 5e-5), 해상도와 텍스트 길이를 늘려 가는 다단계 진행으로 구성된다.

Layout PE는 학습하지 않은 프롬프트 기반 에이전트다. GPT-6가 요청 매체(포스터, 인포그래픽, UI)에 맞춰 과제 모듈을 고른다. 이어서 필요에 따라 웹과 이미지 검색으로 참고 이미지를 직접 살피고, 낯선 사실은 권위 있는 출처로 확인한다. 일반 지침은 검색어 1-3개와 유용한 이미지 2-4장이며, 경로별로는 포스터 3-5개, UI 최소 3장 확인을 권한다(Table 14). 출력은 scene_type, gen_brief, aspect_ratio, layout, elements, anchors, must_not, palette 8개 루트 필드의 JSON이며, 박스는 [0,1000]으로 정규화한 yxyx 정수 좌표다. 반환 전에 JSON 문법, 필수 필드, 좌표 유효성, 문자열 그대로 보존 여부, 텍스트 맞춤을 스스로 점검하라는 지시가 들어 있다.

실험 셋업

  • 사전학습 단계(PDF Table 1, 그림 3c, 부록 A.2): Stage 1은 256px급, 텍스트 상한 320, 2,100,000 step이다. Stage 2는 512px(이후 256/512 혼합), 텍스트 상한 512->1024->2048, 2,100,000 step이다. Stage 3은 면적 1024^2 이하 혼합 해상도, 텍스트 4096, 370,000 step이다. 그런데 PDF Table 1에는 Stage 4(최대 2x1024^2, 4096, 520,000 step)가 따로 있다. 반면 본문과 부록 A.2는 'three stages'라 쓰고, 그림 3c는 Stage 3을 0.31M step으로, 부록 A.2는 최종 Stage 3 체크포인트를 step 310,000의 EMA 가중치로 적는다. Stage 3 noise 스케줄(Table 6)도 274,001-310,000에서 끝난다. 즉 Table 1의 370,000과 Stage 4가 다른 기술과 맞지 않는다. 논문 평가에 쓴 체크포인트와 공개된 Base 가중치가 같은 것인지도 명시되어 있지 않다.
  • 연산 자원(부록 A.2 Text formatting and packing): 512 devices, gradient accumulation 2, device당 microbatch 최대 8576 토큰, update당 명목 용량 8,781,824 토큰이다. 최종 모델의 GPU 종류, 총 GPU-hours, 학습 기간은 원문에서 확인되지 않는다. PDF 전문에서 GPU, H100, A100, hours, device를 검색했는데, 'GPU'는 부록 B.2의 소형 필터 실험(32 GPUs)에만 나온다. README는 'Trained on alternative GPU platforms'(Heterogeneous GPU training)라고만 적는다.
  • 최적화와 노이즈 스케줄(PDF Table 6, 7): AdamW와 Muon 모두 lr 5e-5이고 Muon은 RMS-matched, momentum 0.95, Newton-Schulz 5 step이다. AdamW betas는 (0.9, 0.95), weight decay 0.01, grad clip 1.0, EMA 0.9999, warmup 2000 step이다. Stage 3 timestep 샘플링은 4개 구간으로 바뀐다. 첫 구간은 shift 3에 logit-normal (0,1)이고, 이어서 shift 1에 (-1.45,1.05), 같은 분포에 cutoff 0.95, 마지막으로 (-1.09,0.95)에 cutoff 0.95를 쓴다. 마지막 구간에는 uniform 1%를 섞고, 앞 두 구간은 full-noise 끝점을 확률 0.01로 따로 뽑는다. 텍스트 토큰은 손실에 들어가지 않는다.
  • 예비 ablation은 최종 5B가 아닌 소형 모델로 수행했다. 1회 실행임이 명시된 것은 그림 5(필터)와 그림 7(Muon)이고, RoPE 비교의 실행 횟수는 적혀 있지 않다. 데이터 필터 비교(부록 B.2)는 24층 multi-stream DiT, Qwen3.5-0.8B, ViViT2-REPAE autoencoder, 256x256, 32 GPU, 배치 1024, 1.6M step으로 돌렸다. 평가는 DPG-Bench, GenEval, OneIG, FDR6-LAION(5만 장, CFG sweep 중 최솟값)이다. 결과는 OneIG text 0.5243 대 0.1180, DPG 82.420 대 82.411(거의 동일)이다. 저자는 학습 데이터가 다르면 FDr6가 공정한 비교가 아닐 수 있으니 경향으로만 읽으라고 단서를 단다. RoPE 비교(부록 D)는 1B 모델로 DPG-Bench, GenEval, OneIG를 봤다. 채택한 sequential text-image r=0 배치는 200K step에서 GenEval이 네 설계 중 가장 낮았다(0.6026, baseline 0.6313). 반면 OneIG는 가장 높았고(0.3605, baseline 0.3483) DPG-Bench는 baseline과 거의 같았다(81.89 대 81.94). 저자는 설계 간 전체 성능이 비슷하고 지표별 trade-off가 있다고 정리한다. 이 배치를 고른 이유로는 성능이 아니라 참조 인덱스 축의 확장성을 든다. 800K-1.25M step 장기 비교에는 baseline과 modality 분리 두 변형만 들어가고 채택안은 빠졌다. Muon 비교(부록 E)는 1.016B 모델, 256x256, 1.6M step에서 학습 denoising loss로만 평가했다.
  • LLTB 설정(5.1절, 부록 G.1, PDF Table 2/4/15): 영어와 중국어 각 120개, 총 240 과제를 3개 길이 구간에 나눴다. 각 입력은 'A paper writes:' 접두어, 제목, 저자, 본문으로 구성된다. 본문 줄바꿈은 DejaVuSans 글꼴 기준 1024x1024 캔버스(여백 88픽셀)에서 자동 줄바꿈해 미리 넣는다. 모든 모델이 같은 입력을 받지만, 줄바꿈까지 보존한 전사로 학습한 MOSS와 잘 맞는 형식일 수 있다(분석자 해석, 저자는 논하지 않음). 모델마다 과제당 4장을 생성해 4장 모두 채점하며 best-of-4는 쓰지 않는다. OCR은 Qwen2.5-VL-7B-Instruct(출력 4096 토큰)로 하고 이미지는 1024x1024로 LANCZOS 리사이즈한다. 생성 해상도는 모델별 지원 설정을 따른다. PE 없이 backbone 단독으로 평가하며, MOSS-Image 자신의 CFG와 step 수는 원문에서 확인되지 않는다(PDF에서 CFG를 검색하면 부록 B.2와 Ideogram 관련 문장에만 나온다). Ideogram 4는 CFG 4로 돌렸고 거부 이미지는 0점 처리했다.
  • 7Bench 설정(부록 G.4, PDF Table 3/19/20): 224개 prompt-layout 쌍, 576개 대상 객체, 모델당 1장을 생성했다. 폐쇄형 모델(GPT Image 2, Nano Banana Pro, Seedream 5.0 Pro, Qwen Image 3.0 Pro)에는 원래 vision JSON 프롬프트를 1024x1024로 넣었다. Ideogram 4는 공개 FP8 체크포인트, CFG 4, 규칙 변환한 JSON으로 돌렸다. MOSS-Image 자신에게 어떤 입력 형식과 좌표 체계를 넣었는지는 원문에서 확인되지 않는다. 채점은 Extended TIFA와 OWL-ViT의 IoU로 하며, 탐지에 실패한 객체와 차단된 출력은 0점이다. GPT Image 2는 224건 중 22건이 안전 차단되었다.
  • LongTextBench(부록 G.4, PDF Table 18): 베이스라인 점수는 저자가 직접 돌리지 않고 공개 보고서에서 가져왔다. LLTB, 7Bench, RLA 점수는 모두 저자들이 직접 평가했다(5.1절).
  • RLA 설정(5.1절, 부록 G.2, G.3, PDF Table 17): 수작업으로 고른 디자인 레퍼런스에서 61 과제(포스터 20, 인포그래픽 20, UI 21)를 만들었고 각 과제는 짧은 중국어 요청이다. participant(생성기+프롬프트 전략 조합)마다 과제당 1장, 가능하면 고정 seed로 생성하고 재샘플링은 하지 않았다. 해상도는 약 1MP에 31종이다. 평가자는 원래 짧은 요청만 보고 모델명이 가려진 상태에서 A/B/tie/both bad/skip 중 하나를 고른다. tie와 both bad는 0.5승으로 셈한다. 점수는 Bradley-Terry를 Elo 척도(1500 + 400/ln10 x theta)로 변환하고 asymptotic 95% CI를 붙였다. 각 participant에는 0.25 pseudo-win/loss를 더한다. 표는 세 그룹으로 따로 적합했고 투표 수는 1420, 1533, 576이다. 평가자 수, 신원, 소속, 보상은 원문에서 확인되지 않는다(PDF에서 rater, annotator, crowd, volunteer를 검색함).
  • RLA 구성 차이(부록 F.1, G.3): 메인 시스템은 최종 Layout PE로 과제마다 독립 세션을 돌렸다. 반면 프롬프트 전략 ablation과 공유 프롬프트 backbone 비교에는 61 과제 전체를 한 컨텍스트에서 계획한 이전 버전 PE를 썼다. 베이스라인 8개 시스템은 원래 짧은 요청을 받아 각자의 PE 파이프라인을 쓰며, Ideogram 4에는 로컬 Qwen3VL-8B PE를 붙였다. 공유 프롬프트 비교는 Layout PE 명세를 자연어로 다시 쓴 같은 프롬프트(좌표, 픽셀 크기, 색을 산문으로 표현)를 생성기들에 넣은 것이다. 그림에는 9개가 나오고 Table 17에는 10 participants로 적혀 있다.
  • 보조 루브릭 평가(부록 H, PDF Table 21): 61 과제에 대해 GPT-6가 6개 차원(가중치 30/20/15/10/20/5)을 0-5점으로 매기고 이를 0-100점으로 환산한다. 계획을 세운 모델과 채점하는 모델이 같은 GPT-6라는 점은 저자 스스로 밝힌다. 패널 (a)와 (b)의 MOSS JSON layout 항목은 서로 다른 PE 버전으로 만든 것이라 직접 비교할 수 없다는 점도 저자가 명시한다.
  • 분산과 반복: LLTB는 과제당 4개 샘플이지만 seed 간 분산이나 표준편차는 보고하지 않는다. RLA는 participant당 이미지 1장이다. 예비 ablation 곡선(그림 5, 7)은 'Each curve represents one training run'이다. CI는 같은 과제나 같은 평가자 투표 사이의 상관을 보정하지 않는다고 저자가 명시한다. 추론 시간과 VRAM은 논문에 보고되지 않는다(PDF에서 VRAM, latency 검색 결과 0건).

  • 7Bench — 224 prompt-layout 쌍, 7개 범주 x 32, 576개 대상 객체 (레이아웃(bbox) 조건 생성)
  • DPG-Bench, GenEval, OneIG, FDR6-LAION — FDR6-LAION은 체크포인트당 생성 이미지 50,000장. 최종 5B 모델의 GenEval, DPG-Bench, OneIG 점수는 보고되지 않음 (일반 T2I 정렬과 분포 품질 (예비 ablation에만 사용))

한계 · 비판

  • backbone은 text-to-image만 지원하고 참조 이미지 조건이나 편집은 지원하지 않으며, 현재 연산 예산에서 향후 과제로 남긴다(8장 Limitations). 참고로 Comfy-Org/MOSS-Image 저장소에는 moss_image_edit_lora와 color_depth_control LoRA 파일이 있으나 논문에는 등장하지 않는다. Comfy-Org 모델 카드는 이 파일들의 원 저장소를 제3자 커뮤니티 저장소인 chinoll/Moss-Image-Edit와 darask0/MOSS-Image-color-depth-control로 밝힌다. USERGUIDE도 간단한 SFT로 참조 기반 생성이 가능했다고만 적고 'Stay tuned'로 남긴다. (저자 인정)
  • prompt enhancer가 외부 언어 모델에 의존하므로, 그 모델의 미적 판단, 참조 해석, 사실 오류가 렌더링이 충실해도 명세 품질을 떨어뜨릴 수 있다(8장 Limitations). 8장 원문은 'external language models'라고만 쓰며, 실제 사용 모델이 GPT-6라는 점은 4장과 부록 F.1에 나온다. 초록에는 이 의존성이 언급되지 않는다. (저자 인정)
  • 결과는 완성된 모델을 특성화할 뿐 개별 사전학습 선택의 인과적 기여를 분리하지 않는다고 명시(5.2절). 학습 캡션은 주로 영어이고 중국어 전용 캡션 주석이 없다(부록 B). 가장 긴 중국어 조건 ZH-L 92.4는 GPT Image 2의 98.2보다 낮다(PDF Table 4). (저자 인정)
  • LLTB coverage는 OCR multiset recall이라 순서를 확인하지 않고 추가 OCR 단위에 직접 벌점을 주지 않으며 edit distance나 exact string accuracy가 아니다(부록 G.1). Ideogram 4 거부 이미지 처리 규약에 따라 Mean-6이 63.5에서 68.1로 바뀐다(PDF Table 16). 7Bench에서 Ideogram 4 자체 보고 mIoU 약 0.69와 저자 측정 0.2433의 차이는 모델 변형(FP8), 프롬프트 형식, 평가 구현 차이 때문일 수 있다고 인정(부록 G.4). (저자 인정)
  • RLA의 95% CI는 같은 과제나 같은 평가자 투표 간 상관을 보정하지 않는다(부록 G.2). 보조 루브릭 평가는 GPT-6가 planner와 judge를 겸하고 상위 설정 간 분리력이 낮아(프롬프트 전략 간 0.52pt) 인간 평가를 주 근거로 삼는다고 밝힌다(부록 H). (저자 인정)
  • 새로 만든 두 벤치마크는 아직 외부에서 검증할 수 없다. 초록은 'evaluation framework' 공개를 약속하지만, 2026-10-26 기준으로 LLTB와 RLA의 데이터와 평가 코드를 찾지 못했다. 확인 방법은 세 가지다. (1) GitHub repo 트리(shallow clone)에는 inference_runtime.py, gradio_app.py, gradio_presets.py, scripts/gradio.sh, comfyui, skills, website, paper, assets, 문서 파일만 있다. (2) HF datasets의 author=OpenMOSS-Team 목록 39개에도, LongLongTextBench, LLTB, RealLayoutArena 이름 검색에도 나오지 않는다. (3) 논문에 적힌 HF 컬렉션 링크는 오늘 401을 반환했다. LLTB, 7Bench, RLA의 베이스라인은 모두 저자가 직접 돌렸다. RLA 평가자의 수, 소속, 독립성은 원문에서 확인되지 않는다. RLA 과제 범주(포스터, 인포그래픽, UI)도 PE의 세 라우팅 모듈과 정확히 겹친다. (추가 의문)
  • RLA 순위는 통계적으로 확정적이지 않다. end-to-end에서 MOSS의 95% CI 1655.96-1741.43 안에 3위 Seedream 5.0 Pro의 점추정치 1661.16이 들어간다. 공유 프롬프트 비교에서도 MOSS의 CI 1727.44-1887.24 안에 2위 ERNIE Image의 1748.51이 들어간다. participant마다 과제당 이미지가 1장뿐이고, 공유 프롬프트 그룹은 576표에 task-pair 커버리지 19.6%다. 저자도 이 CI가 상관을 보정하지 않는다고 인정한다. 다만 같은 방향을 가리키는 보조 근거가 있다. GPT-6 루브릭에서도 MOSS는 end-to-end 2위(94.93, GPT Image 2 97.72, 3위 Qwen Image 3.0 Pro+PE 93.64)이고 공유 프롬프트 1위(87.62 대 SenseNova U1 79.51)다. 원시 전적도 메인에서 293승 100무 64패, 공유 프롬프트에서 98승 18무 12패다. 단, 루브릭 judge는 planner와 같은 GPT-6다. 따라서 '2위'와 '1위'는 여러 신호가 일치하는 점추정 순위로 읽되, 인접 순위와의 차이는 확정되지 않았다고 보는 것이 맞다. (추가 의문)
  • 'agentic' PE가 따로 얼마나 기여하는지는 입증되지 않았다. 인간 평가 결과는 JSON layout 1622.87, Direct expansion(에이전트 없는 확장) 1541.45, Detailed 1509.21, Natural(PE 계획을 산문으로) 1506.20, Short 1081.70이다. 즉 큰 이득은 '짧은 요청 대 상세 명세'에서 나온다. PE 계획을 산문으로 바꾸면 단순 확장보다 오히려 낮다. GPT-6 루브릭에서는 Direct expansion 95.59가 JSON layout 95.07보다 높아 순서가 뒤집힌다. 이 ablation은 메인 시스템과 다른 이전 버전 PE(61 과제를 한 컨텍스트에서 계획)로 돌렸고, 본문에 CI 수치도 없다. '에이전트 없는 JSON' 조건도 없어서 형식 효과와 agentic 계획 효과를 분리할 수 없다. (추가 의문)
  • 레시피 기술이 문서 안에서 서로 맞지 않고, 재현에 필요한 정보가 빠져 있다. 본문(3.3절)과 부록 A.2는 'three stages'라 쓰지만 PDF Table 1에는 Stage 4(최대 2x1024^2, 520,000 step)가 있다. Stage 3도 Table 1은 370,000 step인데, 부록 A.2, Table 6, 그림 3c는 310,000으로 적는다. 최종 모델의 GPU 종류, GPU-hours, 학습 기간은 적혀 있지 않다(512 devices만 기재). 공개된 MOSS-Image-Base가 평가 체크포인트(Stage 3 step 310,000 EMA)와 같은지도 명시되지 않았다. MOSS-Image-SFT는 논문에 나오지 않고, README가 'Fine-tuned from MOSS-Image-Base on curated data'라고만 설명한다. 저자들은 부록 L에서 Ideogram 4가 추론 코드는 냈지만 완전한 사전학습 레시피는 밝히지 않았다고 대비하고, 자신들은 코퍼스, 감독, 학습 스케줄을 문서화했다고 말한다. 이 주장은 논문 텍스트 수준에서는 맞다. 그러나 초록은 'training recipe' 공개를 약속했는데, 실제로 사전학습, 데이터 필터링, 재캡션 파이프라인 코드는 repo에 없다. 레시피는 논문 텍스트(와 USERGUIDE 일부) 수준으로만 공개된 상태다. (추가 의문)
  • 공개 비교에서 진 결과와 비교 조건이 초록에 드러나지 않는다. LongTextBench에서 MOSS는 97.63으로 10개 중 5위다(1위 98.85와 1.22pt 차). 이 벤치마크의 베이스라인 수치는 공개 보고서에서 가져왔다(PDF Table 18). 저자들은 수록 점수가 96.05-98.85에 몰려 포화에 가깝다고 보고 이 결과를 부록의 보조 근거로 돌렸다. 이 판단 자체는 표의 분포와 맞는다. LLTB에서는 GPT Image 2(99.0)와 Nano Banana Pro(96.6)가 MOSS(96.3)보다 높다. 7Bench에서 MOSS는 AUC 0.7031로 크게 앞선다. 차순위 0.2046은 bbox 입력을 지원하는 오픈 웨이트 Ideogram 4.0이며, 공개 FP8판, CFG 4, 규칙 변환 JSON 조건에서 나왔다. 이 모델의 자체 보고 mIoU 약 0.69와 저자 측정 0.2433 사이에 큰 차이가 있다는 점은 저자도 인정한다. 폐쇄형 4개(AUC 0.1554-0.1794)에는 원래 vision JSON 프롬프트를 그대로 넣었고, 이 모델들이 bbox 좌표 입력을 얼마나 지원하는지는 논문에서 다루지 않는다. MOSS 자신의 7Bench 입력 형식도 적혀 있지 않다. 최종 5B 모델의 GenEval, DPG-Bench, OneIG 점수는 보고되지 않았다. '5B'는 DiT만 센 크기이고(저자도 부록 A.1에서 명시), 추론에는 Qwen3.5-9B 인코더가 함께 필요하다. HF 저장소의 bf16 합계는 27.23GB다. (추가 의문)

재현 가능성

코드 추론 코드만 공개되어 있다(Apache-2.0). 2026-10-26에 GitHub OpenMOSS/MOSS-Image 트리를 확인했다. 들어 있는 것은 inference_runtime.py(Diffusers 커스텀 파이프라인), gradio_app.py, gradio_presets.py, scripts/gradio.sh, comfyui/, skills/moss-image-prompt-enhancer/(SKILL.md, 좌표 변환 스크립트), website/, paper/MOSS_Image_Technical_Report.pdf, .github/workflows다. 사전학습 코드, 데이터 필터링(SSCD 중복 제거, AI 이미지 탐지), 재캡션과 레이아웃 주석 파이프라인, LLTB와 RLA 평가 코드는 없다. 논문에서 쓴 GPT-6 Layout PE 프롬프트 원문도 공개되지 않았다. 공개 skill은 summary/items 스키마와 abs_centralized yxyx 좌표를 쓰고, 웹 검색은 선택 사항으로 둔다. 부록 F의 8필드, [0,1000] 정규화 좌표 planner와는 다르다. 다만 6장 case study에서 저자들은 0 중심 절대 좌표가 학습에 없던 해상도에 더 잘 일반화된다고 관찰했고, 공개 skill의 좌표 방식은 이 관찰과 일치한다.가중치 HF에 OpenMOSS-Team/MOSS-Image-Base와 OpenMOSS-Team/MOSS-Image-SFT가 공개되어 있다. 생성일은 각각 2026-10-11, gated는 아니며 라이선스는 apache-2.0이다. Base 저장소의 bf16 합계는 27.23GB(transformer 10.16GB, text_encoder 16.79GB, VAE 0.25GB)로 HF API의 blobs 크기로 확인했다. Comfy-Org/MOSS-Image에는 DiT int8 5.41GB, Qwen3.5-9B int8 9.75GB, w4a8 GPTQ 7.34GB 판이 있다. 공개 Base가 논문 평가 체크포인트와 같은지는 명시되어 있지 않다. USERGUIDE는 Base가 'has not undergone any post-training or distillation'이라고 적는다. 사전학습 결과물이라는 점은 이것으로 뒷받침되지만, 특정 step(310,000 EMA)과 같은지는 여전히 확인되지 않는다. SFT 모델은 논문에서 설명되지 않는다.데이터 사전학습 데이터는 16개 공개 소스(ReLAION, OmniCorpus, DataComp 등, PDF Table 8)에서 왔지만, 필터링 후 목록, gemma4 재캡션, 레이아웃 JSON 주석은 공개되지 않았다. 저자 제작 벤치마크 LLTB(240 과제)와 RLA(61 과제, 투표 기록)는 찾지 못했다. 확인 범위는 GitHub repo 트리, HF datasets author=OpenMOSS-Team 목록 39개(키워드에 걸린 것은 무관한 VehicleArena뿐), 그리고 논문의 HF 컬렉션 링크(오늘 401)다. LongTextBench와 7Bench는 외부 공개 벤치마크다.라이선스 Apache-2.0. repo의 LICENSE 파일(Apache License Version 2.0)과 두 모델 카드(license: apache-2.0, 'model weights and bundled inference code are released under the Apache License, Version 2.0')에서 확인했다. 논문은 arXiv에서 CC BY 4.0이다. 함께 묶인 구성요소도 HF API cardData 기준으로 Apache-2.0이다. Qwen/Qwen3.5-9B는 apache-2.0이고, 논문 Table 5에 적힌 VAE 로드 출처 black-forest-labs/FLUX.2-klein-4B도 apache-2.0이다(2026-10-26 조회).

초록의 'will release' 가운데 모델은 이미 공개되었다. 반면 학습 레시피는 논문 서술 수준이고 평가 프레임워크는 미공개 상태다(2026-10-26 기준). 공식 런타임은 CUDA 메모리가 40 GiB 미만이면 자동으로 model CPU offload를 켠다(inference_runtime.py configure_pipeline). 권장 설정은 Euler 50 step, CFG 3이다. 추론 시간과 VRAM 실측치는 논문, README, 모델 카드 어디에도 없다. README에는 day-0 서빙 지원(SGLang, vLLM-Omni, ComfyUI)과, 커뮤니티 파생물인 DiffSynth-Studio 기반 full fine-tuning과 LoRA 학습이 링크되어 있다. 이 밖에 8-step DMD 증류판, KohakuMossTrainer, FP16 호환 가중치(KBlueLeaf/MOSS-Image-FP16-fixed)도 있다. KohakuMossTrainer는 최소 6GB VRAM 어댑터 학습과 Windows 지원을 내세우는데, README에 있는 제3자 주장이며 검증하지 않았다. 논문 수준의 end-to-end 결과를 재현하려면 폐쇄형 GPT-6 API가 필요하다.

📌 내 학습 포인트

  • plan-first 생성에서 '에이전트를 더 복잡하게 만드는 것'보다 '렌더러가 학습한 명세 형식으로 넘기는 것'이 효과가 컸다는 신호가 있다. 다만 교란이 있다. RLA 인간 평가에서 같은 PE 계획도 JSON layout(1622.87)으로 넣으면 산문 변환(1506.20)보다 높았고, 에이전트 없는 단순 확장(1541.45)은 산문 변환보다 높았다. 하지만 JSON 우위는 같은 JSON 스키마로 학습한 렌더러에서 나온 결과다. 또 '에이전트 없는 JSON' 조건이 없어서 형식과 계획의 기여를 분리할 수 없다. Claude Code에서 '계획 subagent -> 실행 subagent' 구조를 만든다면 두 가지를 해 볼 만하다. 첫째, 실행 측이 실제로 잘 따르는 고정 필드 JSON(must_not, 그대로 보존할 문자열, 좌표 등)으로 계획을 넘기고 hook이나 스크립트로 스키마를 검증한다. 둘째, 비교 기준에 반드시 '에이전트 없이 한 번에 확장' baseline을 넣어 agentic 단계의 추가 이득을 따로 잰다. 이 결론은 이미지 생성 61 과제, 이미지 1장 기준이며 LLM 간 계획 전달로 옮길 때는 직접 확인해야 한다.
  • 로컬 실행 조건을 '5B'라는 숫자로 판단하면 안 된다. 공식 bf16 가중치는 DiT 10.16GB + Qwen3.5-9B 인코더 16.79GB로 합계 27.23GB다. 메모리 동작은 실행 방식에 따라 다르다. repo의 inference_runtime.configure_pipeline은 offload='auto'일 때 CUDA 메모리가 40 GiB 미만이면 model CPU offload를 켠다. 반면 README의 Python 예시는 pipe.to('cuda')로 전부 GPU에 올리고, Gradio는 메모리 모드(GPU resident, Component, Sequential)를 고르게 한다. NVIDIA GPU가 있는 Windows PC라면 ComfyUI와 Comfy-Org의 int8 DiT(5.41GB) + w4a8 인코더(7.34GB) 조합이 가장 현실적이다. 이 경우 가중치만 약 12.75GB이므로 16GB급 이상을 가정한다(문서 기반 추정). 시간과 VRAM 실측치는 어디에도 없으니 직접 재야 한다. PE는 필수가 아니다. 직접 쓴 JSON layout을 넣을 수 있고, Apache-2.0인 SKILL.md를 Claude Code skill로 옮겨 계획 단계를 대신 맡기는 실험이 가능하다. 다만 공식 대상은 GPT-6 계열이고, 공개 skill은 논문 Layout PE와 스키마가 다르다.
  • 주간 트렌드 시스템의 카드에 '자체 벤치마크 점검' 필드를 두면 좋다. 이 논문이 좋은 예다. (1) 벤치마크 공개 여부: LLTB와 RLA는 미공개. (2) 지표 정의: coverage는 순서를 무시하는 recall이다. (3) 베이스라인을 누가 돌렸나: 저자 직접, Ideogram은 FP8. (4) 1위 주장의 CI가 2위 점추정을 포함하는가: 포함한다. (5) judge가 생성 측과 같은 모델인가: GPT-6가 planner와 judge를 겸한다. (6) 공개 벤치마크에서 진 결과: LongTextBench 5위. 초록만 보고 tier1 카드를 쓸 때는 'SOTA among open-weight' 같은 한정어를 그대로 옮기고, 폐쇄형 대비 격차(LLTB 96.3 대 99.0)를 함께 적는 규칙을 만들 수 있다.

Claude 종합 코멘트

무엇이 새로운가. 처음부터 사전학습한 5B single-stream DiT 하나가 자연어 캡션과 bbox JSON 레이아웃을 별도 제어 모듈 없이 같은 텍스트 경로(Qwen3.5-9B 인코더)로 받는다. 학습은 공개 데이터를 추가 품질 필터 없이 거의 그대로 쓰고, 다중 길이 재캡션과 줄바꿈까지 그대로 옮긴 전사로 진행한다. 여기에 폐쇄형 GPT-6 기반 Layout PE를 앞단 계획기로 붙인다. 장문 텍스트 렌더링용 LLTB와 end-to-end 디자인 평가용 RLA를 새로 만든 것도 기여다.

증거 강도는 항목마다 다르다. LLTB Mean-6 96.3으로 오픈 웨이트 1위(2위 64.9)라는 결과는 격차가 커서 비교적 단단하다. 하지만 지표가 순서를 무시하는 OCR recall이고, 베이스라인을 모두 저자가 돌렸으며, 벤치마크도 아직 공개되지 않았다. 폐쇄형인 GPT Image 2(99.0)와 Nano Banana Pro(96.6)는 MOSS보다 높다. 7Bench AUC 0.70은 차순위 Ideogram 4(0.20, FP8판)와 폐쇄형(0.16-0.18)을 크게 앞선다. 다만 비교 조건이 모델마다 다르고, Ideogram은 자체 보고치와 크게 어긋난다. RLA 2위와 공유 프롬프트 1위는 95% CI가 바로 아래 순위 시스템의 점추정과 겹치고 participant당 이미지가 1장이다. 그래도 GPT-6 루브릭(planner와 같은 judge라는 한계 있음)과 원시 승률이 같은 순위를 가리킨다. PE의 agentic 요소가 따로 주는 이득은 지표에 따라 뒤집히고, 형식 효과와 분리되지 않는다. 레시피 요소별 기여는 소형 모델 예비 실험뿐이고, 학습 단계와 step 수가 문서 안에서 서로 맞지 않는다.

적용 조건도 있다. 가중치는 Apache-2.0으로 공개되었지만 bf16 기준 27.23GB이고, 속도와 VRAM 실측치는 없다. 공식 runtime의 auto 모드는 40 GiB 미만 GPU에서 offload를 켠다. 논문 수준의 end-to-end 성능을 내려면 외부 GPT-6 API가 필요하다. 사전학습 코드와 평가 코드는 공개되지 않았다(2026-10-26 확인).

인용할 때는 조건을 붙여야 한다. LLTB는 'LLTB에서 오픈 웨이트 모델 중 최고(Mean-6 96.3, PE 없는 backbone, 저자 자체 벤치마크)'로 적는다. RLA는 'GPT Image 2에 이은 2위(1698.70 Elo, CI가 3위 점추정과 겹침)'로 적는다. '5B'는 텍스트 인코더를 뺀 DiT 크기라고 함께 밝히는 것이 정확하다.

방법 상세

정의와 규범. 서론은 개인 에이전트를 한 사람의 계정·기기·파일에서 그를 대신해 몇 주씩, 일부는 그가 없을 때 일하고, 나중에 로그·장부(ledger)·보유 권한 목록으로 해명하는 프로그램으로 정의한다. 4절은 스스로 '의견'이라 밝히며 다섯 질문(무엇을 아는가, 어디서 행동하는가, 누구에게 답하는가, 어떻게 배우는가, 비용과 거버넌스)을 세 지평(2026년에 있는 것, 오픈 대응물이 다음에 더할 것, 몇 년 가는 에이전트)에 걸쳐 답하고, 5절의 nanoMuse가 그 대부분에 못 미친다고 쓴다.

Muse 읽기. 근거는 Meta 공개 문서 4건, 출시 클라이언트 관찰, 2026년 10월에 읽었다는 프로덕션 시스템 프롬프트 사본이며 진술마다 documented·prompt·observed·inferred를 붙인다. 사본은 재현하지 않고 한 번에 몇 단어까지만 인용한다는 자기 제한만 밝힐 뿐 입수 경위는 쓰지 않고, 7절은 그 출처를 공개 문서·클라이언트와의 일관성 이상으로 검증할 수 없으며 프롬프트는 배포마다 바뀐다고 인정한다. 입수와 사용에 관한 법적·윤리적 논의는 없다.

기기와 릴레이. v0.1.40은 Android 앱(OpenMinis 수정본: 샌드박스 Alpine Linux, 셸, 브라우저, MCP, 스킬, 예약 작업), iOS 앱(TestFlight, 손 없음), macOS·Windows·Linux 데스크톱(DeepSeek Harness를 감싼 Electron 앱, Python 런타임 내장), 웹 앱, 릴레이 nanoMuse Cloud로 이뤄진다. 논문 설명으로는 기기마다 완결된 에이전트와 Sentinel이 있고 서로를 도구로 부르며, 넘겨받은 작업은 받은 기기의 Sentinel 아래서 돌아 권한을 빌려줄 수 없다. 저장소 문서상 각 기기는 릴레이의 /v1/hub에 바깥쪽 WebSocket 하나를 열어 두고, 릴레이는 같은 계정의 기기 사이에서만 프레임을 라우팅한다. 릴레이는 Python 프로세스 하나와 SQLite 파일 하나이며, 커뮤니티 릴레이는 프로젝트가 운영하고 Docker로 셀프호스팅할 수 있다.

손. 에이전트는 skill·CLI·MCP -> 로그인된 페이지 -> 브라우저 -> 화면 순서의 사다리에서 되는 가장 낮은 단을 쓰고, 화면 단(Hands)은 기본 꺼져 있다. 스크린샷 하나에 행동 하나인 루프에서 모델은 화면·목표·단계별 한 문장 이력·접근성 요소를 보고 생각, 할 일을 사람의 언어로 말하는 한 문장(라벨), 제스처 하나를 낸다. 휴대폰은 MemGUI-Bench의 mobile_use 오퍼레이터 형식, 컴퓨터는 UI-TARS-desktop 이식이다. 저장소상 Android 손은 자체 접근성 서비스로 돌아 Android 11 이상이 필요하고, 7절에 따르면 Linux에서는 X11 세션만 된다.

Sentinel. 논문에서 에이전트는 도구를 직접 실행하지 않고, 모든 호출이 거부 도구 -> 사람의 규칙 -> 항상 허용·질문 목록 -> taint -> 위험도 x 모드 -> 경고의 고정 순서를 지난다. 모델 분류기 없는 규칙 기반이다(저장소 코드 확인). 논문은 비공개 데이터를 읽은 대화에서 허용 목록 밖으로 내보내는 호출이 질문이 되고, 파괴적 명령·즉석 실행 다운로드·확정어 라벨 같은 경고는 어떤 모드와 목록도 통과시키지 못한다고 쓴다. 그러나 논문이 기술한 v0.1.40 코드(nanomuse/sentinel/gate.py)는 auto 모드에서 모든 질문을 허용으로 바꿔 auto 모드에서는 이 두 보장이 성립하지 않았고, 1.0.0과 1.0.2에서 고쳐졌다(기본값인 ask 모드는 해당 없음). 화면 단계는 그림이 아니라 라벨 문장을 판정하며, Android는 손가락 아래 접근성 텍스트와 비교해 더 엄격한 쪽을 따른다. 승인은 한 번·이 대화·대상별 항상의 grant로 Permissions에서 회수할 수 있고, 거부되면 실행하지 않고 같은 호출을 재시도하지 말라는 결과를 모델에 돌린다(저장소). 저자들은 이를 Muse의 권한 경계가 아닌 같은 프로세스 계열의 정책 경계라 부른다. 저장소상 이 결정 순서와 taint는 Python 런타임 구현이고, Android는 별도 Kotlin 규칙, 설치형 데스크톱 앱은 DeepSeek Harness 승인 정책에 손·메일 도구용 게이트를 더한 형태다.

나머지. 휴대폰 메모리는 SOUL.md·USER.md·GLOBAL.md·일기·HEARTBEAT.md 등 Markdown 파일이다. 논문이 말하는 컴퓨터 쪽 저장소(줄 단위, 변경 로그와 되돌리기, 드문 단어 또는 임베딩으로 회상, 사람이 쓴 줄은 지우지 않는 정리 단계)는 저장소상 Python 런타임(웹 앱·셀프호스팅)의 SQLite memory.db이고, 설치형 데스크톱 앱은 rooms.json에 줄 목록을 따로 둔다. 줄마다 모델·날짜·확신도를 남기는 출처는 로드맵이다. 모델은 18개 공급자의 자기 키, ChatGPT 플랜, 자기 기계의 모델 서버, 커뮤니티 릴레이의 모델 중에서 고른다. 먼저 말하기는 숨은 대화로 쓰는 Feed·Ideas·Goals와 사람이 옮기는 끼어들기 문턱이며, 일정 사이의 능동성은 로드맵이다. 책임은 Sentinel 결정 로그, 권한 목록, 릴레이의 호출 장부(모델·토큰·비용), 손의 궤적 기록으로 지며, 외부 보안 감사는 보고하지 않는다.

실험 셋업

  • 정량적 과제 평가는 없다. 7절('The hands are judged by their words, and not yet measured')에서 저자들은 손의 성공률과 사람 개입(take-over) 횟수가 아직 존재하지 않으며 추정하지도 않겠다고 명시한다. 비교 실험, 사용자 연구, 벤치마크 결과도 본문 전체에 없다(evaluat, benchmark, measure, success rate로 전문 검색해 확인).
  • 데이터셋은 쓰지 않았다(datasets는 빈 목록). AndroidWorld·OSWorld·MemGUI-Bench·OS-Harm은 nanoMuse를 잴 도구로는 6절 Next의 계획으로만 나오고, AndroidWorld·OSWorld는 2절 역사 서술에서 기존 모델의 평가 환경으로도 언급된다.
  • 보고된 수치는 표 2(5절 'Running it yourself')뿐이다. 캡션에 따르면 크기는 릴리스 파일과 1회 설치, 메모리는 Linux 워크스테이션 1대에서 잰 값이고, 비용은 프로젝트 문서와 공급자 가격표에서 낸 추정이며 누구의 실사용도 측정하지 않았다.
  • 앱 크기(표 2): Android 38 MB(arm64 다운로드), 데스크톱 256 MB(Linux)~498 MB(macOS) 다운로드, Windows 266 MB, Linux 설치 후 928 MB, 유휴 시 전체 프로세스 합 약 0.5 GB(비례 집합 크기, PSS).

  • 비용 추정(표 2): 자체 릴레이용 최소 서버 월 30~60위안(중국 본토) 또는 US$4~6(그 밖) + 모델 사용료. Bailian 2026년 10월 가격표 기준 채팅 모델 혼잡 시간대 백만 토큰당 입력 2위안·출력 8위안, 손 모델 3위안·12위안, 하루 채팅은 몇 펀(fen). 본문은 모델 이름을 밝히지 않는다.
  • Muse 분석(3절)은 실험이 아니라 문서 읽기다. Meta 공개 문서 4건(발표문, 안전 아키텍처 에세이, 디자인 에세이, 개인정보 도움말), 출시 클라이언트 관찰, 2026년 10월에 읽은 프로덕션 시스템 프롬프트 사본을 근거로 진술마다 documented·prompt·observed·inferred를 표시하며 정량 비교는 없다.
  • 평가 계획(6절 Next, 그림 6): 실패한 실행으로 만든 자체 평가 세트를 공개 벤치와 나란히 돌려 릴리스마다 인상 대신 숫자를 내고, 그다음 사람들이 기여한 trace로 손 전용 소형 오픈 모델을 학습한다(MobileForge 방식 참조). 날짜는 없다.

한계 · 비판

  • 정책 경계일 뿐 권한 경계가 아니다: 단일 기기에서 Sentinel은 에이전트와 같은 신뢰 영역에서 돌고, 실제 자격증명을 쥔 바깥 호스트가 없어 기기 침해가 곧 에이전트 침해다. 결정 순서·taint 규칙·Linux 샌드박스는 완화일 뿐 해결이 아니다. (7절 'A policy boundary is not a privilege boundary') (저자 인정)
  • 손은 말로 판정되고 아직 측정되지 않았다: 아이콘만 있는 버튼은 라벨로도 접근성 텍스트로도 판정되지 않고, 촘촘한 전문가용 화면에서는 찾는 것 자체가 미해결이며, 지켜보는 사람이 마지막 방어선이다. 성공률과 개입 횟수는 없고, Linux는 X11 세션만 된다. (7절 'The hands are judged by their words, and not yet measured') (저자 인정)
  • 메모리는 누가 썼는지 모른다: 약한 모델이 추측한 줄을 강한 모델이 사실로 읽는다. 저장소는 바뀐 시점과 되돌리기를 기록하지만 모델·날짜·확신도는 없고 오래된 줄의 재검증 규칙도 없다. (7절 'Memory does not yet know who wrote it') (저자 인정)
  • 릴레이는 공유되며 텍스트를 보관한다: 동기화하면 자기가 운영하지 않는 서버에 텍스트가 저장되고, 커뮤니티 릴레이는 프로젝트가 운영하는 1대의 단일 프로세스다. 모델 개선 스위치의 기본 켜짐은 가장 확신 없는 선택이다. (7절 'The relay is shared, and it keeps text') (저자 인정)
  • Muse에 관한 기록이 얇다: 공개 문서 4건, 출시 클라이언트, 출처를 검증할 수 없는 프롬프트 사본에 기대며 프롬프트는 배포마다 바뀐다. prompt·inferred 표시 진술은 그만큼 낮춰 볼 것. (7절 'Where the record is thin') (저자 인정)
  • 논문이 기술한 v0.1.40의 Python 런타임에서는 auto 모드의 방어가 서술보다 약했다. 본문은 taint가 질문을 만들 뿐 그 반대는 없고 경고는 어떤 모드와 목록도 통과시키지 못한다고 쓰지만, v0.1.40의 nanomuse/sentinel/gate.py는 auto 모드에서 모든 질문을 'auto mode: approval skipped'로 허용했다. 그래서 auto 모드(nanomuse daemon은 auto 강제, --auto, 앱의 Hands-off 설정)에서는 비공개 파일을 읽은 뒤 미지의 호스트로 보내는 호출도, rm -rf·sudo 같은 경고 동반 호출도 묻지 않고 돌 수 있었다. 1.0.0(2026-10-09, 커밋 52064468·2ee7502a)이 두 경우를 다시 질문으로 돌렸고, 1.0.2(10-11, PR #291, 커밋 bebdc8f5)는 always-ask 도구(기본값 shell·send_email)에서 taint 검사가 아예 돌지 않아 auto 모드가 넘기던 문제를 고쳤다. 기본값인 ask 모드에는 이 결함이 없었다. (추가 의문)
  • Sentinel과 메모리는 기기마다 다른 코드다. 결정 순서·taint·감사 로그(audit.jsonl)는 Python 런타임(nanomuse/sentinel)에 있고, Android는 별도 Kotlin 규칙(RiskGate·ShellGuard·TapWords)이라 taint·egress 추적 코드가 없다(git grep 확인). 대신 Android는 데이터를 내보내는 셸 명령(curl -d, POST, 메일 등)을 OUTBOUND로 분류해, 기억해 둔 승인이 없으면 taint와 무관하게 묻는다(ShellGuard.kt). 설치형 데스크톱 앱은 DeepSeek Harness 승인 정책에 손·메일 MCP 도구용 위험 게이트(HMAC 확인 티켓)를 더한 형태이고, harness.md는 Sentinel 이식을 phase 4로 남겨 둔다(harness/ 아래 taint 0건). 메모리도 논문이 그린 변경 로그·되돌리기·임베딩 회상 저장소는 Python 런타임(웹 앱·셀프호스팅)의 것이고, 데스크톱 앱은 rooms.json에 줄 목록을 따로 둔다. Windows 사용자가 설치하는 것은 이 데스크톱 앱이다. (추가 의문)
  • 결제 승인을 '절대 기억하지 않는다'는 서술(4·5절)이 Android 앱과 어긋난다. 논문이 인용한 privacy.md의 v0.1.40판과 CHANGELOG 0.1.18(2026-09-29)은 화면 잠금(생체·PIN) 확인 뒤 한 앱·사이트에 한해 결제를 '기억하고 다음엔 실행'하는 선택지를 두고, Risk.kt·RiskGate.kt(v0.1.40, 현재 HEAD도 같음)도 그 결제를 카드 없이 실행한 뒤 모델이 알리게 한다. 데스크톱 Python 런타임의 '경고 동반 호출은 한 번만' 규칙과 구분해 읽어야 한다. (추가 의문)
  • 릴레이 보관 항목이 본문 요약보다 많다. 5절은 계정을 해시된 식별자·발급 키·기기로 요약하지만, 인용된 privacy.md(v0.1.40)는 운영자가 볼 수 있게 암호화한 이메일·전화번호, 로그인·요청·이벤트마다의 IP 주소와 User-Agent, 첫·마지막 IP를 기록한다고 적고(cloud/nanomuse_cloud/db.py의 first_ip·last_ip·last_ua), docs/cloud.md는 관리 화면이 오프라인 IP 데이터베이스로 국가·성·도시까지 보여 준다고 적는다(privacy.md의 '주소를 조회하지 않는다'와 어긋남). 동기화 텍스트는 privacy.md가 기기만 읽을 수 있다고 하지만 sync.py는 SQLite에 평문으로 저장하고 운영자 화면이 집계만 보여 줄 뿐이며, 종단간 암호화는 문서와 코드에서 찾지 못했다. 모델 개선 스위치로 보관된 대화는 운영자 화면에서 전문으로 보이고, 커뮤니티 릴레이의 대화는 Alibaba Cloud Model Studio로 전달된다. (추가 의문)
  • Windows에서 손과 셸을 쓸 때의 방어 수준은 낮게 잡는 편이 맞다. 저장소 sentinel.md에 따르면 Python 런타임의 셸·python_execute 샌드박스(bubblewrap)는 Linux 전용이라 Windows·macOS에서는 승인된 명령이 사용자 권한 그대로 돌고 패턴 검사는 우회 가능한 경보선이며, 볼트 키는 기본적으로 볼트 옆 파일에 있다. 설치형 데스크톱 앱의 셸은 DeepSeek Harness의 권한 프리셋(workspace-write 등)을 따르는데, Windows에서 OS 수준 격리가 되는지는 저장소 문서로 확인되지 않는다. 손이 읽은 화면은 모두 손 모델 공급자로 가고, 비밀번호·PIN·카드번호를 치지 말라는 규칙은 프롬프트 수준이다(코드로 막는 것은 Android 실행기의 비밀번호 필드 입력 거부와 FLAG_SECURE 화면이 검게 찍히는 정도). 허브로는 같은 계정의 다른 기기가 PC의 셸·파일·화면과 Claude Code·Codex·Cursor 세션까지 다룰 수 있고, 현재 데스크톱은 기본으로 승인 카드를 띄우지만 '묻지 않고 원격 제어'를 켜면 계정에 로그인한 어느 기기든 카드 없이 PC에서 명령을 실행할 수 있다. (추가 의문)
  • 확정어와 메신저 판정의 기본값이 중국어·영어 중심이라 한국어 화면에서는 결정적 판정이 약해진다. Python 런타임의 [gui] sensitive_words 기본 목록(nanomuse/config.py)과 Android의 TapWords.kt 정규식에는 한국어 단어가 없고, Android가 Enter를 보내기로 보는 메신저 목록에도 카카오톡이 없다. Android 손 프롬프트는 결제·전송·삭제 탭의 target에 버튼 글자를 그대로 쓰게 하므로, 한국어 앱에서는 이런 탭이 확정어 규칙에 걸리지 않고 프롬프트 규칙에만 기댈 수 있다. 데스크톱·런타임은 [gui] sensitive_words에 한국어 단어를 더할 수 있고(docs/gui.md), 데스크톱 손의 Enter 키와 입력 후 제출은 언어와 무관하게 민감 단계로 분류된다(nanomuse/tools/computer.py). Android에서는 단어를 더하는 설정을 찾지 못했다. (추가 의문)

코드 공개, 확인함. github.com/nano-muse/nanoMuse를 2026-10-13에 부분 클론해 HEAD 9cdba87(v1.0.4 태그 c24dd9a 이후 미배포 커밋 9개)을 읽었다. 한 저장소에 Android(OpenMinis 1.13 수정본, Kotlin), iOS(Swift), 데스크톱(DeepSeek Harness 플러그인 + Electron), Python 런타임, 릴레이(cloud/), 웹 콘솔이 있다. 논문이 기술한 v0.1.40 태그(2026-10-06)도 존재한다. 배포물은 Android APK(8.0 이상, arm64), Windows 10 이상 x64 설치 파일(NSIS, 인증서 없음), macOS 12 이상 dmg(공증 없음), Linux AppImage·deb·tar.gz, Docker 이미지 ghcr.io/nano-muse/nanomuse:1.0.4다. 빌드·설치·실행은 하지 않았다.가중치 없음. nanoMuse는 자체 모델 가중치를 내지 않았고, 손 전용 오픈 모델은 로드맵(6절 Next)이다. 커뮤니티 릴레이의 기본 모델은 저장소 문서상 Alibaba Cloud Model Studio의 deepseek-v4.1-flash(채팅)와 qwen3.8-27b(손)다.데이터 공개 데이터셋·평가 세트 없음. 손 평가 세트는 '실패한 trace 10개가 평가 세트가 된다'는 저장소 로드맵 단계이고, 모델 개선 스위치로 보관된 대화는 커뮤니티 모델 학습용으로 언급될 뿐 공개 여부는 확인되지 않는다. 저장소에는 시뮬레이션 휴대폰 MobileGym 모듈(demo/mobilegym)과 정성 trace 1건만 있다.라이선스 코드는 GPL-3.0-or-later(README, NOTICE, CITATION.cff; LICENSE 파일은 GPLv3 전문)이고 논문 본문은 'GPL-3.0'으로 적는다. Android 부분은 OpenMinis 1.13(GPL-3.0) 수정본이고, 이전 Python 라인은 MIT(태그 pre-openminis)였다. 논문 자체는 arXiv에서 CC BY 4.0이다.

📌 내 학습 포인트

  • Sentinel의 taint 규칙과 '어떤 모드도 못 넘기는 경고'(5절)를 Claude Code 훅으로 옮겨 볼 수 있다. 거부·질문·허용 목록과 권한 모드는 Claude Code가 settings.json의 permissions(deny·ask·allow)로 이미 처리하므로, 훅에는 규칙으로 표현하기 어려운 상태 기반 검사만 둔다. (1) PostToolUse 훅이 비공개 데이터를 읽은 호출(.env·키 파일 Read, 메일 MCP, 개인 메모 폴더)을 보면 세션 ID 이름의 임시 파일에 표시를 남긴다. (2) PreToolUse 훅은 그 표시가 있으면 허용 목록 밖 호스트로 나가는 WebFetch, Bash의 curl·wget, PowerShell의 Invoke-WebRequest·Invoke-RestMethod, 전송형 MCP 도구를 permissionDecision 'ask'로 올린다. (3) 경고 패턴(rm -rf, Remove-Item -Recurse -Force, curl | sh, git push --force)과 한국어 확정어(결제, 송금, 전송, 보내기, 삭제)는 상태와 무관하게 항상 ask로 올린다. nanoMuse v0.1.40은 auto 모드가 taint·경고로 생긴 질문까지 허용으로 바꿨고(1.0.0 수정), always-ask 도구에서는 taint 검사 자체가 돌지 않았다(1.0.2 수정). 그러니 자동 승인 모드에서도 이 ask가 허용으로 바뀌지 않는지 직접 시험하라. 조건: 명령 문자열로 목적지를 판정하므로 우회될 수 있고, 별도 사용자 계정이나 컨테이너 같은 권한 경계를 대신하지 못한다.
  • 메모리 출처(provenance) 규칙(4절 'What it knows', 7절)을 파일 기반 메모리에 바로 적용할 수 있다. 요구는 줄마다 쓴 주체(모델명 또는 사람)·날짜·확신도를 남기고, 새 질문이 오래된 줄과 겹치면 그날의 에이전트가 재확인해 확인·수정·의심 중 무엇을 했는지 기록하며, 사람이 쓴 줄이 모델의 줄보다 우선한다는 것이다. 저장소의 Python 런타임 SQLite 저장소는 이미 source(agent/user)·created_at과 정리 단계의 변경 로그·되돌리기를 두고, 정리 단계는 사람이 쓴 줄을 지우지 않는다. 적용: 논문 트렌드 시스템의 메모나 Claude Code 메모리 파일에서 줄 끝에 '(by: 모델명 또는 user, 2026-10-13, conf: 중)' 꼬리표를 붙이고, 서브에이전트가 메모를 고칠 때 덮어쓰지 말고 이전 문장을 변경 로그 파일에 남기게 하라. 조건: 꼬리표는 쓰는 쪽이 정직하게 채워야 의미가 있으므로 서브에이전트 프롬프트와 저장 전 PreToolUse 훅 검사(Write·Edit 대상이 메모리 파일이면 꼬리표 형식 확인)로 강제해야 한다.
  • 되돌릴 수 없는 행동을 하는 도구를 직접 만들 때는 '확인은 모델이 쓴 인자가 아니라 사람 쪽 통로에서 온다'는 원칙(5절 Hands, 저장소 nanomuse/bridge/mcp_server.py)을 옮겨 쓸 수 있다. nanoMuse 데스크톱의 MCP 브리지는 민감 단계를 이유와 함께 거절하고, 사람이 권한 카드에서 승인하면 호스트가 앱을 켤 때마다 새로 만든 비밀키로 정렬된 인자 JSON의 HMAC 티켓을 붙여 다시 부르므로 모델이 스스로 confirmed: true를 써도 통과하지 못한다. Claude Code에서는 MCP 서버가 권한 프롬프트의 승인을 직접 볼 수 없으니 이렇게 옮긴다. (1) 도구에 모델이 채우는 confirm 같은 불리언을 두지 않는다. (2) 파일 삭제·메일 발송·결제성 API는 prepare와 commit 두 도구로 나누고, prepare가 돌려준 요약·인자 해시와 일치할 때만 commit이 실행되게 한다. (3) commit 도구는 settings.json의 permissions.ask에 넣고 allow에는 넣지 않아, 사람이 실제로 실행될 인자를 보고 매번 승인하게 한다. 사다리 원칙대로 API·CLI가 있으면 브라우저·화면 자동화보다 먼저 쓰게 하라. 조건: 라벨이나 요약은 모델 자신의 말이라 거짓 라벨은 못 잡고(7절), 손을 로컬 모델로 돌리려면 이미지 입력 모델과 그에 맞는 GPU 메모리가 필요하며 사양 적합성은 이 논문으로 판단할 수 없다.

새로운 것은 모델이 아니라 시스템 조립이다. Android 휴대폰 화면을 조작하는 손, 기기마다 도는 에이전트와 규칙 기반 Sentinel, 셀프호스팅 가능한 릴레이를 한 저장소에서 GPL로 끝까지 이었고, 화면 행동을 그림이 아니라 모델의 라벨 문장으로 판정하게 만든 점과 릴레이가 무엇을 보관하는지 문서로 밝힌 점이 실용적 기여다. 증거는 약하다. 과제 성공률이나 사람 개입 횟수 같은 정량 평가가 없고(저자 명시), 표 2는 릴리스 파일 크기·1회 설치·유휴 메모리 측정값과 가격표 기반 비용 추정뿐이다. Muse 분석의 상당 부분은 입수 경위가 밝혀지지 않고 검증도 안 된 프롬프트 사본(prompt 표시)과 저자 해석(inferred)에 기대며, 재현하지 않고 몇 단어만 인용한다는 자기 제한 말고는 법적·윤리적 논의가 없다. 보안 주장은 같은 프로세스 계열 안의 정책 경계라는 조건 위에 있다. 저장소를 보면 Sentinel과 메모리 구현이 기기마다 달라 taint는 Python 런타임에만 있고, 논문이 기술한 v0.1.40에서는 auto 모드가 taint와 경고로 생긴 질문까지 허용으로 바꿨으며(1.0.0·1.0.2에서 수정, 기본 ask 모드는 해당 없음), 결제 승인을 절대 기억하지 않는다는 서술은 Android 앱의 화면 잠금 기반 기억 옵션과 어긋난다. 한국어 사용자에게는 확정어·메신저 규칙의 기본값이 중국어·영어 중심이라 라벨 판정의 이점이 그대로 오지 않는다는 점도 걸린다. 인용할 때는 성능이 검증된 에이전트가 아니라 'v0.1.40 시점의 오픈소스 개인 에이전트 시스템 보고서이자 설계 입장문'으로 인용하고, Muse에 관해서는 documented 표시 진술만 사실로, prompt·inferred 표시는 저자 주장으로 구분해 옮기는 것이 맞다. 코드가 며칠 단위로 바뀌므로 버전 태그를 함께 적어야 한다.
