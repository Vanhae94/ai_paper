금융 분야의 LLM 활용은 대개 단일 에이전트가 특정 작업을 처리하거나 여러 에이전트가 따로 데이터만 수집하는 수준에 머물렀다. 회사처럼 협업·토론하는 구조는 거의 탐구되지 않았다.

펀더멘털·감성·기술 분석가, 강세(Bull)·약세(Bear) 리서처, 리스크 관리팀, 트레이더 등 실제 직무를 LLM 에이전트로 구현한다. 강세·약세 에이전트가 토론하고, 트레이더가 그 결과와 과거 데이터를 종합해 매매를 결정한다.

방법 상세

TradingAgents는 실제 트레이딩 회사를 모사한 LLM 멀티에이전트 프레임워크로, 7개 역할을 5개 팀으로 조직한다. (1) 애널리스트 팀(Analyst Team)은 펀더멘털(fundamental)·감성(sentiment)·뉴스(news)·기술적(technical) 분석가가 각자 구조화 리포트를 생성한다. (2) 리서처 팀(Researcher Team)은 강세(bull)/약세(bear) 연구자가 자연어 토론(natural language debate)을 n라운드 진행하고, 진행자(facilitator) 에이전트가 토론 이력을 검토해 우세 관점을 선택·기록한다(원문 표현 'facilitator ... selects the prevailing perspective'). (3) 트레이더(Trader)가 이를 종합해 매매 신호를 도출한다. (4) 리스크 관리 팀(Risk Management Team)은 공격적(aggressive)·중립(neutral)·보수(conservative) 세 관점이 토론해 노출을 조정한다. (5) 펀드 매니저(Fund Manager)가 최종 승인·집행한다. 에이전트 간 통신은 '구조화 리포트'를 1차 채널로, '자연어 대화'를 2차 채널로 쓰는 하이브리드 방식이며, 공유 글로벌 에이전트 상태(global agent state)와 메모리로 과거 결정 맥락을 유지한다(명시적 reflection 모듈 여부는 본문 확인 필요). 모델은 2계층(two-tier) 전략으로, 추론 집약 노드(분석·연구·트레이딩)에는 심층사고(deep-thinking) o1-preview를, 요약·데이터 변환·검색 등에는 신속사고(quick-thinking) gpt-4o/gpt-4o-mini를 배정하고, 전 에이전트는 ReAct 프롬프팅 프레임워크를 따른다(논문 명시). LangGraph는 논문 본문이 아니라 공식 오픈소스 레포/문서에서 구현 스택으로 명시된다('built with LangGraph').

재현 가능성

코드 공개 (github.com/TauricResearch/TradingAgents, Python, CLI+패키지, 조회 시점 약 94.6k 스타 — 변동값)가중치 해당 없음 — 자체 학습 가중치 없이 OpenAI/Anthropic/Google/xAI/DeepSeek/Qwen/Ollama 등 상용·로컬 LLM API를 호출하는 구조데이터 부분 공개 — Yahoo/FinnHub/EODHD/Reddit 등 공개 API로 수집(API 키 필요), 정제·전처리 세부는 재현 시 재구성 필요라이선스 Apache-2.0 (레포 확인)

코드는 완전 공개이며 레포/문서에 LangGraph 기반 구현, 다중 LLM 프로바이더·Ollama 로컬 모델, CLI가 명시됨. 상용 LLM API 키가 필요해 비용·모델 버전에 따라 결과 재현이 달라질 수 있고, 레포에 '연구 목적이며 금융/투자/트레이딩 조언 아님' 면책이 명시됨. 논문 성과 수치(Table 1)는 원문과 1:1 대조해 일치 확인함.

상수 KV 캐시(R-SWA)로 수십 페이지 문서를 한 번에 받아 적는, 인간 작업기억을 모사한 OCR 모델.

LLM을 디코더로 쓰는 엔드투엔드 OCR은 성능이 좋지만, 출력이 길어질수록 KV 캐시가 누적돼 메모리가 늘고 생성이 느려진다.

DeepSeek OCR을 베이스라인으로 디코더 어텐션을 R-SWA(Reference Sliding Window Attention)로 교체한다. 시각 토큰은 전역 접근을 유지하고 생성 텍스트만 슬라이딩 윈도우로 제한해 KV 캐시를 상수로 유지하며, 32K 길이에서 수십 페이지를 단일 forward로 전사한다.

  • OCR을 넘어 ASR·번역 등에 적용 가능한 범용 파싱 어텐션

핵심은 R-SWA(Reference Sliding Window Attention). 디코딩 중 KV 캐시를 두 부분으로 유지한다 — 고정 프리픽스(시각+프롬프트 토큰, 길이 L_m)와 생성 텍스트에 대한 폭 n(기본 128)의 인과적 슬라이딩 윈도우. 캐시 크기는 C = L_m + min(n, T) ≤ L_m + n 으로, 윈도우 크기까지만 커지고 이후 '상수'다(표준 MHA는 L_m + T로 선형 증가). 시각(reference) 토큰은 상태 전이 없이 디코딩 내내 전역으로 접근 가능해, 일반 슬라이딩 윈도우와 달리 시각 특징이 '흐려지지' 않는다. 베이스라인 DeepSeek OCR의 인코더(DeepEncoder: SAM-ViT + CLIP-ViT, 16× 토큰 압축, 1024² → ~256 토큰)는 동결하고 디코더 어텐션만 R-SWA로 교체, LLM 파라미터만 학습한다. 디코더 3B(MoE로 ~500M 활성).

방법 상세

Kimi K3는 총 2.78T, 토큰당 활성 104.2B의 native multimodal MoE로 93층, hidden 7,168, attention head 96, vocab 160K이며, Kimi K2(61층, 1.04T/32.6B) 대비 층수 +52%, 총 파라미터 +167%, 활성 파라미터 +220%, 학습 컨텍스트 128K -> 1M(8x)이다. 시퀀스 축은 Hybrid Attention으로 블록마다 KDA(Kimi Delta Attention) 3층 + Gated MLA 1층의 3:1 구성(전체 69 KDA + 24 MLA)이고, 백본 끝에 Gated MLA를 하나 더 붙여 마지막 층이 항상 global attention이 되게 한다. KDA는 delta-rule 재귀에 채널별 forget gate를 더한 것인데, K3는 log-decay 매핑을 Kimi Linear의 negative-Softplus에서 scaled sigmoid로 바꿔 gmin = -5의 하한을 두었고, 그 결과 16-token tile의 누적 log-decay가 (-80, 0)에 갇혀 역수 rescaling이 BF16 범위에 들어오므로 대각 tile까지 전부 Tensor Core dense matmul로 처리해 기존의 position-pair 대각 경로를 제거했다(output gate도 low-rank -> full-rank). Gated MLA는 모든 MLA 층에 NoPE를 적용해 컨텍스트 확장 시 RoPE 재조정이나 YaRN이 불필요하고, 위치 정보는 KDA의 decay/gating이 담당하며 학습 시 attention 출력을 FP32로 유지한다. 깊이 축의 Attention Residuals는 층별 학습 pseudo-query로 embedding과 선행 블록 출력에 softmax attention을 걸어 깊이 방향 선택적 접근을 주며, K3는 12층 x 8블록의 Block AttnRes를 써 메모리/통신을 O(Ld)에서 O(Nd)로 낮춘다. 폭 축의 Stable LatentMoE는 routed expert를 896개로 늘려 토큰당 16개만 활성(sparsity 56)하고 full-width shared expert 2개를 두며, latent 폭 3,584(hidden의 0.5x), expert별 MoE hidden 3,072이고, 극단적 sparsity의 활성값 폭발과 부하 불균형을 up-projection 앞 RMSNorm, SiTU-GLU(gate lambda1 = 4, up lambda2 = 25의 tanh softcap), Quantile Balancing(expert bias를 margin의 (1-k/n)-quantile로 설정, histogram all-reduce로 근사)으로 억제한다. 비전은 SigLIP 초기화를 버리고 next-token prediction으로 처음부터 학습한 27층 401M MoonViT-V2(patch 14, head 12, RMSNorm, bias 제거)를 쓰고 2x2 pixel-shuffle로 시각 토큰을 1/4로 줄여 3584x3584까지 1M 컨텍스트에 담으며, optimizer는 Q/K/V 모멘텀을 head별로 Newton-Schulz 직교화하는 Per-Head Muon에 cosine decay(warmup 1%, weight decay 0.1)를 쓰고 컨텍스트는 8K -> 64K(사전학습) -> 256K -> 1M(cooldown) 4단계로 늘린다(총 학습 토큰수와 GPU 규모는 본문 미기재). 사후학습은 SFT(XTML chat template, 이 단계부터 MXFP4 weight/MXFP8 activation QAT) -> RL(general/general agents/coding agents 3도메인 x low/high/max 3단계 = 9개 전문가, partial rollout과 per-token 정규화로 stale 데이터 허용, 문제별 토큰예산 초과 시 보상 -1을 주는 reasoning effort 제어, 비검증 과제는 rubric 프로토콜 기반 Agentic GRM) -> MOPD(교사/학생 로그비를 clip한 per-token 보상으로 9개를 단일 모델로 통합) 3단계이며, 인프라는 FlashKDA 커널과 고정 크기 all-gather + prefix scan으로 동작하는 KDA Context Parallelism, rank당 최대 E/R개의 redundant expert만으로 완전 부하균형과 static shape를 보장하는 MoonEP, Firecracker microVM 기반 AgentENV(checkpoint 133 ms, resume 49 ms, 메모리 overcommit 최대 6.5x)로 구성된다.

Tier 1(취약점 발견)에서 OS 커널, DB, 웹 프레임워크, 블록체인, VPN 등 수십 개 시스템에서 수백 건의 후보를 찾아 인간 검토분의 약 70%가 진성으로 확인되고 6개 프로젝트에서 미공개 취약점 16건을 발견(원격 트리거 heap OOB write, RDMA의 Dirty-COW류 포함)했다. 반면 Tier 2(엔드투엔드 exploit)는 41개 과제 중 0건에서만 임의 코드 실행에 성공해 프런티어 사이버 모델에 못 미치며, 저자들은 이를 능력의 하한으로 규정한다.
  • 제3자 평가(2026-07-23 기준)와 비용 효율: Artificial Analysis Intelligence Index v4.1 57.1로 580개 중 4위(Fable 5 59.9, GPT-5.6 Sol 58.9), Vals Index 74.7로 39개 중 2위(Fable 5 75.1, GPT-5.6 Sol 73.1), WebDev Arena 1,678 Elo로 99개 중 1위(개방 모델 최초 1위, Fable 5 1,634), Text Arena 1,486으로 200개 중 8위, Agent Arena 9.1로 37개 중 4위다. 비용은 BrowseComp 최고점 91.2를 과제당 $2.03(GPT-5.6 Sol의 절반, Claude 계열 max의 약 1/10)에 달성하고, Kimi Code Bench 2.0은 Fable 5보다 4.0점 낮은 대신 비용 38%이며 high effort로 Opus 4.8의 max 점수를 약 1/3 비용에 맞춘다. GDPval-AA v2는 GPT-5.6 Sol과 50 Elo 이내이면서 비용 13% 낮고 Fable 5보다 2.6x 저렴하다.

데이터셋

  • 사전학습 텍스트 코퍼스 (Web Text / Code / Mathematics / Knowledge) — 총 토큰수 본문 미기재. 규칙 휴리스틱 + 분류기 품질점수 + 중복제거로 필터링, 도메인별 샘플링률은 소형 모델 ablation으로 결정. 지식/수학은 K2의 rephrasing 레시피(문체와 관점 다변화 프롬프트, chunk 단위 자기회귀 생성, 원문 대조 충실도 검증)로 재작성. 배치 크기, 학습률, TPP, 모델 shape는 전용 scaling law 연구로 재조정했고 그 값은 미기재. (일반 텍스트, 코드, 수학, 지식)
  • 사전학습 비전 코퍼스 — 규모 미기재. K2.5 분류체계를 따르며 오픈소스 컬렉션 + 사내 필터링/합성/중복제거 파이프라인. 좌표 감독은 절대값과 정규화([0,1]) 두 형식을 병기해 해상도 강건성 확보. SVG, 3D 에셋, Webpage, Game, CAD 스키매틱 등 코드-렌더링 쌍 프로그래매틱 멀티모달 데이터를 대폭 증량. (caption, interleaved image-text, OCR, perception, video, visual coding)
  • 장문 컨텍스트 데이터 — 8K -> 64K(사전학습) -> 256K -> 1M(cooldown) 4단계 커리큘럼. 정확/퍼지 중복제거, 영상은 프레임 perceptual hashing, 휴리스틱과 분류기 품질 필터, 구조 검증. 자연 장문이 희소해 upsample하고, 멀티모달 문서와 하위 과제를 permute-concat해 1M 전역을 봐야 풀리는 과제를 합성. (장문 문서, 장편 영상)
  • 지식그래프 유도 RL 태스크 합성 — 규모 미기재. 에이전트가 웹 탐색으로 재귀 확장하는 자기진화 DAG(조립 시 기존 노드 재사용으로 중복 최소화, 개념이 원자적이면 확장 중단). 다양한 granularity의 노드를 단독 또는 조합 샘플링해 키워드를 만들고 공개 자료를 검색, 합성 에이전트가 과제 유형을 골라 생성. (지식 집약 도메인, 코딩, 비전)
  • Kernel Optimization Tasks — 대규모 스위트, 정확한 개수 미기재. Flash Linear Attention 등 고품질 GitHub 저장소에서 수집, 단일 연산자부터 fused mega-kernel까지. CUDA, Triton, CuTe DSL, Gluon, ThunderKittens, TileLang과 BF16/FP8/FP4 지원. 보상은 정확도 + 성능(전문가 구현 수준 0.5, 하드웨어 roofline 접근 시 1)이며 CUDA graph replay, 입력 캐싱, 정밀도 축소 같은 reward hacking 탐지기를 병행. (GPU 커널 최적화)
  • Personal Assistant 모의 환경 — Gmail, Notion, Slack, Canvas 등의 현실적 mock 구현. 수 시뮬레이션 일에 걸쳐 앱 전반에 수십 개 상호의존 이벤트가 분포하고, 단일 rollout이 최대 수천 tool call과 수백만 컨텍스트 토큰에 이른다. 이벤트마다 결정론적 규칙 또는 LLM 평가자 기준을 가지며 초기 워크스페이스는 에이전트가 웹 검색으로 자율 구성. (장기 개인비서 워크플로 (HR, 법무, 금융))
  • 샌드박스 실행 규모 (AgentENV 등) — K3 학습과 평가 전 과정에서 1,505,678개 이미지에 걸쳐 총 51,219,741개 샌드박스 생성. Firecracker microVM, OverlayBD 이미지 포맷 + 커스텀 ublk 드라이버로 sub-second 기동, 증분 checkpoint 133 ms / resume 49 ms, 메모리 overcommit 최대 6.5x. 1M 컨텍스트 RL 실험 자체는 co-located 설계로 수백 GPU 규모 내에서 수행. (에이전트 RL 및 평가 인프라)
  • 사내 벤치마크 스위트 — Kimi Code Bench 2.0, Kimi Webdev Bench(과제 수 미기재, 도메인은 Games / 3D-WebGL-Shader / Website-UI Clone), Coding Experience, 24/7 ClawBench 2.0, MIRA Bench, KAET, CLIF Bench, Agentic Vision Bench, Swarm Bench, Online Experience, Deep Research Bench, Finance Bench, KWV Bench, DECK Bench, Agent Behavior Bench, Faithfulness, Chat All-in-One Bench. 일부 표기상 80과제 또는 95과제 규모(각주의 fallback/refusal 카운트로 확인). (코딩 경험, 일반 에이전트 경험, 대화 경험)

한계 · 비판

  • 전체 성능이 최상위 상용 모델에 뒤진다고 초록과 1절에서 직접 인정한다. 대상은 Claude Fable 5와 GPT-5.6 Sol이며, 나머지 오픈/상용 모델에는 앞선다는 서술이다. 8절 결론은 '격차가 남는다'고만 쓰고 모델명은 적지 않는다. (저자 인정)
  • 연구급(research-level) 추론이 약점이라고 명시한다. HLE-Full은 도구 없이 43.5%, 도구 사용 56.0%로 두 상위 모델에 뒤지고, CritPt는 23.4%로 GPT-5.5에게까지 밀린다. 본문 표현은 '연구급 추론이 주요 개선 방향으로 남는다'이다. (저자 인정)
  • 사내(in-house) 평가가 공개 벤치보다 강약점을 더 선명하게 갈랐다고 밝히며, Agent Behavior Bench, MIRA Bench, 24/7 ClawBench 2.0, Agentic Vision Bench, KWV Bench 5개에서 선두에 뒤진다고 스스로 나열한다. (저자 인정)
  • 익스플로잇 개발(Tier 2) 36과제 중 14개(38.9%)만 해결했고 그중 10개가 user-space 트랙이다. 구성은 user-space 16 + 커널 20이며, 커널 트랙은 K3와 GLM-5.2 모두 3/4을 못 풀었다. 모든 과제가 인간 전문가로 해결 검증되었고 수트 전체가 약 540 전문가시간(과제당 약 15시간)으로 추정되므로 미해결분이 곧 인간 격차라고 인정한다. (저자 인정)
  • 익스플로잇 실패 모드 4가지를 직접 명시한다. (i) 이미 확보한 primitive에서 체인 최종 단계를 마무리 못함, (ii) 완화기법 하에서 전략 선택 실패(데이터 전용 공격이 쉬운데도 제어흐름 하이재킹 고집), (iii) 비생산적 디버깅 루프에 갇힘, (iv) 최종 산출물 검증 부족. (저자 인정)
  • 사이버 평가 결과를 '능력의 하한(lower bound)'으로 규정하고, 현재 모델 버전과 평가 범위에 조건부라고 단서를 단다. UK AISI/NIST CAISI 공동 평가에서도 41과제 중 0건 임의코드실행으로 프런티어 사이버 모델에 뒤진다고 인용한다. (저자 인정)
  • Anthropic/OpenAI 프런티어 모델이 사이버 과제를 거부해 비교가 불가능하다며 해당 수트에서 제외했다. 결과적으로 Tier 2 베이스라인은 GLM-5.2 단독이다. (저자 인정)
  • SwiGLU가 널리 쓰이지만 '경험적 효과에 대한 완전한 설명은 아직 열려 있다'고 인정하며, SiTU-GLU도 저정밀 오버플로 억제라는 공학적 동기에서 도출했다고 밝힌다. (저자 인정)
  • MOPD에서 더 세밀한 top-k distillation 목적함수를 시도했으나 수렴 속도나 최종 성능 모두 뚜렷한 이득이 없었다고 음성 결과를 보고한다. (저자 인정)
  • WorldVQA에서 모든 모델에 걸쳐 일관된 거부 행동이 관측되어 프롬프트 엔지니어링으로 답변을 강제했다고 밝힌다. 즉 해당 점수는 소재 그대로의 성능이 아니다. (저자 인정)
  • 핵심 주장인 '2.5x scaling efficiency'의 검증 근거가 부족하다. Figure 7의 x축은 절대 FLOPs(1e20 ~ 1e21)이지만 이는 소형 모델 스케일링 법칙 피팅 곡선이고, K3 자체의 총 학습 토큰 수, TPP 최적값, 사전학습 클러스터 규모, 총 FLOPs는 공개되지 않는다. GPU 규모 언급은 RL에 대한 '실험당 수백 GPU'가 유일하다. 외부에서 2.5배를 확인할 방법이 없다. (추가 의문)
  • 2.5x 이득의 분해 ablation이 없다. KDA, Block AttnRes, Stable LatentMoE, 데이터 개선, 학습 레시피 개선이 각각 몇 %를 기여했는지 표가 없고, 개별 근거는 'RMSNorm이 검증 손실과 다운스트림을 일관되게 개선' 같은 정성 서술뿐이다. 부록도 A 기여자, B SiTU-GLU, C QB 유도, D 히스토그램, E MoonEP 증명, F 챗 템플릿으로 기여도 분해표는 없다. 깊이 축과 폭 축 중 무엇이 실제 동력인지 알 수 없다. (추가 의문)
  • 깊이 축의 핵심인 Attention Residuals가 참고문헌 [57] 'Kimi Team. Attention Residuals. Preprint. 2026'으로만 인용된다. arXiv 번호도 URL도 없다. 같은 논문의 [63] Kimi Linear는 arXiv 2510.26692, [14] FlashKDA는 GitHub URL을 주는 것과 대조적이며 3대 축 중 하나의 원 근거에 접근할 수 없다. (추가 의문)
  • 벤치마크 비교의 하네스 비대칭 가능성이 있으나 근거 강도는 항목마다 다르다. 명시적으로 확인되는 것은 Agents' Last Exam 리더보드(K3=Kimi Code, GPT=Codex, Claude/GLM=Claude Code), Table 3 사내 벤치, 6.4절 비용 비교다. Table 2 코딩 항목은 '세 하네스 중 하나'라고만 적혀 모델별 배정이 불명이다. Terminal-Bench 2.1의 하네스별 최고점은 모든 모델에 동일 적용된다고 명시되어 대칭 조건이다. 반면 SWE-Marathon은 공식 v1.1 이전의 H20 재보정 브랜치, PostTrainBench는 공식 H100 대신 H20 3회 평균이라 자사 하드웨어 조건이 섞여 있다. (추가 의문)
  • 경쟁 모델 수치에 열화 조건이 섞여 있다. Claude Fable 5는 fallback 포함(SWE-Marathon 35% 과제에서 fallback 발생, Agents' Last Exam은 xhigh에 40% 과제가 downgraded 표기)이고 GPT-5.6 Sol은 cyberguard 포함이다. 저자들이 각주로 밝힌 점은 정직하지만, 표의 격차를 순수 능력 격차로 읽으면 과대 해석이 된다. (추가 의문)
  • 강점 주장의 상당 부분이 비공개 사내 벤치에 실려 있다. Swarm Bench 76.3, Deep Research Bench 90.0 등은 데이터셋과 채점 루브릭이 공개되지 않아 제3자 재현이 불가능하다. Kimi Webdev Bench의 +31.0은 Claude Opus 4.8 단독 대비이며 도메인 3종(Games +14.9, 3D/WebGL/Shader +59.1, Website/UI Clone +26.3)의 '전문가 블라인드 심사 선호'라는 주관 지표다. (추가 의문)
  • 사이버 이외의 전용 안전성 절이 없다. 전문에서 jailbreak, harmful, biological, chemical, misalignment, red team, safety, system card 문자열이 모두 검출되지 않고 시스템 카드에 해당하는 문서도 없다. 사내 Faithfulness(환각율) 벤치와 Table 3의 모델별 거부 횟수 각주가 유일한 인접 지표다. 3T급 가중치를 전면 공개하는 릴리스로서는 위험 문서화가 비대칭적으로 얕다. (추가 의문)
  • 다국어 평가가 없다. 160K vocab의 native multimodal 모델인데 언어 커버리지, 중국어/영어 외 성능, 언어별 열화에 관한 절이 없다. multilingual 관련 서술 검출 0건이다. (추가 의문)
  • 사전학습 전용 base 체크포인트가 공개되지 않은 것으로 보인다. 단 이는 원문 미기재 사항이며 논문은 각주 1의 moonshotai/Kimi-K3 URL만 제시한다. HuggingFace 공식 계정에 Base/Instruct 구분이 없다는 것은 외부 확인 결과다. 아키텍처 연구자가 KDA나 AttnRes 자체의 사전학습 특성을 후학습 효과와 분리해 검증할 경로가 막힌다. (추가 의문)
  • 공개 가중치가 SFT 단계부터 적용된 QAT 결과물이다. 다만 MXFP4는 MoE expert weights에만 적용되고 activations가 MXFP8이며, attention projections, latent MoE projections, shared experts, router는 고정밀을 유지한다고 4.1.4절이 명시한다. BF16 원본 대비 손실이 얼마인지, 고정밀 재학습이나 파인튜닝 시 어떤 제약이 생기는지에 대한 수치는 없다. (추가 의문)

재현 가능성

코드 부분 공개. 논문이 직접 URL로 밝히는 것은 FlashKDA(참고문헌 [14], github.com/MoonshotAI/FlashKDA), KDA 구현이 들어간 FLA PR #691(각주 2), MoonEP(각주 3, github.com/MoonshotAI/MoonEP), AgentENV(각주 4, github.com/kvcache-ai/AgentENV), 그리고 K3가 만든 산출물인 minitriton(각주 5)과 nano-kpu(각주 6)다. FlashKDA는 CUTLASS 기반이며 flash-linear-attention의 백엔드로 자동 디스패치된다고 밝힌다. FlashKDA API의 'lower_bound' 인자(범위 -5.0 ~ 0)가 논문의 gmin = -5 설계와 일치한다는 것은 원문에 없는 외부 확인 사항이다. GitHub MoonshotAI/Kimi-K3의 추론 배포 레시피(vLLM, SGLang, TokenSpeed 권장, OpenAI/Anthropic 호환 API)도 원문 미기재 외부 정보다. 반면 사전학습/후학습 학습 코드, 1M agentic RL 프레임워크, 평가 하네스, 사내 벤치 코드는 공개되지 않는다.가중치 전체 공개. 각주 1의 HuggingFace moonshotai/Kimi-K3, 총 2.78T 파라미터 / 104.2B 활성, 1M 컨텍스트, MoonViT-V2(401M, 27층) 포함. 양자화는 MoE expert weights만 MXFP4이고 입력 activations가 MXFP8이며, attention projections, latent MoE projections, shared experts, router는 고정밀을 유지한다. SFT 단계부터 QAT를 적용한 배포용 가중치이고 BF16 원본은 논문에서 확인되지 않는다. 사전학습 전용 base 체크포인트 부재와 커뮤니티 파생(GGUF, NVFP4, FP8-BLOCK, REAP 등)은 원문 밖 외부 확인 사항이다.데이터 미공개. 사전학습은 Web Text, Code, Mathematics, Knowledge 4개 텍스트 도메인 + 대규모 비전 코퍼스(캡션, interleaved, OCR, perception, video, visual coding)라고만 서술한다. 총 토큰 수, 도메인별 샘플링 비율, 필터 임계값, 중복제거 파라미터가 모두 없고 '작은 모델 ablation으로 결정했다'는 서술로 대체된다. 장문 데이터는 정확/퍼지 중복제거와 영상 프레임 perceptual hashing으로 정제하고 업샘플했다고만 밝힌다. 후학습 SFT/RL 데이터셋, GRM 루브릭, 사내 벤치 모두 비공개.라이선스 논문 본문에는 라이선스 조항이 전혀 없다(전문 'licen' 검출 0건). 확인 가능한 것은 arXiv 게시물 자체의 CC-BY-NC-ND 4.0(PDF 메타데이터)과 참고문헌 [14] FlashKDA의 공개 저장소 존재다. 자체 Kimi K3 License의 세부 조건, 즉 내부 사용 면제, MaaS 제공 시 라이선시와 계열사 합산 연속 12개월 누적 매출 2000만 달러 초과 시 별도 계약, MAU 1억 또는 월 매출 2000만 달러 초과 제품의 UI 'Kimi K3' 표기 의무, Moonshot 공식 제품 및 인증 추론 파트너 경유 면제, 무보증 조항은 모두 HuggingFace/GitHub 문서 기준의 외부 사실이며 원문으로는 검증되지 않는다.

재현 가능성이 층위별로 크게 갈린다. 서빙/배포 재현성은 높다(가중치 + 추론 엔진 + MIT 커널). 학습 재현성은 0에 가깝다. 총 컴퓨트, 총 토큰 수, TPP 최적값, 사전학습 클러스터 규모, 데이터, 학습 코드가 전부 비공개다. 단 인프라 부품은 전부 비공개가 아니라 MoonEP와 AgentENV가 GitHub에 공개되어 있고, 막혀 있는 것은 이를 조립하는 사전학습/RL 파이프라인과 평가 하네스다. 벤치마크 재현성은 부분적이며, Table 2의 모델별 하네스 배정이 불명이고 SWE-Marathon과 PostTrainBench는 H20 재보정 환경이라 숫자 재생산이 사실상 어렵다. 검증 가능한 실질 자산은 (1) 가중치, (2) FlashKDA 커널, (3) MoonEP, (4) AgentENV, (5) Table 1의 K2 대비 아키텍처 대조표다. 3rd party 검증은 Artificial Analysis(Intelligence Index v4.1 = 57.1, 580개 중 4위), Vals AI(Vals Index 74.7%, 39개 중 2위), WebDev Arena(1,678 Elo, 99개 중 1위), Text Arena(1,486 Elo, 200개 중 8위), Agent Arena(9.1, 37개 중 4위), UK AISI/NIST CAISI 공동 사이버 평가가 존재해 자체 주장의 방향성은 외부에서 대체로 지지된다.

📌 내 학습 포인트

  • FlashKDA(MIT)를 클론해 'lower_bound' 인자를 -5와 무제한(원 Kimi Linear의 negative-Softplus 상당)으로 바꿔가며 16-token tile 벤치를 돌려본다. 대각 tile을 Tensor Core dense matmul로 처리할 수 있게 만든 것이 순수 수학이 아니라 '누적 log-decay를 (-80, 0)에 가둬 역수를 BF16 범위에 넣는다'는 수치 범위 설계였음을 손으로 확인하는 것이 목적이다. 커널 제약이 아키텍처를 역으로 규정하는 사례를 체감할 수 있다.
  • K3의 Table 2를 그대로 옮겨 적고 각주 조건(K3는 Kimi Code / 경쟁사는 Claude Code, Codex, Fable 5의 fallback 35%, ALE의 downgraded 40%, H20 재보정, Terminal-Bench 하네스별 최고점)을 하나씩 제거하며 순위를 다시 매겨본다. 어떤 결론이 각주 제거만으로 흔들리는지 목록화하면, 이후 어떤 테크리포트를 읽어도 '표보다 각주를 먼저 읽는' 습관이 생긴다.
  • 소형 MoE(예: 총 1B 미만, 64 experts, top-4)를 만들고 Stable LatentMoE의 세 요소 중 하나씩만 이식해 검증 손실을 비교한다. 우선순위는 (1) up-projection 앞 RMSNorm, (2) SiTU-GLU의 softcap, (3) Quantile Balancing이다. 논문이 제공하지 않은 분해 ablation을 축소판으로 직접 만들어보는 것이며, 극단 sparsity 안정화가 정규화에서 오는지 게이트 포화에서 오는지 라우팅 균형에서 오는지를 자기 데이터로 판별하는 훈련이 된다.

Claude 종합 코멘트

Kimi K3는 '오픈 진영이 test-time scaling에만 매달리는 동안 사전학습 축에서 1T급에 갇혀 수렴하고 있다'는 진단을 서론에서 정면으로 내놓고, 그 진단에 3T급 실물로 답한 보기 드문 리포트다. 기술적으로 가장 배울 점은 KDA의 log-decay를 negative-Softplus에서 scaled sigmoid(gmin = -5)로 바꾼 대목인데, 이는 표현력 개선이 아니라 누적 decay의 역수를 BF16 범위에 가두어 대각 tile까지 Tensor Core dense matmul로 처리하기 위한 수치 설계이며, 알고리즘이 커널 제약에 맞춰 재설계된 co-design의 교과서적 사례다. 정직성 면에서도 준수하다 - HLE-Full과 CritPt의 열위, 사내 벤치 5개의 열위, 익스플로잇 4대 실패 모드, top-k distillation의 무이득까지 스스로 적었고 경쟁 모델의 fallback과 cyberguard 조건도 각주로 밝혔다. 다만 논문의 최대 주장인 2.5x scaling efficiency는 총 토큰, TPP, GPU, FLOPs가 전부 비공개인 상태에서 정규화 곡선 하나로 지지되고, 3대 축 중 하나인 Attention Residuals는 접근 불가한 preprint 인용에 그치며, KDA/AttnRes/LatentMoE/데이터 각각의 기여를 가르는 분해 ablation이 없어 '무엇이 실제로 작동했는가'는 독자가 검증할 수 없다. 여기에 사이버 외 안전성 평가와 다국어 평가의 공백, base 체크포인트 부재, 매출 2000만 달러/MAU 1억 임계를 둔 자체 라이선스를 함께 놓으면, 이 릴리스는 '재현 가능한 연구'라기보다 '검증 가능한 제품 + 서술형 연구 보고'에 가깝다고 읽는 것이 정확하다.

방법 상세

LongHorizon-Harness는 장기 지평 과제 수행을 "계획-실행 능력"이 아니라 "작업 상태(task state) 관리" 문제로 재정의한다. 기존 하네스는 실행 궤적, 작업 상태, 완료 판정을 하나의 계속 커지는 컨텍스트 안에 함께 담기 때문에 상태 추적이 어렵고 에이전트가 스스로 내린 잘못된 완료 판정이 이후 라운드로 전파되는데, 이 논문은 상태를 실행 컨텍스트 바깥에 명시적으로 두고 환경에서 독립적으로 검증된 사실로만 갱신한다. 핵심 구조인 Manage-Execute-Audit(MEA) 루프는 세 역할로 구성된다. 매니저는 지속적 작업 상태와 누적된 감사 리포트만 읽고 환경에 직접 접근하지 않으며, 다음 하위작업의 계약(contract)을 구성한다. 계약에는 즉시 목표(immediate goal), 수용 기준(acceptance criteria), 경계 제약(boundary constraints), 그리고 실행과 검증에 필요한 관련 작업 상태 레코드 및 이전 감사 리포트가 담긴다. 실행자는 매 라운드 신선한(fresh) 컨텍스트에서 시작해 이전 라운드 궤적에 접근하지 못한 채 해당 라운드에 공급된 정보만으로 역할별 인터페이스(GUI 또는 CLI)를 통해 경계가 정해진 하위작업을 수행하고 실행 리포트를 반환하지만, 스스로 완료를 확정할 권한은 없다. 감사자 역시 신선한 컨텍스트에서 시작해 읽기 전용 도구로 결과 환경 상태를 독립 점검하며, 과제 관련 상태를 수정할 수 없고 실행자 주장을 지지하거나 반박하는 근거를 산출한다. 작업 상태는 세 종류의 레코드로 표현된다. 요구사항(Requirements, 원 과제에서 도출된 목표와 제약), 산출물(Artifacts, 실행 중 생성 혹은 수정된 결과물), 사실(Facts, 이후 라운드에 필요한 환경 정보)이며, 각 레코드는 completed / pending / blocked / untrusted 상태 표시를 갖고 이를 뒷받침하는 감사 증거를 참조한다. 감사 리포트는 세 가지 소견 클래스를 기록한다. (1) 완료 상태: complete / incomplete / blocked, (2) 무결성 상태: clean / suspect / violation, (3) 작업 상태 갱신 항목: 검증된 사실과 그 증거 및 미확인 공백. 무결성 판정은 워크스페이스 변형(mutation), 산출물 유효성과 출처(provenance), 삭제 제약 준수 여부를 점검해 부여되며, 감사자 자신이 보호 대상 산출물을 생성/편집/삭제하면 무결성 위반으로 기록된다. 위반이 발생한 리포트는 completed 레코드를 뒷받침할 수 없으므로 오염된 결과가 지속 상태에 진입하지 못한다. 즉 레코드가 completed가 되는 유일한 경로는 clean 감사 증거이며, 미해결 항목은 pending / blocked / untrusted로 남는다. 매니저는 매 라운드 execute / done / blocked / ask 중 하나의 제어 결정을 내리고, 감사된 상태가 원 과제를 충족하거나, 남은 요구사항을 진전시킬 허용 가능한 하위작업이 없거나, 사용자 입력이 필요하거나, 라운드 예산이 소진되면 종료한다(최대 라운드 Nmax = 25). AgentAdapter는 실행자를 공통 인터페이스로 인스턴스화하는 얇은 계층으로, 계약과 역할별 환경 인터페이스, 실행 예산을 받아 Claude Code, Codex CLI, OpenClaw 같은 기존 백엔드를 하나의 경계가 정해진 에피소드(bounded episode)로 기동한다. 어댑터는 백엔드의 네이티브 플래닝 루프를 수정하지 않은 채 공급 컨텍스트, 가용 도구, 실행 예산, 반환 리포트만 통제하므로 모델(Claude, GPT, Qwen)과 하네스를 상호 교환 가능하게 조합할 수 있다.

한계 · 비판

  • 하네스는 모델이 없는 능력을 만들어내지 못한다. 과제 성능이 시각 지각, 수학 추론, 코딩, 알고리즘 설계 같은 개별 모델 능력에 지배될 때 이득이 최소라고 명시하며, 독립 감사는 결과 오류를 탐지해 복구를 시작할 수는 있어도 모델이 갖지 못한 능력을 공급할 수는 없다고 적는다. (저자 인정)
  • 감사자가 원리적으로 검증하지 못하는 과제군을 인정한다. 숨겨진 성능 임계값(hidden performance thresholds), 랭킹 의미론, 시간축 로컬라이제이션이 필요한 영상 증거, 신체적/시각적 정밀도(embodied visual precision), 가시 상태로부터 복원 불가능한 평가 관례, 그리고 복수 해석이 가능한 과제 의미론이 해당한다. (저자 인정)
  • 요구사항이 순수하게 공간적이거나 모터 수준일 때는 시각 로컬라이제이션과 커서 제어에 성능이 묶여 하네스 이득이 제한된다고 적는다. (저자 인정)
  • 토큰 오버헤드가 상당하고 과제 의존적이다. 매니저는 전체 토큰의 2.0~8.1%, 감사자는 19.4~38.1%를 차지한다. WeaveBench에서 베이스라인 대비 2.3x, OSWorld 2.0에서 출력 토큰 3.6x가 들지만 Terminal-Bench 2.1에서는 오히려 24% 적은 토큰으로 더 높은 성공률을 낸다. 고정 배수가 아니라 실행 및 복구 라운드 수에 좌우된다고 설명한다. (저자 인정)
  • 이득이 과제 구조에 의존한다. 여러 의존 상태를 장기간 보존/점검/수정해야 하는 범주(Design, Spatial/3D 등)에서 개선이 크고 짧은 과제에서는 미미하다. (저자 인정)
  • 저자 스스로 회귀 사례를 표에 남긴다. Terminal-Bench에서 데이터 사이언스 0.792 -> 0.667, 수학 0.917 -> 0.750, 비디오 처리 0.333 -> 0.000이며, WeaveBench Desktop 도메인은 PassRate가 올라도 평균 점수가 0.8671 -> 0.8465로 내려간다. Games에서도 rhythm autoplay 0.950 -> 0.830, FreeCell 0.520 -> 0.410의 회귀가 있다. (저자 인정)
  • 공개 저장소 기준 플랫폼 한계를 인정한다. macOS 위주로 검증되었고 Windows 지원은 포함되어 있으나 충분히 테스트되지 않았다. GUI 플러그인은 macOS에서 접근성(Accessibility) 및 화면/시스템 오디오 녹화 권한을 사용자가 수동으로 부여해야 한다. (저자 인정)
  • 초록과 표의 대표 수치가 어긋난다. 초록은 OSWorld 2.0 34개 서브셋에서 Claude Opus 4.7이 20.0% -> 34.3%라고 쓰지만 Table 3은 20.6% -> 35.3%(부분 점수 55.8% -> 66.9%)다. 표 값은 34개 분모(7/34, 12/34)와 정확히 맞고 초록 값은 35개 분모(7/35, 12/35)와 맞아떨어져 분모가 달랐을 가능성이 있으나 원문에 설명이 없다. 어느 쪽이든 대표 수치가 두 가지로 유통되는 것은 문제다. (추가 의문)
  • OSWorld 2.0 34개 서브셋의 선정 기준이 제시되지 않는다. 왜 108개 중 34개인지, 무작위인지 난이도 기준인지 설명이 없어 체리피킹 가능성을 배제할 근거가 없다. (추가 의문)
  • OSWorld 2.0 비교가 동일 조건이 아니다. Table 2에서 LongHorizon-Harness 행만 hybrid(GUI+CLI) 툴 풀을 쓰고 베이스라인은 single action 또는 batched action의 GUI 계열이다. 2.8% -> 8.3%에 CLI 도구 추가 효과와 하네스 효과가 뒤섞여 있어 상태 관리 기여만 분리할 수 없다. (추가 의문)
  • 절대 성능은 여전히 모델 격차에 못 미친다. 하네스를 얹은 Qwen 3.7-Plus(8.3% / 35.2%)는 무하네스 Claude Opus 4.8 batched(20.6% / 54.8%)에 크게 뒤진다. Games 서브셋에서도 Qwen+하네스 0.733은 Opus+하네스 0.809에 밀린다. 상대 개선폭 중심 서술은 이 사실을 가린다. (추가 의문)
  • 통계적 신뢰도가 약하다. Terminal-Bench 2.1만 과제당 3회 독립 실행 평균이고 WeaveBench와 OSWorld 2.0은 단일 실행으로 보이며 분산이나 표준편차 보고가 없다. OSWorld 2.0의 2.8% -> 8.3%는 108개 기준 약 3개 대 9개 수준이라 실행 간 변동이 큰 컴퓨터 사용 에이전트에서 결론을 지탱하기 어렵다. (추가 의문)
  • 지연과 실제 비용이 보고되지 않는다. 토큰 분해만 있고 벽시계 시간, 라운드당 소요, 평균 사용 라운드 수, 달러 비용이 없다. 실행자 1800초, 매니저 300초, 감사자 300초, 최대 25 MEA 라운드를 곱하면 과제당 최악의 경우가 수 시간대인데 실무 도입 판단의 핵심 값이 비어 있다. (추가 의문)
  • 핵심 요소에 대한 ablation이 없다. MEA는 (1) 실행 바깥의 명시적 상태, (2) 신선 컨텍스트 실행자, (3) 독립 읽기 전용 감사자를 동시에 도입하는데 감사자를 실행자 self-check로 대체한 조건도, 상태 파일 없이 컨텍스트 리셋만 적용한 조건도 없다. 이득의 인과 원천을 분리할 수 없다. (추가 의문)
  • 평가자 신뢰도 검증이 없고 순환 의존 우려가 있다. WeaveBench 채점은 Claude Opus 4.7 궤적 인지형 저지인데 같은 Opus 4.7이 평가 대상 모델이자 실행 백엔드로도 쓰인다. 저지와 인간의 일치도, 판정 일관성, 자기 계열 선호 편향 점검이 없다. (추가 의문)
  • 감사자 자체의 오류율이 정량화되지 않았다. false accept와 false reject 비율, untrusted 표시 발동 횟수, 잘못된 감사로 오염된 상태의 복구 비율이 모두 없다. 논문의 논리는 감사자가 실행자보다 신뢰할 만하다는 전제 위에 서 있는데 그 전제를 측정한 실험이 없다. (추가 의문)
  • 회귀 사례에 대한 원인 분석이 얕다. 수학 0.917 -> 0.750, 비디오 처리 0.333 -> 0.000, 데이터 사이언스 0.792 -> 0.667 같은 하락은 감사 루프가 정상 결과를 반려하거나 라운드 예산을 잡아먹는 부작용 가설을 시사하는데, 이를 계량한 분석이 제시되지 않는다. (추가 의문)
  • 도메인 일반화가 검증 가능한 환경에 한정된다. 세 벤치마크 모두 파일시스템과 화면으로 상태가 관측 가능한 로컬 환경이다. 결제, 메일 발송, 외부 API 호출처럼 비가역이거나 읽기 전용 재확인이 불가능한 부수효과, 다중 사용자가 동시에 상태를 바꾸는 환경, 판단이 주관적인 산출물에는 감사 루프가 그대로 이식되지 않는다. (추가 의문)
  • 비교군이 좁다. 대조는 대체로 같은 백본을 쓰는 네이티브 하네스(Claude Code, Codex CLI, OpenClaw, Hermes Agent)와 외부 리더보드 수치이고, 기존 검증/비평 계열 기법이나 계획 프레임워크와의 직접 비교가 없다. MEA 특유의 기여인지 일반적 다중 롤 구조의 기여인지 구분되지 않는다. (추가 의문)

코드 공개. https://github.com/AMAP-ML/LongHorizon-Harness (AMAP-ML). 본체는 src/lh_harness/ 이고 eval/ 아래에 벤치마크별 동결 재현 스위트가 있다: eval/WeaveBench-harness/(114 tasks), eval/OSWorldv2-harness/(108 tasks, 공식 정의 정렬), eval/TB-harness/(Terminal-Bench 2.1). 각 스위트에 셋업, 파라미터, 실행 커맨드를 담은 개별 README가 포함된다. 설치는 uv tool install lh-harness 또는 pip install lh-harness. 📌 내 학습 포인트

  • 작업 상태를 컨텍스트에서 꺼내 외부 파일로 승격하고, 갱신 권한을 실행 주체에게서 회수한다. 요구사항 / 산출물 / 사실 3종 레코드에 completed, pending, blocked, untrusted 표시와 근거 증거 포인터를 붙여 저장하고, 검증이 끝난 실행 궤적 원문은 버린다. 내 워크플로에 적용하면 '계획 문서'가 아니라 '검증된 사실만 적히는 상태 파일'을 두고, 실행 에이전트에게는 그 파일에 대한 쓰기 권한을 주지 않는 것이 핵심이다. 상태 파일이 곧 컨텍스트 압축 장치이자 실패 복구 지점이 된다.
  • 완료 판정을 실행자로부터 분리하고, 판정자에게 실행 궤적을 보여주지 않는다. 실행자는 리포트만 제출하고, 읽기 전용 도구만 가진 별도의 신선 컨텍스트 검증자가 환경 상태를 직접 확인해 승인 여부를 낸다. 검증자가 실행 로그를 읽지 않아야 실행자의 주장에 앵커링되지 않는다는 점이 이 설계의 실질이다. 단 이 논문이 감사자 자체의 오류율을 측정하지 않았으므로, 나는 도입 시 감사 승인/반려 로그를 남겨 false accept 사례를 주기적으로 표본 검토하는 절차를 함께 넣겠다.
  • 도입 전에 병목의 종류를 판별하고 역할별로 모델과 예산을 라우팅한다. 이 구조는 '여러 의존 상태를 오래 유지해야 하는' 과제에서만 큰 이득을 주고, 단일 능력(시각 정밀도, 수학, 알고리즘 설계)이 병목이면 오버헤드만 늘린다. 비용 측면에서 감사가 토큰의 20~38%를 먹으므로 매니저와 감사자에 강한 모델, 실행자에 저렴한 모델을 배치하는 역할별 라우팅이 실효적이다. 또한 감사 가능성 자체를 설계 조건으로 삼아, 되돌릴 수 없거나 읽기 전용으로 확인 불가능한 액션(결제, 발송, 외부 상태 변경)은 루프 바깥의 사람 승인 지점으로 빼둔다.

이 논문의 진짜 기여는 새 알고리즘이 아니라 권한 설계다. 실행자에게서 '완료를 선언할 권한'을 빼앗아 읽기 전용 감사자에게 넘기고, 상태를 컨텍스트 밖 파일로 승격시켜 검증된 사실만 적히게 만든 것 - 이 두 가지 권한 분리만으로 동일 백본에서 WeaveBench 51.8% -> 80.7%가 나온다는 점은 하네스 계층이 아직 얼마나 저평가되어 있는지를 보여준다. 다만 검증 밀도는 주장 강도를 따라가지 못한다. 방법 상세

OpenHands(구 OpenDevin)는 코딩·명령줄·웹 브라우징을 사람 개발자처럼 수행하는 AI 에이전트를 만들기 위한 오픈 플랫폼으로, 핵심 추상화는 단일 step(self, state: State) 함수와 이벤트 스트림(event stream)이다. 이벤트 스트림은 과거 행동(Action)과 관찰(Observation)을 시간순으로 누적한 State의 핵심 요소로, 사용자 지시/피드백·멀티에이전트 위임 메타데이터까지 담는다. 행동 원시 타입은 IPythonRunCellAction(샌드박스 내 Python 실행), CmdRunAction(bash 실행), BrowserInteractiveAction(BrowserGym DSL 기반 웹 조작), 그리고 AgentDelegateAction·MessageAction·AgentFinishAction 등으로 정의된다. 실행 격리는 Agent Runtime으로, Docker 샌드박스 위에서 bash 쉘, Jupyter IPython 서버, Playwright 기반 Chromium을 제공한다. AgentSkills는 기본 bash/Python으로 얻기 어려운 유틸리티 툴박스로 edit_file, scroll_up/scroll_down, parse_image(비전-언어 모델 기반), parse_pdf 등을 제공한다. 멀티에이전트 협업은 AgentDelegateAction으로 구현되어 범용 CodeActAgent가 웹 태스크를 BrowsingAgent에게 위임할 수 있으며, 커뮤니티 에이전트 구현은 AgentHub에 모인다. 이 이벤트 스트림 + Docker 런타임 + AgentSkills + 위임 구조가 새 에이전트 구현·평가를 표준화하는 프레임워크를 이룬다.
